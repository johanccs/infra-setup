Health Probes, Requests and Limits

Kubernetes can only keep an application healthy if it knows what "healthy" means and how much the application needs. You tell it with probes and with resource settings. Both are powerful, and both are a frequent source of self-inflicted outages.

⏱ 45 min
🎯 Goal of this lesson

Configure readiness and liveness probes and resource requests and limits, and diagnose OOMKilled containers and pods that are Running but not Ready.

Why it matters: without probes, broken pods receive traffic. With wrong probes, healthy pods are cut off or killed. Without requests the scheduler is blind; with limits that are too low the kernel kills your process. Getting these four settings right prevents a large share of production incidents.

By the end of this lesson you will be able to

  • Explain what readiness and liveness probes do when they fail.
  • Write HTTP, TCP and exec probes.
  • Explain the difference between requests and limits, for CPU and for memory.
  • Recognise and fix an OOMKilled container.
  • Explain "Running, 0/1 Ready" and find the cause.

The situation

Two changes were made to the shop this week "to make it more robust": probes on the front end, and memory limits on the API. One of each was configured wrongly, and both took the shop down.

Probes

A probe is a check the kubelet runs against a container at regular intervals.

ProbeQuestionWhen it fails
ReadinessCan this pod take requests right now?The pod is removed from every Service's endpoints. It keeps running and is not restarted.
LivenessIs this container stuck beyond recovery?The container is killed and restarted.
StartupHas a slow-starting app finished starting?Liveness and readiness are held back until it succeeds.
```yaml containers: - name: web image: shop/web:1.0 ports: - containerPort: 8080 readinessProbe: httpGet: path: /healthz port: 8080 periodSeconds: 5 livenessProbe: httpGet: path: /healthz port: 8080 initialDelaySeconds: 10 failureThreshold: 3 ```
MechanismSucceeds when
httpGetThe response status is between 200 and 399.
tcpSocketThe port accepts a connection.
execThe command exits with code 0.

Running is not Ready

The READY column of kubectl get pods counts containers that pass their readiness probe. A pod can be Running and 0/1 at the same time:

```plaintext NAME READY STATUS RESTARTS AGE web-jm5q9ndbwk-7kxvh 0/1 Running 0 3m ``` ```plaintext label="kubectl describe pod (events)" Warning Unhealthy 5s (x36 over 3m) kubelet Readiness probe failed: Get "http://10.244.1.7:80/healthz": dial tcp 10.244.1.7:80: connect: connection refused ```

The message contains everything: which probe, the exact URL, and the error class you know from Lesson 6. Connection refused on port 80 for an app that listens on 8080 is a wrong port in the probe, not a broken app. statuscode: 404 would be a wrong path; statuscode: 503 would be the application itself declaring that it is not ready.

❌ Probes that cause outages
  • A liveness probe that checks a dependency (the database). When the database hiccups, every pod is restarted at once.
  • A liveness probe with too short a delay on a slow-starting app: killed before it finishes starting, forever.
  • A probe pointing at the wrong port or path.
✅ Probes that help
  • Readiness: "can I serve a request?", including the dependencies you can't work without.
  • Liveness: only "is this process hopelessly stuck?". Keep it cheap and independent of other services.
  • Slow start: a startupProbe instead of a huge initialDelaySeconds.

Requests and limits

Each container can state what it needs and what it may use at most.

```yaml resources: requests: # used by the SCHEDULER to place the pod cpu: 100m # 100 millicores = a tenth of a CPU memory: 128Mi limits: # ENFORCED on the node while the container runs memory: 256Mi ```
RequestLimit
Used byThe scheduler: a node must have this much unreservedThe kubelet and the kernel, at run time
CPU exceededA request is a reservation, not a capThe container is throttled (slowed down), never killed
Memory exceededThe container is killed: OOMKilled, exit code 137
If omittedThe scheduler assumes zero: pods may be packed onto a node that cannot hold themNo ceiling: one leaking pod can starve its neighbours

Units: CPU in cores (0.5) or millicores (500m); memory in bytes with suffixes, where Mi and Gi are powers of two. Beware of 128m for memory: that is 0.128 bytes, a typo for 128Mi.

The combination of requests and limits determines the pod's QoS class, which decides who is evicted first when a node runs out of memory: Guaranteed (requests equal limits for everything), Burstable (some set), BestEffort (none set; first to go).

OOMKilled

```plaintext label="kubectl describe pod (excerpt)" State: Waiting Reason: CrashLoopBackOff Last State: Terminated Reason: OOMKilled Exit Code: 137 Restart Count: 6 Limits: memory: 64Mi ```

You have met exit code 137 in Lesson 8. In Kubernetes the reason is spelled out: the container exceeded its memory limit and the kernel killed it. The application's log shows nothing unusual, because a killed process does not get to write a last line.

```bash kubectl top pods # current usage (needs the metrics server) kubectl set resources deployment/api --requests=memory=128Mi --limits=memory=256Mi ```
Size limits from measurements Measure the working set under realistic load with kubectl top pods, add headroom, and set the limit there. Raising the limit cures an undersized limit. It only postpones the kill if the application leaks memory.

🔑 Key takeaways

  • Readiness failing: no traffic, no restart. Liveness failing: restart.
  • "Running 0/1" means the readiness probe fails; the Unhealthy event gives the URL and the error.
  • Requests are for scheduling; limits are enforced. CPU over the limit is throttled, memory over the limit is killed.
  • OOMKilled / exit code 137: compare the memory limit with real usage (kubectl top pods).
  • A wrong probe can take down a healthy application. Keep liveness probes simple.
