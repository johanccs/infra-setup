ConfigMaps and Secrets

In Docker you passed settings with -e. In Kubernetes, configuration lives in its own objects that pods refer to. A wrong reference produces one of the most confusing pod statuses, so this lesson covers both the feature and its failure.

⏱ 40 min
🎯 Goal of this lesson

Store configuration in ConfigMaps and sensitive values in Secrets, consume them from pods, and fix a CreateContainerConfigError.

Why it matters: one image must run in every environment, and passwords must not sit in manifests under version control. Both depend on this mechanism, and a typo in a reference stops a pod before it starts, with nothing in the logs.

By the end of this lesson you will be able to

  • Create ConfigMaps and Secrets from literals and files.
  • Inject them as environment variables and mount them as files.
  • Explain when a change reaches running pods and when it does not.
  • State accurately what a Secret protects and what it does not.
  • Diagnose CreateContainerConfigError from the pod's events.

The situation

Marketing wants a banner on the shop's front page and wants to change the text without waiting for a new image. Meanwhile the security team has noticed the database password in a Deployment manifest in git and wants it gone.

ConfigMaps

A ConfigMap is a set of key-value pairs. Values can be short strings or whole files.

```bash kubectl create configmap web-config --from-literal=BANNER="Free shipping this week" kubectl create configmap nginx-conf --from-file=default.conf # key = file name, value = file content kubectl get configmap web-config -o yaml ``` ```yaml label="The same ConfigMap as a manifest" apiVersion: v1 kind: ConfigMap metadata: name: web-config data: BANNER: Free shipping this week ```

Using configuration in a pod

There are two ways to consume a ConfigMap or Secret, and they behave differently.

```yaml label="As environment variables" containers: - name: web image: shop/web:1.0 envFrom: # every key becomes a variable - configMapRef: name: web-config env: - name: DB_PASSWORD # or pick single keys valueFrom: secretKeyRef: name: db-auth key: password ``` ```yaml label="As files" containers: - name: web image: nginx:1.29 volumeMounts: - name: conf mountPath: /etc/nginx/conf.d # one file per key appears here volumes: - name: conf configMap: name: nginx-conf ```
Environment variablesMounted files
Good forSimple settings, twelve-factor style appsConfiguration files, certificates
When the ConfigMap changesRunning pods keep the old value. Only new pods read the new one.The files are updated in running pods after a short delay; the app must re-read them.
If the object or key is missingCreateContainerConfigErrorPod stuck in ContainerCreating with a FailedMount event
"I changed the ConfigMap and nothing happened" Environment variables are read once, when the container starts. Editing a ConfigMap does not restart anything. After changing a value that pods consume as an environment variable, trigger a rollout: kubectl rollout restart deployment/web.

A quick way to wire a ConfigMap or Secret into an existing Deployment:

```bash kubectl set env deployment/web --from=configmap/web-config # one variable per key kubectl set env deployment/web --list # show what is set ```

Secrets

A Secret works like a ConfigMap, with a separate object type so that access to it can be restricted separately.

```bash kubectl create secret generic db-auth --from-literal=password=secret kubectl get secret db-auth -o yaml kubectl get secret db-auth -o jsonpath='{.data.password}' | base64 -d ``` ```yaml apiVersion: v1 kind: Secret metadata: name: db-auth type: Opaque data: password: c2VjcmV0 # base64 of "secret" ```
Base64 is not encryption The value in a Secret is encoded so that it can hold binary data. Anyone can decode it, as the command above shows. What a Secret gives you is a separate object that RBAC can restrict (Lesson 19), that is not printed by kubectl describe, and that the cluster can encrypt at rest if configured to. Committing a Secret manifest to git exposes the password just like plain text would.

In a manifest you can write plain text under stringData: and the API server encodes it for you. Under data: you must provide valid base64; a common mistake is echo secret | base64, which encodes a trailing newline into the password. Use echo -n.

When a reference is wrong

Before the kubelet creates a container it resolves every reference in the pod spec. If a ConfigMap, a Secret or a key in one of them does not exist, the container is not created at all:

```plaintext label="kubectl get pods" NAME READY STATUS RESTARTS AGE api-7d9c5b8f6d-x2x9z 0/1 CreateContainerConfigError 0 45s ``` ```plaintext label="kubectl describe pod api-7d9c5b8f6d-x2x9z (events)" Warning Failed 12s (x4 over 45s) kubelet Error: secret "api-secrets" not found ```
Event messageMeaning
secret "x" not found / configmap "x" not foundNo object of that name in the pod's namespace. A typo, or it was created in another namespace.
couldn't find key K in Secret ns/xThe object exists but has no such key. Keys are case-sensitive.
MountVolume.SetUp failed … not foundThe same problem for a volume instead of an environment variable.
No logs, by design kubectl logs on such a pod says the container is waiting to start. The container never ran, so it has no output. The evidence is in the pod's events. Remember this split; Lesson 15 turns it into a rule for every pod status.

🔑 Key takeaways

  • ConfigMaps hold configuration, Secrets hold sensitive values; pods consume both as environment variables or files.
  • Environment variables are fixed at container start: change the ConfigMap, then restart the rollout.
  • Secrets are base64-encoded, not encrypted. Protect them with RBAC and keep them out of git.
  • ConfigMaps and Secrets are namespaced; a pod can only reference those in its own namespace.
  • CreateContainerConfigError = an unresolvable reference. The event names the object or key.
