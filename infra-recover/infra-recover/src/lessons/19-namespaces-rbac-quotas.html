Namespaces, RBAC and Quotas

On a shared cluster, some failures have nothing to do with your application: the cluster simply refuses what you ask, because of who you are or how much you have already used. These refusals are precise. This lesson shows how to read them and how to grant exactly what is missing.

⏱ 45 min
🎯 Goal of this lesson

Organise a cluster with namespaces, control access with RBAC, and understand how ResourceQuotas block the creation of pods.

Why it matters: Forbidden errors and quota limits stop deployments in every company that shares clusters between teams. The quick "fix" is to grant admin rights; the correct fix takes the same time and does not create a security problem.

By the end of this lesson you will be able to

  • Work with namespaces and set a default namespace for kubectl.
  • Explain subjects, Roles and RoleBindings, and create them.
  • Take a Forbidden message apart into user, verb, resource and namespace.
  • Test permissions with kubectl auth can-i and impersonation.
  • Find out why a workload has fewer pods than replicas when a quota is involved.

Namespaces

A namespace is a named partition of the cluster. Most objects live in exactly one: pods, Deployments, Services, ConfigMaps, Secrets, claims. Names only have to be unique within a namespace, and permissions, quotas and network policies are attached per namespace.

```bash kubectl get namespaces kubectl create namespace team-a kubectl get pods -n team-a # one namespace kubectl get pods -A # all namespaces kubectl config set-context --current --namespace=team-a # change your default kubectl config view --minify | grep namespace # check what it is ```
NamespacedCluster-wide
Pods, Deployments, Services, ConfigMaps, Secrets, PVCs, Ingresses, Roles, RoleBindings, ServiceAccounts, NetworkPolicies, ResourceQuotasNodes, Namespaces, PersistentVolumes, StorageClasses, IngressClasses, ClusterRoles, ClusterRoleBindings
"No resources found" is often the wrong namespace Before concluding that something is missing, check which namespace you are looking at. kubectl get pods -A | grep NAME finds an object wherever it lives. And remember from earlier lessons: a pod can only reference ConfigMaps, Secrets and claims in its own namespace, and short Service names resolve within the caller's namespace.
Deleting a namespace deletes everything in it kubectl delete namespace team-a removes all its workloads, Secrets and claims, and with them, usually, the data on their volumes.

RBAC: who may do what

Every request to the API server comes from an identity: a human user, or a ServiceAccount, which is the identity pods and automation use. Role-based access control decides whether the request is allowed. Nothing is allowed unless a rule grants it.

```plaintext subject RoleBinding Role (User, Group or ───── "these subjects get ───────► "may get, list, patch ServiceAccount) this role, in THIS deployments" namespace" ```
ObjectScopeContains
RoleOne namespaceRules: verbs on resources
ClusterRoleCluster-wide (or reusable in any namespace)Rules
RoleBindingOne namespaceSubjects + a reference to a Role or ClusterRole
ClusterRoleBindingAll namespacesSubjects + a ClusterRole
```yaml label="A role and its binding" apiVersion: rbac.authorization.k8s.io/v1 kind: Role metadata: name: deploy-manager namespace: team-a rules: - apiGroups: ["apps"] # "" is the core group: pods, services, secrets… resources: ["deployments"] verbs: ["get", "list", "watch", "create", "update", "patch"] --- apiVersion: rbac.authorization.k8s.io/v1 kind: RoleBinding metadata: name: deployer-binding namespace: team-a subjects: - kind: ServiceAccount name: deployer namespace: team-a roleRef: apiGroup: rbac.authorization.k8s.io kind: Role name: deploy-manager ``` ```bash kubectl create serviceaccount deployer kubectl create role deploy-manager --verb=get,list,watch,create,update,patch --resource=deployments kubectl create rolebinding deployer-binding --role=deploy-manager --serviceaccount=team-a:deployer ```

Reading Forbidden

```plaintext Error from server (Forbidden): deployments.apps "web" is forbidden: User "system:serviceaccount:shop:ci" cannot patch resource "deployments" in API group "apps" in the namespace "shop" ```

The message is a complete work order:

PartValue hereGoes into
Whosystem:serviceaccount:shop:ci = ServiceAccount ci in namespace shopThe binding's subjects
VerbpatchThe role's verbs
ResourcedeploymentsThe role's resources
API groupappsThe role's apiGroups
Wherenamespace shopThe namespace of the Role and RoleBinding
```bash kubectl auth can-i patch deployments -n shop --as=system:serviceaccount:shop:ci # yes / no kubectl auth can-i --list -n shop --as=system:serviceaccount:shop:ci # everything it may do kubectl get rolebindings -n shop -o wide # who is bound to what ```
❌ "Just make it work" ```bash kubectl create clusterrolebinding ci-admin \ --clusterrole=cluster-admin \ --serviceaccount=shop:ci ```

The pipeline can now read every Secret and delete every namespace in the cluster. A leaked CI token becomes a full compromise.

✅ Least privilege

Add the one missing verb to the existing Role, in the one namespace, and verify with auth can-i. It takes the same thirty seconds.

ResourceQuotas

A ResourceQuota caps what a namespace may consume in total: number of pods, sum of CPU and memory requests and limits, number of Services or claims.

```yaml apiVersion: v1 kind: ResourceQuota metadata: name: shop-quota namespace: shop spec: hard: pods: "8" requests.cpu: "2" requests.memory: 2Gi ``` ```bash kubectl describe resourcequota -n shop # Used versus Hard ```

A quota is enforced when an object is created: the API server refuses a pod that would exceed it. The consequence is a symptom that looks unlike anything so far:

```plaintext label="kubectl get deployment web; kubectl get pods" NAME READY UP-TO-DATE AVAILABLE AGE web 2/4 2 2 10m NAME READY STATUS RESTARTS AGE web-lz4hfd75pd-l2r7l 1/1 Running 0 10m web-lz4hfd75pd-ljbzj 1/1 Running 0 10m ```

Two pods are missing, and there is no Pending or failing pod to describe, because the missing pods were never stored. The refusal was reported to whoever tried to create them: the ReplicaSet.

```plaintext label="kubectl describe replicaset -l app=web (events)" Warning FailedCreate 15s replicaset-controller Error creating: pods "web-lz4hfd75pd-j6fdt" is forbidden: exceeded quota: shop-quota, requested: pods=1, used: pods=4, limited: pods=4 ```
Go up the ownership chain When a Deployment has fewer pods than it should and no pod looks unhealthy, look one level up: kubectl describe replicaset, or kubectl get events for the namespace. The same applies to Jobs and StatefulSets. A second quota effect: if a quota covers requests.cpu or requests.memory, every pod must declare those requests, or it is rejected with must specify requests.cpu.

🔑 Key takeaways

  • Namespaces partition names, permissions, quotas and policies. Check your namespace before anything else.
  • RBAC = subject + Role (verbs on resources) + RoleBinding, per namespace. Nothing is allowed by default.
  • A Forbidden message names user, verb, resource, group and namespace: grant exactly that.
  • kubectl auth can-i … --as=… tests permissions without switching identity.
  • Quotas reject pods at creation. Missing pods with no Pending pod: read the ReplicaSet's events.
