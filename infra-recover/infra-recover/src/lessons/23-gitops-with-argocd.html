GitOps with Argo CD: Your First Application

So far, you ran kubectl apply and helm upgrade. With GitOps, nobody does. The desired state lives in a git repository, and a controller in the cluster keeps the cluster equal to it. Argo CD is the most widely used such controller.

⏱ 40 min
🎯 Goal of this lesson

Understand the GitOps model, and create, sync and inspect an Argo CD Application.

Why it matters: in a GitOps setup, the two questions you ask about every deployment problem are new: "does the cluster match git?" and "is what is in git actually working?". Argo CD answers them with two separate statuses, and reading those correctly is most of the skill.

By the end of this lesson you will be able to

  • Explain GitOps and how it differs from running kubectl in a pipeline.
  • Describe an Application's source and destination.
  • Distinguish sync status from health status.
  • Create and synchronise an application with the argocd CLI.
  • Find the Application object with kubectl.

The situation

Three people deploy the shop, each with their own kubeconfig and their own habits. Nobody can say with certainty what is running in production, or who changed the replica count last Tuesday. The team decides: from now on, production is whatever is on the main branch of the gitops repository.

What GitOps means

Push: pipeline runs kubectl/helmPull: GitOps
Who changes the clusterCI jobs and people, from outsideA controller inside the cluster
Source of truthWhatever was applied lastThe git repository
Manual change in the clusterStays, unnoticed, until something overwrites itDetected as drift; optionally reverted
Audit trailPipeline logs, if keptGit history: who, what, when, why, reviewed by whom
RollbackRe-run an old pipeline, hopefullygit revert
Cluster credentialsStored in the CI systemNever leave the cluster

It is the reconciliation idea from Lesson 9, one level up: Kubernetes makes pods match Deployments; Argo CD makes Deployments match git.

Argo CD in the cluster

Argo CD is itself a set of pods, by convention in the namespace argocd:

```bash kubectl -n argocd get pods ```
ComponentJob
argocd-repo-serverFetches repositories and generates manifests from them (plain YAML, Helm, Kustomize).
argocd-application-controllerCompares generated manifests with the live cluster and performs syncs.
argocd-serverThe API and web UI that the argocd CLI talks to.

In the sandbox the CLI is already logged in. On a real installation you would first run argocd login HOST.

The Application

An Application connects a place in git to a place in a cluster.

```yaml label="An Application as a manifest" apiVersion: argoproj.io/v1alpha1 kind: Application metadata: name: shop namespace: argocd spec: project: default source: # WHERE the desired state is repoURL: https://git.shop.example/shop/gitops.git targetRevision: HEAD # a branch, tag or commit path: apps # directory inside the repository directory: recurse: true destination: # WHERE it should be applied server: https://kubernetes.default.svc # "the cluster Argo CD runs in" namespace: shop syncPolicy: syncOptions: - CreateNamespace=true ```

The same thing with the CLI:

```bash argocd app create shop \ --repo https://git.shop.example/shop/gitops.git \ --path apps --directory-recurse \ --dest-server https://kubernetes.default.svc \ --dest-namespace shop \ --sync-option CreateNamespace=true ```
An Application is just a Kubernetes object kubectl -n argocd get applications lists them. That means Applications can themselves be stored in git and managed by another Application (the "app of apps" pattern), so even the list of what is deployed is under version control.

Two statuses

```bash argocd app list argocd app get shop ``` ```plaintext label="argocd app get shop, before the first sync (excerpt)" Name: argocd/shop Project: default Server: https://kubernetes.default.svc Namespace: shop Source: - Repo: https://git.shop.example/shop/gitops.git Target: HEAD Path: apps Sync Policy: Manual Sync Status: OutOfSync from HEAD (ba66957) Health Status: Missing GROUP KIND NAMESPACE NAME STATUS HEALTH HOOK MESSAGE apps Deployment shop api OutOfSync Missing Service shop api OutOfSync Missing apps Deployment shop web OutOfSync Missing Service shop web OutOfSync Missing ```
Sync statusQuestion: does the cluster match git?
SyncedEvery resource in git exists in the cluster with the declared content.
OutOfSyncSomething differs: git has a change not yet applied, or the cluster was changed by hand.
UnknownArgo CD could not determine the desired state at all (Lesson 25).
Health statusQuestion: is it actually working?
HealthyAll resources are fine: Deployments fully rolled out, and so on.
ProgressingNot healthy yet, but may become so: a rollout is under way, pods are starting.
DegradedSomething failed: a Deployment exceeded its progress deadline, a Job failed.
MissingA resource declared in git does not exist in the cluster.
The two are independent Synced and Degraded is common and important: the cluster matches git exactly, and what is in git does not work. OutOfSync and Healthy is just as possible: everything runs, but someone changed something by hand. Always read both.

Sync

```bash argocd app sync shop # apply what is in git argocd app wait shop --health # block until it is healthy (or time out) kubectl -n shop get pods ```

A sync is, at its core, a kubectl apply of the generated manifests, performed by the controller. Each resource then reports its own result:

```plaintext Operation: Sync Sync Revision: ba6695702e37edf552b1f0cdb0cca3fa4f38b355 Phase: Succeeded Message: successfully synced (all tasks run) GROUP KIND NAMESPACE NAME STATUS HEALTH HOOK MESSAGE Service shop web Synced Healthy service/web created apps Deployment shop web Synced Progressing deployment.apps/web created ```

Right after the sync the application is Synced and Progressing: the Deployments exist, the pods are still starting. A minute later it is Healthy. With manual sync policy, which is the default, Argo CD only applies changes when you ask. The next lesson switches to automated sync.

How quickly does Argo CD notice a commit? It polls each repository every few minutes. To make it look immediately, refresh the application: argocd app get shop --refresh. In production, a webhook from the git server triggers the refresh the moment a commit is pushed.

🔑 Key takeaways

  • GitOps: git holds the desired state; a controller in the cluster makes the cluster match it.
  • An Application = source (repo, revision, path) + destination (cluster, namespace).
  • Sync status answers "cluster equals git?"; health status answers "does it work?". They are independent.
  • A sync applies the generated manifests; health follows once the workloads are ready.
  • Applications are Kubernetes objects in the argocd namespace.
