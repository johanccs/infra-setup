Volumes: Data That Survives the Container

Containers are meant to be thrown away and replaced. Databases are not. This lesson explains where a container's data really lives and how to keep the part that matters.

⏱ 35 min
🎯 Goal of this lesson

Understand the container's writable layer, and use named volumes and bind mounts to store data outside it.

Why it matters: "we redeployed and the data is gone" is one of the few container mistakes that cannot be undone. It is easy to avoid once you know which path must be on a volume.

By the end of this lesson you will be able to

  • Explain what happens to files written inside a container.
  • Create, mount, inspect and remove named volumes.
  • Choose between a named volume and a bind mount.
  • Recognise an anonymous volume and explain where it came from.
  • Find out why data disappeared when a container was replaced.

The situation

The shop stores its orders in PostgreSQL, running in a container. Every deployment replaces that container with a new one. The orders have to still be there afterwards.

Where files go by default

An image is a stack of read-only layers. When a container is created, Docker adds one thin writable layer on top. Every file the container creates or changes ends up there.

```plaintext label="A container's file system" ┌──────────────────────────────┐ │ writable layer (this container only) ← deleted by docker rm ├──────────────────────────────┤ │ image layer: application code ┐ │ image layer: dependencies │ read-only, shared by all │ image layer: base operating system ┘ containers of this image └──────────────────────────────┘ ```
ActionWritable layer
docker stop / docker start / docker restartKept. It is the same container.
docker rm, then docker run againGone. The new container starts from the image.
Deploying a new image versionGone. A new version always means a new container.

Named volumes

A volume is storage that Docker manages separately from any container. You mount it at a path; whatever the container writes below that path goes to the volume. The volume has its own lifetime and survives the container.

```bash docker volume create dbdata # optional: run creates it on first use docker run -d --name db \ -e POSTGRES_PASSWORD=secret \ -v dbdata:/var/lib/postgresql/data \ postgres:17 # │ └─ path inside the container # └─ volume name docker volume ls docker volume inspect dbdata ```

Remove the container, run a new one with the same -v, and the database finds its files again. Its log even says so:

```plaintext PostgreSQL Database directory appears to contain a database; Skipping initialization ```
The path must be the one the application writes to A volume protects exactly the directory it is mounted on, and nothing else. Mounting dbdata at /data does nothing for a database that keeps its files in /var/lib/postgresql/data. The correct path is part of each image's documentation.
An initialised volume ignores new settings The PostgreSQL image reads POSTGRES_PASSWORD, POSTGRES_USER and POSTGRES_DB only when it initialises an empty data directory. Start it later with a different password on the same volume and the old password still applies. This surprises people regularly: "I changed the password in the config and it has no effect."

Bind mounts

A bind mount maps a directory or file of the host into the container. Docker recognises it by the path on the left-hand side:

```bash docker run -d --name site -p 8080:80 \ -v ./public:/usr/share/nginx/html:ro \ nginx:1.29 # │ └─ read-only inside the container # └─ starts with ./ or / : a host path, not a volume name ```
Named volumeBind mount
Written as-v name:/path-v /host/path:/path or -v ./dir:/path
StoredIn Docker's own storage areaWherever the host path points
Best forApplication data: databases, uploadsInjecting configuration files; live source code during development
Watch out forEasy to forget it exists (docker volume ls)Ties the container to one machine's directory layout and permissions

Anonymous volumes

An image can declare a path as a volume in its Dockerfile (VOLUME /var/lib/postgresql/data). If you start a container without mounting anything there, Docker silently creates an anonymous volume for it, named with a long random ID:

```plaintext label="docker volume ls" DRIVER VOLUME NAME local dbdata local f116cb4717682c4bd02be4da511fb48186c2b233e00fe79b2819bd1950e4245c ```

The data in it survives stop and start, which makes everything look fine. But a new container gets a new anonymous volume, so the old data is orphaned the moment you replace the container. This is the mechanism behind most "we lost the data" stories.

```bash docker inspect -f '{{json .Mounts}}' db # what is mounted where, and from which volume docker volume prune # delete anonymous volumes no container uses ```
Commands that delete data docker volume rm NAME, docker volume prune, docker rm -v and, in the next lessons, docker compose down -v delete volumes for good. There is no undo. Removing a container never deletes a named volume.

🔑 Key takeaways

  • Files written in a container go to its writable layer, which is deleted with the container.
  • A named volume has its own lifetime. Mount it at the exact directory the application stores data in.
  • Bind mounts map host paths and are best for configuration and development.
  • Images that declare VOLUME get an anonymous volume if you mount nothing: data survives restarts but not replacement.
  • docker inspect -f '{{json .Mounts}}' shows the truth about what is stored where.

A plain name would be a named volume. ::: :::quiz a PostgreSQL runs with `-v dbdata:/data`. After replacing the container the tables are empty. Why? a) The database writes to `/var/lib/postgresql/data`, which was not on the named volume b) Named volumes are emptied when a container is removed c) The volume was mounted read-only d) PostgreSQL does not support volumes > The named volume was mounted on a path the database never uses. The real data went to an anonymous volume that the new container does not share. :::
