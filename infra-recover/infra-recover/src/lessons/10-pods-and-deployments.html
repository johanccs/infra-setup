Pods, Deployments and Self-Healing

You almost never create pods by hand. You write a Deployment that says how many copies of which pod you want, and Kubernetes keeps that true. This lesson covers the manifest, the three objects it creates, and the errors the API server reports when the manifest is wrong.

⏱ 40 min
🎯 Goal of this lesson

Write and apply a Deployment manifest, understand the chain Deployment → ReplicaSet → Pod, and read the API server's validation errors.

Why it matters: the Deployment is the object you will edit most often, and a rejected manifest is the first failure every newcomer meets. The messages are precise once you know how to read them.

By the end of this lesson you will be able to

  • Explain every part of a Deployment manifest.
  • Use kubectl apply to create and change objects declaratively.
  • Explain how labels and selectors tie the objects together.
  • Describe what happens when a pod is deleted or a replica count changes.
  • Fix a manifest from the API server's error messages.

The situation

The front end has to run as two copies, come back by itself when a copy dies, and be easy to scale for a sale. That description is, almost word for word, a Deployment.

The manifest

```yaml label="deployment.yaml" apiVersion: apps/v1 # API group and version this kind belongs to kind: Deployment metadata: name: web labels: app: web spec: replicas: 2 # how many pods you want selector: matchLabels: app: web # "my pods are the ones labelled app=web" template: # the pod to stamp out metadata: labels: app: web # must match the selector above spec: containers: - name: web image: shop/web:1.0 ports: - containerPort: 8080 env: - name: API_URL value: http://api:3000 ```

Every Kubernetes object has the same four top-level parts: apiVersion, kind, metadata (name, labels) and spec (what you want). Kubernetes adds a fifth, status (what is currently true).

apply: declare, don't command

```bash kubectl apply -f deployment.yaml # create it, or change it to match the file kubectl get deployments kubectl rollout status deployment/web kubectl get pods ``` ```plaintext deployment.apps/web created NAME READY UP-TO-DATE AVAILABLE AGE web 2/2 2 2 8s ```

kubectl apply is idempotent: run it again with the same file and the answer is unchanged; edit the file and it says configured. The file is the source of truth. This is the habit to build from day one:

❌ Imperative: quick, and forgotten ```bash kubectl scale deployment web --replicas=4 kubectl set image deployment/web web=shop/web:1.1 ```

Works, but the file now lies about what is running. The next apply of the old file silently undoes it.

✅ Declarative: change the file ```bash # edit deployment.yaml: replicas: 4 kubectl apply -f deployment.yaml ```

The file, your git history and the cluster agree. Imperative commands are fine for experiments and emergencies.

Deployment → ReplicaSet → Pod

```plaintext label="kubectl get deployments,replicasets,pods" NAME READY UP-TO-DATE AVAILABLE AGE deployment.apps/web 2/2 2 2 40s NAME DESIRED CURRENT READY AGE replicaset.apps/web-j8p7ln5l7t 2 2 2 40s NAME READY STATUS RESTARTS AGE pod/web-j8p7ln5l7t-bbrt5 1/1 Running 0 40s pod/web-j8p7ln5l7t-l4d6g 1/1 Running 0 40s ```
ObjectResponsibility
DeploymentManages versions: creates a new ReplicaSet when the pod template changes and moves pods over (Lesson 13).
ReplicaSetKeeps the number of pods for one template version at the desired count.
PodRuns the containers on a node.

The names show the ownership: web → web-j8p7ln5l7t (the hash identifies the template version) → web-j8p7ln5l7t-bbrt5.

Labels and selectors

Objects are not linked by name but by labels. The ReplicaSet does not keep a list of "its" pods; it counts pods whose labels match its selector. Services (next lesson) and network policies find pods the same way.

```bash kubectl get pods --show-labels kubectl get pods -l app=web # filter by label ```

Self-healing

Delete a pod and the ReplicaSet's count drops below the desired number, so it creates a replacement within a second. The new pod has a new name and a new IP. You did not restart anything; the control loop closed the gap.

To stop an application, change the Deployment Deleting pods of a Deployment is futile: they come back. Scale it to zero (replicas: 0) or delete the Deployment, which removes its ReplicaSets and pods with it.

When the API server says no

A manifest is checked in stages, and each stage has its own style of message. Read the message and you know the stage.

MessageStageUsual fix
error parsing … yaml: line 12: did not find expected keyThe file is not valid YAML.Indentation near that line (spaces, never tabs).
no matches for kind "Deployment" in version "v1"kind and apiVersion don't go together.kubectl api-resources shows the right apiVersion (apps/v1).
strict decoding error: unknown field "spec.template.spec.containers[0].imagee"A field name the API does not know.A typo, or a field at the wrong indentation level. The path is exact.
cannot unmarshal string into Go struct field … of type int32Wrong data type.replicas: "2" must be replicas: 2. The reverse bites with env values: value: "8080" must be a string.
The Deployment "web" is invalid: spec.template.metadata.labels: … `selector` does not match template `labels`The object is well-formed but makes no sense.Make the template's labels match spec.selector.matchLabels.
Check without changing anything kubectl apply --dry-run=server -f deployment.yaml sends the manifest through all validation stages and stores nothing. kubectl diff -f deployment.yaml shows what an apply would change. kubectl explain deployment.spec.strategy prints the documentation of any field.

🔑 Key takeaways

  • A Deployment declares a pod template and a replica count; a ReplicaSet keeps the count; pods run the containers.
  • Objects find each other through labels and selectors, not names.
  • kubectl apply -f makes the cluster match the file. Keep the file as the source of truth.
  • Deleting a pod triggers a replacement. Change the Deployment to change what runs.
  • Validation errors name their stage: YAML syntax, unknown kind, unknown field, wrong type, invalid object.
