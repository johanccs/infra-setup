Docker Compose: A Whole Stack in One File

Three containers, a network, a volume, five environment variables: typing that as docker run commands every time is slow and error-prone. Compose describes the whole application in one file that you can read, review and commit.

⏱ 40 min
🎯 Goal of this lesson

Describe a multi-container application in a Compose file, operate it with docker compose, and debug a stack that "started" but does not work.

Why it matters: Compose is how most teams run their application locally and in CI. It is also your first contact with declarative configuration, the idea Kubernetes is built on.

By the end of this lesson you will be able to

  • Read and write a Compose file with services, ports, environment, volumes and dependencies.
  • Start, inspect, update and remove a stack.
  • Explain how services find each other.
  • Say what depends_on guarantees and what it does not.
  • Debug a stack one service at a time.

The situation

In Lesson 6 you started the database and the API by hand. A new colleague needs the same setup on their machine, and next month there will be five services. The commands have to become a file.

The Compose file

```yaml label="compose.yaml" services: db: image: postgres:17 environment: POSTGRES_USER: shop POSTGRES_PASSWORD: secret volumes: - dbdata:/var/lib/postgresql/data api: image: shop/api:1.0 environment: DATABASE_URL: postgres://shop:secret@db:5432/shop ports: - "3000:3000" depends_on: - db volumes: dbdata: ```

Every key maps to something you already know:

Composedocker run equivalent
Service name (db, api)--name, and the DNS name on the project's network
image:The image argument
environment:-e
ports:-p (quote the values: "3000:3000")
volumes: under a service-v
Top-level volumes:docker volume create
build: .docker build for that service
The network comes for free Compose creates one user-defined network per project and attaches every service to it. That is why the API can use the host name db: the service name is the DNS name. Nearly every "service A can't find service B" problem in Compose is a host name that does not match a service name.

Operating a stack

```bash docker compose up -d # create and start everything, in the background docker compose ps # containers of this project (add -a for stopped ones) docker compose logs api # one service's output; add -f to follow docker compose exec db psql -U shop -c "SELECT 1" docker compose down # remove containers and the network; keep volumes docker compose down -v # ...and delete the volumes: your data is gone ``` ```plaintext label="docker compose up -d" [+] Running 4/4 ✔ Network shop_default Created 0.1s ✔ Volume "shop_dbdata" Created 0.2s ✔ Container shop-db-1 Started 0.3s ✔ Container shop-api-1 Started 0.4s ```

Names are prefixed with the project name, which defaults to the name of the directory containing the file. The same file in two directories gives two independent stacks.

up is declarative

docker compose up -d does not mean "start". It means "make reality match this file". Run it again after editing the file and Compose changes only what differs: a new service is created, a service whose configuration changed is recreated, everything else is left running.

"Started" is not "working" Compose reports Started as soon as the container's process has been launched. A database that exits one second later because of a missing password was still "Started". After up, always look at docker compose ps -a: a healthy stack shows every service as Up.

depends_on, and what it does not promise

depends_on controls start order: Compose starts db before api. It does not wait until the database is ready to accept connections, which can take several seconds. An application that connects immediately and gives up on the first failure will crash on a cold start.

There are two proper remedies. Make the application retry its connection, which it needs anyway for restarts in production. Or give the dependency a healthcheck and require condition: service_healthy:

```yaml services: db: image: postgres:17 healthcheck: test: ["CMD-SHELL", "pg_isready -U shop"] interval: 5s retries: 10 api: depends_on: db: condition: service_healthy ```

Debugging a stack: outside in

When the application as a whole is broken, follow a request from the outside inwards, and at each hop ask the same three questions.

  1. Is it running? docker compose ps -a. Anything Exited or Restarting?
  2. What does it say? docker compose logs SERVICE.
  3. Can I reach it, and can it reach the next hop? curl the published port; read the error class (Lesson 6).
```plaintext label="Example: following the request" curl localhost:8080 → "Products: unavailable (api responded 500 …)" web is fine; look at api curl localhost:3000/products → "getaddrinfo ENOTFOUND database" api can't resolve its db host compose.yaml → DATABASE_URL uses "database", the service is "db" ```
Validate before you start docker compose config parses the file and prints the result with all defaults filled in, or an error with the offending key. It catches indentation mistakes and references to undefined volumes or services before any container is touched.

🔑 Key takeaways

  • A Compose file declares services, their configuration, volumes and dependencies.
  • Each project gets its own network; service names are DNS names.
  • up -d reconciles reality with the file and only changes what differs.
  • "Started" only means launched. Check docker compose ps -a and the logs.
  • depends_on orders startup; it does not wait for readiness unless you add a health check.
  • down keeps named volumes, down -v deletes them.
