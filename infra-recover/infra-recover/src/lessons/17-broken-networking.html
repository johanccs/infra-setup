Broken Networking: Services, Ingress, Policies

A request crosses several hops between a user and a container, and any of them can be misconfigured while every pod reports Running. This lesson gives you a checklist that walks the path hop by hop, and adds the two objects at its edges: Ingress and NetworkPolicy.

⏱ 50 min
🎯 Goal of this lesson

Debug connectivity systematically from Ingress through Service to pod, and recognise the signature of a NetworkPolicy.

Why it matters: networking faults produce no crashing pod and no log line. The only evidence is the error the client gets, and a handful of objects you must know to inspect. With a fixed order of checks, these become some of the quickest problems to solve.

By the end of this lesson you will be able to

  • Walk a request's path and test each hop.
  • Diagnose selector, readiness and targetPort problems from endpoints.
  • Create an Ingress and explain what 404 and 503 from the ingress controller mean.
  • Explain how a NetworkPolicy changes a pod's behaviour.
  • Tell "refused" from "timed out" and say which layer each points to.

The path of a request

```plaintext user ──► DNS ──► ingress controller ──► Service ──► endpoints ──► pod:port ──► container (1) (2) (3) (4) (5) host/path rule selector ready pods targetPort = → backend Service → pods only listening port? ```

Debug from the inside out: prove the pod works, then the Service, then the Ingress. Each step that passes shrinks the search.

Ingress

A Service of type ClusterIP is only reachable inside the cluster. An Ingress publishes HTTP services to the outside under host names and paths, through one shared entry point.

```yaml label="ingress.yaml" apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: shop spec: ingressClassName: traefik # which controller should handle this rules: - host: shop.local http: paths: - path: / pathType: Prefix backend: service: name: web # a Service in the SAME namespace port: number: 80 # the Service's port, not the pod's ```

An Ingress is only a set of rules. The work is done by an ingress controller: a reverse proxy running in the cluster that watches Ingress objects and configures itself. Without a controller that claims the Ingress's class, the object exists and nothing happens.

```bash kubectl get ingressclass kubectl get ingress # ADDRESS empty = no controller picked it up kubectl describe ingress shop # each rule, resolved to backend endpoints curl -i http://shop.local/ ``` ```plaintext label="kubectl describe ingress shop (excerpt)" Rules: Host Path Backends ---- ---- -------- shop.local / web:80 (10.244.1.3:8080,10.244.2.3:8080) ```
SymptomMeaningLook at
ADDRESS column stays emptyNo controller handles this Ingress.ingressClassName versus kubectl get ingressclass

503 from the proxyA rule matched, but its backend has no ready endpoints or doesn't exist.describe ingress: backend Service name and port; then the Service checklist
Which controller, and what about the Gateway API? The sandbox cluster runs Traefik with the class traefik, so its error pages say 404 page not found and no available server. Other controllers word them differently, but the meaning of 404 and 503 is the same. The widely used community controller ingress-nginx was retired in March 2026; clusters that relied on it are moving to other controllers or to the Gateway API (Gateway and HTTPRoute objects), which is the successor to Ingress for new setups. The Ingress API itself remains stable and supported, and the debugging steps here carry over directly.

NetworkPolicy

By default every pod can talk to every other pod in the cluster. A NetworkPolicy restricts that. The rule that surprises people:

Selected means isolated As soon as any NetworkPolicy selects a pod for ingress, that pod accepts only the connections that some policy explicitly allows. Everything else is dropped silently. Policies are additive allow-lists; there is no "deny" rule.
```yaml label="Typical pair: deny everything, then allow what is needed" apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: name: default-deny-ingress spec: podSelector: {} # every pod in this namespace policyTypes: [Ingress] --- apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: name: allow-api-from-web spec: podSelector: matchLabels: app: api # protects the api pods policyTypes: [Ingress] ingress: - from: - podSelector: matchLabels: app: web # only pods with this label may connect ports: - port: 3000 ``` ```bash kubectl get networkpolicy kubectl describe networkpolicy allow-api-from-web kubectl get pods --show-labels # do the labels in "from" match real pods? ```

Because dropped packets get no reply, the client waits and then reports a timeout. Between two healthy pods with populated endpoints, a timeout is the fingerprint of a NetworkPolicy. And like Services, policies are tied to pods by labels only: a from selector with a label no pod carries is perfectly valid and allows nobody.

🔑 Key takeaways

  • Check in order: pod ready → app answers locally → endpoints exist → ports match → Service from another pod → Ingress.
  • Refused at a Service: no endpoints or wrong targetPort. Timeout between healthy pods: NetworkPolicy.
  • An Ingress needs a controller that claims its class. Empty ADDRESS = nobody did.
  • 404 from the proxy = no rule matched; 503 = rule matched, backend unavailable.
  • A pod selected by any NetworkPolicy accepts only what policies allow. Policies match by label.
