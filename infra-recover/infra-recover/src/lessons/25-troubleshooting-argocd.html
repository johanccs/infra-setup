Troubleshooting Argo CD and the Capstone

Argo CD sits on top of everything you have learned: git, Helm, Kubernetes objects, pods. When it reports a problem, the cause can be at any of those levels. This last lesson gives you a map of where each Argo CD error comes from, and ends with an incident that needs the whole course.

⏱ 60 min
🎯 Goal of this lesson

Classify Argo CD problems by stage (generate, apply, run), fix each kind in the right place, and resolve a multi-layer incident end to end.

Why it matters: "Argo CD is broken" is almost never true. Argo CD is usually reporting, quite precisely, that a path is wrong, a manifest was rejected, or a pod will not start. Knowing which stage failed sends you to git, to the Application, or to kubectl, and that is the difference between a five-minute fix and an afternoon.

By the end of this lesson you will be able to

  • Name the three stages of an Argo CD deployment and the status each failure produces.
  • Resolve a ComparisonError.
  • Resolve a failed sync.
  • Diagnose an application that is Synced but not Healthy.
  • Decide whether a fix belongs in git, in the Application, or in the cluster.

Three stages, three kinds of failure

```plaintext git repo ──(1) GENERATE──► manifests ──(2) APPLY──► cluster objects ──(3) RUN──► working app │ │ │ ComparisonError Sync failed / SyncError Progressing / Degraded Sync Status: Unknown Sync Status: OutOfSync Sync Status: Synced │ │ │ look at: repo URL, revision, look at: the message per look at: pods, with the path, Helm values, YAML resource; namespaces, RBAC, debugging loop of Lesson 15 invalid fields ```

Always begin with the same two commands:

```bash argocd app list # STATUS, HEALTH and CONDITIONS of every application argocd app get APP # conditions with full messages, last operation, per-resource status ```

Stage 1: ComparisonError

```plaintext label="argocd app get web (excerpt)" Sync Status: Unknown Health Status: Healthy CONDITION MESSAGE LAST TRANSITION ComparisonError Failed to load target state: failed to generate manifest for 2026-10-11 09:00:00 +0000 UTC source 1 of 1: rpc error: code = Unknown desc = apps/frontend: app path does not exist ```

Skip the boilerplate and read the end of the message:

The message ends withCauseFix
PATH: app path does not existThe directory isn't in the repository at that revision (renamed, typo, wrong branch).argocd app set APP --path …
unable to resolve 'X' to a commit SHAThe branch or tag in targetRevision doesn't exist.argocd app set APP --revision …
repository not found / authentication requiredWrong URL, or a private repository without credentials.argocd repo add URL --username … --password …
helm template … failed … open …values.yaml: no such fileA Helm values file listed in the Application doesn't exist at that path.argocd app set APP --values …
helm template … failed … nil pointer evaluating …The chart doesn't render with these values (Lesson 21).Fix the chart or values in git
error converting YAML to JSON: yaml: line N…A manifest in the repository is not valid YAML.Fix the file in git
Why Health says "Healthy" during a ComparisonError Health describes the resources Argo CD currently manages. An application that never got past stage 1 manages none, and "nothing is unhealthy" reads as Healthy. An existing application that hits a ComparisonError keeps running its last synced state untouched. Either way, look at the conditions, not only at the health column.

Stage 2: the sync fails

```plaintext label="argocd app sync web (excerpt)" Phase: Failed Message: one or more objects failed to apply, reason: namespaces "storefront" not found GROUP KIND NAMESPACE NAME STATUS HEALTH HOOK MESSAGE apps Deployment storefront web OutOfSync Missing namespaces "storefront" not found Service storefront web OutOfSync Missing namespaces "storefront" not found ```

The per-resource MESSAGE column is exactly what kubectl apply would have printed for that object. You already know these messages:

MessageCauseFix
namespaces "X" not foundThe destination namespace doesn't exist.--sync-option CreateNamespace=true, or create it
… is invalid: spec.… / unknown field …The API server rejected the manifest (Lesson 10).Fix the manifest in git
… is forbidden: … cannot create resource …Argo CD's own permissions, or its project, don't allow this resource or destination.The AppProject, or RBAC
field is immutableThe change can't be applied in place (a selector, a claim template).Delete and recreate that object deliberately

A failed automated sync is retried with increasing pauses, but only a change (a new commit, or a corrected setting) will make it succeed.

Stage 3: Synced, but not Healthy

This is the bad-commit signature from Lesson 24, or a dependency the manifests assume and nobody created. Argo CD has done its part. From here it is ordinary Kubernetes debugging:

```bash argocd app get APP # which resource is Progressing or Degraded? kubectl -n NS get pods # status kubectl -n NS describe pod NAME # events kubectl -n NS logs NAME # logs ```
HealthWhat Argo CD saw
ProgressingA Deployment whose rollout hasn't finished, a claim not yet bound, an Ingress without an address. May resolve by itself, or may be stuck.
DegradedA definite failure: a Deployment that exceeded its progress deadline (ten minutes by default), a failed Job.
MissingA declared resource doesn't exist in the cluster (not yet synced, or deleted by hand).
Where does the fix go?
  • The manifest is wrong (image tag, port, selector, resource limit): fix it in git. With self-heal, nothing else lasts.
  • The Application points at the wrong thing (path, revision, values file, namespace): fix the Application, with argocd app set or in the manifest that defines it.
  • Something the app needs is deliberately not in git, typically a Secret with credentials: create it in the cluster (or through the team's secret-management tool). Argo CD doesn't manage it, so it won't remove it.

The method, one last time

You have used the same approach on a single container, a Compose stack, pods, Services, Helm releases and Argo CD applications:

  1. Look at the state before touching anything: docker ps -a, kubectl get, helm history, argocd app list.
  2. Find the message. Every layer writes down why it stopped: logs, events, conditions.
  3. Identify the layer the message belongs to, and therefore where a fix must go.
  4. Change one thing, in the place where the change will last.
  5. Test again, and read the next message.

The tools will keep changing. That loop will not.

🔑 Key takeaways

  • Generate → apply → run. ComparisonError, sync failure and unhealthy workloads each belong to one stage.
  • Sync Unknown with ComparisonError: the source (path, revision, values, YAML). Read the end of the message.
  • Sync failed: the per-resource message is the API server's own answer.
  • Synced but not Healthy: Argo CD is done; debug the pods as usual.
  • Manifests are fixed in git, pointers in the Application, and intentionally unmanaged prerequisites in the cluster.
