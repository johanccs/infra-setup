Containers and Images: Your First Container

Before you can fix a container, you need a clear picture of what one is. This lesson builds that picture and has you running, reaching and removing containers within ten minutes.

⏱ 30 min
🎯 Goal of this lesson

Understand what a container and an image are, and run your first containers in the sandbox.

Why it matters: almost every Docker and Kubernetes problem you will ever debug comes down to "which process is running, from which image, with which settings?". If the mental model is right, the error messages start making sense.

By the end of this lesson you will be able to

  • Explain the difference between an image and a container.
  • Run a container in the foreground and in the background.
  • Publish a container port and reach it from the host.
  • List, stop and remove containers.

The situation

You joined a team whose application "runs in Docker". On your first day somebody says: "just run the web container and check it on port 8080". You have a terminal and no idea what happens when you press Enter. Let's fix that first.

What a container is (and is not)

A container is an ordinary Linux process that the kernel has been told to isolate. It gets its own view of the file system, its own network interfaces, its own process list and its own host name. It is not a small virtual machine: there is no second operating system kernel and nothing "boots".

The rule that explains most surprises A container exists to run one main process. When that process exits, the container stops. If the process crashes at startup, the container "runs" for a fraction of a second. You will use this rule in almost every fix-it scenario of this course.

Images: the template a container starts from

An image is a read-only package: a file system (the application, its runtime, its libraries) plus metadata such as the command to start. A container is a running instance of an image. One image can back any number of containers, just as one program on disk can be started many times.

Images are identified by a repository name and a tag, and they are stored in registries:

docker.io / library / nginx : 1.29
└ registry  └ namespace └ repository └ tag

nginx            means  docker.io/library/nginx:latest
shop/web:1.0     means  docker.io/shop/web:1.0

If you leave out the tag, Docker assumes latest. That is only a tag name like any other; it does not mean "newest". Naming an explicit version (nginx:1.29) makes it obvious what is running, which matters a great deal once you are debugging.

docker run, step by step

docker run hello-world

This one command does three separate things, and each can fail in its own way:

  1. Pull: the image is not on this machine yet, so Docker downloads it from the registry (Unable to find image … locally, then Pulling from …).
  2. Create: Docker creates a container from the image: a writable layer on top of the image's files, a network interface, a name.
  3. Start: Docker starts the image's command as the container's main process and connects your terminal to its output.

hello-world prints a message and exits, so the container stops again immediately. That is the rule from above in action.

A container that keeps running

docker run -d --name web -p 8080:80 nginx:1.29
PartMeaning
-dDetached: run in the background and print the container ID instead of the output.
--name webA name you choose. Without it Docker invents one, like quirky_turing.
-p 8080:80Publish: connections to port 8080 on the host are forwarded to port 80 in the container.
nginx:1.29The image. Everything after it would be a command to run instead of the image's default.
 
docker ps                 # running containers
curl localhost:8080       # talk to nginx through the published port
CONTAINER ID   IMAGE        COMMAND                  CREATED         STATUS         PORTS                                     NAMES
8aefd9ff8d08   nginx:1.29   "/docker-entrypoint.…"   5 seconds ago   Up 4 seconds   0.0.0.0:8080->80/tcp, [::]:8080->80/tcp   web

Read the PORTS column from left to right: host address and port, an arrow, container port. You will come back to this column often.

Why the port must be published The container has its own network interface with its own address. Nginx is listening on port 80 of that interface, which the outside world cannot reach. -p asks Docker to open a port on the host and forward it. Forget -p and the server runs perfectly, and nobody can reach it.

Stopping and removing

docker stop web        # ask the main process to exit; the container still exists
docker ps -a           # -a also lists stopped containers
docker rm web          # delete the container (its writable layer is gone)
docker images          # the image is still on disk, ready for the next run
❌ A common confusion

"I stopped the container, why can't I run a new one with the same name?"

Because a stopped container still exists. docker ps hides it; docker ps -a shows it.

✅ What to do

Remove it (docker rm web), or start the existing one again (docker start web). For throw-away containers add --rm to docker run, and Docker removes the container when it exits.

🔑 Key takeaways

  • A container is an isolated process, not a small virtual machine. It lives exactly as long as its main process.
  • An image is the read-only template; a container is a running instance with a thin writable layer on top.
  • docker run = pull (if needed) + create + start.
  • -p HOST:CONTAINER publishes a port. Without it the container is unreachable from the host.
  • docker ps shows running containers; docker ps -a shows all of them. Stopped is not the same as removed.

Quiz

You run docker run -d --name job alpine echo done. A second later docker ps shows nothing. Why?

A container lives as long as its main process. echo prints and exits, so the container is now in the Exited state, visible with docker ps -a.

What does -p 8080:80 do?

The format is HOST:CONTAINER. The left side is where you connect from outside, the right side is where the process inside listens.

After docker stop web, which statement is true?

Stopping ends the main process. The container, its settings and its writable layer remain until docker rm.
