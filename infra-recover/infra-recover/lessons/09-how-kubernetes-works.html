How Kubernetes Works

Docker runs containers on one machine. Kubernetes runs them on many, keeps them running, and lets you describe what you want instead of what to do. Before the first YAML file, this lesson gives you the map.

⏱ 35 min
🎯 Goal of this lesson

Understand the parts of a cluster, the idea of desired state, and the basic kubectl commands for looking around.

Why it matters: Kubernetes error messages name its components: the scheduler could not place a pod, the kubelet could not pull an image, the API server rejected a field. Knowing who does what tells you where each problem lives.

By the end of this lesson you will be able to

  • Name the control-plane and node components and their jobs.
  • Explain "desired state" and "reconciliation".
  • List, describe and delete objects with kubectl.
  • Explain what a pod is and how it differs from a container.
  • Follow a pod's creation through its events.

The situation

The shop outgrew a single Docker host. One machine is a single point of failure, and somebody had to notice and react whenever a container died. The team moved to a three-node Kubernetes cluster, and you have just been given access.

Desired state and reconciliation

This is the idea everything else rests on. You do not tell Kubernetes to do something. You store an object that describes what you want, and controllers work continuously to make reality match.

 you:        "there should be 3 replicas of web"   (desired state, stored in the API)
 controller: counts 2 running  →  creates 1
 later:      a node dies, 1 pod is gone  →  counts 2  →  creates 1
 forever:    observe  →  compare  →  act

The practical consequence: you fix things by changing the declaration, and you never need to "restart Kubernetes" to make it notice. It is always looking.

Pods

The smallest thing Kubernetes runs is a pod: one or more containers that share a network address and can share storage. Most pods contain exactly one container. Think of a pod as "a container plus the wrapper Kubernetes needs": an IP address, labels, a restart policy, a place on a node.

Pods are disposable A pod is never repaired or moved. When something goes wrong it is replaced by a new pod, with a new name and a new IP address. That is why you rarely create pods directly (the next lesson introduces Deployments) and why nothing should depend on a pod's IP (Lesson 11 introduces Services).

kubectl: looking around

kubectl talks to the API server. Nearly every command follows the pattern kubectl VERB TYPE [NAME] [flags].

kubectl get nodes -o wide          # the machines
kubectl get pods                   # pods in the current namespace (default)
kubectl get pods -A                # pods in all namespaces
kubectl get pods -o wide           # adds the pod's IP and node
kubectl describe pod NAME          # everything about one pod, with its events
kubectl logs NAME                  # the container's output
kubectl delete pod NAME
kubectl api-resources              # every object type the cluster knows
NAME       STATUS   ROLES           AGE   VERSION
cp-1       Ready    control-plane   4d    v1.37.0
worker-1   Ready    <none>          4d    v1.37.0
worker-2   Ready    <none>          4d    v1.37.0

Namespaces divide a cluster into named areas. The cluster's own components live in kube-system; your objects go to default unless you say otherwise with -n NAME. Lesson 19 covers them properly.

Reading a pod's events

The bottom of kubectl describe pod is the most useful block of text in Kubernetes. Each line is one component reporting what it did:

Events:
  Type    Reason     Age   From               Message
  ----    ------     ----  ----               -------
  Normal  Scheduled  12s   default-scheduler  Successfully assigned default/hello to worker-1
  Normal  Pulling    12s   kubelet            Pulling image "nginx:1.29"
  Normal  Pulled     10s   kubelet            Successfully pulled image "nginx:1.29" in 2s (2s including waiting). Image size: 192000000 bytes.
  Normal  Created    10s   kubelet            Created container: hello
  Normal  Started    10s   kubelet            Started container hello

Scheduled → Pulling → Pulled → Created → Started. When a pod is unhealthy, this chain stops somewhere and a Warning line says why. Finding that line is the core of Lessons 15 to 17.

Scenario: a tour of the cluster

🔑 Key takeaways

  • Everything goes through the API server; controllers, the scheduler and the kubelets all react to what is stored there.
  • You declare desired state. Controllers reconcile continuously: observe, compare, act.
  • A pod is one or more containers with a shared IP. Pods are replaced, never repaired.
  • kubectl get lists, describe explains (with events), logs shows output.
  • The events of a pod tell the story of its start: Scheduled, Pulling, Pulled, Created, Started.

Quiz

Which component decides on which node a new pod runs?

The scheduler assigns pods to nodes. The kubelet on the chosen node then starts the containers.

What does "reconciliation" mean in Kubernetes?

You store what you want; control loops keep making reality match it, for as long as the object exists.

A pod's events end with Scheduled and Pulling, and nothing after that for several minutes. Which component is working on it, and on what?

Scheduling is finished (the pod has a node). Pulling images is the kubelet's job, so the delay or failure is there.
