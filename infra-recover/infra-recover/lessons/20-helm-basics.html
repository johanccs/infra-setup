Helm Basics: Charts, Releases, Values

By now an application is half a dozen YAML files, and each environment needs slightly different numbers in them. Helm packages those files with their variables, installs them as one unit, and remembers every version it installed.

⏱ 40 min
🎯 Goal of this lesson

Understand charts, releases and values, and install, inspect and upgrade an application with Helm.

Why it matters: most third-party software for Kubernetes is distributed as a Helm chart, and most teams deploy their own services with one. To debug a Helm-managed application you need to know what Helm did, what it stored, and what it does not check.

By the end of this lesson you will be able to

  • Explain what a chart, a release and a revision are.
  • Add a chart repository and search it.
  • Install and upgrade a release, overriding values.
  • Inspect what Helm rendered and applied.
  • Explain what "STATUS: deployed" does and does not mean.

The situation

The front end consists of a Deployment, a Service and an optional Ingress. Development wants one replica, production wants three and an Ingress. Copying the manifests per environment and editing them by hand is how the two drift apart.

Three words

TermMeaningAnalogy
ChartA package: templated manifests, default values, metadata. Has a version.An installer
ReleaseOne installation of a chart, with a name, in a namespace.An installed program
RevisionOne version of a release. Each install, upgrade and rollback creates a new one.An entry in the update history

Helm 4 has no server-side component. The helm command renders templates on your machine, talks to the Kubernetes API with your kubectl credentials, and keeps its bookkeeping in Secrets inside the release's namespace.

Repositories

helm repo add shop https://charts.shop.example    # give a repository a local name
helm repo update                                  # refresh the list of charts
helm search repo shop                             # newest version of each chart
helm search repo shop/web --versions              # all versions
NAME    	CHART VERSION	APP VERSION	DESCRIPTION
shop/api	1.1.0        	1.1        	The shop REST API
shop/db 	1.0.0        	17         	A single-instance PostgreSQL for the shop (StatefulSet with a persistent volume)
shop/web	2.0.0        	2.0        	The shop web front end

Two version numbers appear, and they are independent: the chart version is the version of the packaging, the app version is the version of the software inside (usually the default image tag).

Values

A chart exposes its settings as values, with defaults in its values.yaml. Always read them before installing:

helm show values shop/web
replicaCount: 2

image:
  repository: shop/web
  tag: ""              # defaults to the chart's appVersion

env:
  API_URL: http://api:3000

service:
  type: ClusterIP
  port: 80

ingress:
  enabled: false
  host: shop.local

You override values on the command line or, better, in a file of your own:

helm install web shop/web --set replicaCount=1 --set env.BANNER="Hello"
helm install web shop/web -f prod-values.yaml            # preferred: a file you can review and commit

Precedence, lowest to highest: the chart's values.yaml, then each -f file in order, then --set.

Install and inspect

helm install web shop/web --version 1.0.0 -n shop --set replicaCount=1
NAME: web
LAST DEPLOYED: Sun Oct 11 09:00:41 2026
NAMESPACE: shop
STATUS: deployed
REVISION: 1
DESCRIPTION: Install complete
TEST SUITE: None
NOTES:
web 1.0 was installed as release "web" in namespace "shop".
...
helm list -n shop                 # releases in a namespace (-A for all namespaces)
helm status web -n shop
helm get values web -n shop       # the overrides you supplied (--all: merged with defaults)
helm get manifest web -n shop     # the exact YAML Helm applied
helm history web -n shop          # all revisions
kubectl -n shop get all           # the objects are ordinary Kubernetes objects
"deployed" means "accepted", not "running" By default Helm reports success as soon as the API server has accepted the manifests. It does not wait for pods. A chart whose image crashes on start, or whose pods are Pending, still shows STATUS: deployed. Either check with kubectl afterwards, or add --wait, which makes Helm wait until the workloads are ready and fail (after --timeout, five minutes by default) if they are not.
Releases are namespaced A release lives in one namespace, and every Helm command needs the same -n. helm list without it shows only the current namespace, which leads to "my release has disappeared" when it is simply somewhere else. helm list -A shows them all.

Upgrade

helm upgrade web shop/web --version 1.1.0 -n shop --set replicaCount=3 --wait
helm history web -n shop
REVISION	UPDATED                 	STATUS    	CHART    	APP VERSION	DESCRIPTION
1       	Sun Oct 11 09:00:41 2026	superseded	web-1.0.0	1.0        	Install complete
2       	Sun Oct 11 09:03:10 2026	deployed  	web-1.1.0	1.1        	Upgrade complete

helm upgrade renders the new chart version with the values you give, compares the result with the previous revision's manifest, and applies the differences. The Deployment's pod template changed, so Kubernetes performs an ordinary rolling update (Lesson 13). Helm did not replace Kubernetes' mechanics; it only produced the new manifests.

One command for both cases helm upgrade --install web shop/web -f values.yaml -n shop installs the release if it does not exist and upgrades it if it does. That makes it the natural command for pipelines.

What Helm owns

Helm labels the objects it creates (app.kubernetes.io/managed-by: Helm) and records their release in annotations. Two consequences:

  • If an object with the same name already exists and was not created by this release, the install fails with … exists and cannot be imported into the current release: invalid ownership metadata. Helm refuses to take over foreign objects.
  • A manual kubectl edit on a Helm-managed object works, and is overwritten by the next helm upgrade. Change the values instead.

🔑 Key takeaways

  • Chart = package, release = an installation of it, revision = one version of that installation.
  • Values configure a chart: defaults ◄ -f files ◄ --set. Read helm show values first.
  • helm get manifest and helm get values show exactly what was applied and with which settings.
  • STATUS: deployed only means the manifests were accepted. Use --wait or check the pods.
  • Releases are per namespace; Helm stores its history in Secrets there.

Quiz

helm install printed STATUS: deployed, but the application doesn't respond. What is the first thing to check?

Helm's default success criterion is that the API server accepted the manifests. From there on it is ordinary Kubernetes debugging.

You pass -f prod.yaml --set replicaCount=5, the chart's default is 2 and prod.yaml says 3. How many replicas result?

--set has the highest precedence, then -f files, then the chart's defaults.

helm list shows nothing, although a colleague installed the release yesterday. What is the most likely explanation?

Releases and their history are stored per namespace, and helm list looks only at the current one unless told otherwise.
