Building Images: Dockerfile, Layers and Cache

So far you have run other people's images. Now you package your own application, learn why the order of lines in a Dockerfile matters, and debug a build that fails and an image that builds but will not run.

⏱ 45 min
🎯 Goal of this lesson

Write a Dockerfile, understand layers and the build cache, and tell build-time failures from run-time failures.

Why it matters: when a deployment fails with Cannot find module or executable file not found, the cause is in the Dockerfile. You can only find it if you know what each instruction did to the image.

By the end of this lesson you will be able to

  • Explain what each common Dockerfile instruction does.
  • Order instructions so that rebuilds are fast.
  • Read BuildKit's output, including a failed step.
  • Distinguish an error in the build from an error when the container starts.
  • Describe what a multi-stage build is for.

The situation

You wrote a small web service. It runs on your laptop with node server.js. To ship it, the team needs an image. A Dockerfile is the recipe that turns your source directory into one.

A good Dockerfile

FROM node:24-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
InstructionWhat it doesWhen it takes effect
FROMStarts from an existing image (the base).Build
WORKDIRSets (and creates) the directory later instructions and the container work in.Build and run
COPYCopies files from the build context (the directory you pass to docker build) into the image.Build
RUNExecutes a command during the build and saves the result as a layer.Build
ENVSets an environment variable for later build steps and for containers.Build and run
EXPOSEDocuments the port the app listens on. Publishes nothing.Metadata
CMDThe default command a container runs. Not executed during the build.Run
RUN versus CMD RUN happens once, while the image is built. CMD happens every time a container starts. A typo in a RUN line breaks the build. A typo in CMD builds a perfectly "successful" image that crashes the moment you run it.

Layers and the build cache

Every instruction that changes the file system produces a layer. Docker remembers each layer together with the instruction and the inputs that produced it. On the next build, a step whose instruction and inputs are unchanged is not executed again: its layer is taken from the cache, and the output says CACHED.

The catch: once one step has to run, every step after it runs too. So the order of instructions decides how much work a rebuild repeats.

❌ Slow: every code change reinstalls everything 
FROM node:24-alpine
WORKDIR /app
COPY . .
RUN npm ci --omit=dev
CMD ["node", "server.js"]

Editing server.js changes the input of COPY . ., so that layer and the slow npm ci after it are rebuilt.

✅ Fast: dependencies stay cached 
FROM node:24-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
CMD ["node", "server.js"]

The package files rarely change, so npm ci stays cached. Only the last COPY is redone.

The rule of thumb: what changes least goes first, what changes most goes last.

When the build fails

BuildKit marks the failing step with ERROR, prints that step's output, and then shows the Dockerfile with >>> in front of the line:

 => ERROR [4/4] RUN npm ci --omit=dev                                     1.2s
------
 > [4/4] RUN npm ci --omit=dev:
0.216 npm error enoent Could not read package.json: Error: ENOENT: no such file or directory, open '/app/package.json'
------
Dockerfile:4
--------------------
   3 |     COPY server.js .
   4 | >>> RUN npm ci --omit=dev
   5 |     EXPOSE 3000
--------------------
ERROR: failed to build: failed to solve: process "/bin/sh -c npm ci --omit=dev" did not complete successfully: exit code: 254

Read it bottom-up: which line, which command, and then the command's own message. Here npm cannot find package.json inside the image, because no earlier instruction copied it there.

SymptomTypical cause
failed to compute cache key: "/x": not foundCOPY names a file that is not in the build context (wrong path, or excluded by .dockerignore).
/bin/sh: apt-get: not foundWrong package manager for the base image. Alpine uses apk, Debian and Ubuntu use apt-get.
pull access denied … repository does not exist on FROMA typo in the base image name or tag.
Build succeeds; container exits with Cannot find moduleCMD points at a file that is not where it says, or dependencies were never installed.

Smaller images: multi-stage builds

Build tools are needed to produce the application but not to run it. A multi-stage Dockerfile uses one stage to build and a second, clean stage that copies only the result:

FROM node:24-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.29-alpine
COPY --from=build /app/dist /usr/share/nginx/html

The final image contains nginx and the built files, and nothing of Node.js, node_modules or your source code. Smaller images pull faster and have fewer packages that can contain vulnerabilities.

Two more habits
  • Add a .dockerignore file listing node_modules, .git and local secrets, so they are neither sent to the builder nor copied by COPY . ..
  • Prefer the JSON form CMD ["node", "server.js"]. The plain form CMD node server.js wraps your process in a shell, which then receives the stop signal instead of your application.

🔑 Key takeaways

  • A Dockerfile is a list of instructions; file-changing instructions create layers.
  • RUN executes at build time, CMD at container start. Each fails in a different place.
  • A changed step invalidates the cache for all later steps: copy dependency manifests and install before copying the source.
  • Build errors: read the >>> line and the step output above it. Run-time errors: docker logs.
  • Images are immutable. After changing the Dockerfile, rebuild and create a new container.

Quiz

You change one line in server.js and rebuild the "fast" Dockerfile from this lesson. Which steps are executed again?

The package files did not change, so the steps up to and including npm ci are cached. COPY . . has new input and is redone.

A build ends with /bin/sh: apt-get: not found on a RUN apt-get install -y curl line. The base image is node:24-alpine. What is wrong?

The command itself is missing from the base image. On Alpine the equivalent is RUN apk add --no-cache curl.

docker build succeeds, but docker run exits at once with Error: Cannot find module '/app/app.js'. Where is the mistake most likely?

A successful build proves the instructions ran, not that CMD names a file that exists in the image. The container's log names the missing file.
