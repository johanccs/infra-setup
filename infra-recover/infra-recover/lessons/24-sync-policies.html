Sync Policies, Drift and Rolling Back with Git

With manual sync, Argo CD is a reporting tool. Turn on automated sync, pruning and self-healing, and git becomes the only way to change production. That is powerful, and it changes how you fix things at three in the morning.

⏱ 45 min
🎯 Goal of this lesson

Configure automated sync, prune and self-heal, deploy and roll back through git, and investigate drift.

Why it matters: on a self-healing application, a kubectl hot-fix disappears within seconds. If you don't know why, you will fight the system. If you do, you will fix the problem in the one place where the fix lasts.

By the end of this lesson you will be able to

  • Explain what automated sync, prune and self-heal each do.
  • Deploy a change by committing to git.
  • Use argocd app diff to see exactly what differs.
  • Roll back with git revert, and say when argocd app rollback applies.
  • Tell a pending commit from drift.

The situation

The shop is managed by Argo CD. The team wants deployments to happen when a pull request is merged, wants deleted manifests to disappear from the cluster, and wants to stop finding surprises left behind by late-night kubectl sessions.

Three switches

SettingOff (default)On
Automated syncNew commits show as OutOfSync until someone runs argocd app sync.New commits are applied automatically.
PruneA resource removed from git stays in the cluster, shown as OutOfSync ("requires pruning").Resources removed from git are deleted from the cluster.
Self-healA manual change in the cluster shows as OutOfSync and stays.Manual changes are reverted to the git state within seconds.
 
argocd app set shop --sync-policy automated --auto-prune --self-heal
argocd app get shop        # Sync Policy: Automated (Prune)
spec:
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
Prune deletes With prune enabled, deleting a file from the repository (or moving it outside the application's path, or a rendering change that drops a resource) deletes the object from the cluster, including a StatefulSet or a Namespace. Review deletions in pull requests as carefully as additions. For objects that must never be pruned there is the annotation argocd.argoproj.io/sync-options: Prune=false.

Deploying is committing

git clone https://git.shop.example/shop/gitops.git
cd gitops
sed -i 's/replicas: 2/replicas: 3/' apps/web/deployment.yaml
git diff                                 # review your own change
git add .
git commit -m "web: scale to 3 replicas"
git push

argocd app get shop --refresh            # don't wait for the next poll
kubectl -n shop get deployment web

Nothing else is needed. In a real team the push would be a pull request, reviewed and merged by someone else, and that review is the approval step for production.

Drift

Drift is any difference between the live cluster and git that did not come from git. Somebody ran kubectl scale, kubectl set image or kubectl edit.

kubectl -n shop scale deployment web --replicas=1    # someone "just tries something"
argocd app diff shop
===== apps/Deployment shop/web ======
10c10
<   replicas: 1
---
>   replicas: 3
PolicyWhat happens next
Manual syncThe app stays OutOfSync. The change remains until someone syncs.
Automated, no self-healStill OutOfSync: automated sync reacts to new commits, not to drift.
Automated with self-healAfter a few seconds Argo CD re-applies git. The Deployment is back at 3.

OutOfSync: which side moved?

ClueGit moved (pending change)Cluster moved (drift)
Revision in argocd app getA new commit hashSame commit as the last sync
argocd app historyLast entry is older than the newest commitLast entry is the current commit
git logA recent commit touching that fileNothing recent

In both cases argocd app diff shows the exact fields, and argocd app sync makes the cluster equal to git.

Rolling back

❌ Fighting the controller 
kubectl -n shop set image deploy/web web=shop/web:1.0
# ...ten seconds later it is 1.2 again

With self-heal on, every manual correction is drift, and drift is reverted. The cluster is faithfully reproducing a mistake that lives in git.

✅ Fixing the source 
git revert HEAD --no-edit
git push
argocd app get shop --refresh

A revert is a new commit that undoes an old one. The history keeps the record of what went wrong and when it was undone.

There is also argocd app rollback APP ID, which re-applies an earlier entry of the application's history. It only works with automated sync disabled; otherwise Argo CD refuses (rollback cannot be initiated when auto-sync is enabled), because it would immediately sync forward to git again. On automated applications, git is the rollback mechanism.

Emergency procedure If you truly must change the cluster by hand during an incident on a self-healing application, first switch the application to manual (argocd app set APP --sync-policy none), make the change, and afterwards put the same change into git before re-enabling automation. Otherwise the next sync silently undoes your fix.

What Argo CD ignores

Argo CD only tracks resources that it created from the application's manifests, plus the fields those manifests specify. Pods created by a Deployment, status fields, and fields set by other controllers are not drift. Objects created by hand in the same namespace are simply not part of the application: they are neither reported nor pruned.

🔑 Key takeaways

  • Automated sync applies new commits; prune deletes what left git; self-heal reverts manual changes.
  • With these on, a deployment is a commit and a rollback is a git revert.
  • argocd app diff shows the exact difference between live and git.
  • OutOfSync has two causes: an unapplied commit, or drift. The revision tells you which.
  • On a self-healing app, manual fixes vanish. Fix git, or switch to manual first.

Quiz

An application has automated sync with self-heal. Someone runs kubectl scale deployment web --replicas=10. What happens?

Self-heal treats any deviation from git on a managed field as drift and re-applies the declared state.

A manifest file is deleted from the repository. Automated sync is on, prune is off. What is the result?

Without prune, Argo CD never deletes. It reports that the resource "requires pruning".

A bad commit broke production on an application with automated sync and self-heal. What is the right way back?

Git is the source of truth. kubectl rollout undo would be reverted as drift, and argocd app rollback is refused while auto-sync is enabled.
