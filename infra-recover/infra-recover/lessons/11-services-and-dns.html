Services and DNS

Pods come and go, and each new one has a new IP address. A Service gives a changing group of pods one stable name and address. Understanding how a Service finds its pods is what lets you fix it when it finds none.

⏱ 40 min
🎯 Goal of this lesson

Expose pods with a Service, understand selectors, endpoints and cluster DNS, and diagnose a Service that does not answer.

Why it matters: "all pods are Running but the app is down" is the most common Kubernetes support request, and it is almost always a Service problem that kubectl get endpoints reveals in five seconds.

By the end of this lesson you will be able to

  • Explain what a Service is and how it selects pods.
  • Distinguish port, targetPort and nodePort.
  • Choose between ClusterIP, NodePort and LoadBalancer.
  • Use Service DNS names within and across namespaces.
  • Test a Service from inside the cluster and read its endpoints.

The situation

The front end must call the API. There are three API pods, their IP addresses change with every rollout, and the front end must neither know nor care. It should simply call http://api:3000.

What a Service is

A Service is a small object with three jobs: it has a stable virtual IP (the ClusterIP) and DNS name; it selects pods by label; and it load-balances connections across the selected pods that are ready.

apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api            # send traffic to pods with this label
  ports:
    - port: 3000        # the port of the Service itself
      targetPort: 3000  # the port on the pods where traffic is delivered
 web pod ──► api:3000 ──DNS──► 10.96.0.27:3000 ──► one of the ready pods matching app=api
             (name)           (ClusterIP)          10.244.1.5:3000   10.244.2.4:3000

Endpoints: the Service's actual targets

For every Service, Kubernetes maintains a list of the pod IPs that currently match the selector and are ready. That list is the Service's endpoints, and it is the first thing to look at when a Service misbehaves.

kubectl get service api
kubectl get endpoints api
kubectl describe service api      # selector, ports and endpoints in one place
NAME   TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)    AGE
api    ClusterIP   10.96.0.27   <none>        3000/TCP   2m

NAME   ENDPOINTS                         AGE
api    10.244.1.5:3000,10.244.2.4:3000   2m
An empty endpoint list is not an error to Kubernetes If the selector matches no pod, or no matching pod is ready, the endpoints are <none>. Nothing warns you. Clients get connection refused from the Service's IP. Selector and labels are compared as exact strings: app: api and app: backend are simply different.

The three port numbers

FieldWhere it appliesExample
portOn the Service. What clients connect to.http://api:3000
targetPortOn the pod. Must be a port the container actually listens on. Defaults to port.The app's listening port
nodePortOn every node (NodePort and LoadBalancer types only), range 30000–32767.http://NODE-IP:30869

A Service can translate: port: 80, targetPort: 8080 lets clients say http://web while the app keeps listening on 8080.

Service types

TypeReachable fromUse for
ClusterIP (default)Inside the cluster onlyEverything internal: APIs, databases
NodePortAlso from outside, on a high port of every nodeSimple external access, test clusters

For HTTP applications the usual production setup is ClusterIP Services behind one Ingress (Lesson 17).

Cluster DNS

The cluster runs a DNS server (CoreDNS), and every pod is configured to use it. Each Service gets a name of the form SERVICE.NAMESPACE.svc.cluster.local.

From a pod in namespace shopResolves to
apiService api in the same namespace
api.paymentsService api in namespace payments
api.payments.svc.cluster.localThe same, fully qualified
The short name is namespace-relative http://api:3000 means "the Service api in my namespace". A pod in another namespace calling the same URL gets a name-resolution error, or worse, reaches a different Service that happens to have the same name.

Creating and testing a Service

kubectl expose deployment web --port=80 --target-port=8080   # generates a Service from the Deployment's selector
kubectl get service,endpoints web

# a ClusterIP is only reachable from inside, so test from a temporary pod
kubectl run tmp --rm -it --restart=Never --image=busybox -- wget -qO- http://web

# or forward a local port to the Service while you test
kubectl port-forward service/web 8080:80 &
curl localhost:8080
Why your shell can't curl a ClusterIP ClusterIPs and pod IPs only exist inside the cluster's network. From your workstation they time out. Use a temporary pod, kubectl port-forward, a NodePort, or an Ingress.

The Service checklist

When a Service does not answer, three checks in this order find nearly every cause:

  1. Are there endpoints? kubectl get endpoints NAME. None → selector mismatch, or pods not ready (Lesson 14).
  2. Do the endpoint ports match what the container listens on? If not, fix targetPort (Lesson 17).
  3. Is the client using the right name and port? Same namespace? The Service's port, not the pod's?

🔑 Key takeaways

  • A Service is a stable name and IP in front of the ready pods that match its selector.
  • Endpoints are the Service's real targets. Empty endpoints mean no pod matches, or none is ready.
  • port is on the Service, targetPort on the pod, nodePort on the nodes.
  • Short DNS names resolve within the caller's namespace; use name.namespace across namespaces.
  • Test ClusterIP Services from inside the cluster.

Quiz

kubectl get endpoints api shows <none>, and the api pods are Running and Ready. What is the most likely cause?

Endpoints are built from pods that match the selector and are ready. Ready pods that are not listed are not being selected.

A Service has port: 80 and targetPort: 8080. Which URL does a client pod in the same namespace use?

Clients talk to the Service's port. The Service forwards to targetPort on the pods.

A pod in namespace shop must call the Service api in namespace payments. Which host name works?

The pattern is SERVICE.NAMESPACE. The bare name api would look for a Service in the caller's own namespace.
