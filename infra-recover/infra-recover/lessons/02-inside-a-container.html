Inside a Container: Logs, Exec, Inspect

Three commands answer almost every question about a container: what did it say, what does it look like from the inside, and how was it configured. This lesson teaches them, and then uses them on a database that refuses to stay up.

⏱ 35 min
🎯 Goal of this lesson

Learn the container lifecycle and the three commands that explain a container's behaviour: docker logs, docker exec and docker inspect.

Why it matters: troubleshooting is collecting evidence. These commands are where the evidence is. Engineers who reach for them first fix problems in minutes; those who guess restart things for hours.

By the end of this lesson you will be able to

  • Name the states a container moves through and what causes each transition.
  • Read a container's output and its exit code.
  • Run commands and open a shell inside a running container.
  • Find a container's configuration with docker inspect.
  • Diagnose a container that exits immediately after starting.

The situation

A container is running on a machine you have just been handed. Nobody remembers how it was started. Later, a second container is started and vanishes from docker ps within a second. Both situations are solved with the same small toolkit.

The lifecycle

docker create            docker start                 main process exits
     │                        │                              │
     ▼                        ▼                              ▼
  Created  ───────────────►  Running  ───────────────────►  Exited (code)
                              ▲   │ docker stop / kill           │
                              │   └──────────────────────────────┤
                              └────────── docker start ──────────┘
                                                                 │ docker rm
                                                                 ▼
                                                              (gone)

docker run is create + start. The STATUS column of docker ps -a shows the state, and for an exited container the exit code of its main process:

CONTAINER ID   IMAGE          COMMAND                  CREATED          STATUS                      PORTS     NAMES
1abf541becdf   postgres:17    "docker-entrypoint.s…"   2 minutes ago    Exited (1) 2 minutes ago              db
247720201ef0   shop/web:1.0   "docker-entrypoint.s…"   10 minutes ago   Up 10 minutes               ...       web
Exit codeUsual meaning
0The process finished successfully. Normal for one-off jobs, suspicious for a server.
1 (or another small number)The application reported an error. The reason is in the logs.
126 / 127The command could not be executed / was not found in the image.
137Killed with SIGKILL (128 + 9): docker kill, a stop that timed out, or the out-of-memory killer.
143Terminated with SIGTERM (128 + 15): a normal docker stop of a process that exits on the signal.

docker logs: what did it say?

Docker captures everything the main process writes to standard output and standard error. That stream is the container's log, and it is kept even after the container has exited.

docker logs web              # everything so far
docker logs --tail 20 web    # the last 20 lines
docker logs -f web           # follow new output (Ctrl+C to stop following)
docker logs -t web           # prefix each line with a timestamp
Logs survive the crash A container that died still has its logs until you remove it. That is why the first step with a container that "won't start" is never to run it again, but to read what the last attempt said: docker ps -a, then docker logs NAME.

docker exec: look from the inside

docker exec starts an additional process inside a running container. It shares the container's file system, network and environment, so it sees exactly what the application sees.

docker exec web env                 # the environment the app was given
docker exec web ls /app             # files in the image
docker exec -it web sh              # an interactive shell; leave with: exit

-i keeps standard input open and -t allocates a terminal; together they give you an interactive session. Many small images contain sh but not bash:

$ docker exec -it web bash
OCI runtime exec failed: exec failed: unable to start container process: exec: "bash": executable file not found in $PATH: unknown

That message does not mean the container is broken. It means the image has no bash. Use sh.

exec needs a running container You can't exec into a container that has exited: there is nothing to attach to. For a container that dies at startup the evidence is in docker logs and docker inspect, not in a shell.

docker inspect: how was it configured?

docker inspect prints everything Docker knows about an object as JSON: the image, the command, environment variables, mounts, port mappings, network addresses, the state and the exit code. The output is long, so pick out what you need with a Go template:

docker inspect web                                         # everything
docker inspect -f '{{.State.Status}} {{.State.ExitCode}}' web
docker inspect -f '{{json .Config.Env}}' web               # environment variables
docker inspect -f '{{json .Mounts}}' web                   # volumes and bind mounts
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web
What you can and cannot change afterwards A container's image, command, environment variables, port mappings and mounts are fixed when it is created. docker restart re-runs the same configuration. To change any of them you remove the container and run a new one. This is by design: containers are meant to be replaced, not repaired.

🔑 Key takeaways

  • A printed container ID means "created and started", not "working". Always check docker ps.
  • docker ps -a shows exited containers and their exit code. docker logs shows why.
  • docker exec runs an extra process inside a running container. Try sh when bash is missing.
  • docker inspect shows the configuration a container was created with.
  • Configuration is fixed at creation. To change it, remove the container and run a new one.

Quiz

A container shows Exited (1) 10 seconds ago. What is the best next command?

Exit code 1 means the application reported an error, and it wrote the reason to its output. exec is impossible on an exited container, and a restart would repeat the same failure.

You started a container without the environment variable it needs. How do you add it?

The environment is part of the configuration fixed at creation. An export inside an exec session only affects that one extra process.

docker exec -it api bash fails with executable file not found in $PATH. What does that tell you?

Small images (Alpine-based ones in particular) ship without bash. The container itself is fine.
