Ports, Environment Variables and Restart Policies

The same image runs in development, in testing and in production. What differs is how you start it: which ports you publish, which settings you pass in, and what should happen when the process dies.

⏱ 35 min
🎯 Goal of this lesson

Configure a container from the outside: publish ports correctly, pass environment variables, and choose a restart policy.

Why it matters: "it's running but I can't reach it" is the single most common Docker complaint, and it is nearly always a port mapping. Knowing how to read the mapping turns a mystery into a ten-second check.

By the end of this lesson you will be able to

  • Read and write -p HOST:CONTAINER mappings and explain each side.
  • Tell "connection refused" from "connection reset" and say what each implies.
  • Configure an application through environment variables.
  • Pick a restart policy and recognise a restart loop.
  • Resolve a host port conflict.

The situation

The shop's front end is published as the image shop/web. Its documentation is two lines long: "Listens on port 8080. Optional environment variables: PORT, API_URL, BANNER." That is all you need, if you know how to use it.

Publishing ports

docker run -d --name web -p 8080:8080 shop/web:1.0
#                           │    └─ container port: where the process listens
#                           └─ host port: where you connect from outside

The two numbers are independent. The container port is decided by the application (and its configuration); you cannot choose it with -p. The host port is yours to choose, as long as it is free.

MappingMeaning
-p 8080:8080Host 8080 → container 8080
-p 80:8080Host 80 → container 8080 (users type no port; the app is unchanged)
-p 127.0.0.1:8080:8080Only reachable from this machine, not from the network
-p 8080Container 8080 on a random free host port (see docker port NAME)
EXPOSE is documentation An image can declare ports with EXPOSE. That shows up in docker ps as 8080/tcp (no arrow), and it tells you where the app is expected to listen. It does not publish anything. Only -p does.

Reading the failure

When a published port does not answer, the error message already narrows down the cause:

What curl saysWhat it meansWhere to look
(7) Failed to connect … Could not connect to serverNothing is listening on that host port: no container publishes it, or the container is not running.docker ps -a
(56) Recv failure: Connection reset by peerThe host port is published, but nothing listens on the container port it forwards to.Right-hand side of -p versus the port in docker logs
An HTTP error page (404, 500, 502)You reached a process. The problem is in the application or behind it.docker logs

Environment variables

Environment variables are the standard way to configure a containerised application, because they let one image serve every environment.

docker run -d --name web-sale -p 8081:8080 \
  -e BANNER="Sale today" \
  -e API_URL=http://api:3000 \
  shop/web:1.0

docker exec web-sale env          # check what the process actually received
❌ Easy to get wrong
  • A misspelt name (-e BANER=…) is not an error. The app just never sees its setting.
  • -e placed after the image name is passed to the application as an argument, not to Docker.
  • Secrets passed with -e are visible to anyone who can run docker inspect.
✅ Habits that help
  • Verify with docker exec NAME env or docker inspect -f '{{json .Config.Env}}' NAME.
  • Options go between docker run and the image: docker run [OPTIONS] IMAGE [COMMAND].
  • Use --env-file for many variables, and a secrets mechanism for real credentials.

Restart policies

By default a container that exits stays exited. A restart policy tells the Docker daemon to start it again.

PolicyBehaviourTypical use
no (default)Never restart.One-off commands, experiments
on-failure[:N]Restart when the exit code is not 0, at most N times.Jobs that may fail transiently
alwaysAlways restart, also after the Docker daemon or the machine restarts.Long-running services
unless-stoppedLike always, but a container you stopped by hand stays stopped after a daemon restart.Long-running services
 
docker run -d --name api --restart unless-stopped shop/api:1.0
docker inspect -f '{{.RestartCount}}' api      # how often Docker has restarted it
A restart policy hides crashes With --restart always, a container that crashes at startup shows Restarting (1) 3 seconds ago in docker ps, then briefly Up, then Restarting again. Docker waits longer between attempts each time. The container is not "flaky": it is failing every single time, and docker logs shows the same error repeated once per attempt.

🔑 Key takeaways

  • -p HOST:CONTAINER: you choose the host port; the application decides the container port.
  • Connection refused: nothing on the host port. Connection reset: published, but nothing listening inside on the mapped port.
  • Environment variables configure the app; a misspelt variable fails silently, so verify with docker exec NAME env.
  • Restart policies keep services up and also disguise crash loops. Check RestartCount and the logs.
  • A host port can be bound once. A docker run that fails on the port leaves a Created container behind.

Quiz

An app listens on port 3000 inside its container. You want users to reach it on port 80 of the host. Which option?

HOST:CONTAINER. Host 80 forwards to container 3000. -p 3000:80 would forward host 3000 to a container port where nothing listens.

curl localhost:8080 answers Recv failure: Connection reset by peer, and docker ps shows 0.0.0.0:8080->80/tcp. What is the most likely cause?

The host side works (the connection was accepted), so the container side of the mapping is wrong. Check the app's log for the port it listens on.

A container with --restart always crashes one second after every start. What will docker ps show most of the time?

Docker keeps retrying with an increasing delay. The fix is in the logs, not in the restart policy.
