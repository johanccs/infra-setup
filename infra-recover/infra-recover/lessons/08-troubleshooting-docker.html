Troubleshooting Docker: A Method

You have now met most of the ways a container can fail, one at a time. Real incidents rarely come one at a time. This lesson turns what you learned into a method you can apply when you don't yet know what is wrong.

⏱ 45 min
🎯 Goal of this lesson

Apply a repeatable four-step method to any misbehaving container, and solve an incident with several simultaneous faults.

Why it matters: under pressure people restart things, change three settings at once and lose track of what helped. A method keeps you calm and fast, and it is the same method you will use on Kubernetes.

By the end of this lesson you will be able to

  • Work through state, logs, configuration and connectivity in order.
  • Interpret exit codes, including 137 and OOM kills.
  • Set and check memory limits.
  • Untangle several faults by fixing one visible error at a time.
  • Clean up a Docker host safely.

The method: four questions, in this order

#QuestionCommandYou learn
1State: is it running? Since when? How did it end?docker ps -aUp / Exited (code) / Restarting / Created; ports; age
2Logs: what did the process say?docker logs --tail 50 NAMEThe application's own error message
3Configuration: how was it started?docker inspect NAMEImage and tag, env, ports, mounts, networks, limits, restart count
4Connectivity: can it be reached, and can it reach what it needs?curl, docker exec … wget/nc/nslookup, docker network inspectError class: not found / refused / reset / timed out / auth

The order matters. There is no point testing connectivity to a container that is not running, and no point reading configuration before the logs have told you what to look for.

Three rules that save hours
  1. Read before you change. Collect the state and the message first. A restart destroys evidence and usually reproduces the failure.
  2. One change at a time. Then test again. If you change three things and it works, you learned nothing; if it doesn't, you may have added a fault.
  3. Fix the error you can see. When several things are broken, each fix reveals the next message. That is progress, not failure.

Memory limits and exit code 137

A container can use as much of the host's memory as it likes unless you limit it. A limit is enforced by the kernel: when the container's processes need more than the limit, the kernel's out-of-memory killer ends one with SIGKILL. The process cannot catch that signal and logs nothing.

docker run -d --name api -m 256m shop/api:1.0      # hard limit: 256 MiB

docker stats --no-stream                            # current usage versus limit
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' api
CONTAINER ID   NAME   CPU %   MEM USAGE / LIMIT   MEM %    NET I/O      BLOCK I/O   PIDS
ee8fe5ec7647   api    0.60%   125.8MiB / 256MiB   49.14%   1.2kB / 0B   0B / 0B     11
❌ Misreading 137

"Exit code 137 and nothing in the logs: the app is silently broken." Then an afternoon is spent in the application's code.

✅ Reading it correctly

137 = 128 + 9 = killed from outside. Check OOMKilled. If it is true, compare the limit with real usage (docker stats) and raise the limit or reduce the usage.

Keeping a host tidy

Stopped containers, unused images and forgotten volumes pile up and eventually fill the disk, which causes its own strange failures.

docker system df            # what uses space: images, containers, volumes, build cache
docker container prune      # remove all stopped containers
docker image prune          # remove dangling images (add -a for all unused ones)
docker system prune         # containers + networks + dangling images + build cache
Prune with care docker system prune never deletes named volumes unless you add --volumes. With that flag it deletes every volume no container currently uses, including the database volume of a stack you merely stopped. Read the confirmation prompt.

🔑 Key takeaways

  • State → logs → configuration → connectivity. Always in that order.
  • Read first, change one thing, test again.
  • Exit codes above 128 mean "killed by signal". 137 with OOMKilled: true is a memory limit, not an application bug.
  • A Created container never ran and has no logs; a Restarting one fails the same way on every attempt.
  • With several faults, each fix uncovers the next error. Follow the messages.

Quiz

A container is Restarting (1) 4 seconds ago. What should you do first?

The container fails on every attempt for the same reason, and the reason is in its output. Restarting adds one more identical failure.

A container exits with code 137, OOMKilled is true, and its logs end with normal request lines. What is the cause?

SIGKILL cannot be caught, so nothing is logged. The fix is to size the limit from measured usage, or to reduce the usage.

You fixed a crash at startup, and now the app answers with "password authentication failed". What does that tell you?

A new, later-stage error is evidence that the earlier stages now work. Authentication can only fail after name resolution and the connection succeeded.
