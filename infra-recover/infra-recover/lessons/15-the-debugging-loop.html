The Debugging Loop: Get, Describe, Logs

You have fixed several broken pods by now, each with a hint about where to look. This lesson removes the hints. It gives you one loop and one table that together tell you, for any pod status, where the explanation is.

⏱ 45 min
🎯 Goal of this lesson

Diagnose any unhealthy pod with the loop get → describe → logs, using the pod's status to decide where the evidence is.

Why it matters: there are only about a dozen ways a pod fails to run. Each shows a characteristic status, and each status has one place where the cause is written down. Learn the mapping once and you can debug clusters you have never seen.

By the end of this lesson you will be able to

  • Run the debugging loop without prompting.
  • Say for each common pod status whether the cause is in the events or in the logs.
  • Use kubectl logs --previous, -c and label selectors.
  • Explain what "BackOff" means and why it is never the root cause.
  • Debug a pod whose command cannot be started.

The loop

 ┌─► 1. kubectl get pods            What is the STATUS? How many RESTARTS? How old?
 │   2. kubectl describe pod NAME   State / Last State / Exit Code, and the Events at the bottom
 │   3. kubectl logs NAME           What did the application say?  (--previous for the last crash)
 │   4. Form ONE hypothesis, change ONE thing
 └── 5. Watch the status change, and go round again

It is the method from Lesson 8 with Kubernetes commands. Step 1 tells you whether step 2 or step 3 has the answer.

A pod's life, and where it can stop

 created ─► scheduled ─► image pulled ─► config resolved ─► container started ─► running ─► ready
    │           │             │                 │                   │               │         │
  rejected   Pending   ErrImagePull /   CreateContainer-    RunContainerError   CrashLoop-  Running
  by API               ImagePullBackOff   ConfigError                           BackOff,    but 0/1
                                                                                OOMKilled
            └──────────── no container yet: read EVENTS ───────────┘└── container ran: read LOGS ──┘

That last line is the rule. If no container has run, there are no logs: the kubelet or scheduler reports the reason as an event. If a container ran and died, the application's own output has the reason.

"BackOff" is the waiting, not the problem CrashLoopBackOff and ImagePullBackOff both mean: "this keeps failing, so I wait longer before each retry" (10 s, 20 s, 40 s … up to 5 minutes). Searching the web for "CrashLoopBackOff" leads nowhere, because it describes Kubernetes' reaction. The cause is one step earlier: the crash, or the failed pull.

Getting the right logs

kubectl logs web-5d4f8c7b9-x2x9z             # current container instance
kubectl logs web-5d4f8c7b9-x2x9z --previous  # the instance before the last restart
kubectl logs web-5d4f8c7b9-x2x9z -c sidecar  # a specific container in a multi-container pod
kubectl logs deployment/web                  # one pod of the Deployment (kubectl picks it)
kubectl logs -l app=web --tail=20            # the last lines of every pod with that label
kubectl logs -f deployment/web               # follow
kubectl saysMeaning
container "x" in pod "y" is waiting to start: ContainerCreating (or trying and failing to pull image)No container has run yet. Go to the events.
previous terminated container "x" … not foundThe container has not been restarted, so there is no previous instance.
Empty outputThe process wrote nothing to stdout or stderr. It may log to a file inside the container, or it was killed before it could log.

describe, read properly

Three places in kubectl describe pod carry most of the information:

Containers:
  api:
    Image:          shop/api:1.0            ← is this the image you expected?
    State:          Waiting
      Reason:       CrashLoopBackOff
    Last State:     Terminated              ← how the previous attempt ended
      Reason:       Error
      Exit Code:    1
    Restart Count:  5
    Environment:    <none>                  ← what the container was given
...
Events:                                     ← what the scheduler and kubelet did, and why they stopped
  Warning  BackOff  3s (x12 over 2m)  kubelet  Back-off restarting failed container api in pod …

Events are kept for about an hour and are aggregated: (x12 over 2m) means the same event occurred twelve times within two minutes. For the whole namespace in time order, use kubectl get events --sort-by=.lastTimestamp or kubectl events.

When the pod won't stay up long enough to look inside You can't kubectl exec into a container that keeps crashing. Reproduce the environment instead: start a temporary pod from the same image with a harmless command (kubectl run debug --rm -it --restart=Never --image=IMAGE --command -- sh) and inspect files and environment there, or compare the pod's -o yaml with a working one.

Scenario: three pods, three different failures

No per-pod story this time. Use the status table to decide, for each Deployment, whether to read events or logs, and fix the Deployment (not the pod).

🔑 Key takeaways

  • get → describe → logs → one change → repeat.
  • No container has run (Pending, ImagePull…, CreateContainerConfigError, RunContainerError): the cause is in the events.
  • A container ran and exited (CrashLoopBackOff, Error, OOMKilled): the cause is in the logs and in Last State.
  • "BackOff" is Kubernetes waiting between retries. Look for the failure that precedes it.
  • Fix the owner (Deployment), never the individual pod.

Quiz

A pod is in ImagePullBackOff. You run kubectl logs and get "container is waiting to start". What now?

The image was never pulled, so no container ever started. The registry's answer is recorded as an event.

A pod shows CrashLoopBackOff with 8 restarts, and kubectl logs prints only a start-up line. Which command most likely shows the error?

The current instance has only just started. The crash message belongs to the previous instance.

What is the correct way to fix a pod that fails because its Deployment's template has a wrong environment variable?

Pods of a Deployment are created from its template. Any direct change to a pod is lost with the next replacement.
