Storage and Stateful Apps

A pod's file system dies with the pod, just as a container's did in Lesson 5. Kubernetes solves this with three objects that are easy to mix up. This lesson sorts them out and follows the chain that leads from a Pending database pod to a misspelt storage class.

⏱ 45 min
🎯 Goal of this lesson

Understand PersistentVolumeClaims, PersistentVolumes and StorageClasses, run a database with persistent storage, and know when to use a StatefulSet.

Why it matters: storage problems stop pods before they start, and the error sits two objects away from the pod. Data is also the one thing in a cluster you cannot recreate from a manifest, so the deletion rules matter.

By the end of this lesson you will be able to

  • Explain how claim, volume and storage class relate.
  • Give a pod persistent storage through a claim.
  • Explain why a claim can be Pending, including WaitForFirstConsumer.
  • Describe what a StatefulSet adds over a Deployment.
  • Trace a Pending pod to its unbound claim and fix it.

The situation

The database moves into the cluster. Its pod will be rescheduled during node maintenance and replaced on upgrades, and the orders must be there every time it comes back.

Three objects

 Pod ──mounts──► PersistentVolumeClaim ──bound to──► PersistentVolume ──► real storage
                 "I need 1Gi, read-write"            "here is a 1Gi disk"   (cloud disk, NFS,
                 (yours, namespaced)                 (cluster-wide)          local directory …)
                          ▲                                   ▲

ObjectWho creates itWhat it is
PersistentVolumeClaim (PVC)You, next to your appA request for storage: size, access mode, optionally a class.
PersistentVolume (PV)Usually the cluster, automaticallyAn actual piece of storage that a claim can be bound to.
StorageClassThe cluster administratorA recipe for creating volumes on demand ("dynamic provisioning").
 
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-data
spec:
  accessModes: [ReadWriteOnce]      # mountable read-write by one node at a time
  resources:
    requests:
      storage: 1Gi
  # storageClassName: standard      # omit to use the cluster's default class
spec:
  containers:
    - name: db
      image: postgres:17
      volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: db-data

Why a claim is Pending

Event on the claimMeaningAction
waiting for first consumer to be created before bindingNormal. The class uses WaitForFirstConsumer: the volume is created once a pod that uses the claim is scheduled, so that it lands on the right node.None. Create the pod.
storageclass.storage.k8s.io "X" not foundThe claim names a class this cluster doesn't have.Use an existing class (see below: this needs a new claim).
no persistent volumes available for this claim and no storage class is setNo default class, and no pre-created volume fits.Set a class, or create a matching volume.

And the pod waits for the claim. That gives the chain you follow when a pod with storage is Pending:

 kubectl describe pod db-0          →  "pod has unbound immediate PersistentVolumeClaims"
 kubectl get pvc                    →  data-db-0   Pending   …   fast-ssd
 kubectl describe pvc data-db-0     →  storageclass.storage.k8s.io "fast-ssd" not found
 kubectl get storageclass           →  only "standard" exists
A claim's class and size request are (mostly) fixed You can't change the storage class of an existing claim; the API server answers Forbidden: spec is immutable after creation. To correct a wrong class on a claim that never bound, delete the claim and create it again. For a claim that holds data, that means a migration, so get it right the first time.

What happens to the data when you delete things

You deleteThe data
The podSafe. The replacement pod mounts the same claim.
The Deployment or StatefulSetSafe. Claims are separate objects.
The claim, with reclaim policy Delete (the usual default for dynamic volumes)Deleted for good, together with the volume.
The claim, with reclaim policy RetainThe volume is kept as Released and must be cleaned up or re-bound by hand.
The namespaceDeletes every claim in it. See above.

A claim that a pod is still using is not removed immediately: it shows Terminating until the pod is gone.

StatefulSets

A Deployment's pods are interchangeable: random names, any order, and (if you mount a claim) all sharing the same claim. That is wrong for most databases. A StatefulSet gives each pod an identity:

DeploymentStatefulSet
Pod namesdb-7d9c5b8f6d-x2x9z (random)db-0, db-1 (stable, ordered)
StorageAll replicas share the claims you referencevolumeClaimTemplates: one claim per pod (data-db-0, data-db-1)
Start and update orderAll at once / surgeOne at a time, in order
Network identityOnly through a ServiceStable DNS name per pod via a headless Service (db-0.db)
 
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db                 # a headless Service (clusterIP: None) with this name
  replicas: 1
  selector:
    matchLabels: {app: db}
  template:
    metadata:
      labels: {app: db}
    spec:
      containers:
        - name: db
          image: postgres:17
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 1Gi
Two StatefulSet rules that matter in incidents
  • volumeClaimTemplates can't be edited on an existing StatefulSet. A change requires deleting and recreating the StatefulSet (its claims and data stay).
  • Deleting or scaling down a StatefulSet keeps its claims. That protects data, and it means a claim created with a wrong class survives and must be deleted by hand before a corrected template can create a new one.

🔑 Key takeaways

  • A claim requests storage; a StorageClass provisions a volume for it; the pod mounts the claim.
  • A Pending pod with storage: describe the pod, then the claim, then check the classes.
  • Waiting for first consumer is normal. Storageclass not found is a typo or a manifest from another cluster.
  • Deleting a pod or workload keeps the data; deleting the claim (or the namespace) usually destroys it.
  • StatefulSets give pods stable names and one claim each; their claim templates are immutable and their claims outlive them.

Quiz

A new claim is Pending with the event "waiting for first consumer to be created before binding". What should you do?

With WaitForFirstConsumer, provisioning is delayed until a pod using the claim is scheduled. It is the expected state before the pod exists.

You delete a Deployment whose pod mounted the claim db-data. What happened to the data?

Claims are independent objects. Only deleting the claim itself (or its namespace) removes the data under the usual Delete reclaim policy.

db-0 of a StatefulSet is Pending because its claim names a StorageClass that doesn't exist. You correct the class in the manifest. Why is kubectl apply not enough?

The API server forbids changing volumeClaimTemplates, and an existing claim is never re-created from the template.
