Container Networking and DNS

Real applications are several containers that talk to each other. This lesson shows how containers find each other by name, why that sometimes fails, and how to tell a naming problem from a connection problem.

⏱ 40 min
🎯 Goal of this lesson

Connect containers with user-defined networks, understand Docker's built-in DNS, and classify network errors by their message.

Why it matters: network errors look alike to beginners and are completely different to someone who can read them. "Not found", "refused" and "timed out" each point to a different layer, here and later in Kubernetes.

By the end of this lesson you will be able to

  • Explain the difference between the default bridge network and a user-defined network.
  • Make one container reach another by name.
  • Explain when -p is needed and when it is not.
  • Map an error message to "name resolution", "nothing listening" or "blocked".
  • Inspect networks and attach running containers to them.

The situation

The shop has three parts: a web front end, an API, and a PostgreSQL database. The API has to reach the database; the front end has to reach the API; customers only ever reach the front end.

Every container has its own network stack

Each container gets its own network interface and IP address. localhost inside a container is that container, not the host and not its neighbours.

The localhost trap An API configured with DATABASE_URL=postgres://…@localhost:5432/… works on a laptop where everything runs side by side, and fails in containers with connection refused: there is no database inside the API's own container. Between containers you connect to the other container's name.

The default bridge versus your own network

Without --network, a container joins the built-in network called bridge. Containers there can reach each other by IP address, but there is no name resolution. On a network you create yourself, Docker runs a small DNS server, and every container is reachable by its name.

Default bridgeUser-defined network
Reach another container by IPYesYes
Reach another container by nameNoYes
Isolation from other applicationsShared by everything started without --networkOnly the containers you attach
 
docker network create shopnet

docker run -d --name db --network shopnet \
  -e POSTGRES_USER=shop -e POSTGRES_PASSWORD=secret postgres:17

docker run -d --name api --network shopnet -p 3000:3000 \
  -e DATABASE_URL=postgres://shop:secret@db:5432/shop shop/api:1.0
#                                         └─ the database container's name

curl localhost:3000/products

When do you need -p?

Publishing is for traffic that comes from outside Docker: your browser, curl on the host, other machines. Containers on the same network reach each other's ports directly, on the port the application listens on.

 your shell ──► localhost:3000 ──(-p 3000:3000)──► api:3000 ──► db:5432
               published on the host              container to container
                                                  on shopnet, no -p needed
Publish as little as possible The database above has no -p at all, so nothing outside the Docker network can connect to it. That is a deliberate security benefit, not an omission. Publishing 5432 "to make the API work" would not even help: the API does not go through the host.

Reading network errors

This table is worth memorising. It applies to Docker, to Kubernetes and to networking in general.

Message containsWhat happenedCheck
ENOTFOUND, bad address, Could not resolve host, NXDOMAINName resolution failed. No connection was even attempted.Spelling of the name; are both containers on the same user-defined network?
ECONNREFUSED, Connection refusedThe name resolved and the machine answered, but nothing listens on that port.Is the target running? Is it listening on that port? Did it finish starting?
ETIMEDOUT, timed outThe packets went nowhere: dropped by a firewall or policy, or the address is unreachable.Firewalls, network policies, wrong IP
authentication failed, HTTP 401/403The network is fine. The credentials are wrong.User, password, token

Looking at networks

docker network ls
docker network inspect shopnet        # subnet, gateway and the containers attached
docker inspect -f '{{json .NetworkSettings.Networks}}' api

# test from a throw-away container on the same network
docker run --rm --network shopnet alpine nslookup db
docker run --rm --network shopnet alpine wget -qO- http://api:3000/healthz
docker run --rm --network shopnet alpine nc -zv db 5432

A running container can be attached to an additional network without restarting it:

docker network connect shopnet api
docker network disconnect bridge api

🔑 Key takeaways

  • localhost inside a container is the container itself.
  • Name resolution between containers exists only on user-defined networks. The default bridge has none.
  • -p is for access from outside Docker. Containers on one network talk directly.
  • Not found = name. Refused = no listener. Timed out = blocked. Auth failed = credentials.
  • docker network inspect shows who is attached; docker network connect fixes it without a restart.

Quiz

Two containers were started with plain docker run (no --network). Container A tries to reach http://b:8080. What happens?

The default bridge network has no DNS between containers. The fix is a user-defined network.

The API logs connect ECONNREFUSED 172.18.0.2:5432. What does this tell you?

An IP address in the message proves that resolution worked. "Refused" means the port is closed: the database is not running, still starting, or listening elsewhere.

The database container has no -p option. Which statement is true?

Publishing only concerns access from outside Docker. Keeping internal services unpublished is the safer default.
