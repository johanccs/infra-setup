Upgrades, Rollbacks and Broken Releases

Installing a chart is the easy part. Releases live for years and are upgraded hundreds of times, and that is where values get lost, upgrades fail half-way, and a release ends up in a state where Helm refuses to touch it. This lesson covers each of those and the way out.

⏱ 45 min
🎯 Goal of this lesson

Upgrade releases without losing settings, use --wait and automatic rollback, read the release history, and repair failed and pending releases.

Why it matters: a Helm release has its own state, separate from the state of the pods. When the two disagree (Helm says failed, the app runs; or Helm says deployed, the app is down; or Helm says another operation is in progress and nothing is running), you need to understand Helm's bookkeeping to proceed.

By the end of this lesson you will be able to

  • Predict which values an upgrade will use.
  • Make Helm verify a rollout and undo it automatically on failure.
  • Interpret every status in helm history.
  • Roll back a release.
  • Recover a release stuck in pending-upgrade.

Which values does an upgrade use?

This is the most common Helm surprise. An upgrade computes the values from scratch:

You runValues used
helm upgrade web shop/web (no value flags at all)The previous revision's overrides are reused.
helm upgrade web shop/web --set image.tag=1.1Only chart defaults plus image.tag. Earlier overrides are dropped.
… --reuse-values --set image.tag=1.1Previous overrides, plus image.tag.
… -f values.yamlChart defaults plus exactly what the file says.
… --reset-valuesChart defaults only.
❌ The silent regression 
helm install web shop/web --set replicaCount=3
# three weeks later
helm upgrade web shop/web --set image.tag=1.1
# replicaCount is back to the chart default (2)
✅ Values in a file, passed every time 
# values-prod.yaml is in git and contains ALL overrides
helm upgrade --install web shop/web \
  -f values-prod.yaml --wait

What is deployed is always "the chart plus this file". No history to remember.

helm get values web -n shop           # what the current revision was given
helm get values web -n shop --all     # merged with the chart's defaults
--reuse-values and new chart versions --reuse-values re-applies the old overrides on top of the new chart's defaults. That is usually what you want, but if the new chart renamed or restructured a value, your old override silently no longer applies. Read the chart's release notes on upgrades, and prefer a values file.

Making Helm check its own work

FlagEffect
--waitWait until Deployments, StatefulSets and so on are ready. On timeout the command fails and the revision is marked failed.
--timeout 3mHow long --wait waits (default 5m).
--rollback-on-failureImplies waiting. If the upgrade fails, Helm rolls back to the previous revision by itself. (Called --atomic before Helm 4; the old name still works with a deprecation warning.)
--dry-runRender and validate, change nothing.
 
$ helm upgrade web shop/web --version 1.2.0 -n shop --wait --timeout 20s
Error: UPGRADE FAILED: context deadline exceeded

Context deadline exceeded is Helm's way of saying "I waited for the timeout and the workloads were still not ready". Note what happened in the cluster: Kubernetes started a rolling update, the new pod crashed, and the old pods kept serving (Lesson 13). Helm noticed only because of --wait. Without it the release would say deployed while the rollout is stuck.

Reading the history

helm history web -n shop
REVISION	UPDATED                 	STATUS         	CHART    	APP VERSION	DESCRIPTION
1       	Sun Oct 11 09:00:40 2026	deployed       	web-1.0.0	1.0        	Install complete
2       	Sun Oct 11 09:01:20 2026	failed         	web-1.2.0	1.2        	Upgrade "web" failed: context deadline exceeded
3       	Sun Oct 11 09:11:40 2026	pending-upgrade	web-1.2.0	1.2        	Preparing upgrade
StatusMeaning
deployedThe current, successfully applied revision. There is at most one.
supersededAn earlier revision that was replaced by a later successful one.
failedThe operation ended with an error. The cluster may be partly changed.
pending-install / pending-upgrade / pending-rollbackAn operation started and has not recorded its end.
uninstalledRemoved, with history kept (--keep-history).

Rollback

helm rollback web 1 -n shop      # to a specific revision; omit the number for "the previous one"
helm history web -n shop

A rollback re-applies the stored manifest of the chosen revision and records that as a new revision ("Rollback to 1"). History is never rewritten. As with kubectl rollout undo, the cluster then performs a normal rolling update back to the old pod template.

"another operation is in progress"

Helm writes a revision record with a pending status before it starts changing the cluster, and updates it when it finishes. If the Helm process dies in between (a cancelled CI job, a closed laptop, a killed pod), the record stays pending forever. Helm treats a pending record as a lock:

$ helm upgrade web shop/web --version 2.0.0 -n shop
Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress

No operation is in progress; only the record says so. Two more things make this confusing: helm list hides releases whose latest revision is pending (use helm list -a), and the application may be running perfectly well the whole time.

StepCommand
1. Make the release visiblehelm list -n shop -a
2. Find the last good revisionhelm history web -n shop
3. Roll back to it. This marks the stuck revision as failed and re-applies known-good manifests.helm rollback web 1 -n shop
4. Run the upgrade again, this time with --waithelm upgrade web shop/web --version 2.0.0 -n shop --wait
Don't reach for uninstall helm uninstall also "fixes" a stuck release, by deleting the application and, depending on the chart, its volume claims. In production that is an outage and possibly data loss. Rollback first.
Where Helm keeps this state Each revision is a Secret named sh.helm.release.v1.NAME.vN in the release's namespace (kubectl -n shop get secrets). Its status label is what helm history shows. Knowing that these are just Secrets explains why Helm needs no server, and why deleting the namespace erases the release history too.

🔑 Key takeaways

  • Passing any --set or -f without --reuse-values drops earlier overrides. Keep all overrides in a values file and pass it on every upgrade.
  • --wait makes Helm verify readiness; --rollback-on-failure also undoes a failed upgrade.
  • helm history is the release's own state: deployed, superseded, failed, pending.
  • A pending revision left by a killed Helm process blocks further operations. helm list -a shows it; helm rollback clears it.
  • A rollback creates a new revision from an old manifest. Uninstall is not a repair tool.

Quiz

A release was installed with --set replicaCount=5. Later someone runs helm upgrade web shop/web --set image.tag=2.0. How many replicas does the release have now?

Giving a value flag without --reuse-values recomputes the values from the chart defaults plus only the new flags.

helm upgrade fails with "another operation (install/upgrade/rollback) is in progress", and helm list shows no release. What is the state?

A killed Helm process leaves a pending record that acts as a lock. Nothing is actually running.

What does helm rollback web 2 do to the history?

History is append-only. The rollback is recorded as the newest revision, described as "Rollback to 2".
