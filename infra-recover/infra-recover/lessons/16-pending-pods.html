Pending Pods: Scheduling, Taints and Nodes

A Pending pod is a pod the scheduler could not place. There is no container, no log and no crash, only one event with a sentence that looks cryptic and is in fact a complete explanation. This lesson teaches you to read that sentence.

⏱ 40 min
🎯 Goal of this lesson

Understand how the scheduler chooses a node, decode FailedScheduling messages, and manage nodes with cordon, drain, labels and taints.

Why it matters: Pending pods appear exactly when you scale up for load or lose a node, the moments when you most need capacity. The fix differs completely depending on the reason, and the reason is written in the event.

By the end of this lesson you will be able to

  • Describe the scheduler's filter-then-score process.
  • Read a 0/3 nodes are available: … message reason by reason.
  • Explain why an idle cluster can still report Insufficient cpu.
  • Use node selectors, taints and tolerations.
  • Take a node out of service and return it safely.

The situation

Two workloads have been Pending for ten minutes, a node is still marked for a maintenance that ended yesterday, and somebody needs to patch worker-1 tonight without an outage.

How the scheduler decides

For every pod without a node, the scheduler works in two phases:

  1. Filter: discard every node that cannot run the pod. Not enough unreserved CPU or memory, a node selector that doesn't match, a taint the pod doesn't tolerate, the node is cordoned, a required volume isn't available there.
  2. Score: rank the remaining nodes (spread pods out, prefer nodes that already have the image, and so on) and pick the best.

If the filter phase leaves no node, the pod stays Pending and the scheduler records why, counting nodes per reason:

  Warning  FailedScheduling  2m  default-scheduler  0/3 nodes are available: 1 Insufficient cpu, 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 1 node(s) were unschedulable. preemption: 0/3 nodes are available: 1 No preemption victims found for incoming pod, 2 Preemption is not helpful for scheduling.

Read it as a list. The numbers add up to the number of nodes, and each node is excluded for one reason:

FragmentMeaningFix
Insufficient cpu / Insufficient memoryThe pod's requests don't fit into what is still unreserved on that node.Lower the request, free capacity, or add nodes
node(s) didn't match Pod's node affinity/selectorThe pod demands a node label that node lacks.Label a node, or correct the selector
node(s) had untolerated taint {key: value}The node repels pods that don't tolerate this taint.Add a toleration, or remove the taint
node(s) were unschedulableThe node is cordoned.kubectl uncordon
pod has unbound immediate PersistentVolumeClaimsThe pod's volume claim isn't bound.Fix the claim (Lesson 18)
Too many podsThe node has reached its pod limit.Add nodes

The part after preemption: says whether evicting lower-priority pods would have helped. You can usually ignore it.

The control-plane taint is normal Almost every message includes untolerated taint {node-role.kubernetes.io/control-plane: }. Control-plane nodes are reserved for the cluster's own components. That fragment is background noise; the other reasons are the ones to act on.

Requests, not usage

The scheduler does not look at how busy a node is. It adds up the requests of the pods already assigned to the node and compares that sum with the node's allocatable capacity.

kubectl describe node worker-1
Allocatable:
  cpu:     2
  memory:  4Gi
  pods:    110
...
Allocated resources:
  Resource           Requests      Limits
  --------           --------      ------
  cpu                450m (22%)    0 (0%)
  memory             448Mi (10%)   896Mi (21%)
❌ The puzzling case

"kubectl top nodes shows 5% CPU usage, and my pod is Pending with Insufficient cpu."

✅ The explanation

Usage is irrelevant to scheduling. Either the existing pods have reserved the capacity through their requests, or this pod requests more than any single node has. A request of cpu: 3 can never be placed on 2-CPU nodes.

Steering pods: selectors, taints, tolerations

MechanismSet onEffect
nodeSelectorPod"Only run me on nodes with these labels." Pod is attracted to nodes.
TaintNode"Keep away unless you tolerate me." Node repels pods.
TolerationPod"I can live with that taint." Permission, not attraction.
 
kubectl get nodes --show-labels
kubectl label node worker-1 disktype=ssd                 # add a label
kubectl label node worker-1 disktype-                    # remove it

kubectl taint nodes worker-2 dedicated=batch:NoSchedule  # add a taint
kubectl taint nodes worker-2 dedicated:NoSchedule-       # remove it
spec:
  nodeSelector:
    disktype: ssd
  tolerations:
    - key: dedicated
      operator: Equal
      value: batch
      effect: NoSchedule

Node maintenance: cordon and drain

kubectl cordon worker-1                      # no new pods; existing ones keep running
kubectl drain worker-1 --ignore-daemonsets   # cordon + evict the pods
# ... do the maintenance ...
kubectl uncordon worker-1                    # schedulable again
NAME       STATUS                     ROLES           AGE   VERSION
cp-1       Ready                      control-plane   4d    v1.37.0
worker-1   Ready,SchedulingDisabled   <none>          4d    v1.37.0
worker-2   Ready                      <none>          4d    v1.37.0
drain refuses because of…WhyFlag
DaemonSet-managed podsTheir controller would recreate them on the same node at once.--ignore-daemonsets
Pods with local storage (emptyDir)Their data is deleted with the pod.--delete-emptydir-data
Pods without a controllerNobody will recreate them.--force (they are gone for good)
Two things people forget
  • Uncordon. A node left in SchedulingDisabled silently removes a third of your capacity until the day you scale up and pods go Pending.
  • Nothing moves back. After uncordon the node is empty and stays empty; the scheduler only places new pods. The next rollout redistributes them.

🔑 Key takeaways

  • Pending = the scheduler found no node. The FailedScheduling event lists one reason per excluded node.
  • The scheduler compares requests with unreserved capacity, never actual usage.
  • Node selectors attract, taints repel, tolerations permit.
  • cordon stops new pods, drain also evicts, uncordon reverses it. Pods don't move back by themselves.
  • The control-plane taint in the message is expected; act on the other reasons.

Quiz

kubectl top nodes shows all nodes nearly idle, yet a pod is Pending with Insufficient cpu. What explains this?

Capacity is reserved by requests. Idle but fully reserved nodes can't accept more, and a single request larger than a node can never fit.

A node has the taint dedicated=batch:NoSchedule. Which pods can be scheduled there?

A taint repels everything that doesn't tolerate it. A node selector is a separate mechanism; to force pods onto the node you would use both.

After kubectl drain worker-1 --ignore-daemonsets and the maintenance, what must you do?

Drain leaves the node cordoned. Until you uncordon it, the scheduler ignores it.
