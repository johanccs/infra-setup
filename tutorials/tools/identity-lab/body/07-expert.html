Stronger sign-in: MFA and passkeys

Advanced

Goal: rank sign-in methods by how well they resist phishing, and explain why a passkey cannot be handed to a look-alike site.

Why this step

A strong password policy still loses to a convincing fake page. This step is about the factors that go on top of a password, which of them can be phished, and the one that cannot. It builds on steps 01 (factors), 02 (signatures) and 03 (passwords).

What is it? MFA

What it is
Multi-factor authentication: proving who you are with two different kinds of factor: something you know (a password), something you have (a phone, a key) or something you are (a fingerprint).
The problem it solves
Passwords are guessed, reused, leaked and phished. A second, independent factor means one stolen thing is not enough.
Everyday comparison
A bank vault that needs a key and a code. A thief with only one is still outside.
What it is not
Not automatically phishing-resistant. A code you read from your phone and type into a page can be typed into a fake page too. Two factors that are both typed are two things to steal.
Where you meet it
Authenticator apps, SMS codes, push prompts, hardware keys. Turn it on in the identity provider (step 19), not in every app.

What is it? A passkey

What it is
A credential that is a key pair made for one site. The private key stays in your device or password manager; the site keeps the public key. Signing in is a signature over a fresh challenge (step 02), confirmed with a fingerprint, face or PIN. The standard is WebAuthn, with FIDO2 for the authenticator side.
The problem it solves
There is no secret to type, so there is none to phish, guess or leak from a server breach. The server holds only public keys.
Everyday comparison
A door that recognises your key by its shape and only opens for its own building. A copy of the building on another street does not fit it.
What it is not
Not a password you do not have to remember: nothing about it can be typed, shared or recovered by asking. And "synced" passkeys are copies of the private key in a cloud, which is a trade-off, not a flaw.
Where you meet it
"Sign in with a passkey" or "Use your fingerprint" on many sites, Keycloak 26 (WebAuthn passwordless), Windows Hello, Touch ID, security keys.

Which factors can be phished?

MethodPhishable?Why
Password onlyYesTyped into whatever page asks. Also guessable, reusable and leakable.
SMS or voice codeYes, and moreTyped into a fake page, and also intercepted or redirected (SIM swap). NIST restricts the public telephone network for out-of-band codes.
Email codeYes, and moreNIST SP 800-63B-4: email SHALL NOT be used for out-of-band authentication.
Authenticator app (TOTP)YesA six digit code is typed, so a fake page can ask for it and use it within 30 seconds.
Push approvalYes"Approve?" prompts get approved by a tired person, one after another (MFA fatigue). Number matching helps; it is still a person deciding.
Passkey or security key (WebAuthn)NoThe browser signs for the real origin only. Nothing the person can type or approve gives away a usable credential.

NIST SP 800-63B-4 defines phishing resistance as preventing "the disclosure of authentication secrets and valid authenticator outputs to an impostor verifier ... without relying on the vigilance of the claimant", and says it requires cryptographic authentication: manually entered authenticator output (OTP, out-of-band) is not phishing-resistant. Applications assessed at AAL2 must offer a phishing-resistant option.

Codes: TOTP

An authenticator app and the server share a secret (the base32 text in the QR code). Both compute HMAC-SHA-1(secret, floor(time / 30)) and show six digits of it (RFC 6238, built on RFC 4226). It needs no network, which is its advantage, and it is a shared secret, which is its weakness: the server holds a secret that can be stolen.

Passkeys: make one and use one

The demo below makes a real passkey for localhost with your device, and signs in with it. The page plays the server and checks the same fields a real server must check. Try changing the "origin the server expects" before step 2: that is what a look-alike site would produce.

What the server checks in a registration and a sign-in
clientDataJSON.type
webauthn.create or webauthn.get. Stops a signature made for one ceremony being used in the other.
clientDataJSON.challenge
The one-time random value the server made. Stops replay.
clientDataJSON.origin
Written by the browser, not by the page. This is what defeats phishing: a fake site cannot make it say your origin.
authenticatorData.rpIdHash
SHA-256 of the relying party ID (here the host name). Ties the signature to the site.
authenticatorData.flags
UP user present, UV user verified (PIN, fingerprint, face), BE backup eligible and BS backed up (a synced passkey). A server that needs verification must check UV.
signature
Over authenticatorData || SHA-256(clientDataJSON), verified with the public key stored at registration.
signCount
A counter some authenticators increment; many synced passkeys keep it at 0, so a server must not treat a stuck 0 as an attack.

Synced and device-bound

A synced passkey is stored in a platform account (a password manager or the phone maker's cloud) and is available on your other devices: easy to recover, and good enough for most apps. A device-bound one, such as a hardware security key, never leaves the device. NIST SP 800-63B-4 allows syncable authenticators at AAL2 under its requirements, and notes that syncing "violates the non-exportability requirements of AAL3". Which one you need is a risk decision: a banking admin and a recipe site differ.

The weak point is recovery

The strongest sign-in is only as strong as "I lost my phone". If recovery is an email link or a call to support, an attacker uses that instead. Offer a second passkey or security key, one-time recovery codes stored offline, and treat recovery as a sign-in event that is logged, delayed and notified.

Asking for more before something risky

Not every action needs the strongest sign-in. Step-up authentication (RFC 9470) lets an API answer 401 with WWW-Authenticate: Bearer error="insufficient_user_authentication" and the acr_values or max_age it needs; the client sends the user back to the identity provider with those, and gets a new token. Deleting an account asks for a passkey even though a session already exists.

Practice

What you just learned

  • MFA means two different kinds of factor. Typed codes, push approvals and SMS can all be phished; a passkey cannot, because the browser signs for the real origin only.
  • A passkey is a key pair per site: the server stores a public key and checks a signature over a fresh challenge, the origin and the RP ID hash.
  • Synced passkeys are convenient and acceptable at AAL2; device-bound keys are for the highest assurance. Recovery is the weak point, so design it.
  • Step-up lets a sensitive action ask for a stronger, fresher sign-in.

Hardening

Expert

Goal: explain how a stolen token is made useless, and plan a signing-key rotation.

Why this step

A bearer token works for whoever holds it. Everything in this step is about making the token, the code and the client harder to steal or misuse. It builds on steps 09 to 14, 20 and 22.

What is it? Sender-constrained tokens (DPoP)

What it is
Demonstrating Proof of Possession (RFC 9449). The client holds a key pair. The access token is bound to the public key (cnf.jkt, the thumbprint). Every request carries the token and a short proof, a JWT signed with the private key that names the method, the URL and a hash of the token.
The problem it solves
A leaked bearer token (a log, a proxy, a browser extension) works from anywhere. A bound token is useless without the key.
Everyday comparison
A ticket with your photo and a signature you have to repeat at the gate, instead of a ticket anyone can hand in.
What it is not
Not encryption, and not a substitute for keeping scripts out of the page: code running in the client context can still use the key while it is there. Mutual TLS (step 08, RFC 8705) is the same idea at the transport layer.
Where you meet it
Keycloak (DPoP is supported by the token endpoint), banking and open-data APIs under FAPI 2.0.

The tool uses the same code the test suite checks against the example proof in RFC 9449. Make a proof for GET /api/todos, then change what the server receives: another method, another URL, another token, another key, or send it twice. Each is refused for a different reason.

Rotating a signing key

Step 09 covered the idea; here is the full sequence with the reason for each step, because getting it wrong logs everybody out or leaves a leaked key trusted.

  1. Add the new key to the key set, passive: published, not yet used to sign. Verifiers' caches pick it up (the handler refetches when it sees an unknown kid).
  2. Switch signing to the new key. New tokens carry the new kid.
  3. Wait for the longest-lived token signed with the old key to expire, plus the cache time of verifiers.
  4. Remove the old key from the key set.

After a leak you skip the waiting: remove the old key at once and accept that the tokens it signed stop working. That is why short lifetimes matter.

What OAuth 2.1 changes

OAuth 2.1 is still an Internet-Draft (revision 16, September 2026, expiring 7 March 2027), so treat it as a direction, not a standard. Its own non-normative list of changes from OAuth 2.0:

  • The code flow requires PKCE parameters by default.
  • Redirect URIs are compared by exact string matching.
  • The implicit grant and the password grant are gone.
  • Bearer tokens may not be sent in the query string.
  • Refresh tokens for public clients must be sender-constrained or one-time use.
  • redirect_uri is no longer sent in the token request, and the PKCE plain method is removed.
  • Authorization servers must support client credentials in the request body.

Almost all of it is already the advice of RFC 9700, which you have followed since step 12.

FAPI 2.0. The OpenID Foundation's FAPI 2.0 Security Profile (final, 22 February 2025) is a profile of OAuth for high-value APIs. It combines exactly the parts above: PKCE, pushed authorization requests, sender-constrained tokens (DPoP or mutual TLS) and a short list of allowed algorithms. If you need to say "as secure as the banks", this is what you point at.

Practice

What you just learned

  • A bearer token works for whoever holds it. DPoP binds it to a key, so a copied token without the key is refused.
  • PAR, iss, resource indicators, refresh rotation, short lifetimes and private-key client authentication each close a specific, named gap.
  • Rotate a signing key in four steps (add, switch, wait, remove), and skip the wait only after a leak.
  • OAuth 2.1 is a draft that gathers the advice of RFC 9700. FAPI 2.0 is the final profile for high-value APIs.
