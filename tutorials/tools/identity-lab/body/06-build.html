19

Run an identity provider

Intermediate

Goal: run Keycloak, find your way around a realm, and get tokens from it with curl.

Why this step

Until now the identity provider was a name in a diagram. From here on the Todo API checks real tokens, so you need a real issuer on your own machine. Keycloak is free, open source and speaks standard OpenID Connect, so everything you learn here carries over to any other provider.

This lesson builds on steps 09 (JWT), 12 (the code flow) and 14 (OpenID Connect).

What is it? An identity provider (IdP)

What it is
The service that knows your users, checks their credentials and issues tokens that other systems trust. In OAuth terms it is the authorization server; in OpenID Connect it is the OpenID Provider.
The problem it solves
Without one, every app stores passwords, builds its own login page, its own MFA and its own account recovery, and each gets some of it wrong. With one, apps hold no passwords and just validate tokens.
Everyday comparison
A passport office. Countries (apps) do not issue their own proof of identity at the border; they trust the passport and check that it is genuine.
What it is not
Not your user database for application data (todos stay in PostgreSQL), and not your API. It answers "who is this and what are they called?", never "what are their todos?".
Where you meet it
Keycloak, Microsoft Entra ID, Okta, Auth0, Google. Keycloak is the one you can run on a laptop.

What is it? A realm

What it is
Keycloak's unit of isolation: one set of users, roles, clients and settings. The master realm is for administering Keycloak itself; applications get a realm of their own.
The problem it solves
Two apps (or two customers) must not share users or settings by accident.
Everyday comparison
A separate building with its own front desk and its own guest list.
What it is not
Not a tenant of the whole machine: realms share one server and one database.
Where you meet it
The issuer address: http://localhost:8180/realms/todo contains the realm name.

Start Keycloak with the Todo realm

You will write one file, the realm file, and tell Keycloak to import it on first start. Everything in it is a practice value: the passwords and secrets are not secrets, and the file must never go near production.

Line by line: the realm file
sslRequired: "external"
Plain HTTP is allowed from localhost and private addresses only. Anything else must use HTTPS. This is Keycloak's default and the reason practice on localhost works.
accessTokenLifespan: 300
Access tokens live five minutes. Short lifetimes limit what a stolen token is worth (step 26).
roles.realm
Three realm roles. A role is only a name until the API gives it a meaning (step 21).
users
Alice has todo-user. Bob has todo-user and todo-admin. The user service-account-todo-reporter is the identity Keycloak creates for the machine client; it is listed so the import can give it the todo-reporter role.
todo-api with bearerOnly
A client that exists only so tokens can name it as their audience. It never signs anyone in.
todo-web
A confidential client (it has a secret) for the Todo app's own backend. Only the authorization code flow is on, directAccessGrantsEnabled (the password grant) is off, and pkce.code.challenge.method: S256 makes Keycloak refuse a code request without a PKCE challenge.
redirectUris
The exact addresses Keycloak may send the browser back to (RFC 9700: exact matching). Port 4200 is the Angular dev server, which forwards /api to the API.
protocolMappers
Two mappers per client. oidc-usermodel-realm-role-mapper writes the realm roles into a top-level roles claim. oidc-audience-mapper adds todo-api to aud. Without the second one, the API would correctly refuse the token.
todo-reporter with serviceAccountsEnabled
The machine client: client credentials grant, no browser flow.

Port 8180 is free in the series (8080 is the Todo app). start-dev is the development mode: HTTP allowed, an embedded H2 database inside the container, and nothing persisted once the container is removed. Its documentation lists what to do before production: a real database, your own certificates and a stronger admin password. The container reads every .json file in /opt/keycloak/data/import and skips a realm that already exists, so to change the file you remove the container and start again.

Version note. Keycloak 26.8.1 was published on the day this lesson was checked and fixes several security issues in 26.8.0, including some in OpenID Connect brokering. Use the newest patch release of the minor version you run, and read its release notes before you upgrade.

Ask the server what it is

Every OpenID Connect provider publishes a discovery document (step 14) and its keys (step 09). The first one tells a client everything it needs; the second is how an API checks signatures without calling Keycloak for each request.

The issuer is the address you used. Keycloak builds the issuer from the host name in the request. Open the realm at localhost:8180 and tokens say http://localhost:8180/realms/todo; open it at 127.0.0.1:8180 and they say http://127.0.0.1:8180/realms/todo. An API that expects one and receives the other refuses the token with an issuer error. Use one name everywhere. In production you pin it with the hostname option.

Get a token

The machine client can ask for a token on its own: no browser needed. The secret comes from a shell variable so that it never lands in your shell history.

Paste the access token into the workbench to read it. Three things matter for the next lessons:

  • iss is the realm address, and aud contains todo-api: that is what the API will check.
  • roles is a top-level array. Keycloak also writes realm_access.roles; both carry the same roles, and the API will read roles.
  • azp (authorized party) and client_id name the client that asked, sub names the user or, here, the service account.

Practice

What you just learned

  • An identity provider holds the users and issues the tokens; your apps hold no passwords. Keycloak runs on a laptop and speaks standard OpenID Connect.
  • A realm file describes users, roles and clients, and Keycloak imports it on first start. Mappers decide what lands in the tokens: here a top-level roles claim and the todo-api audience.
  • The issuer is built from the address you used, so use one name. The discovery document and the JWKS tell any client what to trust.
  • A machine client gets a token with the client credentials grant, with its secret kept out of the command line.

Protect the API with JWT bearer tokens

Advanced

Goal: make GET /api/todos answer 401 without a valid token, and explain every 401 the API can send.

Why this step

The API from Part 1 answers anyone. Step 10 showed that validating a token is where most mistakes are made, so this step configures a library and does not write the checks. It builds on steps 09, 10 and 19.

Add the package and the settings

Both files below are yours to change in src/api. The package version is the newest at the time of writing; check dotnet add package for yours.

In the cluster the same setting arrives as the environment variable Auth__Authority, exactly like ConnectionStrings__Todos. Step 22 explains why its value must be an address the API can reach.

The new Program.cs

Explained: what each new line does
AddJwtBearer with Authority
At first use the handler downloads {Authority}/.well-known/openid-configuration and the keys it points to, caches them, and refreshes them when a token names an unknown kid (step 09). The issuer to expect comes from the same document.
Audience = "todo-api"
A valid token meant for another API is refused (step 10: the "no audience check" attack).
MapInboundClaims = false
By default .NET renames incoming claims (sub becomes a long nameidentifier URI, roles becomes another). Switching it off keeps the names exactly as the token has them, so the code reads "sub" and "roles".
RequireHttpsMetadata
The handler refuses to fetch the discovery document over plain HTTP unless this is off. It is off only in Development, so a mistake in production fails closed.
ClockSkew
The default is five minutes: an expired token is still accepted for five minutes after exp. That is a lot when tokens live for five. Thirty seconds covers real clock drift.
NameClaimType and RoleClaimType
Tell the handler which claims are the user's name and roles. Keycloak writes preferred_username and roles.
SetFallbackPolicy
The policy used by every endpoint that has none. Requiring an authenticated user makes deny by default the rule: a new endpoint you forget about is protected, not open.
AllowAnonymous on three endpoints
The health, readiness and info endpoints stay open so that Kubernetes probes and the platform keep working.
UseAuthentication before UseAuthorization
Order matters: the user must be built before a rule can ask about it.

Try it

Start the API, get an access token for Alice with the code flow against your Keycloak (the by-hand flow of step 15 works with this realm: use client todo-web), then call it five ways. Every answer below was observed against a real Keycloak 26.8.1:

RequestAnswerWWW-Authenticate
No token401Bearer
A good token200
A token for another audience401Bearer error="invalid_token", error_description="The audience 'empty' is invalid"
A token that has expired401Bearer error="invalid_token", error_description="The token expired at '…'"
A token with one changed character401Bearer error="invalid_token", error_description="The signature is invalid"
/healthz with no token200

The error value is defined by RFC 6750 (section 3.1): a request with no credentials gets a bare Bearer challenge, and a request with a bad token gets invalid_token. The description helps you during development. Do not show it to a stranger in production as part of the page: it tells an attacker which check failed.

Why "audience 'empty'"? The token had no aud claim at all, because that client has no audience mapper. The message prints the audiences it found, and "empty" means none. A token with another audience prints that value.

Practice

What you just learned

  • Configure the JwtBearer handler with an authority and an audience; it fetches and caches the keys and checks signature, issuer, audience and expiry for you.
  • Set a fallback policy so that every endpoint is closed unless it says otherwise, and keep health endpoints open for the platform.
  • The default clock skew is five minutes. Set it small, and keep claim names as the token has them.
  • 401 means the API does not know who is calling, and WWW-Authenticate says why. Do not echo that detail to strangers.

Roles, policies and "only your own todos"

Advanced

Goal: turn roles into policies, store an owner on every todo, and make a user see and change only their own.

Why this step

Step 17 showed that checking "signed in" is not authorization. This step fixes the Todo API the way that lesson taught: an ownership rule in the query, plus role policies for the endpoints that are only for some people. It builds on steps 16, 17 and 20.

The rules, as a table

Write the rules down before the code. This is the table the tests of this lesson check, cell by cell, against a real Keycloak and a real PostgreSQL:

RequestNobodyAlice (user)Bob (user + admin)Reporter (machine)
/healthz, /readyz, /api/info200200200200
GET /api/todos401200, her own200, his own403
POST /api/todos401201201403
Toggle or delete her own todo401200 or 204(his own: 200 or 204)403
Toggle or delete someone else's todo401404404403
GET /api/admin/todos401403200, everyone's403
GET /api/admin/stats401403200200
  • 404, not 403, for someone else's todo. The answer for "yours, but not allowed" and "does not exist" is the same, so nobody learns which ids exist (step 17).
  • Admin is not "owner of everything". An admin can read everyone's todos on the admin route. They still cannot toggle or delete another person's todo. Giving a role more power than its job is how roles explode.
  • Reporter reads statistics only. It has no business with anyone's list.

The code

Two new records, a new column, and every store method takes the owner. The owner is the token's sub: the one value the user cannot choose.

Line by line: the store
add column if not exists owner
Existing rows get an empty owner, so after the upgrade nobody sees the old todos. That is the safe failure. Decide deliberately what to do with them (assign them, or delete them); do not default them to an admin.
where owner = $1
The owner is part of the query, not a check after it. A todo that is not yours is not found. This is the fix for the object-level flaw in step 17.
where Id = $1 and owner = $2
The same for toggle and delete: one statement, so there is no gap between "check" and "change" for someone to slip through.
EveryoneAsync and StatsAsync
Only called from endpoints guarded by an admin or statistics policy. They are the only methods that do not filter by owner, and the names say so.
Explained: policies and the owner
AddPolicy("TodoUser", …RequireRole("todo-user"))
A named rule. RequireRole reads the roles from the claim type you set in step 20. A signed-in caller without the role gets 403.
MapGroup(...).RequireAuthorization("TodoUser")
One line protects the whole group, including endpoints you add later.
Owner(user)
Reads sub from the validated principal. Never from the body, a header or the URL (step 17).
"Statistics" with two roles
RequireRole("a", "b") means either. Admins and the reporter machine may read the numbers.
The reporter and /api/todos
The reporter has the role todo-reporter, not todo-user, so the group policy answers 403. One more reason to give each caller its own role.

Roles are as old as the token. If Bob's admin role is removed in Keycloak, tokens already issued still carry it until they expire. A five-minute lifetime keeps that window short; step 26 covers the options when five minutes is too long.

Get tokens for Alice and Bob, post a todo as each, and walk the table. The most instructive row is the third:

Practice

What you just learned

  • Write the access table first; then name the policies and put the ownership rule in the query.
  • The owner is the token's sub, taken from the validated principal and written into every select, update and delete.
  • Someone else's object answers 404, an unauthorized role answers 403 and no token answers 401.
  • A role in a token is as old as the token. An admin role should open admin endpoints, not every object.

Sign in from the Angular UI (BFF)

Expert

Goal: sign in from the browser without a token ever reaching it, and explain the three patterns for a browser app.

Why this step

So far the callers were curl and a machine. People use a browser, and a browser is the most hostile place to keep a token. This step builds the pattern that RFC 10017 puts first for browser-based apps. It builds on steps 03 (cookies, CSRF), 12 (the code flow) and 20.

What is it? A backend for frontend (BFF)

What it is
A small server that sits beside the browser app and does the OAuth work on its behalf. It runs the code flow, keeps the tokens, and gives the browser a session cookie. In this lesson it is the Todo API itself.
The problem it solves
A page that holds a token can lose it to any script that runs in the page (XSS, a compromised dependency). A page that holds only an HttpOnly cookie has nothing to lose that script can carry away.
Everyday comparison
A concierge. You do not carry the hotel master key around; you ask the concierge, who holds it and recognises you.
What it is not
Not a way to skip authorization: the API still checks roles and owners. And not a stronger cookie: the cookie is still a bearer credential for this site, which is why SameSite and the CSRF header exist.
Where you meet it
Microsoft calls it a web app with a cookie session, Duende ships a BFF library, and RFC 10017 names it the first-choice pattern.

Three patterns

Pattern (RFC 10017)Tokens liveWhat XSS can doUse it when
1. BFF (a backend that is the OAuth client)On the serverMake requests while the page is open. Nothing to carry away.The default. Required for anything with personal data.
2. Token-mediating backendAccess token in the browser, refresh token on the serverSteal the short-lived access token.The browser must call other APIs directly.
3. Browser-based OAuth clientIn the browserSteal tokens, including refresh tokens, and use them from elsewhere.Only where a server is truly impossible, and with the extra care of the RFC.

The API becomes the OAuth client

One new package, one client secret kept out of the repository, and three kinds of change in Program.cs: two sign-in schemes (a cookie and OpenID Connect) behind a selector so the same endpoints accept a browser cookie or a machine's bearer token, a header check for cookie requests that change data, and the four /api/auth endpoints.

Explained: the sign-in parts
AddPolicyScheme("smart", …)
One name for "authenticate this request". If the Authorization header starts with Bearer it uses JwtBearer, otherwise the cookie. Machines and browsers share the same endpoints and the same policies.
Cookie.Name = "__Host-todo"
The __Host- prefix makes the browser accept the cookie only if it is Secure, has Path=/ and no Domain, so a sibling sub-domain cannot overwrite it (step 03).
HttpOnly, SameSite = Strict
Script cannot read it, and the browser does not send it on requests that start from another site. RFC 10017 recommends Strict for a BFF.
OnRedirectToLogin returns 401
For a fetch, a redirect to a login page is useless: the script would receive HTML. The API answers 401 and the page decides what to show.
AddOpenIdConnect
ResponseType = "code" with UsePkce = true: the code flow with PKCE (step 12), using the client secret as well. ResponseMode = "query" returns the code in the address; CallbackPath is where Keycloak sends the browser back, and it must match redirectUris in the realm.
SaveTokens = false
The cookie holds the person (name, sub, roles), not the tokens. The API does not call other APIs as the user, so it has no use for them, and the cookie stays small.
The X-Todo-Csrf check
A cookie-authenticated request that changes data must carry this header. A page on another site can make the browser send the cookie, but it cannot add a custom header without a CORS preflight that this API does not allow.
/api/auth/login
A GET that challenges the OpenID Connect scheme. The returnUrl is accepted only if it is a relative path on this site, so the endpoint cannot be used as an open redirect.
/api/auth/me
Returns who is signed in, from the cookie. The Angular app calls it at start-up: 200 means signed in, 401 means show the sign-in link.
/api/auth/logout
POST, signs out of the cookie scheme and of Keycloak. It is exempt from the header check because a browser form cannot add one; SameSite=Strict already keeps another site from triggering it.

The Angular side

Four small changes in src/ui. There is no OAuth library and no token anywhere in the UI code: signing in is a link, signing out is a form post, and everything else is the HttpClient you already have.

  • Sign in is a link. <a href="/api/auth/login"> makes the browser navigate, so it can follow the redirects to Keycloak and back. A background fetch cannot: the identity provider's pages are not meant to be read by script, and a cross-origin redirect fails.
  • Sign out is a form post, for the same reason.
  • isAdmin() only decides what to show. Hiding a button is convenience. The server refuses the call anyway (step 17).
  • The dev server forwards /api to the API (proxy.conf.json already does), so the browser sees one origin, localhost:4200, and the cookie is first-party. The callback address in the realm file is on that origin.

Observed in Chromium on http://localhost. The __Host-todo cookie with Secure is accepted over plain HTTP on localhost, because browsers treat it as a secure context. On any other host name the cookie would be dropped over HTTP, which is the point of the prefix. Signing out ends at Keycloak's own page asking to confirm, because the cookie does not hold an ID token to prove who is leaving; storing it (SaveTokens) would make the logout seamless at the cost of a bigger cookie.

The sign-in, message by message

Behind a proxy or a gateway

The callback address is built from the request's scheme and host. Behind the dev server's proxy the host header is kept, so it is right. Behind a gateway or load balancer, forward the original host and scheme (X-Forwarded-Host, X-Forwarded-Proto) and call UseForwardedHeaders, or the callback address will be the internal one and Keycloak will refuse it. In the cluster the issuer address also has to be one that works from inside a pod and from the browser, and two API pods must share the key that protects the cookie (ASP.NET Core data protection).

Practice

What you just learned

  • A browser app can run the code flow itself, use a token-mediating backend, or let a BFF hold the tokens. RFC 10017 puts the BFF first.
  • The BFF is the OAuth client: it keeps the tokens and gives the browser an HttpOnly, Secure, SameSite=Strict, __Host- cookie.
  • Cookie requests that change data need a custom header, so another site cannot forge them. Sign-in and sign-out are navigations, not fetch calls.
  • The UI code only decides what to show. The server enforces. Behind a gateway, forward the host and scheme.

Add "Log in with Google" to the app

Advanced

Goal: let people sign in with Google without changing a line of application code.

Why this step

Step 15 did the Google flow by hand. In a real app you rarely let every service talk to Google: you add Google to the identity provider, and the apps keep trusting one issuer. It builds on steps 14, 15 and 19. It needs a Google account and the OAuth client you made in step 15.

What is it? Identity brokering

What it is
An identity provider that lets people sign in with another identity provider (Google, a company directory, GitHub) and then issues its own tokens to your apps.
The problem it solves
Each app would otherwise implement Google, then Microsoft, then the customer's SSO. With a broker, apps implement one thing, and adding a provider is configuration.
Everyday comparison
A currency exchange desk: you hand in foreign money and receive local notes that every shop accepts.
What it is not
Not the same as "just use Google in the app". The app would then hold Google's tokens, Google's claims and Google's idea of roles. Here the app sees Keycloak's token and Keycloak's roles.
Where you meet it
Keycloak identity providers, Entra External ID, Auth0 connections.

Add Google to the realm

  1. In the Keycloak admin console choose the todo realm, Identity providers, Add provider, Google.
  2. Copy the Redirect URI it shows. For this realm it is http://localhost:8180/realms/todo/broker/google/endpoint.
  3. In the Google Auth Platform console (step 15), open your web client and add that address to its Authorized redirect URIs.
  4. Back in Keycloak, paste the client ID and secret of step 15, and save.

The same provider as it is stored in the realm, if you prefer to keep it in the file:

The Keycloak login page then shows a Google button under the password form. When Keycloak sends the person to Google, the authorize request goes to https://accounts.google.com/o/oauth2/v2/auth with redirect_uri set to the address above and scope=openid profile email; that is the request you built by hand in step 15, made by Keycloak.

Decisions that are yours

  • What role does a new Google user get? A person who signs in with Google for the first time becomes a Keycloak user with no role you gave them. Decide it: give todo-user as a default role, or leave them without and let an admin approve. Granting by email domain is a policy, and it must use the verified email, never a name.
  • Trust Email. Off by default, and for a reason: if on, Keycloak treats the email address from Google as verified. Turn it on only for a provider whose email you trust.
  • Account linking by email. The default first login flow can link a Google sign-in to an existing local user with the same email. Done carelessly this is an account takeover: if the other provider does not verify email addresses, anyone can claim any address. Keycloak 26.8.1 fixed a wrong-account linking flaw in the brokering code, which is a good reason to stay current.
  • What to key on. The stable identity is the issuer plus sub (step 15). Keycloak does this internally with a "federated identity" link; your app uses Keycloak's sub.

Not machine-tested. The tests import the provider into a real Keycloak and check the login page offers Google and sends the browser to Google with the redirect address above. They cannot sign in to Google: that needs your account. Tick this step by hand when it works for you.

Practice

What you just learned

  • A broker lets people sign in with Google while your apps keep trusting one issuer with one set of roles.
  • Adding Google is configuration: a redirect URI at Google, a client ID and secret in Keycloak.
  • Decide what a new user may do, do not trust unverified email, and be careful with automatic account linking.

Calls between services

Advanced

Goal: give a service its own identity, and call the API with it.

Why this step

A report generator, a nightly job and a sync tool have no person behind them. They need an identity of their own and the least access that does the job. It builds on steps 13, 19 and 21.

A small client

A console app that asks Keycloak for a token with the client credentials grant, keeps it until shortly before it expires, and reads the statistics endpoint three times. The secret comes from an environment variable.

Line by line: the token cache
TokenCache.GetAsync
Returns the cached token unless it is missing or within 30 seconds of expiring. The three API calls cause one token request, which the program prints.
grant_type=client_credentials
The client acts as itself (step 13). The response has an access token and expires_in, and no refresh token: when it runs out, ask again.
REPORTER_SECRET
Never in the source and never on the command line. In the cluster it is a Kubernetes Secret (Part 4); locally it is a variable or user-secrets.
/api/admin/stats
The one endpoint this role may call. The same token on /api/todos gets 403.

Output, from a real run:

Stronger than a shared secret

  • A key instead of a secret. Keycloak can verify a signed assertion from the client (private_key_jwt, RFC 7523) so that no shared secret exists. RFC 9700 prefers asymmetric client authentication over a shared secret.
  • Mutual TLS. The service presents a certificate (step 08). A certificate-bound token (RFC 8705) is useless without the matching key.
  • In the cluster, the pod's own token (step 18) can be the credential, so no long-lived secret is stored anywhere.
  • Least privilege. One client per service, one role per job. A report service that can also delete todos is a breach waiting for a bug.

Practice

What you just learned

  • A service is a client with its own identity: client credentials, its own role, its own secret or key.
  • Cache the token until shortly before it expires, and never ask for a token per call.
  • Keep the secret out of the source and the command line, prefer a key or mutual TLS where you can, and give each service the least role.
