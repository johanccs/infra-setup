06

Caches and artifacts

Goal: packages restored from a cache instead of downloaded, and a build output kept as an artifact that a later job can download.

Why this step

Every job starts on an empty machine, so each run downloads every package again, and the files a job makes disappear when it ends. A cache removes the repeated download. An artifact keeps what you built. They look alike and do different jobs.

CacheArtifact
ForThings you can rebuild, to save time: packages, build intermediatesResults you want to keep or pass on: build output, test reports
Found byA key. An exact match is a hit; restore-keys are prefixes tried nextA name, unique within the run
If it is missingThe job still works, only slower. A new cache is saved at the end if the job succeededThe job that needs it fails
LifetimeRemoved after 7 days without use. 10 GB per repository by defaultKept for the retention you set
Visible toRuns on the same branch, or on the default branchDownloadable from the run page and with gh run download
  • A cache key should change only when the inputs change: hashFiles('**/*.csproj'). A key that includes github.sha never matches an earlier run.
  • actions/setup-dotnet has cache: true, but it needs a packages.lock.json and fails without one. The Todo API has none, so use actions/cache with the project files. actions/setup-node has cache: npm, which uses the package-lock.json.
  • Do not store secrets in a cache: anyone who can open a pull request against the repository can read caches of the base branch.
  • Artifact names must be unique in a run and artifacts cannot be changed once created. In a matrix, put the matrix values in the name.
  • working-directory does not apply to uses: steps, so an action's path starts from the repository root.

Sources. Dependency caching, actions/upload-artifact, actions/cache

What you just learned

  • A cache key must repeat when the inputs repeat. hashFiles does that.
  • Artifacts are the way to hand files to a later job, and each name can be used once.
  • Paths in with: are from the repository root.
07

Secrets, variables and least privilege

Goal: a workflow where secrets cannot leak through a script, the automatic token has only the access the job needs, and untrusted text is never run as code.

Why this step

A pipeline holds your keys and can write to your repository. It runs code that came from other people's pull requests and from third-party actions. The habits here are the difference between a pipeline and an open door.

  • Secrets (secrets.NAME) are encrypted, and masked in logs. Variables (vars.NAME) are plain text, for settings such as a user name. Both can be set for a repository, an environment, or an organization. gh secret set and gh variable set are in the command drills.
  • Anyone with write access can read every repository secret through a workflow. Secrets are not a defence against your own collaborators, so keep the value's power small.
  • Masking is not guaranteed once a secret is transformed (Base64, URL-encoding, a JSON blob). Do not store structured data as a secret, and register any derived sensitive value with ::add-mask::.
  • The GITHUB_TOKEN is created for each run. Its permissions come from permissions: once you list any scope, every scope you do not list becomes none. A job-level permissions replaces the workflow-level one for that job. read-all, write-all and {} (none) are the shorthands. GitHub's advice is to default the token to read-only for repository contents and raise it per job.
  • Script injection. ${{ }} is replaced before the shell runs, so text written by other people (a pull request title, a branch name, a commit message, an issue body) pasted into run: becomes code. Pass it through env and read the shell variable.
  • Fork pull requests get a read-only token and no secrets. That is why pull_request is safe for untrusted code.

Sources. Secure use reference, Use GITHUB_TOKEN for authentication

What you just learned

  • Put secrets and untrusted text in env, never in the script text.
  • Name the permissions you need and nothing else. Raise them on the one job that needs it.
  • secrets are for sensitive values, vars for settings.
08

Build and push the image

Goal: the Docker workflow of the Todo project, with pull requests that build without pushing, tags that are derived for you, and layers cached between runs.

Why this step

In the first tutorial you wrote docker build and docker push by hand in a script. The actions published by Docker do the same work, with caching, multiple tags and the right labels, and they make "build on pull requests, publish on merges" a two-line condition.

  • docker/login-action logs in to the registry. Without registry it uses Docker Hub. Store the token as a secret, the user name as a variable.
  • docker/setup-buildx-action prepares the builder that supports caching and multiple platforms.
  • docker/metadata-action computes tags and labels from the event: type=sha gives sha-a1b2c3d (add prefix= for the bare 7 characters), type=ref,event=tag gives the tag name, type=raw,value=… gives a fixed name. Its outputs are tags and labels.
  • docker/build-push-action builds, and pushes when push: true. cache-from: type=gha and cache-to: type=gha,mode=max keep layers in the GitHub Actions cache.
  • Docker Hub limits. GitHub-hosted runners are exempt from Docker Hub's pull rate limit when pulling public images. Pulling private images from Docker Hub is subject to it, and self-hosted runners always are.
  • Never publish a moving tag like latest as the thing you deploy: you cannot tell what is running or roll back. Deploy by commit tag, and later by digest.

Sources. docker/build-push-action, docker/metadata-action, Publishing Docker images

What you just learned

  • Build on every pull request, push only on trusted events: one condition used twice.
  • Let metadata-action compute tags and labels, and the Docker cache keep the layers.
  • Tag with the commit, not latest.
09

Environments, approvals and concurrency

Goal: a path from build to staging to production where production waits for approval, deploys never overlap, and a running production deploy is never cancelled.

Why this step

Continuous delivery is not "deploy everything instantly". It is a pipeline where each stage has the checks it deserves. GitHub environments hold those rules, and concurrency keeps two deploys from fighting.

Environments

An environment is named in the job with environment: production. Its rules are set in the repository under Settings → Environments, not in the YAML:

  • Required reviewers: up to six people or teams; one of them must approve. You can forbid the person who started the deployment from approving it.
  • Wait timer: delay a job by 1 to 43,200 minutes (30 days).
  • Deployment branches and tags: which refs may deploy to it.
  • Environment secrets and variables: available only to jobs that name the environment, and for an environment with reviewers only after approval.

Check your plan. On GitHub Free, Pro and Team, required reviewers and wait timers on environments are available for public repositories only. Private repositories need a higher plan for them. Environment secrets for private repositories also need a paid plan. The YAML in this step is valid either way, but the gate only holds if your plan supports it.

Concurrency

  • A concurrency group allows one running job or run at a time. A new one waits as pending, and by default a newer pending run replaces an older pending one.
  • cancel-in-progress: true also cancels the one that is running. It is right for pull request checks and wrong for a deployment.
  • Group names are case-insensitive and can use the github, inputs and vars contexts (at job level also needs, strategy and matrix).
  • Set timeout-minutes on every job. The default is 360 minutes (6 hours), the longest a GitHub-hosted job can run.

Sources. Deployments and environments, Workflow syntax: concurrency

What you just learned

  • An environment is a name in the YAML and a set of rules in the settings. The job pauses until the rules are met.
  • Cancel superseded checks, never a running deploy.
  • A timeout is part of every job.
10

Keyless access to the cloud

Goal: a deploy job that reaches AWS with a short-lived identity token, with no access key stored in GitHub.

Why this step

A cloud access key kept as a secret never expires, can be copied by anyone who can run a workflow, and is the thing that leaks. OpenID Connect replaces it: GitHub vouches for the job, and the cloud decides whether to trust that statement.

The subject claim

The trust policy should accept only the subjects you expect. By default the subject is built from the job:

The jobSubject, repositories created before 15 July 2026
uses an environmentrepo:OWNER/REPO:environment:NAME
runs for a pull request, no environmentrepo:OWNER/REPO:pull_request
on a branch, no environmentrepo:OWNER/REPO:ref:refs/heads/BRANCH
on a tag, no environmentrepo:OWNER/REPO:ref:refs/tags/TAG

Newer repositories use a different form. For repositories created after 15 July 2026, and for repositories renamed or transferred after that date, the default subject includes the numeric owner and repository ids: repo:OWNER@OWNER_ID/REPO@REPO_ID:environment:NAME. A trust policy written in the old form is refused for such a repository. Older repositories keep the old form unless you opt in. Use GitHub's actions-oidc-debugger action to print the claims a run would send before you write the policy.

Always put at least one condition on sub in the trust policy. Without one, any repository could ask for your role. Using an environment in the job, with deployment branch rules on that environment, makes the subject depend on a protected name.

Sources. OpenID Connect reference, OIDC in Amazon Web Services, aws-actions/configure-aws-credentials

What you just learned

  • id-token: write lets a job request an identity token. The cloud's trust policy decides whether to accept it.
  • The subject names the environment, branch, tag or pull request, and in newer repositories the numeric ids.
  • Give id-token: write only to the job that deploys.
