Goal: one build workflow that every service calls, and one composite action that packages a few steps, with typed inputs, secrets and outputs.

Why this step

Teams copy a pipeline into every repository, and then fix a bug in one of twelve copies. Two tools remove the copies, and they are not the same thing, so knowing which to use is part of the skill.

Supply-chain security: pin, scan, sign

Goal: pinned actions, code and dependency scanning on every change, and an image that is signed and carries proof of how it was built.

Why this step

Your pipeline runs other people's code with your secrets, and it ships what it builds to production. Attackers know. Three layers cover most of the risk: control what runs in the pipeline, look for problems before they merge, and prove what you shipped.

Control what runs

  • Pin to a full commit SHA. A tag can be moved or deleted if the action's repository is compromised. A SHA cannot. Verify the SHA belongs to the action's own repository, not a fork, and keep a # v… comment so Dependabot can update it.
  • Actions with immutable releases publish exact tags (such as dependency-review-action@v5.0.0) that cannot be moved, with no moving v5 tag. An exact version is as strong as it gets without a SHA.
  • GitHub is previewing workflow dependency lockfiles (gh actions-lock), which pin every action including the ones your actions use. It was in preview on GitHub Enterprise Cloud when this page was written.
  • Untrusted checkouts. pull_request_target and workflow_run run with secrets and a writable token. Never build or run code from a pull request's head in them (a "pwn request"). actions/checkout refuses a fork's head ref in pull_request_target unless you set allow-unsafe-pr-checkout: true. GitHub also adds a default policy that blocks pull_request_target in public repositories, enforced from 2 November 2026 for repositories that were on the default policy.
  • persist-credentials: false on checkout keeps the token out of the repository's git config for a build that never pushes.

Look for problems

CodeQL scans source code for vulnerabilities and uploads the findings to the Security tab. Dependency review compares the dependencies of a pull request with the base and fails when it introduces a vulnerable package. Code scanning is free for public repositories. Dependency review works on public repositories, and on private ones with GitHub Advanced Security.

Prove what you shipped

Sign the image by digest (a tag can move, a digest cannot) with cosign, keyless, so the signature is tied to this workflow's identity and nothing is stored. Create a build provenance attestation with actions/attest: signed facts about which repository, workflow and commit built a digest. Check it later with gh attestation verify. In part 4 of the Todo series a Kyverno policy refuses an unsigned image from entering the cluster. This is the pipeline half of that.

Plans. Artifact attestations are available for public repositories on every plan. For private repositories on Free, Pro and Team they need GitHub Enterprise Cloud. Cosign signing works on any plan.

Sources. Secure use reference, Securely using pull_request_target, Artifact attestations

What you just learned

  • Pin by SHA (or exact immutable tag), and let Dependabot update the pin.
  • Never run a pull request's code in a privileged trigger.
  • Scan on every pull request, sign by digest, and attest what you built.

Governance: keep the pipeline honest

Goal: dependencies that update themselves, one stable required check that works with a merge queue, and the right people reviewing the pipeline files.

Why this step

A good pipeline file means little if anyone can change it unreviewed, if it quietly falls out of date, or if the merge rules depend on job names that change. The last layer is a handful of files and settings around the workflow.

  • Dependabot opens pull requests for outdated dependencies, including the actions in your workflows, NuGet and npm packages, Docker base images, Helm charts and Terraform. Updates wait a default 3 days after a release (a cooldown), and you can lengthen that. Security updates are never delayed.
  • Rulesets (Settings → Rules) can require status checks, pull request reviews and review from code owners before merging, and a merge queue. These are settings, not YAML, so you cannot test them here.
  • A required check is a name. If you require api and ui by name, renaming or adding a job breaks the rule, and a skipped job reports success. Require one gate job that always runs and fails if anything failed.
  • Merge queue. A queued pull request is built together with the latest main and the changes ahead of it. It starts workflows with the merge_group event, so every required workflow must listen for it, or the check never reports and the pull request never merges.
  • CODEOWNERS asks the right team to review files they own. The last matching line wins. Owners must have write access. It is only a requirement if the ruleset says "require review from code owners".
