The capstone: the enterprise pipeline

Goal: write one pipeline for the Todo project that a security review would pass: 20 requirements, from an empty editor.

Why this step

This is the whole job in one file: continuous integration on pull requests and the merge queue, a signed and attested image for each push and release tag, a staged deployment with approval, no stored cloud keys, and every action pinned. If you can write this without looking, you can write the pipeline of a real team.

Read it and fix it

Goal: given a broken pipeline and what the team saw, find the cause and fix it, from a one-word typo to a pipeline with seven separate faults.

Why this step

Most of your life with pipelines is reading ones you did not write, at the moment something has gone wrong. That is a different skill from writing. Each scenario starts with the symptom: a message, a log line, a person's complaint. You read the file, form a theory, and fix it. The right-hand list shows only how many problems remain, until you fix each one.

A method for reading a pipeline

  1. Does it start? Triggers and filters. Branch or tag? Which files? Is it on the default branch (for schedule and workflow_dispatch)? Use the preview.
  2. What may it do? permissions at the top and on each job. Anything broader than the job needs is a finding.
  3. In what order? needs, if and the status functions. Which jobs run, which are skipped, and why?
  4. Where does text go? Every ${{ }} inside run: is the value written by someone outside the team? Is a secret pasted into a script?
  5. What does it depend on? Every uses: a branch, a tag, or a SHA? An old major version?
  6. What can run away? timeout-minutes, concurrency, caches that never hit, artifacts that collide.
  7. What changes production? Environments, approval, concurrency on deploys, image tags.

The scenarios are in order of difficulty. Each is a real mistake that people make.

What you just learned

  • Start from the symptom, then read in a fixed order: start, permissions, order, text, dependencies, limits, production.
  • A skipped job is quiet, a missing permission is loud, and an injected script is invisible until someone uses it.

Where to go next

You can write and read a pipeline. These widen what you can run it on and how you run it at scale:

  • Wire it to the cluster. Part 1 of the Todo series commits the new image tag to values.yaml and lets Argo CD deploy it. Replace that script with the image job from the capstone, and let the deploy jobs update the chart instead of calling kubectl.
  • Your own runners. Self-hosted runners and the Actions Runner Controller on Kubernetes give you your own hardware and network access, and need more care: they are not isolated between runs, so never use them for untrusted pull requests.
  • Larger and slim runners. GitHub-hosted larger runners (Team and Enterprise plans) have more CPU and static IP addresses. ubuntu-slim is a single-CPU, lower-cost runner for light jobs, with a 15-minute job limit.
  • Share across an organisation. Workflow templates in the organisation's .github repository, and reusable workflows called by tag, give every team the same pipeline.
  • Lock the dependencies. When workflow dependency lockfiles reach your plan, gh actions-lock pins every action, transitive ones included.
  • More clouds. The OIDC pattern is the same for Azure, Google Cloud, HashiCorp Vault and others: only the trust configuration and the login action change.
  • Custom protection rules. Environments can ask an outside system (an observability or change-management tool) to approve a deployment, through GitHub Apps.
  • Terraform in the pipeline. Part 6 builds the layers. A pipeline job can run terraform plan on every pull request and apply after approval, with OIDC to the cloud.
