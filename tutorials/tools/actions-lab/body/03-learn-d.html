Delivery patterns: several workflows, three environments, real apps

Goal: know how a team's pipeline is split into files, how settings and passwords reach a job, how one build travels from dev to uat to prod, and what is different about deploying a .NET API and a single-page app.

Why this step

So far every lab was one file with one purpose. A real repository has several workflow files that share work, and the same build must run in three places with three sets of settings. Nothing here is new syntax. It is how the pieces you know are arranged, and where the settings come from. You read this step, then write all of it yourself in the next one.

1. One file per purpose

A workflow file answers two questions: when does it run, and what is it allowed to do. When two things have different answers, they belong in different files.

FileStarts onDoesMay use
pr.ymlpull_requestBuilds and tests. Deploys nothingNo secrets, no environment, a read-only token
release.ymlpush to mainBuilds once, then dev, uat, prodEnvironments, their secrets, cloud login
build.ymlworkflow_callThe build itself, written once and called by the two aboveWhatever the caller allows
deploy.ymlworkflow_callDeploys to the one environment it is toldThat environment's variables and secrets
  • A pull request workflow that cannot deploy. If pr.yml names no secret and no environment, no change to it by a contributor can reach production. A pull request from a fork gets no secrets and a read-only token in any case, so a build that needs neither works for everyone.
  • The build is written once. The pull request check and the release call the same reusable build.yml, so what you tested is what you ship.
  • A called workflow is part of the caller's run. Its artifacts can be downloaded by the caller's later jobs, and its outputs are read with needs.<job>.outputs.
  • A job that calls a workflow has no runs-on, no steps and no environment. It has uses, with, secrets and needs.

The other way to chain: workflow_run. It starts a workflow when another one is requested or completes. Use it only when the second workflow needs secrets that the first must not see, for example to comment on a pull request from a fork. It runs the file from the default branch, with secrets, and chains at most three levels deep. For "build, then deploy", a reusable workflow is simpler and shows as one run.

2. How a value gets into a job

Kind of valueWhere you keep itHow the workflow reads itShown in logs
The same everywhere, safe to read (Release)In the file: env: on the workflow, a job or a step$NAME in a script, env.NAME in an expressionYes
Differs per environment, not secret (a URL, a namespace)A variable: Settings → Secrets and variables → Actions${{ vars.NAME }}Yes
Grants access (a password, a token)A secret, in the same place${{ secrets.NAME }}Masked as ***
Worked out during the run (a version, an image tag)Nowhere: a step writes itecho "NAME=value" >> "$GITHUB_ENV" for later steps, >> "$GITHUB_OUTPUT" for other steps and jobsYes
  • The most specific wins. For variables and secrets: environment over repository over organization. For env:: step over job over workflow.
  • Environment values need the environment. A job sees an environment's variables and secrets only when it has environment: that-name, and its secrets only after any required reviewer has approved.
  • A wrong name is silent. A secret or variable that does not exist gives an empty text and no error. This is the most common reason for "it works in dev and not in uat".
  • Keep a secret narrow. Put it in the env of the one step that needs it. At job or workflow level it is handed to every step, including actions written by other people. Never write ${{ secrets.X }} inside a script.
  • $GITHUB_ENV starts at the next step. The step that writes a value cannot read it yet.
  • Not in if. secrets cannot be read in an if:. Put it in env and test the variable.
  • A reusable workflow gets no secrets by itself. The caller passes them, one by one or all with secrets: inherit.

3. Dev, uat, prod: build once, deploy three times

The rule is short: the thing that reaches production is the same thing that was tested. So the image or the publish folder is built in one job, and three deploy jobs take it to three places. What differs between the places is not in the YAML. It is in the three environments in the repository's settings.

EnvironmentVariable K8S_NAMESPACESecret DB_PASSWORDProtection
devtodo-devthe dev passwordNone: every merge deploys
uattodo-uatthe uat passwordA tester approves
prodtodo-prodthe prod passwordA reviewer approves, and only main may deploy
  • List build in every stage's needs. A job can read the outputs of the jobs in its own needs list only. Through dev alone, needs.build.outputs.image_tag is empty.
  • One deployment per environment at a time: concurrency with the environment in the group name and cancel-in-progress: false.
  • The job's name is a label. Where it deploys is decided by the value of environment. Copying a stage and forgetting that one word is the classic mistake (scenario 12 in step 18).

4. A .NET API: overwriting appsettings

ASP.NET Core reads its settings from several places, one after the other, and a later place wins for any setting it also has:

OrderSourceWhat the pipeline does with it
1appsettings.jsonNothing. It is in the repository, with the defaults
2appsettings.<Environment>.jsonWrites it at deploy time, for settings that are not secret
3Environment variablesSets them where the app runs, for secrets
4Command-line argumentsRarely used
  • <Environment> is the value of ASPNETCORE_ENVIRONMENT where the app runs. When it is not set, the app uses Production.
  • The capital letters must match on Linux. With ASPNETCORE_ENVIRONMENT=uat, the file appsettings.Uat.json is skipped, and a missing settings file is not an error.
  • In a variable name, __ is the : between levels. The setting ConnectionStrings:Todos is overridden by the variable ConnectionStrings__Todos. One underscore does nothing.
  • An override needs the same shape. To replace Api:BaseUrl, the file must contain {"Api": {"BaseUrl": …}}. Anything else is a new setting that nobody reads.
  • Write JSON with jq, never with echo or sed. jq -n --arg quotes every value correctly. It is already on GitHub's runners.

These are not claims from memory. This is a real .NET 10 app on Linux, with Api:BaseUrl and ConnectionStrings:Todos in appsettings.json and an appsettings.Uat.json beside it, started six ways:

5. An Angular app, or any single-page app

The output of ng build is a folder of static files. Deploying it means copying that folder to something that serves files: a bucket behind a CDN, GitHub Pages, or nginx in a container. Three things need care, and they are the same for React and Vue.

ProblemWhyWhat the pipeline does
Settings are compiled inAngular's environment.ts and --configuration are applied while building. A build made for dev points at dev for everBuilds once. At deploy time it writes a small config.json next to index.html, and the app fetches it when it starts
Browsers keep filesA production build puts a hash in the name of each script and stylesheet (main-5T3KQ2AB.js), so those never change. index.html keeps its name and names the current scriptsUploads *.js and *.css with a one-year cache, and everything else with no-cache
A release is not instantFor a moment the server has a mix of old and new files, and open tabs still hold the old index.htmlUploads the hashed files first and index.html last, and leaves the old hashed files in place
  • Everything in config.json is public. A browser app cannot keep a secret: anything it can read, its users can read. Passwords and keys stay on the API.
  • The filters are read left to right and the last match wins. --exclude "*" --include "*.js" means nothing, except scripts. With --delete, files that a filter excludes are left alone in the bucket, which is how the old scripts survive.
  • no-cache does not mean "do not store". It means "ask the server whether it changed before using your copy". That is one tiny request, and a new release is seen at once.
  • A cached index.html cannot be fixed from the server. If it ever went out with a one-year cache, the browsers that have it will not ask again (scenario 14 in step 18).
  • Routes need a fallback. For /todos/42 the server has no file, so it must answer with index.html and let the app's router take over. On CloudFront that is a custom error response, on nginx try_files $uri $uri/ /index.html;.
  • A sub-path needs a base href. If the app is served from /todo/ and not from /, build with ng build --base-href /todo/.

The same app on GitHub Pages needs no cloud account, which makes it a good way to practise. Pages takes one artifact and publishes it. Choose GitHub Actions as the source under Settings → Pages first.

What you just learned

  • One workflow file per trigger and purpose. The pull request file builds and cannot deploy. The build is one reusable file.
  • Fixed values in env, per-environment settings in vars, anything that grants access in secrets, and a secret only in the step that needs it.
  • Build once, deploy three times. The environments hold the differences, and the YAML stays the same.
  • .NET: a later source wins, __ is the separator, and the environment name must match the file name exactly.
  • A single-page app: settings from a file fetched at start-up, long cache only for hashed files, hashed files first and index.html last.
