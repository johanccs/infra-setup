What you'll be able to do

Goal: by the end you can write an enterprise CI/CD pipeline for GitHub Actions from an empty file, and read someone else's pipeline, find what is wrong with it and fix it, without looking up a single command.

How this lab works

Reading about pipelines does not teach you to write them. So most of this page is an editor. You are told what to build, you type it, and the page checks it as you type. A line with a mistake turns red with the line number and a plain explanation. A requirement turns green when you meet it. The answer stays out of sight until you ask for it.

Each lesson lab can start two ways, and you choose: Guided gives you the lesson's starting file and you add the new part, Empty gives you a blank file and you type every line. You do not need to know the keywords first. Under the editor, the page lists the keys that fit on the line your cursor is on, each with what it means, and Ctrl+Space types the first one. When you are stuck, Next line shows only the next line your file needs, and Show solution opens the finished file next to yours. Neither changes what you typed, and you never have to start a lab over to see the answer.

The checking is done by three things working together: actionlint, the most widely used linter for GitHub Actions workflows (an open-source project, not made by GitHub; version 1.7.12, compiled to WebAssembly so it runs inside this page, and nothing you type leaves your browser); requirement checks written for each exercise (the right trigger, the right permission, the right order); and a run preview that shows which jobs would start for a push, a pull request, a tag or a merge queue, and why.

Every example is about the project you build in the other tutorials: a .NET API in src/api, an Angular UI in src/ui, a Docker Hub image, a Helm chart and a cluster. Every action named here is at the version its own repository publishes today, read from GitHub when this page was built.

What the checker cannot do. It cannot run your workflow, reach GitHub or AWS, or know your repository's settings. To run an exercise on GitHub itself, follow step 20. It checks structure, names, types, expressions and the logic of your conditions. GitHub also validates a file when you push it. Things that live in the repository's settings (rulesets, environment protection rules, secrets) cannot be tested here, and each step says where they are. The actionlint build in the browser leaves out the optional shellcheck and pyflakes checks of your scripts.

Words you will meet

Workflow
One YAML file in .github/workflows/. It says when to run and what to run. A repository can have many.
Event
What starts a workflow: a push, a pull request, a tag, a schedule, a button, or another workflow.
Job
A group of steps that run on one machine. Jobs run in parallel unless one needs another.
Step
One command (run) or one action (uses), run in order inside a job.
Runner
The machine that runs a job. GitHub-hosted runners are fresh virtual machines; self-hosted runners are your own.
Action
A packaged, reusable step written by someone else (or you), such as actions/checkout.
Context
An object of facts about the run that you read in ${{ }}: github, runner, env, vars, secrets, needs, matrix, steps, inputs.
Expression
A small formula in ${{ }} or in an if: comparisons, &&, ||, and functions like contains().
Secret and variable
Stored values. Secrets are encrypted and masked; variables are plain settings.
Artifact and cache
An artifact keeps files from a run, for download or for a later job. A cache keeps files (such as packages) so the next run does not download them again.
Environment
A named place you deploy to, such as staging. It can require approval and holds its own secrets.
Matrix
One job definition run once for every combination of values you list.
Reusable workflow
A workflow that other workflows call as a job, with inputs, secrets and outputs.
OIDC
OpenID Connect: GitHub gives a job a short-lived signed token, and a cloud exchanges it for temporary credentials, so no long-lived key is stored.
