01

Your first workflow

Goal: a workflow that starts on the right events and prints two facts about the run, with no red lines in the editor.

Why this step

A workflow is a text file. If you can read the file, you can predict what GitHub will do. This step names the four parts you will see in every file, and the few YAML rules that cause most of the "why does nothing run" problems.

GitHub looks for workflows in the .github/workflows folder at the root of your repository, in files ending in .yml or .yaml. When something happens, GitHub reads the files as they are in the commit that caused the event. A workflow has these parts:

YAML rules that bite. Indent with spaces: a tab is an error. A value that contains : (a colon and a space) must be quoted or written as a block: run: echo "Title: x" is invalid, while run: | followed by an indented line is fine. A pattern that starts with *, [ or ! needs quotes. And a version such as 3.10 is the number 3.1 unless you quote it: '3.10'. The editor below reports each of these as you type.

Wherever you see ${{ … }}, GitHub evaluates the expression and pastes the result into the file before the shell sees it. github and runner are contexts: objects of facts about the run, such as github.repository and runner.os.

Sources. Workflows, Workflow syntax

What you just learned

  • A workflow has events, jobs, a runner, and steps. Steps are either run (a command) or uses (an action).
  • Branch filters sit under the event: push: branches: [main].
  • ${{ }} is replaced with a value before the command runs.
02

Build and test the .NET API

Goal: a job that checks out the code, installs .NET 10, restores, builds and tests the Todo API.

Why this step

Continuous integration is this job: on every change, build the code and run the tests on a clean machine, so "works on my PC" is not the only evidence. Nearly every pipeline starts with these three moves.

The runner is empty at the start. actions/checkout downloads your repository onto it. actions/setup-dotnet puts the SDK you ask for on the path. GitHub-hosted runners come with some SDKs installed, but naming the version makes it part of your file: a build today and a build next year use the same SDK.

An action is written owner/repo@version. The version after the @ is a tag, and each action's own repository decides which tags exist. The versions used on this page were read from each repository: checkout@v7, setup-dotnet@v6. The editor warns you if you use an older major version, or a version that does not exist.

  • uses runs an action. Its inputs go in with:.
  • run runs a shell command. It uses bash on Linux runners.
  • defaults.run.working-directory sets the folder for every run step in a job. It does not apply to uses steps.
  • --no-restore and --no-build let each dotnet command reuse the work of the one before.

Sources. Building and testing .NET, actions/setup-dotnet

What you just learned

  • The standard CI job: checkout, setup, then restore, build and test.
  • Actions are versioned. Use the current major version, and read the action's repository for its inputs.
  • The red gutter and the Problems panel are the same rules a linter would apply on your own PC.
03

Choose when it runs

Goal: triggers that start the pipeline for the right branches, tags and files, by hand, and on a schedule, and the filter patterns to match them.

Why this step

A trigger that is too wide wastes minutes and hides the runs that matter. One that is too narrow leaves a change unchecked. Most "my workflow did not run" questions are a filter question, and filters have rules worth knowing exactly.

Events and their filters

  • push has branches, tags, branches-ignore, tags-ignore, paths and paths-ignore. If you list only tags (or only branches), the workflow does not run for the other kind of ref. If you list neither, it runs for both.
  • pull_request filters branches on the target branch, the one you merge into. Its default activity types are opened, synchronize and reopened.
  • workflow_dispatch adds a "Run workflow" button, with typed inputs (string, number, boolean, choice, environment). The file must be on the default branch for the button to show.
  • schedule takes POSIX cron in UTC, runs on the latest commit of the default branch, and the shortest interval is 5 minutes. Runs are delayed when GitHub is busy, which includes the start of each hour. In a public repository, scheduled workflows are disabled after 60 days without repository activity.

You cannot use branches with branches-ignore, tags with tags-ignore, or paths with paths-ignore for the same event. To include and exclude together, use the include list with ! entries.

Path patterns must match the whole path, from the repository root. Because *, [ and ! are special in YAML, a pattern that starts with one of them must be quoted. Try the drills first. You write the patterns, and the table shows every case at once.

Filters and required checks. If a workflow is skipped because of a path filter, a branch filter or a [skip ci] commit message, its checks stay pending. A pull request that requires those checks cannot merge. Do not put path filters on a workflow that a ruleset requires (step 13 shows the pattern that avoids this).

Now write the whole on: block. Use the preview under the editor: it takes the event you pick and tells you whether the workflow would start, and why.

What you just learned

  • Branch and tag filters and path filters are separate, and both must pass when both are present.
  • pull_request filters on the target branch. ** crosses folders, * does not.
  • Skipped by a filter means pending, not passed, which matters for required checks.
04

Jobs, conditions and expressions

Goal: jobs in the right order, a condition that decides whether one runs, and data passed from one job to the next. You can write the condition and the expression yourself.

Why this step

A pipeline is a graph of jobs. needs draws the edges, if decides which jobs take part, and outputs carry data along the edges. Conditions are small programs, and they fail silently: a wrong one skips a job without a warning.

  • needs makes a job wait. If a needed job fails or is skipped, the job is skipped too, unless its if contains a status function such as always().
  • A skipped job reports success. It does not stop a pull request from merging, even if it is a required check.
  • Job outputs are how data crosses jobs: a step writes name=value to the file $GITHUB_OUTPUT, the job lists it under outputs, and another job reads needs.<job>.outputs.<name>. A job can read only the jobs it lists in its own needs.
  • Status functions: success() is applied by default. failure(), cancelled(), always(). GitHub recommends !cancelled() over always(), because always() also runs when you cancel the run.

Expressions

Inside ${{ }} (or directly in an if) you can use literals, the operators ( ) [ ] . ! < <= > >= == != && ||, and a few functions. Rules worth knowing:

  • Strings use single quotes; double quotes are an error. Comparing strings ignores case, so 'Main' == 'main' is true.
  • Comparing different types converts them to numbers. null is 0, true is 1, an empty string is 0, and text that is not a number is NaN, which is never equal to anything.
  • && and || return one of their values, so a || 'default' works as a default.
  • In an if, false, 0, '' and null are false, and everything else is true. That is why if: "${{ x }} == 'y'" is always true: the text around the braces makes it a non-empty string.
  • contains(), startsWith(), endsWith() ignore case. format(), join(), toJSON(), fromJSON(), hashFiles() and case() are the others, and .* picks a field from every item of a list.

Where can you use which context? It depends on the key. The if of a job can read only github, needs, vars and inputs: no secrets, no env, no matrix. The if of a step can also read env, steps, job, runner, matrix and strategy, but still not secrets. The checker reports a context used in the wrong place.

What you just learned

  • needs orders jobs, outputs pass data, and if decides who takes part.
  • An if is an expression: case-insensitive strings, single quotes, && and || that return values.
  • Never mix text and ${{ }} in an if. Use github.ref for the full ref and github.ref_name for the short one.
05

One job, many combinations

Goal: a matrix that runs the tests on several systems and SDKs from one job definition, minus the combinations you do not need.

Why this step

Software has to work on more than one thing: a second operating system, the SDK you support next to the one you build with. A matrix turns that into one job definition and a few lists, instead of copying jobs.

  • Every key under matrix is a variable with a list. The job runs once for every combination: os: [a, b] and dotnet: [x, y] make four jobs.
  • exclude removes the combinations that match every key you list.
  • include adds values to the combinations it fits, or adds a new combination if it fits none without changing an original value.
  • A run can have at most 256 matrix jobs.
  • fail-fast defaults to true: one failure cancels the jobs still running or waiting. Set it false to see every failure. max-parallel limits how many run at once. continue-on-error on the job lets one matrix job fail without failing the run.
  • The matrix can come from data: matrix: ${{ fromJSON(needs.plan.outputs.matrix) }}.

Sources. Running variations of jobs, Actions limits

What you just learned

  • Matrix variables multiply: two lists of two are four jobs. exclude subtracts.
  • matrix.<name> reads the current job's values.
  • Think about fail-fast: it is on by default.
