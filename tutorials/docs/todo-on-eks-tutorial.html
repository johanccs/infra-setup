    00

    What you'll build

    A todo list. The Angular UI is served by nginx, which forwards every /api/… call to the .NET API inside the cluster. The API keeps the todos in a PostgreSQL database and reports its version and pod name, so you can see each deployment happen in the browser.

    How the work flows

    1. You build container images and push them to ECR (Amazon's container registry).
    2. The Helm chart in Git says which image tags should run.
    3. Argo CD runs inside the cluster, watches the Git repo, and makes the cluster match it. Changing a tag in Git is how you deploy; reverting the commit is how you roll back.

    The big picture: what problem each piece solves

    Every tool in this tutorial exists because of a specific pain. Learn the pain and the tool makes sense.

    Platform engineering is the job of putting these pieces together so other developers get them ready-made. They push code and the rest just works. In this tutorial you play both roles: the developer and the platform team.

    Who this is for

    Developers who can write a .NET API and have used Git, but haven't run containers in the cloud. You don't need Kubernetes experience. Each step says why it exists and ends with what you learned. You'll use your own AWS account.

    Words you'll meet

    Image
    A packaged, read-only snapshot of your app plus everything it needs to run (runtime, libraries). Built from a Dockerfile.
    Container
    A running instance of an image. Like an object created from a class.
    Registry
    A store for images. ECR (Elastic Container Registry) is AWS's.
    Kubernetes (K8s)
    A system that runs containers across many machines, restarts them when they fail and spreads traffic between them.
    Cluster
    One Kubernetes installation: a control plane (the "brain" that stores what should run) plus nodes (the machines, here EC2 virtual machines, that actually run containers). EKS is AWS's managed Kubernetes: AWS runs the control plane for you.
    Pod
    The smallest thing Kubernetes runs: one or more containers that share a network address. Pods are disposable; Kubernetes replaces them freely.
    Deployment
    Tells Kubernetes "keep N copies of this pod running, using this image". Changing the image triggers a rolling update.
    Service
    A stable name and address in front of a changing set of pods. The UI reaches the API through a Service called todo-api.
    Gateway
    The front door of the cluster: a listener (here HTTP on port 80) that a controller turns into a running reverse proxy. HTTPRoute objects say where each path goes. On EKS the controller also asks AWS for a load balancer in front of it.
    StatefulSet
    Like a Deployment, but for programs that keep data, such as a database. Its pod keeps a stable name and its own disk.
    Volume claim
    A request for a disk that outlives the pod using it. On EKS the disk is an Amazon EBS volume.
    Namespace
    A folder inside the cluster that keeps one app's resources apart from another's.
    Probe
    A health check Kubernetes calls on your container. Readiness: "can it take traffic yet?" Liveness: "is it stuck and needs a restart?"
    Helm chart
    A folder of Kubernetes YAML templates with placeholders, plus a values.yaml that fills them in. Think of it as a NuGet package for a deployment.
    GitOps
    Keeping the desired state of the cluster in Git, and letting a tool make the cluster match it. You deploy by merging a pull request.
    Argo CD
    The GitOps tool. It runs inside the cluster, watches your repo, and applies changes. It pulls from Git; nothing pushes into the cluster.

    This costs money. An EKS cluster with two small nodes, a NAT gateway and a load balancer runs at roughly $0.30 an hour (about $7 a day) in us-east-1. These are approximate list prices. Plan to do steps 7–13 in one sitting, and always finish with step 13 (clean up). Steps 1–6 cost nothing or a few cents. The database adds a small EBS disk (about 10 cents a month for 1 GiB), which step 13 also removes.

    Two things that raise the bill: a cluster running a Kubernetes version past its standard-support window is charged $0.60 an hour for the control plane instead of $0.10, so use the default version eksctl picks and don't pin an old one. And a brand-new AWS account on the Free plan can't use every service; if eksctl is refused, upgrade the account to the Paid plan (your credits stay valid).

    Install the tools

    Goal: every command in the "Check" list prints a version, and Docker Desktop is running.

    Why this step

    Each tool talks to a different layer. Knowing which tool talks to what is half of debugging later:

    • dotnet and node build your code, the same as always.
    • docker packages the built code into images and runs them locally.
    • aws talks to AWS itself: accounts, ECR, load balancers, billing.
    • eksctl creates and deletes whole EKS clusters (the infrastructure).
    • kubectl talks to Kubernetes inside a cluster: list pods, read logs, apply YAML. It's the tool you'll use most.
    • helm installs packaged apps (charts) into Kubernetes. Under the hood it sends YAML through the same API as kubectl.
    • git holds the source of truth that Argo CD deploys from.

    You work on your laptop with your usual tools. The servers are not on it: the Kubernetes cluster runs in AWS, and the PostgreSQL you develop against runs as a container in Docker Desktop (a PostgreSQL pod takes over in the cluster). Nothing server-side is installed on your laptop.

    02

    Build the .NET API

    Goal: curl http://localhost:5080/api/todos returns [].

    Why this step

    You need something to deploy, and it should behave like a well-behaved cloud app. Platforms expect a few things from the apps they run, and this API does all of them:

    • Settings come from environment variables (APP_VERSION), not from files baked into the build. The platform injects different values per environment.
    • A health endpoint (/healthz) so the platform can tell a working copy from a stuck one.
    • Logs go to the console (ASP.NET's default). The platform collects console output; it never reads log files inside a container.
    • It keeps no data of its own. Todos live in PostgreSQL, so the API can be stopped, replaced or copied at any time without losing anything.

    These ideas come from the "Twelve-Factor App" guidelines (12factor.net), a widely used checklist for cloud-friendly apps.

    Look inside the database (optional)

    The database is a normal PostgreSQL server, so the tools you already use work with it.     Line by line: how the API uses the database
    Host=localhost;Database=todo;…
    The connection string: which server, which database, and who to log in as. Think of it as the ConnectionStrings entry you know from appsettings.json.
    NpgsqlDataSource
    Npgsql's connection pool. It opens a few connections once and lends them out, because opening one for every request is slow.
    $1 in the SQL
    A parameter. The value is sent separately from the SQL text, so a todo titled '; DROP TABLE todos; -- is just text. Never build SQL by joining strings.
    CREATE TABLE IF NOT EXISTS
    Makes the table the first time, and does nothing afterwards. Real teams use migrations for this; one table doesn't need them.
    ConnectAsync loop
    In a cluster the API and the database start at the same moment, and the database is usually slower. So the API keeps trying every 2 seconds instead of crashing.
    /healthz and /readyz
    Two questions Kubernetes asks. Liveness (/healthz): "is the process alive?" It deliberately ignores the database, or a database outage would make Kubernetes restart healthy API pods for nothing. Readiness (/readyz): "can it take traffic?" It says no until the database answers.

    What you just learned

    • A platform-friendly app reads its settings from environment variables and offers a health endpoint.
    • State belongs in a database, not in the app. That is what lets Kubernetes replace or multiply API pods freely.
    • Liveness asks "is it running?" and readiness asks "can it serve?". Keep them separate.
    • /api/info is your window into deployments: it will show a new version each time you release.

    04

    Dockerize both apps

    Goal: docker compose up --build serves the whole app at http://localhost:8080.

    Why this step

    Kubernetes doesn't run .NET or Angular code directly. It only runs containers, so every app has to become an image first. An image is a frozen filesystem: your compiled app plus the exact runtime and OS libraries it needs. That gives you three things:

    • Build once, run anywhere: the image you test is byte-for-byte the image production runs. No "but the server has a different .NET patch".
    • Isolation: each container has its own filesystem and network, so apps can't break each other.
    • Speed: containers start in seconds, which is what lets Kubernetes replace and scale them freely.

    Docker Compose is a small local "orchestrator": it starts several containers and gives them a shared network. It's a good rehearsal for what Kubernetes will do at scale.

    How to write a Dockerfile: build one up yourself

    A Dockerfile is a recipe: a list of instructions Docker runs top to bottom to produce an image. Instead of copying the finished file, write it in three rounds and build after each one, so you see why every line is there.

    Before you start: create api/.dockerignore with the two lines bin/ and obj/ (it's explained below). Otherwise COPY . . drags your Windows build output into the Linux build, which can break it.

    Build it. Read the command as: "build an image, call it todo-api with tag round1, using the Dockerfile in the ./api folder":

    Line by line: the docker build command
    docker build
    Reads a Dockerfile and runs its instructions to make an image.
    -t todo-api:round1
    "Tag": the image's name (todo-api) and version label (round1). Without -t you'd only get an anonymous ID.
    ./api
    The build context: the folder Docker may copy files from. COPY . . means "copy from the context into the image". Docker looks for a file called Dockerfile in this folder unless you pass -f.

    Run it. -p 5080:8080 maps port 5080 on your PC to port 8080 inside the container, because .NET apps in containers listen on 8080 by default. The container has no database to talk to yet, so only /api/info works here; the database arrives with Docker Compose below:

    It works, but the image is huge (around 900 MB) because it contains the whole SDK, which production doesn't need. It also rebuilds slowly: change one line of C# and dotnet publish re-downloads every NuGet package. Press Ctrl+C to stop it.

    Round 2: use the build cache. Docker saves the result of each instruction as a layer. When you rebuild, it reuses every layer up to the first instruction whose inputs changed. So put things that rarely change (the package list) before things that change often (your code):

    Build it twice: once, then change a string in Program.cs and build again. The second time, the output says CACHED next to the restore step.

    Round 3: multi-stage, small and safe. Use the SDK image only to compile, then copy the output into a second, tiny image that just runs it. Only the last stage becomes your image. This is the final version, shown next.

    API image (final)

    A multi-stage build: the SDK image compiles, and the small chiseled runtime image runs it. Chiseled images have no shell or package manager and run as a non-root user.

    Line by line: the API Dockerfile
    FROM … sdk:10.0 AS build
    Stage 1 starts from Microsoft's image that has the full .NET SDK, and names the stage build so later lines can refer to it.
    WORKDIR /src
    Creates the folder /src inside the image and makes it the current directory, like cd.
    COPY *.csproj then RUN dotnet restore
    Copies only the project file and restores NuGet packages before copying your code. Docker caches each line as a layer. If only your C# changes, this slow restore layer is reused and rebuilds take seconds.
    COPY . .
    Copies the rest of your source in (minus what .dockerignore excludes).
    RUN dotnet publish … -o /app
    Compiles a Release build into /app.
    FROM … aspnet:10.0-noble-chiseled
    Stage 2 starts again from a tiny image with only the ASP.NET runtime: no SDK, no shell, no package manager. Everything from stage 1 is thrown away except what you copy next.
    COPY --from=build /app .
    Takes just the compiled output from stage 1.
    EXPOSE 8080
    Documents which port the app listens on. It doesn't open anything by itself.
    ENTRYPOINT
    The command that runs when a container starts from this image.

    .dockerignore works like .gitignore: it keeps your local bin/ and obj/ out of the build context. Copying them in would slow the build and could mix Windows build output into a Linux image.

    -e APP_VERSION=hello sets an environment variable in the container. curl http://localhost:5080/api/info now reports version hello, which is exactly how Kubernetes will pass settings in later. Exact image sizes vary by version.

    Tidy up the experiments: docker rmi todo-api:round1 todo-api:round2

    UI image

    Node builds the Angular app; an unprivileged nginx image serves the files and forwards /api/ to a host called todo-api. That name works in both Docker Compose and Kubernetes because both give the API that name.

    Line by line: the UI Dockerfile
    FROM node:24-alpine AS build
    Stage 1: Node.js on Alpine, a very small Linux. It's needed only to run the Angular compiler.
    COPY package*.json then RUN npm ci
    The same caching trick as the API: install packages before copying code. npm ci installs exactly what package-lock.json says, so builds are repeatable.
    RUN npx ng build --configuration production
    Compiles Angular into plain static files (HTML, JS, CSS) in dist/todo-ui/browser.
    FROM nginxinc/nginx-unprivileged
    Stage 2: nginx, a fast web server, in a version that runs as a normal user and listens on 8080. The final image has no Node.js at all, because static files don't need it.
    COPY nginx.conf …
    Replaces nginx's default site config with yours, which serves the files and forwards /api/.
    COPY --from=build … /usr/share/nginx/html
    Puts the compiled Angular files where nginx serves them from.

    Running the UI on its own fails: nginx stops with host not found in upstream "todo-api", because there's no todo-api container on its network. That's the problem Compose solves next.

    Run both together

    Line by line: docker-compose.yml
    services:
    Each entry becomes a container. The entry's name (todo-api) is also its hostname on the shared network Compose creates.
    build: ./api
    Build the image from that folder's Dockerfile, the same as docker build ./api.
    environment:
    Environment variables for that container, like -e on docker run.

    What you just learned

    • Multi-stage builds: the big SDK and Node images are only used to compile. The final images contain just the runtime and your output, so they're smaller and have fewer things an attacker could use.
    • Non-root containers: both final images run as an ordinary user, which many clusters require.
    • Service names as hostnames: containers find each other by name (todo-api), not IP address. Kubernetes works the same way.

    Put it in Git

    Goal: the project is on GitHub. Argo CD will read the Helm chart from this repo later.

    Why this step

    In GitOps, Git is the control panel for production. Argo CD can only deploy what's in a repo it can read, and every deployment becomes a commit with an author, a timestamp, a review and a way back (revert). You've used Git for code. Here you start using it for operations.

    Create an empty public repo called infra-setup on GitHub. A public repo means Argo CD needs no credentials. A private repo works too, but you then have to add a repository credential in Argo CD.

    This first push goes straight to main because the repo is empty. After this, make every change on a branch and merge it with a pull request (step 12). With GitOps, a merge to main is a deployment.

    06

    Push images to Amazon ECR

    Goal: both images, tagged 1.0.0, are in ECR.

    Why this step

    Your images only exist on your laptop. The cluster's machines are in an AWS data centre and need to download (pull) them from somewhere they can reach. A registry is that somewhere. ECR is a good choice here because it sits in the same AWS account as the cluster: the nodes are allowed to pull through AWS permissions, with no passwords to manage. Docker Hub would work too, but you'd then handle credentials and rate limits.

    The docker login line swaps your AWS identity for a temporary Docker password that's valid for 12 hours. That's why you'll rerun it after a break.

    Set these variables in every new terminal you use from here on:

    Create one repository per image. Immutable tags stop anyone overwriting 1.0.0 with different contents.

    Build for linux/amd64, the architecture of the cluster's nodes. This matters if you're on an Apple Silicon or other ARM machine.

    Line by line: building for a registry and pushing
    $REGISTRY/todo-api:1.0.0
    An image's full name has three parts: registry host (123456789012.dkr.ecr.us-east-1.amazonaws.com), repository (todo-api) and tag (1.0.0). Locally you used short names like todo-api:final. Including the registry tells docker push where to send the image.
    --platform linux/amd64
    Builds for Intel/AMD 64-bit Linux, which is what t3 nodes run. On an ARM laptop, a missing flag gives an image that crashes on the nodes with exec format error.
    docker push
    Uploads the image's layers. Layers the registry already has are skipped, so pushing 1.1.0 later only uploads what changed.
    docker tag (alternative)
    If you already built todo-api:final, you can give it the registry name instead of rebuilding: docker tag todo-api:final $REGISTRY/todo-api:1.0.0. A tag is just a label pointing at an image; one image can have many.

    Check they arrived: aws ecr list-images --repository-name todo-api --region $AWS_REGION. You can also see them in the console under Amazon ECR → Repositories.

    What you just learned

    • An image's full name is registry/repository:tag. The cluster will pull exactly that name.
    • Version tags, never latest: a fixed tag like 1.0.0 tells you exactly what's running and makes rollback a matter of switching back to the old tag.
    07

    Create the EKS cluster

    Goal: kubectl get nodes lists two Ready nodes.

    Why this step

    Compare this with deploying to a few IIS servers. Someone has to choose which server runs what, notice when an app crashes and restart it, replace a dead server, spread traffic, and roll out a new version one server at a time so users see no downtime. Kubernetes does all of that automatically. You give it a description of the desired state, and its controllers loop forever, comparing reality with your description and fixing any difference. That loop is called reconciliation, and it's the single most important idea in Kubernetes.

    A cluster has two halves:

    • Control plane: the API server you talk to with kubectl, a database (etcd) holding the desired state, and the scheduler and controllers that act on it. On EKS, AWS runs this half for you; that's what the $0.10/hour pays for.
    • Nodes (worker machines): EC2 virtual machines in your account that actually run your containers. Each runs an agent called the kubelet that takes orders from the control plane.

    eksctl is used here because it builds all the AWS plumbing from one file. Platform teams usually define clusters in Terraform instead, so changes are reviewed like code.

    eksctl creates the VPC, IAM roles, the control plane, a managed node group and one add-on from a config file. It takes about 15–20 minutes. The cost clock starts now. The region must match the AWS_REGION you exported in step 6.

    Line by line: the cluster config
    metadata.name and region
    The cluster's name (you'll use it again to delete it) and the AWS region to build in. Everything else (ECR, load balancer) must be in the same region.
    iam.withOIDC: true
    Lets Kubernetes service accounts take on AWS permissions (IAM roles for service accounts). The disk driver below uses it to create EBS volumes, without putting AWS keys inside the cluster.
    managedNodeGroups
    A node group is a set of identical worker machines, and a managed one means AWS handles creating, patching and replacing the EC2 machines. Clusters often have several groups, e.g. one for general apps and one with GPUs.
    instanceType: t3.medium
    The EC2 size: 2 vCPUs and 4 GB of memory per node. Smaller types fit very few pods once Kubernetes' own system pods are running.
    desiredCapacity: 2
    Two machines, so you can see pods spread across them and survive one failing.
    addons: aws-ebs-csi-driver
    An add-on is software AWS installs and updates for you. This one lets Kubernetes create EBS disks when a pod asks for storage, which the database in step 8 does. Without it the database's disk request would wait forever. wellKnownPolicies gives it the AWS permissions it needs.

    eksctl also updates your ~/.kube/config, so kubectl now talks to the new cluster. (If kubectl ever points somewhere else, aws eks update-kubeconfig --name todo-demo --region $AWS_REGION brings this login back.)

    The nodes can pull from ECR in the same account without extra setup. eksctl gives the node role the AmazonEC2ContainerRegistryPullOnly policy, which lets nodes pull images but not push.

    Add the front door: NGINX Gateway Fabric

    Why this part

    A Service gives pods a stable name, but only inside the cluster. In production, traffic from the internet arrives at one entry point, usually a load balancer in front of a reverse proxy, which looks at the host name and path and sends each request to the right service. It is also where HTTPS certificates and limits are handled.

    In Kubernetes you describe that with objects, and a controller keeps a real proxy configured to match (the reconciliation loop again). There are two ways to describe it: the older Ingress API and the newer Gateway API. The well-known ingress-nginx project was retired in March 2026 and gets no more security fixes, so a new setup shouldn't use it. NGINX Gateway Fabric is the Gateway API controller from the NGINX team. The proxy it runs is nginx, the same program that serves your UI.

    Install it once per cluster, with three commands:

    kubectl kustomize "<url>" | kubectl apply -f -

    Write the Helm chart

    Goal: helm lint charts/todo ends with 1 chart(s) linted, 0 chart(s) failed. That means the chart has no errors. (A line starting with [INFO] is only a hint. Ignore it.)

    Why this step

    Kubernetes is configured with YAML files called manifests. Each one describes an object you want to exist: "a Deployment named todo-api running image X". You could write them by hand and run kubectl apply -f. Teams stop doing that quickly, for three reasons:

    • Repetition: dev, cert and prod need the same YAML with a few values changed (image tag, replica count, URLs). Copies drift apart.
    • Releases: you want to install, upgrade and roll back the app as one unit, not as a pile of files.
    • Sharing: a platform team wants to hand developers a ready-made, tested package.

    Helm solves all three. A chart is a folder of templates (YAML with {{ placeholders }}) plus values.yaml. Helm fills in the placeholders and sends the result to Kubernetes. It's the NuGet of Kubernetes: thousands of public charts exist (Argo CD itself ships as one), and you'll write your own.

    A Helm chart is a folder of Kubernetes YAML templates plus a values.yaml file holding the settings that change between releases, mainly the image tags.

    Line by line: the Deployment and Service
    apiVersion, kind
    Which type of object this is. Deployment lives in API group apps/v1; Service in core v1.
    metadata.name
    The object's name, unique per kind within a namespace.
    replicas
    How many identical pods to keep running. Set from values.yaml via {{ .Values.api.replicas }}.
    selector.matchLabels
    How the Deployment recognises "its" pods: any pod labelled app: todo-api. Must match the labels in template.
    template
    The blueprint for each pod. Change anything here (like the image tag) and the Deployment does a rolling update: start a new pod, wait until it's ready, stop an old one, repeat.
    containers[].image
    The full ECR image name, assembled from registry and tag in values.
    env
    Environment variables, the same as -e on docker run. | quote wraps the value in quotes so 1.0 stays a string. The database connection comes in the same way; $(DB_PASSWORD) is replaced by the variable defined just above it.
    secretKeyRef
    "Take this value from the Secret todo-db" instead of writing it in the Deployment. The password then lives in one object.
    readinessProbe
    Kubernetes calls /readyz, and only sends traffic once it answers 200, which here means once the database is reachable. This is what makes rolling updates have zero downtime.
    livenessProbe
    If /healthz (which ignores the database on purpose) keeps failing, Kubernetes restarts the container. initialDelaySeconds gives the app time to start first.
    resources.requests
    What the scheduler reserves on a node for this pod: 50m = 5% of one CPU core, 64Mi = 64 MiB of memory.
    resources.limits
    The ceiling. Going over the memory limit gets the container killed (OOMKilled); no CPU limit is set, so it can use spare CPU.
    ---
    Separates two YAML documents in one file.
    Service selector
    Sends traffic to every ready pod with label app: todo-api, wherever it runs. Pods come and go; the Service name stays.
    port / targetPort
    port is what callers use (todo-api:8080); targetPort is the container's port. In ui.yaml they differ: callers use 80, the container listens on 8080.
    type
    Default ClusterIP: reachable only inside the cluster. All the Services in this chart are like that. The only thing exposed to the internet is the Gateway's own Service, which the controller creates with type LoadBalancer: AWS then adds an internet-facing load balancer.

    The database

    Postgres needs three things the apps didn't: a password, a disk that survives restarts, and a pod with a stable identity. One more file covers all three:

    Line by line: the database
    kind: Secret
    A place for a password, kept apart from ordinary settings. Both Postgres and the API read it with secretKeyRef, so the password is written down once.
    clusterIP: None
    A headless Service. It has no virtual address of its own: the name todo-db resolves straight to the database pod. With only one database pod, that is all you need.
    kind: StatefulSet
    A Deployment for programs that keep data. Its pod has a fixed name (todo-db-0) and always gets the same disk back. A Deployment's pods are interchangeable and disposable; a database is neither.
    replicas: 1
    One database. A real production setup runs copies that replicate each other, which is a topic of its own (and a good reason to use a managed database).
    PGDATA
    A sub-folder of the disk. A new disk contains a lost+found folder at its top, and Postgres refuses to start in a folder that isn't empty.
    readinessProbe with exec
    Instead of calling a web address, Kubernetes runs a command inside the container. pg_isready exits successfully once Postgres accepts connections.
    volumeMounts
    Where the disk appears inside the container. Postgres writes its files there.
    volumeClaimTemplates
    "Give each pod its own disk of this size." Kubernetes creates a PersistentVolumeClaim (a request for a disk) and the cluster supplies the disk. on EKS the EBS disk driver from step 7 creates a real EBS volume.

    The password is in Git. That is fine for a practice database on your own PC, but never do it for real data: anyone who can read the repo can read the password, and a Kubernetes Secret is only base64-encoded, not encrypted. Real teams keep secrets out of Git with tools such as Sealed Secrets, External Secrets or SOPS, or use a managed database from their cloud. On AWS the natural home is Secrets Manager, read into the cluster by External Secrets (part 4 of the series builds exactly that), or a managed Amazon RDS database that keeps its own password there.

    The front door

    One last file tells the gateway what to do with traffic:

    Line by line: the Gateway and the route
    kind: Gateway
    Asks for a front door. When Kubernetes sees it, NGINX Gateway Fabric starts an nginx pod (named todo-nginx-…) in the same namespace and gives it a Service of type LoadBalancer, which makes AWS create the load balancer.
    gatewayClassName: nginx
    Which controller should handle this Gateway. nginx is the class the controller registered in step 7.
    listeners
    The ports and protocols the front door accepts. Port 80 is where the load balancer sends traffic. HTTPS would be a second listener with a certificate.
    kind: HTTPRoute and parentRefs
    A set of routing rules, attached to the Gateway by name. Separate objects let different teams manage their own routes behind one shared front door.
    PathPrefix /api
    Requests whose path starts with /api go straight to the todo-api Service on port 8080. This is the same split the UI's own nginx makes on your PC; in the cluster the gateway does it first.
    PathPrefix /
    Everything else goes to the todo-ui Service. The most specific prefix wins, so /api beats /.

    Put your registry into values.yaml, then check the chart:

    Your AWS account ID ends up in Git. It isn't a secret, but if your repo is public and you'd rather not share it, use a private repo.

    What you just learned

    • Each app needs a Deployment (what to run, how many copies) and a Service (a stable name to reach it).
    • A database needs a StatefulSet and a volume claim instead, so its data survives. A Gateway plus an HTTPRoute is the front door: one address, and rules for which path goes to which Service.
    • Labels and selectors tie them together: the Service sends traffic to any pod labelled app: todo-api.
    • Resource requests tell Kubernetes how much CPU and memory to reserve when placing a pod. Limits cap what it may use. 50m means 0.05 of a CPU core.
    • Templates stay the same between releases; only values.yaml changes. That's why a release becomes a one-line diff.

    Why this step

    Deploying once by hand shows you exactly what Argo CD will automate, and gives you something to compare against when things go wrong later. helm upgrade --install means "install if new, upgrade if it exists", so the same command is safe to run again and again.

    What happens behind the scenes when you run it
    1. Helm renders the templates with your values into plain YAML (exactly what helm template printed).
    2. It sends that YAML to the cluster's API server, which stores the objects as desired state.
    3. The Deployment controller sees "want 1 api pod, have 0" and creates a pod object.
    4. The scheduler picks a node with enough free CPU and memory for the pod's requests.
    5. That node's kubelet pulls the image from ECR and starts the container.
    6. The readiness probe passes, and the pod is added to the todo-api Service's list of endpoints.
    7. The Gateway makes the NGINX controller start an nginx pod and a LoadBalancer Service for it, and AWS creates a load balancer outside the cluster and points it at your nodes.

    Nobody runs these steps in order. Each component watches the API server and reacts. That's reconciliation in action.

    Install Argo CD

    Goal: you're logged in to the Argo CD web UI.

    Why this step

    In step 9 you deployed by pushing: your laptop, holding admin credentials for the cluster, sent changes in. That works for one person, but on a team it means:

    • Every person and every CI server needs powerful cluster credentials.
    • Nothing records who ran what. The cluster slowly drifts from what's in Git.
    • A hand-made "quick fix" in production is forgotten until it causes an outage.

    Argo CD flips it to pull. It runs inside the cluster, reads your Git repo, and keeps the cluster matching it: the same reconciliation idea as Kubernetes, applied to your whole app. Nobody outside needs cluster credentials, and every change is a reviewed commit.

    Argo CD is itself just an app in the cluster (installed in its own argocd namespace). Its main parts: the repo server fetches Git and renders your Helm chart, the application controller compares the result with the cluster and syncs differences, and the API server/UI is the web page you're about to open.

    Get the generated admin password, then open the UI through a port-forward. Keep that terminal open.

    Browse to https://localhost:8443, accept the self-signed certificate warning, and sign in as admin with that password.

    Line by line: the install commands
    kubectl apply -f <url>
    Sends Argo CD's official manifests (hundreds of objects) to the cluster. apply means "create or update to match this file".
    --server-side --force-conflicts
    Lets the API server do the merge. It's needed because some of Argo CD's object definitions are too large for the default, client-side mode.
    rollout status
    Waits until the Deployment's pods are ready.
    get secret … | base64 -d
    Kubernetes Secrets store values base64-encoded (an encoding, not encryption). This decodes the generated admin password.
    port-forward svc/argocd-server 8443:443
    Opens a private tunnel from your PC's port 8443 to the Argo CD service inside the cluster. Nothing is exposed to the internet; the tunnel lasts as long as the command runs.

    Hand the app to Argo CD

    Goal: the todo app shows Synced and Healthy in Argo CD, and the site works again.

    Why this step

    Argo CD is installed but doesn't know about your app yet. You tell it with one small file, and that file is the only thing you'll ever apply to the cluster by hand for this app. From here on, every change goes through Git.

    An Argo CD Application is a Kubernetes resource that says "make namespace X match folder Y of repo Z".

    • automated applies changes from Git by itself.
    • selfHeal undoes manual changes made with kubectl.
    • prune deletes resources that you remove from Git.
    • The finalizer makes deleting the Application also delete the app, including its load balancer.
    Line by line: the Argo CD Application
    kind: Application
    A custom resource: a new object type that Argo CD added to Kubernetes when you installed it. Kubernetes stores it; Argo CD acts on it.
    namespace: argocd
    Applications live where Argo CD lives, even though they deploy elsewhere.
    finalizers
    Makes Kubernetes wait for Argo CD to delete everything the app created before the Application itself disappears. Without it, deleting the Application would leave the app running.
    project: default
    Argo CD projects limit which repos and namespaces an app may use. default allows anything, which is fine for learning.
    source
    Where the desired state is: the repo, which branch (targetRevision), which folder (path) and which values file. Argo CD sees Chart.yaml and renders it with Helm.
    destination
    Where to deploy it: kubernetes.default.svc means "the cluster Argo CD itself runs in"; one Argo CD can also manage other clusters.
    automated
    Sync automatically when Git changes. Without it, Argo CD only shows "OutOfSync" and waits for you to click Sync.
    prune: true
    If you delete a file from Git, delete that object from the cluster too.
    selfHeal: true
    If someone changes the cluster by hand, put it back to match Git.
    CreateNamespace=true
    Create the todo namespace if it doesn't exist.

    Two statuses you'll see: Sync status answers "does the cluster match Git?" (Synced / OutOfSync). Health status answers "is it actually working?" (Healthy / Progressing / Degraded). An app can be Synced but Degraded, for example the right YAML pointing at an image that crashes.

    Ship a change, then roll it back

    Goal: the browser shows version 1.1.0, then 1.0.0 again after a git revert.

    Why this step

    Steps 1–11 were setup you do once. This step is the loop a team runs every day: change code, build, release, and roll back when something's wrong. You'll do it by hand first, so you know exactly what a pipeline automates.

    Release 1.1.0

    1. Create a branch: git switch -c release-1.1.0
    2. Make a visible change, e.g. in ui/src/app/app.html change <h1>Todo</h1> to <h1>Team todo</h1>.
    3. Build and push new images. Tags are immutable, so this needs a new tag:
    1. In charts/todo/values.yaml, change both tag: "1.0.0" lines to tag: "1.1.0".
    2. Commit, push the branch, open a pull request on GitHub and merge it:

    Argo CD checks Git about every 3 minutes. Click Refresh on the app in the UI to check straight away. Watch the rolling update, where new pods start before old ones stop:

    Reload the site: the heading changes and the version line says 1.1.0. Your todos are still there: the API pods were replaced, but the data lives in the database, which this release didn't touch.

    Roll back with git revert

    Rolling back is a Git operation. Revert the merge commit on a new branch and merge that. -m 1 tells Git to keep the main side of the merge. This assumes you merged with GitHub's default Create a merge commit. If you squashed, there is no merge commit: revert the single squashed commit and leave out -m 1.

    The site goes back to 1.0.0. The 1.1.0 images stay in ECR, so a roll-forward is another tag change. GitHub's Revert button on a merged pull request does the same thing in one click.

    What you just learned

    • The full release loop: build an image → push with a new tag → change the tag in Git → review → merge → Argo CD rolls it out.
    • Rollback is a revert, not a hotfix. Because the cluster follows Git, undoing the commit undoes the deployment, and the history shows both.
    • Stateless vs stateful: the API pods can be replaced at will because the data lives in the database, on its own disk.

    Where a CI/CD pipeline fits

    Everything you just typed is what a pipeline does for you. The work splits into two halves with different owners:

    1. PR merged to main
    2. CI: GitHub Actions / Jenkins
      1. Build + unit test
      2. Scan image
      3. Push to ECR with new tag
      4. Open PR: bump tag in values.yaml
    3. Review + merge
    4. CD: Argo CD
      1. Notice Git changed
      2. Render chart + sync
      3. Rolling update

    13

    Clean up

    Goal: nothing from this tutorial is still billing you.

    Why this step

    Some resources exist outside Kubernetes even though Kubernetes asked for them: the load balancer, and the disks attached to the nodes. If you delete the cluster first, nothing is left to clean those up, and they keep billing quietly. The cluster's network (VPC) can't be deleted while a load balancer still sits in it. So work from the inside out: app, then cluster, then registry.

    Order matters. Delete the app first so its load balancer is removed, and delete the database's disk claim yourself: Argo CD leaves a StatefulSet's disk alone on purpose, and an EBS volume left behind keeps billing after the cluster is gone. A leftover load balancer keeps costing money and can stop the cluster's VPC from being deleted.

    Also remove the development database and its volume if they are still around (docker rm -f todo-dev-db and docker compose down -v). Your AWS keys stay in ~/.aws on your laptop; delete the access key in the IAM console (IAM → Users → Security credentials) if you no longer need it.

    Finally, check the AWS console: no EKS clusters, load balancers, NAT gateways or unattached EBS volumes in your region. Look at Billing → Bills the next day to see what the tutorial cost.

    Want to practise again later? Everything except the cluster is in your Git repo. Re-running steps 6, 7, 10 and 11 brings the whole thing back in about 25 minutes. Practising tear-down and rebuild is a useful platform skill in itself.

    Where to go next

    • CI pipeline: make GitHub Actions (or Jenkins) build, test, scan and push the images and open the values.yaml pull request for you. Let it sign in to AWS with GitHub's OIDC integration (a short-lived identity, no stored AWS keys).
    • A managed database: swap the PostgreSQL StatefulSet for Amazon RDS, and keep the password out of Git with External Secrets or Sealed Secrets.
    • HTTPS and a better load balancer: add a second listener on port 443 to the Gateway with a certificate (cert-manager, or AWS Certificate Manager in front), and install the AWS Load Balancer Controller to get a Network Load Balancer instead of the Classic one.
    • Environments: add values-dev.yaml and values-cert.yaml plus one Argo CD Application per environment.
    • Observability: add OpenTelemetry to the API and view traces in Grafana.
