    00

    What you'll build

    Security on a platform works best as layers, each catching what the one before missed. Each layer here answers one "what could go wrong?". Follow one image from your commit to a running pod:

    What could go wrongThe layerWhat it does about it
    The image ships with a library that has a known, fixable vulnerability.Trivy (step 2)Fails the pipeline before the image is pushed.
    Someone runs an image that didn't come from your pipeline: built on a laptop, or swapped in the registry.cosign + Kyverno (steps 3–5)The pipeline signs each image; the cluster refuses images without that signature.
    A container runs as root or privileged, so one bug in the app becomes control of the node.Pod Security Admission (step 6)The namespace refuses pods that ask for more power than an app needs.
    Any pod in the cluster can call any other pod, so one break-in spreads everywhere.NetworkPolicy (step 7)Only listed callers reach the API and the database.
    Passwords and keys end up in Git, where they stay forever.External Secrets (step 8)The cluster fetches secrets from a store. Git holds only a reference.

    Each layer gets a drill. Most of them end the same way: the fault is caught, and the work is finding where it was caught, because a blocked deployment can look a lot like a broken one.

    Words you'll meet

    Digest
    A hash of an image's contents, like sha256:4f…. Unlike a tag, it can't be moved to a different image.
    Signature
    Proof, stored next to the image, that a specific identity produced that exact digest.
    Admission controller
    A program the Kubernetes API server asks "may this be created?" before it stores anything.
    Policy
    A rule an admission controller applies, written as YAML. It can allow, refuse or change objects.
    NetworkPolicy
    A firewall rule for pods: once a policy selects a pod, only the traffic a policy allows reaches it.
    Secret store
    A service that keeps passwords and keys outside your cluster and Git, such as AWS Secrets Manager.

    02

    Scan images before they ship

    Goal: the pipeline prints a vulnerability report for each image and fails on any critical issue that has a fix.

    Why this step

    Your image contains far more code than you wrote: an operating system layer, the .NET runtime, nginx, OpenSSL. New vulnerabilities in those are published every day. Trivy compares every package in an image against public vulnerability databases.

    The scan runs before the push, so a failing image never reaches the registry and can't be deployed by accident.

    This step and the next both change ci.yml, so here is the whole file with both changes. It is the file from part 1 with a scan step and a signing step added. Replace yours. The Trivy version, 0.75.0, was the newest when this was written:

    Line by line: the scan step
    trivy() { … }
    A small shell function so the long docker run is written once. "$@" passes on whatever arguments it's called with.
    -v /var/run/docker.sock…
    Lets Trivy, running in its own container, read the images the runner's Docker just built, without pushing them anywhere first.
    -v "$HOME/.cache/trivy…"
    Keeps the vulnerability database between the two calls, so it downloads once per run.
    --ignore-unfixed
    Skip vulnerabilities nobody has fixed yet. You can't act on them, and failing on them blocks every release until the base image's maintainers catch up.
    Two calls
    The first prints HIGH and CRITICAL for people to read, and never fails. The second only looks at CRITICAL and fails the step (--exit-code 1) if it finds any. Report broadly, block narrowly: a gate that blocks too much gets switched off.
    ::group::
    Folds the report into a collapsible section in the Actions log.

    Don't push yet. The signing part needs step 3's explanation first.

    New vulnerabilities appear in images you already shipped. A scan at build time says nothing about next month. Running Trivy on a schedule against the images on Docker Hub, or Trivy Operator inside the cluster, covers that. It's in "Where to go next". The official PostgreSQL image isn't built by your pipeline, so this scan doesn't see it.

    03

    Sign every image the pipeline builds

    Goal: cosign verify on your newest API image says the signature is valid and names your workflow.

    Why this step

    A tag like todo-api:a1b2c3d says nothing about where the image came from. Anyone with push rights to the registry could replace it. A signature proves this exact image (identified by its digest, a hash of its contents) was produced by your pipeline.

    Keyless signing with Sigstore means you don't manage a signing key at all. GitHub gives each workflow run a short-lived identity token. Sigstore's certificate service, Fulcio, swaps it for a certificate valid for ten minutes that says "this is the ci.yml workflow in your repo, on main". cosign signs with it and records the signature in Rekor, a public log anyone can check. There's no long-lived key to leak.

    Line by line: the signing steps in ci.yml
    id-token: write
    Allows the run to ask GitHub for its identity token. Without it, keyless signing fails.
    sigstore/cosign-installer@v4 with cosign-release
    Installs the cosign command on the runner, at the exact version in COSIGN_VERSION. Version 2.6.5 stores the signature as an extra tag in the same Docker Hub repository, which every registry supports. Newer cosign 3 versions default to a newer storage format that not every registry accepts.
    docker inspect … RepoDigests
    After a push, Docker knows the image's digest in the registry, like sha256:4f…. cut -d@ -f2 keeps only that part. You always sign the digest, never the tag: tags can move, digests can't.
    cosign sign --yes
    Signs and uploads the signature next to the image. --yes accepts that the signature is recorded in the public Rekor log, which includes your repo and workflow name.

    Push both changes. A change to ci.yml starts the pipeline:

    In the Actions log, open Report for todo-api and Report for todo-ui. You'll probably see a short table or "no vulnerabilities". Then Sign the images shows a Rekor entry for each.

    Check a signature yourself

    Run cosign from its container so you don't need to install it. Use the tag from the newest "Deploy …" commit, and put your Docker Hub user name (lowercase) and your GitHub user name (exactly as GitHub shows it) in the placeholders.

    Expected output starts with Verification for docker.io/… -- and lists the checks that passed, followed by JSON describing the signature. Now try an older tag, from before this commit. It fails with "no signatures found". That's the line the cluster will enforce.

    What you just learned

    • Sign digests, not tags.
    • Keyless signing ties an image to who built it (a specific workflow in a specific repo on a specific branch), not to a key someone has to guard.

    05

    Refuse images the pipeline didn't sign

    Goal: an unsigned image is refused at the door, and the todo app keeps running.

    Why this step

    This rule makes the cluster itself check every todo image's signature, so it no longer matters who has registry or kubectl access. Roll it out in two stages: Audit (record what would be refused) and then Enforce (refuse it). Going straight to Enforce on a real cluster is how teams take down their own production.

    Put your Docker Hub user name (lowercase) in the image pattern and your GitHub user name, exactly as GitHub shows it, in the subject.

    Line by line: the policy
    ClusterPolicy
    Applies in every namespace. A plain Policy would apply only in its own.
    webhookTimeoutSeconds: 30
    Checking a signature means calling the registry and Rekor over the internet, which can take a few seconds.
    background: false
    Only check new pods as they arrive, not existing ones on a timer. Signature checks need the network, so they're only done at admission.
    kinds: [Pod]
    Check pods. Kyverno also writes matching rules for Deployments and ReplicaSets automatically, so problems show up earlier.
    imageReferences
    Which images the rule covers: only yours. PostgreSQL, Prometheus, Loki and the rest aren't signed by your pipeline, so they must be left out.
    failureAction
    Audit lets the pod in and records a failure in a policy report. Enforce refuses the pod.
    mutateDigest: false
    By default Kyverno rewrites the image tag to its digest in the object it lets in. Argo CD would then see the Deployment differ from Git and change it back, and the two would fight forever. Switched off here; "Where to go next" covers deploying by digest from the start.
    verifyDigest: false
    Normally Kyverno also insists the image is referenced by digest. Your chart uses tags, so this is off as well.
    subject and issuer
    Who must have signed: your ci.yml on main, as certified by GitHub. A signature from a fork, another workflow or another branch doesn't count.

    Once kyverno and policies are Healthy, restart the API so it goes through the check, and read the report:

    The report's PASS column should count the new API pod. If it shows FAIL, the running image predates step 3, or the names in the policy don't match. kubectl -n todo get policyreport -o yaml shows the message for each result.

    Switch to Enforce

    When the reports show only passes for your current images, change failureAction: Audit to failureAction: Enforce, commit and push. Then test the door with an old, unsigned tag (any tag from before step 3, from your Git history):

    Expected: Error from server: admission webhook "…kyverno…" denied the request, followed by the policy name require-signed-todo-images, the rule name and a message saying no matching signatures were found.

    What you just learned

    • Admission control is the last gate before something runs. It applies to everyone, including people with kubectl access.
    • Roll out every new rule in Audit first. The policy report tells you what Enforce would break.

    Drill: a release that never arrives

    Break it, two ways

    First: in src/ui/Dockerfile, change the second FROM to the old image nginxinc/nginx-unprivileged:1.20-alpine. Push and watch the pipeline. Revert when you've seen it fail.

    Second: in the policy, change the subject's branch from refs/heads/main to refs/heads/release, as if someone had tightened the rule. Push it. Then make any small change in src/api/ (a comment will do) and push that to trigger a release.

    Diagnose

    • First break: at which step did the pipeline stop? Was anything pushed to Docker Hub? Did the cluster change?
    • Second break: the pipeline is green and Argo CD says Synced. Is the new version running? What does the version line on the site say?
    • Where is the evidence? Try kubectl -n todo get deploy,rs,pods, then kubectl -n todo describe rs on the newest ReplicaSet, and kubectl -n todo get events --sort-by=.lastTimestamp.
    • Why did the site stay up?
    Check your answers

    The old nginx image fails at Scan the images, with a table of CRITICAL vulnerabilities in packages such as curl and libcurl (the image is about five years old). Push never ran, so nothing reached Docker Hub or the cluster. The cheapest place to catch a problem is the earliest.

    With the wrong branch in the policy, the new pods are refused, so the old version keeps running. Argo CD shows Synced because the Deployment object matches Git, but Progressing and later Degraded, because its pods never appear. The new ReplicaSet wants one pod and has none, and its events read FailedCreate … admission webhook … denied the request. No pod exists, so kubectl get pods shows nothing new and kubectl logs has nothing to show.

    That's the hard part of admission failures: the evidence lives on the ReplicaSet and in events, not on a pod. Remember "Synced but not Healthy, and no new pod" as a pattern.

    06

    Take away powers the app doesn't need

    Goal: the todo namespace enforces the restricted Pod Security Standard, and the apps and the database run under it.

    Why this step

    By default a container can run as root, gain more privileges, and use Linux kernel features the app never touches. If an attacker gets in through a bug in your code, all of that is theirs. Kubernetes defines three Pod Security Standards: privileged (anything), baseline (blocks the obviously dangerous) and restricted (what a normal web app needs and nothing more). It enforces them per namespace through a label. No extra software is needed; it's built in.

    First ask the cluster what would break, without changing anything:

    You'll get warnings for the two Deployments and for the database's StatefulSet, listing what's missing: allowPrivilegeEscalation != false, unrestricted capabilities, runAsNonRoot != true and seccompProfile. The pod that NGINX Gateway Fabric creates for your Gateway isn't listed, because it already meets the standard. Your API and UI images already run as non-root users; the chart just doesn't say so.

    Add security settings to the templates. In charts/todo/templates/api.yaml, the pod spec gets a securityContext above containers, and the api container gets one of its own:

    Make exactly the same two additions in charts/todo/templates/ui.yaml for the ui container.

    The database needs a little more, because the official PostgreSQL image starts as root and only then switches to its own user. Under restricted it isn't allowed to start as root, so you tell Kubernetes to start it as that user from the beginning. In charts/todo/templates/db.yaml, in the StatefulSet:

    Line by line: the security settings
    runAsNonRoot: true
    Refuse to start if the image would run as root. The .NET chiseled image runs as user 1654, and nginx-unprivileged as user 101.
    runAsUser: 999 (database only)
    PostgreSQL's image doesn't set a non-root user by itself, so runAsNonRoot alone would refuse it. 999 is the postgres user in that image.
    fsGroup: 999 (database only)
    Files on the data disk are made group-writable for this group, so the non-root database user can write its data. Your data folder is already a subfolder (PGDATA), which PostgreSQL needs when the disk's top folder isn't its own.
    seccompProfile: RuntimeDefault
    Blocks rarely used kernel calls that exploits like to use. Apps almost never notice.
    allowPrivilegeEscalation: false
    The process can never gain more rights than it started with.
    capabilities.drop: [ALL]
    Linux splits root's powers into "capabilities" (change file owners, bind low ports, and so on). Your apps need none of them. That's why the API and UI listen on 8080, not 80.

    07

    Decide who may call what

    Goal: a test pod in another namespace can't reach the API, and the gateway, the load generator, Prometheus and the API's own database connection all still work.

    Why this step

    Kubernetes networking is flat: every pod can reach every other pod, in any namespace. If one pod is broken into, the attacker can call everything, the database included. A NetworkPolicy works like a firewall rule on pods: once any policy selects a pod, only traffic a policy allows reaches it.

    The policies themselves are just objects. It's the cluster's network plugin that enforces them. kind's built-in plugin enforces them from kind 0.24 on; check with kind version. On EKS you'd switch on network policy support in the VPC CNI.

    Think about who really calls whom in your app. The browser reaches the gateway, and the gateway sends /api to the API and everything else to the UI. Only the API talks to the database. Prometheus and the load generator call the API from their own namespaces.

    First prove the network is open. From a throwaway pod in the default namespace:

    It prints the API's version JSON. Any pod anywhere can do that. Now add the rules to the chart:

    Line by line: the policies
    podSelector: {}
    Empty means every pod in the namespace. With policyTypes: [Ingress] and no ingress rules, it allows nothing in. Policies add up, so the next four open specific holes.
    gateway-from-anywhere
    NGINX Gateway Fabric labels the pod it creates for your Gateway with gateway.networking.k8s.io/gateway-name. - {} is one rule with no from and no ports, which means "from anywhere, on any port". The gateway is where your browser's traffic arrives, so it has to be open. Everything behind it is not.
    podSelector inside from
    Pods in this namespace with that label. Here the gateway's pod is in todo too, because a Gateway's proxy runs in the Gateway's namespace.
    namespaceSelector
    Any pod in a namespace with that label. Every namespace gets kubernetes.io/metadata.name automatically.
    Two from blocks on the API
    Kept apart so the Prometheus rule can be removed on its own in the drill. Items in one from list are OR-ed together.
    db-from-api
    The database accepts connections only from API pods, only on PostgreSQL's port. Without this rule, the default-deny policy would cut the API off from its own database.

    After the sync, run the same probe again. This time it waits five seconds and gives up, printing nothing (exit code 28, a timeout). Check that http://localhost:8080 still works and the Todo API dashboard still fills.

    A policy that blocks gives a timeout, not an error. The packets are dropped silently, so a call to a blocked pod waits until it gives up. "Connection refused" would mean nothing is listening; a timeout means something is in the way. That difference is the first clue in the drills below.

    08

    Keep secrets out of Git

    Goal: the API receives a key from a secret store, /api/info shows its fingerprint, you've seen what happens when the key is rotated, and the database password has moved out of values.yaml into the store too.

    Why this step

    Everything else is in Git, but secrets can't be: anything committed stays in the history forever, and Kubernetes Secrets in a repo are only base64, which anyone can decode. (Look at db.password in values.yaml: part 1 warned that it is for practice only. You'll move it at the end of this step.) Real platforms keep secrets in a secret store such as AWS Secrets Manager, Azure Key Vault or HashiCorp Vault. Git holds only a reference to them.

    The External Secrets Operator (ESO) reads an ExternalSecret ("fetch the key todo-notify from the store") and creates a normal Kubernetes Secret from it, refreshing it on a timer. The app sees a normal Secret and needs no code for the store.

    You have no cloud account here, so a locked-down namespace called secret-store plays the part of the store. The ESO objects are exactly what you'd write for AWS Secrets Manager; only the provider block would differ.

    The platform side

    Add the operator as an Application. The chart version, 2.12.0, was the newest when this was written:

    The fake store: a namespace, plus permission for one service account in todo to read Secrets in it, and nothing else.

    Add the ESO chart to platform-check.yml the same way you added Kyverno's:

    The secret-store Application has no finalizer on purpose. If it's ever deleted, the store and its secrets stay. Losing secrets by deleting a Git file is a mistake you only make once.

    Push, wait for external-secrets and secret-store to be Healthy, then put the secret into the store by hand. This is the one thing in the whole series that is meant not to be in Git. At work, this is someone adding a value in Secrets Manager.

Every platform needs an answer to "what happens when this secret rotates?" before the first rotation, not during it.

    Drill: rotate in the wrong order

    Rotate again, but this time change only the store: run the second command with a new value and skip the ALTER USER. Then restart the API. Predict what kubectl -n todo logs deploy/todo-api says and whether the site still works.

    The API pods start but never become Ready, and the logs say password authentication failed for user "todo". Postgres still has the old password, and the API now sends the new one.     Repair it by running the ALTER USER with the value that is now in the store, then restart the API again. A real platform scripts this order, or avoids it with two database users that are rotated one at a time. A managed database such as Amazon RDS can rotate its own password and write it to Secrets Manager for you.

    What you just learned

    • Git holds where a secret lives, never its value.
    • Fetching a new secret value and the app using it are two different events. Design for rotation from the start.
    • A database password has two homes: the secret store, and the database itself. Rotate it in the database first, then in the store.
    • Removing a password from Git doesn't make it safe. If it was ever committed, change it.

    Clean up

    Note that after the next ./infra/bootstrap.sh, the hand-made secrets are gone. The API shows "notifyKey": "not set" until you run the notify kubectl -n secret-store create secret line again, and the database pod waits in CreateContainerConfigError until you create todo-db in the store too. On a new disk any password works. A real store lives outside the cluster and survives a rebuild. That's one more reason it belongs outside.

    The scan step fails on an image you didn't changeA new CRITICAL vulnerability was published for its base imageRebuild with the newest base image (the tags float to patched versions). If no fix exists yet, --ignore-unfixed already skips it
    Trivy fails downloading its databaseA temporary rate limit on the database mirror, or a very old Trivy versionRe-run the job; update TRIVY_VERSION
    cosign sign fails with "getting key from Fulcio" or an OIDC errorid-token: write is missingCheck the permissions block
    cosign verify says "none of the expected identities matched"The subject differs: case, branch or workflow file nameThe error prints the identity it found; copy it exactly
    Policy report shows FAIL for current imagesSame as above, inside the policyFix the subject; image pattern lowercase, subject exactly as GitHub shows it
    Kyverno rejects failureAction as unknownA Kyverno version older than 1.13Use a newer chart, or put validationFailureAction: Audit under spec instead
    New pods everywhere fail with a Kyverno webhook timeoutKyverno is down or slow, and its webhook fails closedkubectl -n kyverno get pods; the webhook only covers your images, so platform pods are unaffected
    The database pod crash-loops after step 6, with a permission error on its data folderThe data disk isn't writable for user 999, or fsGroup is missingkubectl -n todo logs todo-db-0 names the folder. Check runAsUser and fsGroup are both 999 in the StatefulSet's pod spec. If the volume was created earlier with other owners, delete it (kubectl -n todo delete pvc --all after scaling the app down) and let it be created again
    The probe in step 7 still gets an answer after the policies syncYour kind is older than 0.24 and ignores NetworkPolicyUpdate kind and rebuild the cluster
    The site shows nothing at all after step 7The gateway rule doesn't match the gateway pod's labelkubectl -n todo get pods --show-labels and look for gateway.networking.k8s.io/gateway-name=todo on the todo-nginx pod

    Where to go next

    • Part 5, Scale and Capacity, sizes the pods from measurements, load-tests the API and scales it on demand.
    • Deploy by digest. Have the pipeline write each image's digest into values.yaml as well as its tag. Then you can switch on verifyDigest, and what runs is provably what was scanned and signed.
    • Attach the scan to the image. cosign attest can attach Trivy's results or a software bill of materials (SBOM) to the image, and Kyverno can require them.
    • Keep scanning after release. Run Trivy on a schedule against what's deployed, or install Trivy Operator to scan in the cluster.
    • Limit outgoing traffic too. Add Egress policies. Remember the API must still reach DNS in kube-system.
    • Use a real store. On AWS, swap the kubernetes provider for aws (Secrets Manager) with an IAM role for the service account. Nothing in the ExternalSecret changes. Or skip the database pod: with Amazon RDS, AWS can create and rotate the database password in Secrets Manager itself (manage_master_user_password in Terraform), and the todo-db StatefulSet goes away.
    Written October 2026 against Trivy 0.75, cosign 2.6, Kyverno 1.19 (chart 3.9.1), External Secrets Operator 2.12 with the v1 API, NGINX Gateway Fabric 2.7 and kind 0.24 or later. Policy APIs evolve quickly; check each project's release notes when you upgrade.
