    Scale and Capacity

    How much CPU and memory does the todo API really need, how much traffic can one copy take, and what happens when there is more? Measure it, size it from the measurements, check what all the copies share, then let the cluster add copies on its own as load rises.

    00

    What you'll build

    Capacity questions come up on every platform: a team's pods won't schedule, the cloud bill doubled, the app falls over at 9am every Monday. They come down to three numbers per container and one decision about how many copies to run. Follow what happens when load rises and the platform answers it:

    The problemThe toolWhat it does about it
    The scheduler places pods by what they ask for, not what they use. Wrong asks waste nodes or crash pods.Requests and limits (steps 2–3)Sized from measured usage instead of guesses.
    The list endpoint returns every todo ever added, and the database has a limited number of connections. More copies of the API multiply both.A look at what the API leans on (step 4)Cap the list and cap each pod's connection pool, so copies don't overload the database.
    Nobody knows how much traffic one copy can take.k6 (step 5)A load test that ramps up users and reports where latency gives way.
    A CPU limit set too low makes an app slow without any error.Throttling metrics (step 6)Show when a container is held back by its limit.
    Traffic varies, and a fixed number of copies is either too few at peak or wasted at night.HPA and KEDA (steps 7–8)Add and remove copies automatically, on CPU or on request rate.

    Words you'll meet

    Request
    The amount of CPU or memory a container reserves. The scheduler uses it to choose a node. cpu: 50m is 50 millicores: 5% of one CPU.
    Limit
    The most a container may use. Over the memory limit it is killed; over the CPU limit it is slowed down.
    Throttling
    The kernel making a container wait because it used up its CPU limit for the current 100 millisecond period.
    Replica
    One running copy of a pod. A Deployment keeps the number of replicas you ask for.
    Load test
    Sending many simulated users at an app on purpose, to find where it slows down or fails.
    p95
    The 95th percentile: 95 out of 100 requests were faster than this. It shows what slow requests feel like without being thrown by one outlier.
    HPA
    HorizontalPodAutoscaler. Built into Kubernetes; changes a Deployment's replica count to keep a metric near a target.
    KEDA
    An add-on that lets the same mechanism scale on other signals, such as requests per second from Prometheus or the length of a queue.

    02

    See the node the way the scheduler does

    Goal: you can say how much CPU and memory on the node is already promised to pods, and what QoS class the API has.

    Why this step

    Each container can state two numbers per resource:

    • A request is a reservation. The scheduler only places a pod on a node with enough unreserved capacity. It never looks at actual usage.
    • A limit is a ceiling. Going over the memory limit gets the container killed. Going over the CPU limit gets it slowed down (throttled), never killed.

    Request too much and nodes sit idle but "full". Request too little and pods are crammed onto nodes that then run out of memory.

    Look at three parts. Allocatable is what pods may use in total (your Docker's CPUs and memory, minus a little for the system). Non-terminated Pods lists every pod's requests and limits. Allocated resources adds them up as a percentage of allocatable. The CPU requests figure is what decides whether the next pod fits.

    Then see each pod's QoS class:

    QoS classWhenWhen the node runs short of memory
    BestEffortNo requests or limits at allEvicted first
    BurstableSome requests or limits, but not all equalEvicted next, those furthest over their request first
    GuaranteedEvery container has requests equal to limits for CPU and memoryEvicted last

    Your API, UI and database are Burstable: they have requests and a memory limit, but no CPU limit.

    Check your answers

    The new pod stays Pending. kubectl -n todo describe pod on it ends with an event like 0/1 nodes are available: 1 Insufficient cpu. The old pods keep running, because the rolling update waits for the new one to be Ready, so the site stays up. Argo CD shows Progressing.

    Pending means "the scheduler can't find a place". The event always says why: CPU, memory, a node selector or taint that doesn't match, or a volume in another zone. In the cloud, a cluster autoscaler reacts to exactly this event by adding a node, which is why oversized requests turn directly into cost.

    03

    Size from measurements

    Goal: the API's, UI's and database's requests and limits are set from their own usage, and you can explain each number.

    Why this step

    The numbers in the chart were guesses from part 1. Prometheus has been recording what the containers actually use since part 2. Use the history: requests close to normal usage, memory limits with room for peaks.

    Run these in Prometheus (kubectl -n monitoring port-forward svc/prometheus-operated 9090). They need at least 30 minutes of history; a day of normal traffic is better. Each one returns a line for every container in the todo namespace: api, ui and postgres.

    CPU in normal use

    CPU cores used per container, as the 95th percentile over the last hour: busier than 95% of the hour. [1h:1m] is a subquery: work out the inner expression once a minute for the last hour, then take the percentile over those 60 points. The sum by (container) adds the pods of one Deployment together, so with two API pods you get the total. Divide by the number of pods to get a per-pod figure.

    Memory at its highest

    What's reserved now

    Turn them into numbers

    SettingRule of thumbWhy
    CPU requestAbout the p95 usage per pod, rounded up to a tidy numberReserves what the pod normally uses. Short bursts above it borrow idle CPU.
    CPU limitUsually noneA limit slows the app even when the node has CPU to spare. Step 6 shows this.
    Memory requestAbout the peak usageMemory can't be borrowed back once used, so reserve what you really need.
    Memory limitPeak plus 30–50%, and at least the requestRoom for unusual moments, while still stopping a leak before it hurts the node.

    A .NET app at rest typically uses tens of MiB and a few millicores; nginx uses even less. Expect your API's CPU request to drop and its memory request to rise. Update api.resources in values.yaml from your own numbers. The UI's and the database's numbers are written straight into ui.yaml and db.yaml, so change them there. PostgreSQL's memory climbs as it caches data, so give the database the most headroom. Push.

    .NET reads the memory limit. The runtime caps its own heap at 75% of the container's memory limit, as you saw in part 2's drill 3. A limit set too tight makes .NET collect garbage more often and throw OutOfMemoryException instead of being killed. That's another reason to size from measurements.

    What you just learned

    • Requests are for the scheduler and cost; limits are for protection. Each is set from a different measurement.
    • Right-sizing is a loop, not a one-off. Usage changes with every release, so repeat it now and then.
    04

    Check what the API leans on

    Goal: the list endpoint returns at most 100 todos, each API pod can open only as many database connections as you chose, and you know both numbers.

    Why this step

    Your API is already stateless: since part 1 the todos live in PostgreSQL, so two API pods show the same list and a restarted pod loses nothing. That's what makes scaling out possible at all.

    But all copies share one database, so adding copies multiplies whatever the API does to it. Two things to check before you load-test: how much data one request moves, and how many connections all the copies together can open.

    What you just learned

    • Stateless means any copy can serve any request. It doesn't mean copies are free: they all share one database.
    • Anything a request does in proportion to the size of a table is a scaling problem waiting for data. Find it before the load test does.
    • Budget connections: pods × pool size has to fit inside what the database accepts.
    05

    Find out how much it can take

    Goal: a k6 test ramps up to 100 virtual users and reports throughput and p95 latency, and you can see the run on the Todo API dashboard.

    Why this step

    The load generator from part 2 is one patient user. To learn where the app's limits are, you need many users at once, increasing in steps, while you watch latency. k6 is a load-testing tool where the test is a small JavaScript file. You'll run it as a Kubernetes Job, from inside the cluster, so your PC's network isn't the bottleneck.

    Line by line: the load test
    stages
    The number of virtual users (VUs) over time. Each VU runs the default function in a loop.
    sleep(0.5)
    Each user waits half a second between requests, so 100 users send up to about 190 requests a second, fewer if responses are slow.
    thresholds
    Pass/fail rules for the whole run. If one fails, k6 exits with an error and the Job shows Failed. You could run the same test in a pipeline as a gate.
    check
    Counts how many responses passed a condition, without stopping the test.
    Job
    A pod that runs to completion once. backoffLimit: 0 means don't retry a failed test; ttlSecondsAfterFinished deletes the Job and its logs after an hour, so read the summary before then.
    resources
    Even a test needs a request, or the scheduler wouldn't count it (step 2) when it decides what fits on the node.
    namespace: loadgen
    Part 4's NetworkPolicy already lets this namespace call the API.

    This file sits in its own folder, infra/platform/loadtest/, which no Argo CD Application watches, and it is applied by hand on purpose. A load test is something you run, not something that should always be running.

    While it runs (nine minutes), watch the Todo API dashboard, and in another terminal:

    At the end k6 prints a summary. Note three lines: http_reqs (requests per second), http_req_duration (look at p(95)) and http_req_failed, and whether the thresholds passed (✓) or failed (✗). On a typical PC two API copies handle this comfortably. Write the numbers down: they're your baseline, and every later step is compared with them.

    Write down one more number: how much CPU one API pod used at the peak. Graph this in Prometheus over the last 15 minutes and read its highest point:

    A value of 0.08 means 80 millicores (80m). You'll use this number in the next step and in step 7.

    To run the test again, delete the old Job first: kubectl -n loadgen delete job k6, then apply again.

    A load test on a laptop measures the laptop. k6, the API, PostgreSQL and Prometheus share the same CPUs, so absolute numbers mean little. Changes between runs are what count: same test, one change, compare.

    06

    Drill: a limit that slows everything

    Goal: you can prove CPU throttling from metrics, and explain why the CPU graph alone hides it.

    Break it

    Someone adds a CPU limit "to be safe". Take the peak CPU of one API pod from step 5, halve it, and set that as the API's CPU limit in values.yaml: for a peak of 80m, limits: { cpu: 40m, memory: 256Mi } (keep your own memory figure from step 3, and don't go below 20m). A limit under what the pod needs at the peak is sure to bite. Push, wait for the new pods, then run the k6 test again.

    Diagnose

    • Compare the k6 summary with your baseline. Which thresholds failed?
    • On the dashboard, how does latency look? Did TodoApiSlow fire?
    • Graph the API's CPU usage: sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="todo", container="api"}[1m])). What's odd about its shape?
    • Now graph throttling: the share of time slices in which the container wanted more CPU than its limit allowed.
    Check your answers

    p95 latency climbs well past 500 ms as users increase, the duration threshold fails and the Job ends Failed. TodoApiSlow may fire while the test runs. There are no errors, just slowness.

    CPU usage goes up with the load and then flattens at exactly your limit: a flat top at a round number. A graph that looks "calm" at a round number is the giveaway. The node had idle CPU the whole time; the limit kept the API from using it.

    The throttling ratio jumps from near 0 to a large share, often over 50%. The kernel hands out CPU in 100 ms periods, and a container over its limit has to wait for the next period. That waiting is added directly to request times.

    Compare with part 2's drill 2: there CPU was flat and low, and the wait was outside the app. Here CPU is flat and high, pinned to a round number. The same symptom, slow requests with no errors, has two opposite causes. Look at the throttling ratio before anyone adds CPU or removes a limit.

    Revert and push.

    07

    Add copies when CPU runs high

    Goal: during a k6 run the API grows past two pods on its own, and shrinks back afterwards.

    Why this step

    A HorizontalPodAutoscaler (HPA) checks a Deployment's pods every 15 seconds and changes its replica count to keep a metric near a target. The classic target is CPU: "keep average CPU at 70% of the request". At 140% it doubles the pods; at 35% it halves them, slowly, so it doesn't flap.

    The HPA gets CPU figures from metrics-server, a small component that asks each node for its pods' current usage. That's also what kubectl top uses.

    Why replicas has to go

    Once an HPA owns the replica count, the Deployment in Git must stop stating one. Otherwise the HPA sets 5, Argo CD sees 5 ≠ 2, and selfHeal sets it back to 2. Then the HPA sets 5 again, all day. The site wobbles under load and nothing reports an error.

    This is the most common GitOps-and-autoscaling bug. The alternative fix is an ignoreDifferences on /spec/replicas in the Application, like the webhook fields in part 3.

    Set scaling: cpu and push. When the line disappears from the Deployment, Kubernetes can briefly fall back to one copy before the HPA brings it up to minReplicas. That's a good reason to change this on a quiet cluster. Then check: kubectl -n todo get hpa shows TARGETS like cpu: 12%/70%. Now run k6 again and, in another terminal, watch:

    As load rises, CPU passes 70% of the request, and the HPA adds pods within a minute or so. After the test, it waits five minutes (the default scale-down stabilisation) before removing them. Compare the k6 summary with your baseline.

    The HPA's percentage is of the request, not of the node. If step 3 gave the API a small CPU request, 70% of it is very little and the HPA scales early. A larger request makes it scale late. Right-sizing and autoscaling are one decision, not two.

    What you just learned

    • Under GitOps, exactly one thing owns each field. Hand the replica count to the autoscaler explicitly.
    • CPU-based scaling is only as good as the CPU request it's measured against.
    08

    Scale on what users actually do

    Goal: the API scales on requests per second from Prometheus instead of on CPU.

    Why this step

    CPU is an indirect signal. An API that mostly waits on a database can be overloaded at 20% CPU. Requests per second is what you actually want to keep in check, and Prometheus already has it. KEDA (Kubernetes Event-Driven Autoscaling) feeds metrics like that, or queue lengths, into an HPA it manages for you. It can even scale to zero.

    Add KEDA as an Application. The chart version, 2.21.0, was the newest when this was written:

    Add requestsPerPod: 40 to the api: block. Because the two autoscalers must never both exist, switch in two pushes. First set scaling: fixed and push, and wait until kubectl -n todo get hpa shows none. Then set scaling: requests and push. KEDA creates its own HPA, called keda-hpa-todo-api.

    The two pushes are not just caution. KEDA's admission webhook refuses a ScaledObject for a Deployment that another HPA already manages, with the message the workload 'todo-api' of type 'apps/v1.Deployment' is already managed by the hpa 'todo-api'. Switching in one push puts both objects in the same sync, and the new one is refused.

    Line by line: the ScaledObject
    scaleTargetRef
    The Deployment to scale.
    query
    Total requests per second across all API pods, from the same metric as the dashboard's traffic panel in part 2.
    threshold
    The target per pod. At 200 requests a second and a threshold of 40, KEDA asks for 5 pods.
    Why not both?
    Two autoscalers on one Deployment fight like Argo CD and the HPA did. The scaling value makes sure only one exists at a time.

    Check that KEDA can read the metric: kubectl -n todo get scaledobject shows READY True. Run k6 again and watch kubectl -n todo get hpa,pods -w. KEDA asks Prometheus every 30 seconds, so scaling follows the request rate on the dashboard a little behind it, whatever the CPU does. Compare the summary with the CPU run.

    Drill: more pods than the node can hold

    Set the API's CPU request to "1", requestsPerPod: 5 and maxReplicas: 20, push, and run k6. Predict what happens around the peak.

    Check your answers

    KEDA asks for many pods, the node's allocatable CPU fills with requests, and the rest wait in Pending with Insufficient cpu, just like step 2's drill. How many fit depends on the CPUs you gave Docker. Autoscaling pods only helps while there's room for them. In the cloud, a cluster autoscaler or Karpenter watches for exactly these Pending pods and adds nodes, which takes minutes, not seconds. Pod autoscaling and node autoscaling are two layers that have to be planned together.

    There's a second limit hiding behind the first: the database. With dbPool: 10, 20 pods could ask for 200 connections from a database that accepts 97. Under heavy load, new pods start failing with sorry, too many clients already. Before raising maxReplicas, work out pods × pool size, as in step 4.

    Revert and push.

    What you just learned

    • Scale on the signal closest to user demand: request rate, queue length, or latency.
    • Every autoscaler hands the problem to the next layer: pods need nodes, and more app copies need more database.

    Clean up

    Set scaling back to the mode you prefer (requests is a good default now), put the API's resources and maxReplicas back to the values you chose in steps 3 and 7 and push. Then:

    Deleting the cluster deletes the database's disk too. The todos come back empty after the next bootstrap, and the hand-made secret from part 4 has to be created again. That's fine for a lab. For real data you would take backups, to object storage, and restore from them.

    Where to go next

    • Part 6, Terraform the Lab, replaces the bootstrap script with Terraform, and gives the cluster worker nodes so you can try the items below.
    • Survive maintenance. With several nodes, add a PodDisruptionBudget so draining a node for an upgrade never takes all API pods down at once, and topology spread constraints so the copies land on different nodes.
    • Let the cluster suggest numbers. The Vertical Pod Autoscaler in recommendation-only mode, or Goldilocks, which shows its suggestions on a dashboard.
    • A pooler in front of the database. PgBouncer lets many pods share a small number of real connections, which raises the ceiling from step 4.
    • A highly available database. An operator such as CloudNativePG runs a primary and replicas, and fails over on its own when the primary dies.
    • A load test in the pipeline. Run k6 with its thresholds against a test environment on every release.
