    00

    What you'll build

    In Code to Cluster you built the road from your editor to a running cluster. Once code is running, a platform engineer's next job is answering two questions quickly: is it working? and if not, why not? That ability is called observability, and every serious platform team provides it as a service to the developers on it.

    The diagram plays by itself. Use the buttons to pause it or step through:

    What problem each tool solves

    The problemThe toolWhat it does about it
    The app doesn't say how many requests it handles, how many fail, or how slow they are.OpenTelemetry (step 4)A standard library that counts and times things inside your code and serves the numbers at /metrics.
    Numbers that only exist "right now" can't show a trend or what happened at 2am.Prometheus (step 2)Collects the numbers every 15 seconds and keeps the history so you can ask questions about it.
    kubectl logs only shows one pod, and the logs vanish when the pod is replaced.Alloy + Loki (step 8)Alloy copies every pod's logs to Loki, which keeps and searches them.
    Nobody wants to type queries to see if things are fine.Grafana (step 9)Turns queries into dashboards you can read at a glance.
    Nobody watches a dashboard all day.Alertmanager (step 10)Tells people when a rule says something is wrong, and stays quiet otherwise.

    Words you'll meet

    Metric
    A named number that changes over time, such as http_server_request_duration_seconds_count. Together with its labels it forms a series.
    Label
    A name="value" pair on a metric or a log stream, such as status="500". Labels are how you narrow a question.
    Scrape
    One visit by Prometheus to an app's /metrics address to collect its numbers.
    PromQL
    Prometheus' query language. Like SQL for numbers over time.
    LogQL
    Loki's query language. It looks like PromQL, but it finds log lines.
    Operator
    A program in the cluster that adds new object types to Kubernetes (here ServiceMonitor and PrometheusRule) and acts on them.
    Alert
    A rule that fires when a query stays true for long enough. Prometheus decides, Alertmanager delivers.
    SLO
    Service level objective: a target such as "99% of requests succeed". The part you may fail is the error budget.

    The second half of the tutorial (steps 11 to 15) is break/fix drills. You flip a fault switch in the app through Git, then use only the dashboard, alerts and logs to work out what broke. That's the skill troubleshooting interviews and 2am pages actually test.

    02

    Install Prometheus and Grafana

    Goal: every pod in the monitoring namespace is Running.

    Why this step

    Prometheus pulls. Every 15 seconds it calls a /metrics address on each app it knows about and stores the numbers it gets back. This is called scraping. Apps don't need to know where Prometheus lives; they only need to answer when asked.

    You'll install kube-prometheus-stack, a Helm chart that bundles Prometheus, Alertmanager, Grafana, ready-made Kubernetes dashboards and a set of standard alerts. It also installs the Prometheus Operator, which adds new object types to Kubernetes. The important one is ServiceMonitor: a small YAML file that says "scrape this Service". That lets each app team switch on monitoring from their own Helm chart, without touching Prometheus. That self-service shape is what makes it a platform.

    Platform settings live in Git too. Make a folder for them:

    Line by line: the values file
    adminPassword
    Grafana's login. Fine for a lab. At work the password comes from a Kubernetes Secret (grafana.admin.existingSecret) and never sits in Git.
    sidecar.dashboards
    A helper container next to Grafana watches for ConfigMaps labelled grafana_dashboard: "1" and loads them as dashboards. You'll use it in step 9 to keep a dashboard in Git.
    additionalDataSources
    Tells Grafana where Loki will be. Loki doesn't exist until step 8, so this data source shows an error until then. That's expected.
    scrapeInterval: 15s
    How often Prometheus collects. Shorter shows changes sooner and costs more storage.
    retention: 2d
    How long to keep the history. Plenty for a lab.
    …SelectorNilUsesHelmValues: false
    By default Prometheus only watches ServiceMonitors and rules carrying this Helm release's label. Setting these to false makes it watch all of them, so your app's chart doesn't need to know the release name.
    kubeEtcd and friends
    Turns off scraping of control-plane parts that kind doesn't expose. Left on, they'd show as down and fire alerts that mean nothing.

    Add the chart repositories once, then install:

    --version 92.3.0 pins the chart to the one this tutorial was checked against. Without it Helm picks the newest, and a newer chart may have renamed values.

    It takes two or three minutes. You should end up with pods for Prometheus, Alertmanager, Grafana, the operator, kube-state-metrics and one node-exporter.

    What the two less obvious pods do
    kube-state-metrics
    Turns Kubernetes' own records into metrics: how many replicas a Deployment wants, how often each container has restarted, what each pod's memory limit is.
    node-exporter
    Reports the machine's CPU, memory, disk and network. One runs on every node.

    Why install by hand and not with Argo CD? You could, and at work you would: the monitoring stack becomes another Argo CD Application. Doing it by hand once shows you what's being installed. Moving it under Argo CD is in "Where to go next".

    What you just learned

    • Prometheus pulls metrics on a timer. Apps only have to serve them.
    • An operator extends Kubernetes with new object types (ServiceMonitor, PrometheusRule) and acts on them, using the same reconciliation loop you met in Code to Cluster.

    04

    Give the API metrics, logs and fault switches

    Goal: running locally, curl http://localhost:5080/metrics shows http_server_request_duration_seconds lines.

    Why this step

    Only the app knows how many requests it handled, how many failed and how long they took. OpenTelemetry is the vendor-neutral standard for reporting that. ASP.NET Core already records request timings internally; OpenTelemetry collects them and serves them at /metrics in Prometheus' format.

    You'll make two more changes in the same build:

    • JSON logs. One JSON object per line, so Loki can search by field (level, message) instead of guessing at text.
    • Fault switches. Three environment variables that make the API fail, slow down or run out of memory. They're off by default. The drills turn them on through Git.

    The Prometheus exporter for ASP.NET Core has only ever shipped as a pre-release, which is why it needs --prerelease. It's widely used anyway. In production many teams send metrics to an OpenTelemetry Collector instead, which you'll see in "Where to go next".

    Replace src/api/Program.cs with this. The todo endpoints and the PostgreSQL store are the ones you wrote in Code to Cluster; the new parts are commented.

    Line by line: the new parts
    AddJsonConsole()
    Each log entry becomes one JSON line with fields like LogLevel, Category and Message. Still console output, which is all a platform needs.
    AddService("todo-api")
    Names the app in its telemetry.
    AddAspNetCoreInstrumentation()
    Collects ASP.NET Core's built-in request metric, http.server.request.duration: one timing per request, labelled with route, method and status code. Rate, errors and latency all come from this one metric.
    AddMeter("Todo.Api")
    Also collects metrics your own code creates under that name.
    Meter / CreateCounter
    .NET's built-in metrics API (System.Diagnostics.Metrics). A counter only goes up. Prometheus works out the rate from how fast it rises.
    AddEndpointFilter
    Runs before every endpoint in the /api/todos group, like middleware scoped to a route group. It applies the fault switches. /api/info, /healthz, /readyz and /metrics are outside the group, so the app stays "healthy" while users suffer. That's realistic, and it matters in the drills.
    Results.Problem(…, 500)
    A standard error response. The 500 lands in the metric's status-code label.
    MapPrometheusScrapingEndpoint()
    Serves /metrics in the plain-text format Prometheus reads.

    Try it locally. The API needs its database, so make sure the dev database from Code to Cluster is running. The first command starts it, or creates it if you removed it:

    You should see lines like this:

    Notice the names changed on the way out. Prometheus doesn't allow dots, so http.server.request.duration became http_server_request_duration, the unit was added as _seconds, and counters get _total. The terminal running the API now prints JSON lines.

    Now try a fault switch. Stop the API with Ctrl+C and start it with half of the requests failing:

    Call curl -i http://localhost:5080/api/todos a few times. About half return 500, and each failure prints an error line in terminal 1. Stop the API when you're done.

    What you just learned

    • One timing metric per request, with route and status labels, answers three of the four questions you'll ask about any service.
    • Structured logs are a contract with the platform: fields it can filter on, not text it has to parse.

    07

    Ask questions with PromQL

    Goal: you can write the four golden-signal queries for the API from memory.

    Why this step

    Google's SRE book names four golden signals to watch on any service. If you know these four numbers, you can usually tell whether something's wrong, and roughly what kind of wrong.

    SignalThe questionComes from
    TrafficHow many requests per second?request count
    ErrorsWhat share of them fail?request count, status label
    LatencyHow long do they take?request duration buckets
    SaturationHow close to full is it?memory and CPU against limits

    Run each of these in Prometheus' Query page, switch to Graph, and read the result before moving on.

    Traffic

    How this query works
    …_count
    A counter: requests handled since the pod started. It only goes up, and starts again at zero when the pod restarts.
    [2m]
    Take the last two minutes of samples. With a 15-second scrape that's about eight points.
    rate(…)
    How fast the counter rose, per second, averaged over those two minutes. It copes with the counter going back to zero on a restart. Never graph a raw counter; always rate it.
    sum by (http_route)
    Add up all the series (one per status code, method, pod) and keep only the route label. Like GROUP BY in SQL.

    You'll see /api/todos/, /api/info, /healthz, /readyz and /metrics. The last three are the platform talking to the app, not users. From now on, filter them out with http_route=~"/api/.*" (=~ means "matches this pattern").

    Errors

    Failed requests per second divided by all requests per second gives a fraction from 0 to 1. Right now it's 0.

    The or vector(0) matters. While nothing has failed, no series with status 5xx exists, so the top half returns nothing, and nothing divided by anything is nothing. "No data" and "zero errors" look alike on a graph and mean different things. You'll meet this again in drill 4.

    Latency

    How this query works
    …_bucket
    The duration metric is a histogram: a set of counters, one per bucket. le="0.1" counts requests that took 0.1 seconds or less, le="0.25" those under 0.25 seconds, and so on.
    sum by (le)
    Combine routes and pods, but keep the buckets apart. histogram_quantile needs the le label.
    histogram_quantile(0.95, …)
    Estimates the p95: 95% of requests were faster than this. Use p95 or p99, not the average. An average hides the slow 5% that users complain about.

    Expect a few milliseconds. The answer is an estimate, interpolated between bucket edges, so don't read too much into the third decimal place.

    Saturation

    Memory used as a share of the limit. The top comes from the kubelet; the bottom from kube-state-metrics. At 1.0 the container gets killed.

    What you just learned

    • Counters get rate(). Histograms get histogram_quantile(). sum by decides which labels survive.
    • An empty result is not the same as zero. Always ask which one you're looking at.
    08

    Collect the logs

    Goal: in Grafana's Explore page, choosing Loki and {namespace="todo"} shows the API's JSON log lines.

    Why this step

    Metrics tell you that something is wrong and where. Logs tell you what happened. kubectl logs works for one pod, but it loses everything when the pod is replaced, which happens on every deployment and every crash. You need the logs from before the crash.

    Alloy reads every pod's console output through the Kubernetes API and sends it to Loki. Loki indexes only a few labels (namespace, pod, app) and stores the text compressed. That makes it cheap to run, and it's why you choose labels carefully.

    Line by line: the Loki values
    SingleBinary
    All of Loki in one pod. Large installs split reading, writing and storage into separate scalable parts; read, write and backend set to zero turn those off.
    auth_enabled: false
    One tenant, no login. Shared Lokis use tenants to keep teams' logs apart.
    storage.type: filesystem
    Keep logs on the pod's disk. In the cloud this would be S3 or Azure Blob storage.
    schemaConfig
    How Loki lays out its index. Loki asks you to choose explicitly so a later upgrade doesn't silently change it.
    chunksCache, resultsCache
    Memory caches that by default ask for several gigabytes each. Off, or they won't fit on your PC.
    How the Alloy config reads

    Alloy config is a pipeline of named blocks. Each block's output feeds the next one by name, like method chaining:

    discovery.kubernetes
    Lists every pod, with its metadata in labels starting __meta_.
    discovery.relabel
    Copies four of those into short labels. Labels starting __ are dropped at the end, so only these four reach Loki.
    loki.source.kubernetes
    Follows each pod's log stream, as kubectl logs -f would.
    loki.write
    Pushes the lines to Loki's gateway.

    In Grafana, open Explore (the compass icon), choose the Loki data source and switch the query editor to Code. Try these one at a time:

    How LogQL reads
    {…}
    The stream selector. Uses only labels, so Loki can find matching log streams fast. Every query starts with one.
    | json
    Parses each line as JSON and turns its fields into temporary labels you can filter on. Expand a line in the results to see them.
    | LogLevel="Error"
    Keeps lines where that field matches. This filtering happens after the stream is found, on the text.

    The last query probably shows nothing yet. Good: there's nothing wrong. It'll have plenty to show in drill 1.

    Never put user IDs, request IDs or anything with many values in a Loki label. Each unique set of labels is a separate stream with its own index entry. A few hundred streams is fine; a million brings Loki down. Keep that kind of detail in the log line and filter with | json. The same rule applies to Prometheus labels.

    What you just learned

    • Logs need to live outside the pod, or the evidence dies with it.
    • Labels for finding (few values), content for reading (anything). This one rule drives the cost of both Loki and Prometheus.

    10

    Write alerts that mean something

    Goal: Prometheus' Alerts page lists four TodoApi… rules, all Inactive.

    Why this step

    An alert should mean "a person needs to act now". Alert on what users feel (errors, slowness, the service gone), not on every internal number that wobbles. Teams that alert on everything learn to ignore alerts, and then miss the real one.

    Alerts are rules Prometheus checks every 30 seconds. A PrometheusRule object carries them, and like the ServiceMonitor, it lives in the app's chart.

    Line by line: the rules
    record:
    A recording rule. Prometheus runs the query on every check and saves the answer as a new series with this name. The level:metric:operation naming is a Prometheus convention.
    expr
    The condition. Any series it returns is a problem.
    for: 2m
    The condition has to stay true this long before the alert fires. Until then it's Pending. This stops one bad scrape from waking someone.
    severity
    A label Alertmanager uses to decide where an alert goes: critical to the on-call phone, warning to a chat channel.
    absent(up{…} == 1)
    Fires when there's no target that's up, including when the target has disappeared entirely. up == 0 would miss that case, because a missing target has no up series to be 0. Drill 4 tests this.
    increase(…[10m])
    How much a counter grew in ten minutes. The restart count is a counter.

    Refresh in Argo CD. Then check two places:

    • Prometheus → Alerts: four TodoApi… rules, green and Inactive.
    • Alertmanager: open a third tunnel with kubectl -n monitoring port-forward svc/alertmanager-operated 9093 and visit http://localhost:9093. This is where firing alerts arrive. It groups them, holds repeats back and, once you configure a receiver, sends them on to Slack, Teams, email or a pager.

    What you just learned

    • An alert has three states: Inactive, Pending (condition true, waiting out for), Firing.
    • Prometheus decides whether something's wrong. Alertmanager decides who hears about it.

    How to run the drills

    You have signals. Now use them. Each drill flips one fault switch through Git, exactly as a bad release would arrive. Then you diagnose it without looking at what you changed, as if a colleague had shipped it.

    1. Predict. Before you push, write down what you expect each panel and alert to do.
    2. Break it. One commit, one fault.
    3. Diagnose from signals. Start at the dashboard, then the alert, then the logs, then kubectl. Note the order you looked in and how long each took.
    4. Fix it with Git. Revert the commit. Watch the signals return to normal and the alert resolve.
    5. Write it up. Three lines: the symptom as it first appeared, the actual cause, how you connected the two.

    Step 5 is the one people skip and the one that pays. Keep the write-ups in a drills.md in the repo. A year from now, "here are thirty failures I've diagnosed" says more in an interview than any certificate.

    At work, the fault arrives as a pull request. Here you push straight to main to keep the loop short. The mechanics are the same.

    11

    Drill 1: some requests fail

    Goal: TodoApiHighErrorRate fires, you find the cause in the logs, and it resolves after your revert.

    Break it

    In charts/todo/values.yaml, set faultRate: "0.2". Then:

    Click Refresh in Argo CD. New API pods start, because changing an environment variable changes the pod template.

    Diagnose

    • Which dashboard panel changed first, and by roughly how much?
    • Which routes and methods are affected? (Hint: change the Errors query to sum by (http_route, http_request_method) in Explore.)
    • How long between the pod starting and the alert reaching Firing? Why that long?
    • What do the error log lines say? Do they explain the cause, or only the symptom?
    • Is the pod Ready? Is Argo CD showing it as Healthy? Why?
    Check your answers

    The error panel jumps to about 20% within a minute or two. Both GET and POST on /api/todos/ are hit; /api/info isn't, because the fault filter only covers the todos group.

    The alert takes about three to four minutes to fire. The 5-minute rate window has to fill with enough failures to cross 5% (well under a minute at 20%), then the condition has to hold for for: 2m, and Prometheus only checks every 30 seconds.

    The logs say "Injected fault on GET /api/todos". In a real incident you'd see an exception and stack trace here instead.

    The pod is Ready and Argo CD says Healthy, because /healthz doesn't touch the failing code. Health checks prove the process is alive, not that users are being served. This is why you alert on user-facing errors, not on pod health.

    Fix it

    Refresh Argo CD. The error panel drops to zero and, a few minutes later, the alert resolves. Write your three lines.

    12

    Drill 2: everything gets slow

    Goal: TodoApiSlow fires, and you can explain why the traffic graph dropped too.

    Predict, then break it

    Before pushing, predict what happens to requests per second when every todo request takes 0.8 seconds longer. Then set slowMs: "800" in values.yaml, commit with a vague message, push and refresh Argo CD.

    Diagnose

    • What does p95 latency settle at? Does it match 800 ms exactly? Why or why not?
    • What happened to requests per second, and why? Was your prediction right?
    • Are there any error log lines? What does that tell you about relying on logs alone?
    • CPU and memory: did either change? What would you tell a developer who asked for more CPU to fix this?
    Check your answers

    p95 settles near, but not exactly at, 800 ms. The histogram only has bucket edges at fixed points (0.75 s and 1 s here), and histogram_quantile estimates between them.

    Requests per second falls. The load generator sends one request at a time and waits for each answer, like a real user, so slower answers mean fewer requests. A drop in traffic can be a symptom of slowness, not of fewer users. Always check latency alongside traffic.

    No errors, no error logs. Slowness often leaves no trace in logs, which is why latency needs its own metric and its own alert.

    CPU and memory stay flat. The time is spent waiting, not working. More CPU wouldn't help; the cause is something the request waits on (here a delay, in real life a database, another service or a lock). This is the most common wrong fix in practice.

    Fix it

    Revert, push, refresh. Write your three lines.

    Drill 3: the new version won't start

    Goal: you find out why the new pod keeps restarting, and why users barely noticed.

    Break it

    Set memoryHogMb: "250" in values.yaml. The API's limit is 256 MiB. Commit, push, refresh Argo CD.

    Diagnose

    • What does Argo CD show for the app? What does kubectl -n todo get pods show?
    • Is the error-rate panel showing problems? Is the site working? Why?
    • Which alert fires, and how long does it take?
    • Find the reason the container died, using kubectl -n todo describe pod <new-pod> (look at Last State) and kubectl -n todo logs <new-pod> --previous.
    • The logs of the crashed container: can you also find them in Loki? Which is easier?
    Check your answers

    Argo CD shows the app as Progressing and later Degraded. get pods shows three API pods: the two old ones Running and the new one in CrashLoopBackOff with a climbing restart count.

    Users are mostly fine, and the error panel stays near zero. The rolling update starts a new pod first and only stops an old one once the new one is Ready. The new one never becomes Ready, so the old ones keep serving. A bad release that can't start is the safe kind of failure, as long as you have a readiness probe.

    TodoApiRestarting fires after the third restart, a few minutes in. The waits between restarts grow (10 s, 20 s, 40 s and so on), which is what "back-off" means.

    The previous container's log is a single line: Out of memory. It isn't JSON, because the .NET runtime printed it as it died, so a | json filter in Loki would skip it. .NET caps its own heap at 75% of the container's memory limit (here 192 MiB), so .NET gave up before Kubernetes had to step in. Last State shows Reason: Error and Exit Code: 134. If the app had used native memory beyond the limit instead, you'd see Reason: OOMKilled and exit code 137, often with nothing in the logs at all. Learn to recognise both.

    Loki has the crashed container's lines too, with {namespace="todo", app="todo-api"}. For one pod, --previous is quicker. Once that pod has been replaced, or for "what happened at 2am", Loki is the only place left.

    Fix it

    Revert, push, refresh. The broken pod is removed and nothing else changes, because the old pods never stopped. Write your three lines.

    Set an SLO and an error budget

    Goal: an error-budget alert that ignores a short blip but fires on a sustained problem.

    Why this step

    "More than 5% errors for 2 minutes" is a guess. Real teams agree a target with the business first. That target is the SLO (service level objective), for example: 99% of todo API requests succeed, measured over 30 days.

    The 1% you're allowed to fail is the error budget. Over 30 days it's the same as about 7 hours and 12 minutes of total outage. While budget remains, the team ships features. When it runs low, they slow down and fix reliability. It turns "how reliable should we be?" into a number both sides agreed.

    The alert then asks: how fast are we spending the budget? That speed is the burn rate. A burn rate of 1 uses the budget up in exactly 30 days. A burn rate of 14.4 sustained for an hour uses 2% of the month's budget in that hour (14.4 × 1 hour ÷ 720 hours). That's the standard threshold for paging someone, from Google's SRE workbook.

    Add a second group to the end of charts/todo/templates/alerts.yaml, indented to line up with the first - name::

    Why two windows
    The 1-hour window
    Makes sure the problem is big enough to matter. A 30-second blip barely moves a one-hour average, so nobody gets paged for it.
    The 5-minute window
    Makes sure it's still happening. Without it, the alert would keep firing for most of an hour after the problem was fixed, because the 1-hour average takes that long to come down.
    and
    Both must be true. Together they give alerts that are slow to fire on blips and quick to clear after a fix.

    See the difference

    Refresh Argo CD, then set faultRate: "0.5" in values.yaml, push and refresh again. Keep Prometheus' Alerts page open and graph the burn rate:

    Within a few minutes TodoApiHighErrorRate fires. The 5-minute burn rate shoots to about 50. The 1-hour burn rate climbs slowly, and TodoApiErrorBudgetBurn only fires once it passes 14.4, around 20 minutes in. Then revert, and watch which alert clears first.

    That's the trade-off you now get to choose deliberately: a fast, noisy alert for a chat channel, and a slower, trustworthy one that's allowed to wake people up.

    What you just learned

    • An SLO turns reliability into an agreement, and the error budget into a number you can spend.
    • Burn-rate alerts with two windows page only for problems big enough to matter, and stop paging soon after a fix.

    Where to go next

    You now have the two halves of a platform: a road to production, and the means to see what's on it. These take it further, roughly in order:

    • Part 3, Platform as Code, puts the monitoring stack, Loki and Alloy under Argo CD as an "app of apps", so the rebuild drill becomes one script and a wait.
    • Watch the front door. The drills only see requests that reach the API. When the database is down the API pods stop being Ready, the Gateway has nowhere to send traffic, and users get errors that none of the API's own metrics record. NGINX Gateway Fabric exposes its own Prometheus metrics. Scrape them, graph them next to the API's, and write that drill yourself.
    • Send alerts somewhere. Configure an Alertmanager receiver for a Slack or Teams webhook, routing critical and warning differently.
    • Add tracing. Add OpenTelemetry tracing to the API and the UI's nginx, run Grafana Tempo, and follow one request across both services. Tracing is the third pillar after metrics and logs.
    • Use an OpenTelemetry Collector. Have the app push to a collector (which can be Alloy) instead of being scraped. That's how most large platforms send telemetry to several back ends.
    • Scale on your metrics. A HorizontalPodAutoscaler that adds UI pods under load, then load-test it and watch it work on your dashboard.
    • Write your own drills. A failing readiness probe, a wrong image tag, a CPU limit far too low, a Service selector typo. Predict each one first.

    The same skills in the cloud. On EKS, the equivalents are Amazon Managed Service for Prometheus, Amazon Managed Grafana and CloudWatch Container Insights. The PromQL, ServiceMonitors, dashboards and alert rules carry over unchanged; only the hosting changes.
