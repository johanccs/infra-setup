    Terraform the Lab

Along the way: state, modules, refactoring without destroying anything, drift, import, and how the same layout carries over to EKS.

    00

    What you'll build

    Part 3's bootstrap.sh works, but a script only knows how to do things, not what already exists. Run it twice and it fails. Change one setting and you rebuild everything by hand. Terraform works the way Argo CD does for Kubernetes: you describe what should exist, it compares that with what does exist, shows you the difference as a plan, and only changes what's needed. Follow one run:

    Terraform and Argo CD split the work. Terraform builds the ground, in two layers; Argo CD builds everything on it:

    LayerFolderBuilt byWhat it holds
    Cluster (steps 2–5)infra/terraform/clusterTerraformThe kind cluster: control plane, workers and the port that opens it to your PC.
    Bootstrap (steps 6–7)infra/terraform/bootstrapTerraformThe Gateway API types, NGINX Gateway Fabric, Argo CD and the root Application.
    Everything elseinfra/platform/ and charts/todoArgo CD, from GitMonitoring, Kyverno, External Secrets, KEDA, the load generator and the todo app: parts 2 to 5.

    The name infra/platform/ is the folder Argo CD watches since part 3. The Terraform code lives next to it, under infra/terraform/, so the two never get mixed up.

    The words you'll need

    Provider
    A plugin that knows one system's API: kind, Helm, Kubernetes, AWS. Like a NuGet package for Terraform. It supplies resource types such as kind_cluster.
    Resource
    One thing Terraform manages, such as a cluster or a Helm release.
    State
    Terraform's record of what it created and the IDs it got back. It's how Terraform knows what "already exists" means.
    Plan
    The list of changes Terraform would make. Nothing changes until you apply it.
    Module
    A folder of Terraform code with inputs and outputs, reusable like a class. Every folder you run Terraform in is a root module.

    This part is also a good start on the HashiCorp Terraform Associate exam. The steps cover most of its core objectives: the workflow, state, variables and outputs, modules, moved and import, and backends.

    02

    Describe the cluster and read the plan

    Goal: terraform apply creates a kind cluster with one control plane and one worker node, and localhost:8080 is wired to the gateway's port.

    Why this step

    This is the whole Terraform loop in miniature: write what you want, init to download providers, plan to see the difference, apply to make it so. The plan is the important part. On real infrastructure you'll spend more time reading plans than writing code.

    Line by line: the first two files
    required_version
    Which Terraform versions may run this code.
    source = "tehcyx/kind"
    Where to get the provider: the Terraform Registry, publisher tehcyx, provider kind. Community providers like this always need their source written out.
    version = "~> 0.11"
    "0.11 or newer, but below 1.0." The ~> operator allows the rightmost number to grow, so you get fixes without a surprise major version.
    resource "kind_cluster" "lab"
    A resource of type kind_cluster, called lab inside your code. Its address is kind_cluster.lab. The cluster's real name is the name argument.
    kind_config
    The same settings a kind config file would hold, which is what infra/kind-config.yaml did in part 1. Here: two nodes.
    extra_port_mappings
    The same door as part 1's extraPortMappings: port 31437 on the node, where the gateway listens, appears as port 8080 on your PC.
    wait_for_ready
    Don't report success until the nodes are Ready.

    init downloads the provider into .terraform/ and writes .terraform.lock.hcl, which records the exact version and checksums, like package-lock.json. fmt tidies the layout. validate checks the code makes sense without contacting anything.

    Read the plan before going on. You'll see:

    SymbolMeans
    +Create
    ~Change in place
    -Destroy
    -/+Destroy and create again. Read every one of these twice.
    (known after apply)A value only the provider can tell you once the thing exists, such as an ID or an address

    Terraform builds the cluster, but it doesn't add it to your kubeconfig file, so kind export kubeconfig does that. Run terraform plan again. It says No changes. That's the difference from a script: running it twice is safe.

    The provider carries its own copy of kind. The Kubernetes version of a cluster built this way is the one inside that copy of kind, which can be older than your own kind command's default. kubectl version shows it. Step 4 adds a node_image input, so you can choose a version when it matters.

    03

    Look inside the state

    Goal: you know where the state is, what's in it, and why it must never go into Git.

    The state is a JSON file, terraform.tfstate, in this folder. state show prints what Terraform knows about the cluster, including client_key: the private key that gives full admin access to the cluster. State files contain secrets in plain text. On real infrastructure that means database passwords, keys and tokens.

    Keep it out of Git. Create a .gitignore in infra/terraform/:

    Do commit .terraform.lock.hcl. Everyone, including CI, then uses the exact same provider builds.

    The state on your PC is a single point of failure. Lose it, and Terraform forgets everything it built. Two people with two copies will overwrite each other's work. Teams keep state in shared storage with locking. Step 11 shows how.

    04

    Add inputs and outputs

    Goal: the cluster name, worker count and node image are variables, and you've seen a plan that would destroy the cluster without applying it.

    Why this step

    Hard-coded values make code single-use. Variables are a module's parameters; outputs are its return values, which other code can read. You'll use the outputs in step 6 to connect the two layers.

    Replace main.tf:

    Line by line: variables, outputs and the dynamic block
    var.cluster_name
    How code reads a variable. The default applies unless you pass a value with -var, a .tfvars file or an environment variable named TF_VAR_cluster_name.
    validation
    Rejects bad values before any plan is made, with your message.
    default = null
    "Not set." The provider then uses its own default image. An unset optional input is not the same as an empty string.
    dynamic "node"
    Writes a node { } block once for each item in for_each. range(2) is [0, 1], so two worker blocks.
    "kind-${…}"
    String interpolation, like C#'s $"kind-{name}".
    sensitive = true
    Hides a value in plans and in terraform output. It does not keep it out of the state file. Step 3 showed that already holds the key.

    Plan. It lists no resource at all, only Changes to Outputs and a note that you can apply it to save them without changing any real infrastructure: the defaults describe exactly what you built. Then see what a second worker would do:

    The second plan reads -/+ destroy and then create replacement, with # forces replacement next to the new node, and 1 to add, 0 to change, 1 to destroy. kind can't add a node to a running cluster, so Terraform would delete the whole cluster and make a new one, taking everything on it with it. Don't apply it. On EKS a node group change can do the same to every node.

    That line is why you read plans. Then run terraform apply with no -var, which only records the new outputs, and commit.

    05

    Turn it into a module, without destroying it

    Goal: the cluster code lives in a reusable module, and the plan after the move shows nothing to add, change or destroy.

    Why this step

    Modules let one team write "how we build a cluster" once and others use it with a few inputs. Moving existing code into a module is a refactor, and Terraform tracks resources by address. Move kind_cluster.lab into a module and its address changes. Terraform then sees one resource deleted and a different one created. A moved block tells it they're the same thing.

    06

    Add a second layer: the gateway controller

    Goal: a separate Terraform root module installs NGINX Gateway Fabric into the cluster, the same as part 3's script did.

    Why this step

    Why not put the gateway in the same folder as the cluster? A provider's settings are worked out at plan time, but the Helm provider needs to connect to a cluster that, on a first run, doesn't exist yet. Splitting into layers, each a root module with its own state, avoids that. It also limits damage: a mistake in the bootstrap layer can't plan to destroy the cluster.

    The bootstrap layer reads the cluster layer's outputs from its state, so nothing is typed twice. That's what the outputs from step 4 are for.

    Line by line: the bootstrap layer so far
    terraform_remote_state
    A data source: something Terraform reads but doesn't manage. This one reads the outputs from the cluster layer's state. Data sources are read during the plan, so the provider settings below are known in time.
    locals
    Named values inside a module, like local variables.
    provider "helm" { kubernetes = { … } }
    How the Helm provider reaches the cluster: the address and the certificates the cluster layer exported. It doesn't depend on any kubeconfig file. In version 3 of the Helm provider, kubernetes is an attribute with =; older examples online use a block without it.
    terraform_data and local-exec
    An escape hatch: a resource that runs a command on your PC. Use it only when no provider can do the job. Terraform can see that the command ran, never what it changed. triggers_replace makes it run again when the NGINX version changes. The command needs kubectl and the kubeconfig that kind export kubeconfig wrote in step 2.
    helm_release
    The Terraform version of helm upgrade --install. oci:// is how a chart stored in a container registry is addressed.
    yamlencode
    Turns a Terraform object into YAML for the chart's values. It replaces part 3's --set-json flag and is safer than building YAML strings by hand.
    depends_on
    Terraform works out order from references between resources. Nothing in ngf refers to the CRD step, so you state the order yourself.
    terraform.tfvars
    Values for variables, loaded automatically. Fine to commit when, as here, nothing in it is secret.

    The controller needs no proxy yet. As in part 3, NGINX Gateway Fabric creates one the moment a Gateway object appears, and that comes with the todo chart.

    08

    Replace the bootstrap script

    Goal: ./infra/bootstrap.sh runs both layers, and ./infra/teardown.sh removes them in the right order.

    Replace part 3's infra/bootstrap.sh with this. Every other part still starts with ./infra/bootstrap.sh, and that doesn't change:

    Line by line: the scripts
    -chdir=
    Run as if in that folder.
    output -raw
    Prints one output's value with no quotes, so a script can use it.
    -auto-approve
    Skip the "type yes" prompt. Fine for a lab you rebuild daily. On shared infrastructure, always apply a plan someone has read.
    Reverse order
    The bootstrap layer needs the cluster to exist to destroy its releases. Destroy the cluster first and the bootstrap layer is left with a state describing things it can no longer reach.

    Compare the time with part 3's script. It's similar; the difference is that running bootstrap.sh on a lab that already exists now does nothing harmful. Remember to put the store secret back after a rebuild.

    09

    Drill: change things behind Terraform's back

    Goal: you know what Terraform notices on its own, what it doesn't, and how that differs from Argo CD.

    Break it, two ways

    Diagnose

    • Which of the two changes does the plan show? Which doesn't it?
    • What happened to the platform apps when the root release was removed? (Look at kubectl -n argocd get applications.)
    • How is this different from part 3's drift drill?
    • If someone deleted the Gateway API types by hand, would the plan notice? Why, or why not?
    Check your answers

    The plan wants to create helm_release.root_app again: the Helm provider checks whether each release exists, and that one doesn't. It does not show the scaled-down Argo CD server, because the provider tracks the release, not each object inside it. Terraform only sees drift its provider reads back, and only when you run a plan.

    Uninstalling the root release deleted the root Application. The child Applications are still there, still running the platform, but nothing manages them anymore: delete a file from infra/platform/apps/ now and nothing happens.

    Argo CD compares continuously and undoes drift within seconds. Terraform compares only when someone runs it, which is why teams run terraform plan on a schedule to spot drift. That's also why the split in this part makes sense: Terraform for the few things that rarely change, Argo CD for everything that changes often.

    No, the plan wouldn't notice the deleted types. The CRD step is a terraform_data with a command: Terraform only remembers the values that make it run again, not what the command created. That's the price of an escape hatch, and the reason to prefer a real resource whenever one exists.

    Fix: terraform -chdir=infra/terraform/bootstrap apply restores the release. Scale the server back with kubectl -n argocd scale deploy/argocd-server --replicas=1. Write your three lines.

    11

    Plan for shared state

    Goal: you can explain what a remote backend and state locking do, and how the bootstrap layer would read the cluster layer's outputs from one.

    Why this step

    Your state sits on one PC. On a team, state lives in a backend, shared storage that everyone and every pipeline uses, with a lock so two applies can't run at once and corrupt it. On AWS the usual backend is an S3 bucket. This step is reading only; you'd need an AWS account to run it.

    The bootstrap layer's data source would then read from the same place:

    key
    The file's path in the bucket. One key per layer per environment.
    encrypt
    State holds secrets, so it's encrypted at rest.
    use_lockfile
    Writes a lock file next to the state during an apply. A second apply waits or fails instead of overwriting. Older setups used a DynamoDB table for this.
    Moving to it
    Add the block and run terraform init -migrate-state. Terraform copies the local state up.

    Who may read that bucket is a security decision: anyone who can read the state can read every secret in it, including the cluster's admin key from step 3.

    12

    Check Terraform in pull requests

    Goal: a pull request with badly formatted or invalid Terraform gets a red cross.

    GitHub's runners can't reach the kind cluster on your PC, so CI can't plan. It can still check formatting and that the code is valid. In .github/workflows/platform-check.yml, add one line to the paths list at the top, then a second job at the same indentation as render::

    Line by line: the job
    terraform_version
    Installs exactly the version you use, so a new Terraform release can't turn the check red on its own.
    fmt -check
    Fails if any file isn't formatted the way terraform fmt would leave it. Ends arguments about style.
    init -backend=false
    Downloads providers and modules without touching any state. Enough to validate.
    validate
    Checks references, types and required arguments. It doesn't contact any API, so it can't catch everything a plan would.

    Test it: on a branch, put a few extra spaces in front of a line in infra/terraform/cluster/main.tf, open a pull request and watch the job fail. Run terraform fmt -recursive infra/terraform, push the fix, and watch it pass.

    At work, CI also runs the plan. With a cloud cluster and remote state, the pipeline posts the plan on the pull request and applies it after merge. Tools like Atlantis or HCP Terraform do this. Reviewers approve the plan, not just the code.

    • Practise for the Terraform Associate exam. You've covered the workflow, state, modules, variables, outputs, moved, import and backends. Fill the gaps with HashiCorp's own tutorials on workspaces, count versus for_each, and provisioners (and why to avoid them: step 6 used one).
