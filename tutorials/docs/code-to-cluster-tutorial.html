    00

    What you'll build

    A todo list. The Angular UI calls a .NET API, and the API keeps the todos in a PostgreSQL database. The API also reports which version it is, so you can watch a new version arrive in your browser.

    The app is deliberately tiny. The real subject is the road the code travels from your editor to a running cluster:

    The same thing in words

    1. You push code to GitHub.
    2. GitHub Actions builds a container image for the API and one for the UI, and stores them in a registry (Docker Hub).
    3. GitHub Actions then writes the new image version into the Helm chart in your repo.
    4. Argo CD, running inside the cluster, sees the repo changed and updates the cluster to match.
    5. Visitors reach the app through an NGINX gateway, the single front door that sends each request to the right service.

    Once it's set up, you never run a deploy command. You merge, and it ships. To undo a release you undo a commit.

    What problem each tool solves

    Every tool here exists because of a specific pain. Learn the pain and the tool makes sense.

    The problemThe toolWhat it does about it
    "It works on my machine" but not on the server.Docker (step 4)Packs your app and everything it needs into one image. The same image runs everywhere.
    Someone has to start the containers, restart them when they crash, and swap in new versions without downtime.Kubernetes (step 5)You describe what you want ("2 copies of the UI") and it keeps that true, all day.
    Kubernetes needs a lot of YAML, mostly the same for every environment.Helm (step 6)Turns the YAML into templates with a small settings file. A release becomes a one-line change.
    Building and publishing by hand is slow, easy to get wrong, and depends on one person's laptop.GitHub Actions (step 9)A server runs the same scripted steps on every change.
    Nobody knows who deployed what, and the cluster drifts from what people think is running.Argo CD (steps 10–11)The cluster follows Git. Every deployment is a commit you can read, review and revert.
    Pods come and go and their addresses change, but users need one stable address, and each request must reach the right service.NGINX Gateway (steps 5–6)One front door. You describe routes ("/api goes to the API") and a controller keeps an nginx proxy configured to match.

    Platform engineering is the job of joining these pieces into a "paved road" so other developers only have to push code. In this tutorial you play both roles: the developer who writes the app, and the platform engineer who builds the road.

    Who this is for

    You can write a little C# and have used Git. You don't need to know Docker, Kubernetes or pipelines. Each step says why it exists before it says what to type, and ends with what you learned.

    Words you'll meet

    Image
    A packaged, read-only copy of your app plus everything it needs to run. Built from a Dockerfile.
    Container
    A running image. Like an object created from a class.
    Registry
    A store for images, like NuGet is a store for packages. You'll use Docker Hub, the default public registry.
    Cluster
    One Kubernetes installation. Yours runs on your PC using a tool called kind.
    Pod
    The smallest thing Kubernetes runs: usually one container. Pods are disposable.
    Deployment
    Tells Kubernetes "keep N copies of this pod running, using this image".
    Service
    A stable name in front of pods that come and go.
    Gateway
    The front door of the cluster: a listener (here HTTP on port 80) that a controller turns into a running reverse proxy. HTTPRoute objects say where each path goes.
    Secret
    A Kubernetes object for a password or token, kept apart from ordinary settings.
    StatefulSet
    Like a Deployment, but for programs that keep data, such as a database. Its pod keeps a stable name and its own disk.
    Volume claim
    A request for a disk that outlives the pod using it. Kubernetes finds or makes the disk for you.
    Namespace
    A folder inside the cluster that keeps one app apart from another.
    Helm chart
    A folder of Kubernetes YAML templates plus a values.yaml file that fills in the blanks.
    CI
    Continuous integration: a server builds and checks every change automatically.
    GitOps
    Keeping the wanted state of the cluster in Git and letting a tool make the cluster match.

    Build the .NET API

    Goal: curl http://localhost:5080/api/todos returns [].

    Why this step

    You need something to deploy. This API also follows four habits that every platform expects from an app:

    • Settings come from environment variables (here APP_VERSION), so one build can run anywhere.
    • It has a health endpoint (/healthz), so the platform can ask "are you OK?".
    • It logs to the console, which is ASP.NET's default. Platforms collect console output.

    Line by line: how the API uses the database
    Host=localhost;Database=todo;…
    The connection string: which server, which database, and who to log in as. Think of it as the ConnectionStrings entry you know from appsettings.json.
    NpgsqlDataSource
    Npgsql's connection pool. It opens a few connections once and lends them out, because opening one for every request is slow.
    $1 in the SQL
    A parameter. The value is sent separately from the SQL text, so a todo titled '; DROP TABLE todos; -- is just text. Never build SQL by joining strings.
    CREATE TABLE IF NOT EXISTS
    Makes the table the first time, and does nothing afterwards. Real teams use migrations for this; one table doesn't need them.
    ConnectAsync loop
    In a cluster the API and the database start at the same moment, and the database is usually slower. So the API keeps trying every 2 seconds instead of crashing.
    /healthz and /readyz
    Two questions Kubernetes asks. Liveness (/healthz): "is the process alive?" It deliberately ignores the database, or a database outage would make Kubernetes restart healthy API pods for nothing. Readiness (/readyz): "can it take traffic?" It says no until the database answers.

    What you just learned

    • A platform-friendly app reads its settings from environment variables and offers a health endpoint.
    • State belongs in a database, not in the app. That is what lets Kubernetes replace or multiply API pods freely.
    • Liveness asks "is it running?" and readiness asks "can it serve?". Keep them separate.
    • /api/info is your window into deployments: it will show a new version each time you release.

    04

    Put both apps in containers

    Goal: docker compose up --build serves the whole app at http://localhost:8080.

    Why this step

    Kubernetes doesn't run .NET or Angular code. It only runs containers, so each app has to become an image first. An image is a frozen copy of your compiled app plus the exact runtime it needs. That gives you:

    • Build once, run anywhere. The image you test is the image that ships.
    • Isolation. Each container has its own files and network.
    • Speed. Containers start in seconds, so Kubernetes can replace them freely.

    A Dockerfile is the recipe for an image: a list of instructions Docker runs from top to bottom.

    The API image

    Where the file goes. A Dockerfile is a plain text file named exactly Dockerfile: capital D, no extension. It lives in the src/api folder, next to Todo.Api.csproj, because that folder is what Docker builds from. Your project should end up looking like this:

    How to create it. In a Git Bash terminal in infra-setup/, run code src/api/Dockerfile. That creates the empty file and opens it in VS Code. Paste the contents below and save with Ctrl+S. Or in VS Code's Explorer, right-click the src/api folder, choose New File and type Dockerfile. Avoid Notepad: it quietly saves Dockerfile.txt, which Docker will not find. Check with ls src/api.

    Line by line: the API Dockerfile
    FROM … sdk:10.0 AS build
    Stage 1 starts from Microsoft's image that contains the full .NET SDK, and names the stage build.
    WORKDIR /src
    Creates the folder /src inside the image and moves into it, like cd.
    COPY *.csproj then RUN dotnet restore
    Copies only the project file and downloads NuGet packages before copying your code. Docker saves the result of each line as a layer and reuses it if nothing above changed. So when you only edit C#, the slow restore is skipped.
    COPY . .
    Copies the rest of your source in.
    RUN dotnet publish … -o /app
    Compiles a Release build into /app.
    FROM … aspnet:10.0-noble-chiseled
    Stage 2 starts again from a tiny image with only the ASP.NET runtime. "Chiseled" means no shell and no package manager, and it runs as a normal user rather than root. Everything from stage 1 is thrown away except what the next line copies.
    COPY --from=build /app .
    Takes just the compiled output from stage 1.
    EXPOSE 8080
    A note saying which port the app listens on. .NET container images listen on 8080 by default.
    ENTRYPOINT
    The command that runs when a container starts.

    What you just learned

    • Multi-stage builds: big images compile, small images run. Smaller images download faster and give an attacker less to work with.

    05

    Create a Kubernetes cluster

    Goal: kubectl get nodes lists one node with status Ready, and the NGINX Gateway Fabric pod is running.

    Why this step

    Think of deploying to a few IIS servers. Someone has to choose which server runs what, notice a crashed app and restart it, and roll out a new version one server at a time. Kubernetes does all of that for you.

    You give it a description of what you want. It then loops forever: compare what's running with what you asked for, and fix any difference. That loop is called reconciliation, and it's the most important idea in this whole tutorial. You'll see it again in Argo CD.

    kind ("Kubernetes in Docker") runs a real Kubernetes cluster inside a Docker container on your PC. It's free, starts in about a minute, and is easy to throw away. What you learn on it applies to cloud clusters too.

    Here is that loop in action. The diagram plays by itself; use the buttons to pause it or step through:

    Explained: how your browser gets into the cluster

    The problem: boxes inside boxes. Your app will run three layers deep, and each layer has its own private network:

    • Your PC. Your browser runs here. localhost means "this PC".
    • The node. A node is a machine that runs containers for Kubernetes. In kind, that machine is one Docker container, named todo-control-plane.
    • The pods. A pod is one running copy of your app. The pods run inside the node.

    By default each layer is closed to the one outside it. Your browser can't reach the node, and it certainly can't reach a pod inside the node. To get a request from the browser to a pod, you have to open one door per layer.

    What a port is. A port is a numbered door on a machine. localhost:8080 means "door 8080 on this PC". A request only gets in if something is listening behind that door.

    The route a request takes. When everything is set up (after step 7), a request for http://localhost:8080 goes through two doors, as the animated diagram above this section shows.

    Door 1 is this file. You have already opened a door like it. In step 4 you ran docker run -p 5080:8080, which meant "port 5080 on my PC leads to port 8080 in the container". The two lines in this file say the same thing in kind's words:

    hostPort: 8080
    The door on your PC. "Host" means the machine Docker runs on.
    containerPort: 31437
    The door on the node, which is a container.

    kind passes this to Docker when it creates the node. Docker fixes a container's published ports at the moment the container is created, and can't add one later. That is why this must be in the config file before you create the cluster. If you forget it, you have to delete the cluster and create it again.

    Door 2 comes later, from Kubernetes. Being on the node isn't enough, because the pods are one layer further in. Kubernetes opens that door with a NodePort Service: "open this port number on every node, and send whatever arrives there to these pods". You create it in the next part, when you install the gateway with nodePorts=[{"port":31437, …}].

    Why 31437? Kubernetes only allows node ports between 30000 and 32767. 31437 is simply a number picked from that range. What matters is that both doors use the same number: this file sends traffic to 31437 on the node, and the NodePort Service listens on 31437 on the node. If the numbers differ, the request arrives at a door with nothing behind it.

    Why the tutorial says "load balancer". Every cluster has this problem: traffic starts outside and must reach a node. Only the solution differs.

    On your PC (kind)In the cloud (AWS, Azure)
    What a node isA Docker containerA virtual machine in a private network
    How traffic reaches a nodeThe port mapping in this fileA load balancer the cloud creates for you, with a public address
    How you ask for itextraPortMappings in kind-config.yamlA Service of type LoadBalancer
    Address you openlocalhost:8080A public IP or host name

    So the port mapping is a stand-in for the load balancer. Everything behind it (the gateway, the routes, the Services, the pods) works the same way on your PC as in the cloud.

    See it for yourself. After you create the cluster below, list the running containers:

    The PORTS column includes 0.0.0.0:8080->31437/tcp. That is door 1. If you open http://localhost:8080 at this point, the browser can't connect, because door 2 doesn't exist yet and nothing is listening on 31437. That is expected until you deploy the app in step 7.

    Two different 8080s. Your UI and API containers also listen on port 8080, inside their pods. That has nothing to do with port 8080 on your PC. The numbers are the same by coincidence, and they are doors on different machines.

    Port 8080 on your PC must be free, so run docker compose down in infra/ first if step 4 is still running. kind starts the cluster as a container in Docker Desktop.

    A node is a machine that runs your containers. Here the "machine" is one Docker container. A cloud cluster has several real ones.

    kind also wrote the cluster's address and login into ~/.kube/config. That's how kubectl and helm know where to send commands.

    Add the front door: NGINX Gateway Fabric

    Why this part

    A Service gives pods a stable name, but only inside the cluster. In production, traffic from the internet arrives at one entry point, usually a load balancer in front of a reverse proxy, which looks at the host name and path and sends each request to the right service. It is also where HTTPS certificates and limits are handled.

    In Kubernetes you describe that with objects, and a controller keeps a real proxy configured to match (the reconciliation loop again). There are two ways to describe it: the older Ingress API and the newer Gateway API. The well-known ingress-nginx project was retired in March 2026 and gets no more security fixes, so a new setup shouldn't use it. NGINX Gateway Fabric is the Gateway API controller from the NGINX team. The proxy it runs is nginx, the same program that serves your UI.

    Install NGINX Gateway Fabric into the cluster. You do this once per cluster, in three commands: add the Gateway API object types, install the controller with Helm, then wait until it is running.

    Line by line: the install commands
    kubectl kustomize "<url>" | kubectl apply -f -
    Builds the YAML for the Gateway API object types from the NGINX repository (kustomize is built into kubectl) and sends it to the cluster. ?ref=v2.7.2 pins the version so the steps stay reproducible.
    helm install ngf oci://…
    Helm can install a chart straight from a registry. ngf is the release name, and --version pins the chart.
    nginx.service.type=NodePort
    The proxy that the controller creates is reached through a NodePort Service: a fixed port opened on every node. On a cloud cluster you would leave the default, LoadBalancer, and AWS or Azure would create a real load balancer.
    nodePorts=[{"port":31437,"listenerPort":80}]
    "The Gateway's port 80 listener uses node port 31437." That number must equal containerPort in kind-config.yaml, which is what links your browser to the proxy.
    kubectl … wait
    Blocks until the controller's Deployment reports it is available.

    Confirm the install worked. The controller's pod should be running, and the cluster should list a GatewayClass called nginx:

    That installs the controller only. There is no proxy yet: it creates one the moment a Gateway object appears, which happens when you deploy the chart in the next two steps. This needs Kubernetes 1.32 or newer, which current kind versions provide.

    What you just learned

    • A cluster has a control plane (the brain: it stores what you want and makes it happen) and nodes (where containers run). In kind, both live in one container.
    • kubectl is how you talk to the control plane.
    • Three Gateway API objects split the work: a GatewayClass says which controller is in charge, a Gateway is the front door, and HTTPRoutes say where each path goes. A platform team usually owns the first two and app teams add routes.
    06

    Write the Helm chart

    Goal: helm lint charts/todo ends with 1 chart(s) linted, 0 chart(s) failed. That means the chart has no errors. (A line starting with [INFO] is only a hint. Ignore it.)

    Why this step

    You tell Kubernetes what you want with YAML files called manifests. You could write them by hand, but dev, test and production need almost the same YAML with a few values changed, and copies drift apart.

    Helm fixes that. A chart is a folder of YAML templates with {{ placeholders }}, plus a values.yaml file that fills them in. Think of it as a NuGet package for a deployment.

    For each app you need two Kubernetes objects:

    • a Deployment: what to run and how many copies;
    • a Service: a stable name for reaching those copies.

    You'll build the chart by hand, one file at a time. First create its folder. Helm expects the templates in a subfolder called templates:

    Every chart starts with Chart.yaml, which gives the chart its name and version:

    In the next file, replace YOUR-DOCKERHUB-USER with your Docker Hub user name in lowercase. Image names can't contain capital letters. (Don't have an account yet? Create one free at hub.docker.com; step 9 needs it.)

    Now the first template: the API's Deployment and Service. Each {{ … }} placeholder is filled in from values.yaml:

    Line by line: the Deployment and Service
    kind
    Which type of object this is.
    metadata.name
    The object's name.
    replicas
    How many identical pods to keep running. Filled in from values.yaml.
    labels and selector
    Labels are name tags on pods. A selector says "the pods with this tag are mine". The Deployment uses it to count its pods; the Service uses it to find where to send traffic.
    template
    The blueprint for each pod. Change anything in it (like the image tag) and Kubernetes does a rolling update: start a new pod, wait until it's ready, stop an old one.
    image
    The full image name, built from registry and tag.
    env
    Environment variables, the same as -e on docker run. This is where APP_VERSION and the database connection come from. $(DB_PASSWORD) is replaced by the variable defined just above it, so the password stays in one place.
    secretKeyRef
    "Take this value from the Secret todo-db" instead of writing it in the Deployment. The password then lives in one object.
    readinessProbe
    Kubernetes calls /readyz and only sends traffic to the pod once it answers, which here means once the database is reachable. This is why a rolling update has no downtime.
    livenessProbe
    If /healthz (which ignores the database on purpose) keeps failing, Kubernetes restarts the container.
    resources.requests
    How much CPU and memory to reserve. 50m means 5% of one CPU core.
    resources.limits
    The ceiling. A container that goes over its memory limit is stopped and restarted.
    ---
    Separates two YAML documents in one file.
    Service port / targetPort
    port is what callers use; targetPort is the container's port.

    The Deployment keeps the pods running. The Service is how anything else reaches them. This diagram shows what the Service does when a request arrives, and when a pod is replaced:

    The UI gets the same pair of objects, a Deployment and a Service:

    The database

    Postgres needs three things the apps didn't: a password, a disk that survives restarts, and a pod with a stable identity. One more file covers all three:

    Line by line: the database
    kind: Secret
    A place for a password, kept apart from ordinary settings. Both Postgres and the API read it with secretKeyRef, so the password is written down once.
    clusterIP: None
    A headless Service. It has no virtual address of its own: the name todo-db resolves straight to the database pod. With only one database pod, that is all you need.
    kind: StatefulSet
    A Deployment for programs that keep data. Its pod has a fixed name (todo-db-0) and always gets the same disk back. A Deployment's pods are interchangeable and disposable; a database is neither.
    replicas: 1
    One database. A real production setup runs copies that replicate each other, which is a topic of its own (and a good reason to use a managed database).
    PGDATA
    A sub-folder of the disk. A new disk contains a lost+found folder at its top, and Postgres refuses to start in a folder that isn't empty.
    readinessProbe with exec
    Instead of calling a web address, Kubernetes runs a command inside the container. pg_isready exits successfully once Postgres accepts connections.
    volumeMounts
    Where the disk appears inside the container. Postgres writes its files there.
    volumeClaimTemplates
    "Give each pod its own disk of this size." Kubernetes creates a PersistentVolumeClaim (a request for a disk) and the cluster supplies the disk. kind includes a provisioner that does this automatically; cloud clusters provision real cloud disks.

    The password is in Git. That is fine for a practice database on your own PC, but never do it for real data: anyone who can read the repo can read the password, and a Kubernetes Secret is only base64-encoded, not encrypted. Real teams keep secrets out of Git with tools such as Sealed Secrets, External Secrets or SOPS, or use a managed database from their cloud. Part 4 (Secure the Road) moves this password into a secret store and changes it.

    The front door

    One last file tells the gateway what to do with traffic:

    Line by line: the Gateway and the route
    kind: Gateway
    Asks for a front door. When Kubernetes sees it, NGINX Gateway Fabric starts an nginx pod (named todo-nginx-…) in the same namespace and gives it a Service.
    gatewayClassName: nginx
    Which controller should handle this Gateway. nginx is the class the controller registered in step 5.
    listeners
    The ports and protocols the front door accepts. Port 80 is the listenerPort you mapped in step 5. HTTPS would be a second listener with a certificate.
    kind: HTTPRoute and parentRefs
    A set of routing rules, attached to the Gateway by name. Separate objects let different teams manage their own routes behind one shared front door.
    PathPrefix /api
    Requests whose path starts with /api go straight to the todo-api Service on port 8080. This is the same split the UI's own nginx makes on your PC; in the cluster the gateway does it first.
    PathPrefix /
    Everything else goes to the todo-ui Service. The most specific prefix wins, so /api beats /.

    What you just learned

    • Each app needs a Deployment and a Service, tied together by labels. A database needs a StatefulSet and a volume claim instead, so its data survives.
    • A Gateway plus an HTTPRoute is the front door: one address, and rules for which path goes to which Service.
    • The templates never change between releases. Only tag in values.yaml does. Remember that line: the pipeline will edit it for you.

    09

    Build images with GitHub Actions

    Goal: a push to main builds both images, stores them in Docker Hub, and writes the new tag into values.yaml.

    Why this step

    In step 7 you built the images on your own PC. On a team that causes trouble: builds differ from laptop to laptop, they can include changes nobody committed, and releases wait for one person.

    A CI pipeline moves the build to a clean server that runs the same steps every time. GitHub Actions is GitHub's built-in pipeline. You describe it in a YAML file in the repo, and GitHub runs it on a fresh virtual machine called a runner.

    The pipeline needs somewhere to put the images. Docker Hub is the default public registry: a free account can hold any number of public repositories, which is all this tutorial needs. The cluster can pull public images without a password.

    Set up Docker Hub and GitHub (once)

    The pipeline logs in to Docker Hub with an access token, which is a password you can revoke and limit. It will be stored as a GitHub secret, so it never appears in your code or in the logs.

    1. On hub.docker.com, click Repositories → Create a repository. Create todo-api and then todo-ui, both with visibility Public. (Pushing to a repository that doesn't exist creates it too, but with your account's default visibility, so create them yourself to be sure.)
    2. Click your avatar, then Account settings → Personal access tokens → Generate new token. Name it github-actions, choose Read & Write, and copy the token. Docker Hub shows it only once.
    3. In your GitHub repo open Settings → Secrets and variables → Actions → New repository secret. Add DOCKERHUB_USERNAME (your Docker Hub user name) and DOCKERHUB_TOKEN (the token).

    The steps in the workflow are the same commands you've already typed by hand:

    Line by line: the workflow
    on: push
    When to run: on a push to main, but only if files in src/api/, src/ui/ or this workflow changed. A change to the chart alone doesn't need new images.
    permissions
    What the pipeline's temporary GitHub login may do. It only needs to write to the repo, to commit the new tag. Give a pipeline only what it needs.
    jobs / runs-on
    A job is a list of steps that run on one runner, here a fresh Ubuntu machine with Docker and Git installed.
    uses: actions/checkout@v6
    A ready-made step that downloads your repo onto the runner. uses runs someone's packaged action; run runs shell commands.
    env and REGISTRY=…
    Reads your Docker Hub user name from the secret and builds docker.io/your-user. The ,, turns the name into lowercase. Writing to $GITHUB_ENV makes the variable available to later steps.
    TAG=${GITHUB_SHA::7}
    The first 7 characters of the commit ID, e.g. a1b2c3d. Every image can be traced back to the exact code it was built from.
    docker build
    The same command you ran in step 7, with the registry in the name.
    secrets.DOCKERHUB_TOKEN
    The token you stored. GitHub hides its value in the logs and never shows it again. It is passed in through an environment variable, rather than pasted into the command, so it can't be mistaken for part of the script.
    docker push
    Uploads the images to Docker Hub.
    sed -i …
    Rewrites the tag: line in values.yaml to the new tag. The if git diff --quiet line stops the step cleanly when nothing changed, for example when you re-run a finished build.
    git commit … git push
    Commits that one-line change back to main as "Deploy a1b2c3d". git pull --rebase first picks up anything pushed in the meantime. This push uses GitHub's automatic token, and pushes made with it don't start another run, so there's no loop.

    Commit the workflow file and push it. That push starts the first pipeline run:

    Open your repo on GitHub and click the Actions tab. Click the run to watch each step. It takes 2–3 minutes. A green tick means it worked.

    When it's done, look at the repo's commits: there's a new one called Deploy … made by github-actions[bot]. Fetch it:

    Run git pull before you start any new work. The pipeline adds a commit to main after every build. If you forget, your next push is rejected until you pull.

    Check the images arrived

    Open https://hub.docker.com/u/<your-user>. Both repositories should show a Public badge and a tag that matches the commit ID. Public matters: the cluster has no Docker Hub login, so it can only pull public images.

    Real teams keep images private and give the cluster a login (an image pull secret). Public is fine for a practice app with nothing secret in it. Docker Hub also limits anonymous downloads to 100 per 6 hours per network address, which this tutorial stays far below.

    What you just learned

    • A pipeline is your own commands, written down and run by a server on every change.
    • Tagging images with the commit ID links what's running to the code that built it. Never deploy a tag like latest: you can't tell what's in it.
    • The pipeline never touches the cluster. It only changes one line in Git. The next two steps explain why that's the clever part.

    Roll it back

    Goal: the site shows the old heading again, by undoing one commit.

    Why this step

    Sooner or later a release breaks something. When the cluster follows Git, rolling back is a Git operation. The old images are still in Docker Hub, so you only need to point the chart back at the old tag. No rebuild, so it's fast.

    Undo the latest deployment by reverting the pipeline's Deploy … commit, the one that changed the tag in values.yaml. Pushing the revert is all it takes:

    git revert adds a new commit that undoes an earlier one. Here it puts the previous tag back in values.yaml. Only the chart changed, so the pipeline doesn't run. Click Refresh in Argo CD and reload: the heading is Todo again.

    The code on main still has the new heading. You rolled back what's running, not the source. The next build would ship the heading again. So after the emergency is over, fix or revert the code too. On GitHub, the Revert button on the merged pull request does that.

    What you just learned

    • Rollback is a revert. The Git history shows the release and the rollback, with who and when.
    • Because every image has its own tag and is never overwritten, the old version is always still there to go back to.

    Ports and addresses on one map

    Goal: you can say which port number belongs to which layer, which kind of address you are looking at, and which way in is right for which job.

    Why this step

    You have now met eight port numbers (8080, 31437, 80, 5432, 5433, 5080, 8443, 443) and four kinds of address. Most Kubernetes confusion is one of them in the wrong place. This map puts them all in one picture. Play it with the arrows, or let it run.

    Which port number belongs where

    The same number often appears twice. What matters is which layer listens on it, and where you set it:

    PortWhich layer listensWhere you set it
    8080 (first)Your PC (hostPort): the door you open in a browserkind-config.yaml
    31437The node (containerPort in the kind file, NodePort in Kubernetes). Must be 30000–32767kind-config.yaml and nginx.service.nodePorts in step 5. The two must match
    80The gateway's listener, and the todo-ui Service portgateway.yaml, the UI Service
    8080 (Service)The todo-api Service port: what callers useThe API Service, and backendRefs in the route
    8080 (container)The apps inside the pods (containerPort, targetPort)The Dockerfiles (EXPOSE 8080), the Deployments
    5432PostgreSQL, in its pod and on its Service. This is Postgres's own defaultNothing to set: it is Postgres's default
    5080, 5433, 8443Your PC only: the local end of docker run -p or port-forward. You pick any free numberOn the command line

    One rule reads every one of these: in a:b the left number is where you stand and the right number is where it goes. -p 5080:8080, port-forward 5433:5432 and 8443:443 all work this way. In a Service, port: 80 is what callers use and targetPort: 8080 is what arrives at the pod.

    The four kinds of address

    AddressWhat it isGood forBad for
    localhost / 127.0.0.1"This machine", whichever machine is askingYour browser, and port-forward: only you can use itAnything inside a container. localhost:5432 in an API pod means the API pod itself, not the database. Use todo-db

    Which way in for which job

    Way inGood forBad for
    kubectl port-forwardLooking at one thing: the database in pgAdmin, the Argo CD page. Needs no change to the cluster and only reaches your PCServing users.     NodePortThe lab's front door on kind: one fixed number, no cloud neededReal clusters. It opens the port on every node, the 30000–32767 numbers are awkward, and a load balancer does the job better

    What you just learned

    • The same number can be different doors: the Service port, the pod's targetPort and the host's port are separate things.
    • In a:b, a is where you stand and b is where it goes.
    • Pods come and go, so apps call Service names. IP addresses are for reading, not for writing into files.
    • port-forward is a debugging tool. Real traffic goes through a gateway or load balancer.

    Where to go next

    You've built the smallest complete version of a delivery platform. Each of these makes it more like a real one:

    • Add tests to the pipeline. Create a test project and add a dotnet test step before the build. A failing test should stop the release.
    • Scan the images. Add a step that runs Trivy and fails on serious known vulnerabilities.
    • Check pull requests. Run the build (without the push) on every pull request, so problems show up before the merge.
    • Add a second environment. Make values-dev.yaml and values-prod.yaml with one Argo CD Application each, and promote a tag from one to the other.
    • Add HTTPS. Install cert-manager, add a second listener on port 443 to the Gateway with a certificate, and redirect HTTP to HTTPS. Give the route a host name instead of matching everything.
    • Protect the data. Move the password out of Git with Sealed Secrets, External Secrets or SOPS. Back up the database (for example with pg_dump on a schedule), or switch to a managed database such as Amazon RDS.
    • Go to the cloud. The Todo on EKS tutorial runs the same app on Amazon EKS with a real load balancer. It costs money, so read its cost warning first.
