    Glossary

    Short definitions, in the standards' own meaning. Each term gets its "What is it?" box where it is first used.

    Authentication
    Proving who or what is making a request.
    Authorization
    Deciding what an authenticated caller may do.
    Credential
    Something used to prove an identity: a password, a key, a token, a certificate.
    Identity provider
    The service that signs users in and tells other applications who they are. OpenID Connect calls it the OpenID Provider.
    Resource owner, client, authorization server, resource server
    The four OAuth roles: the one who can grant access (often you), the app that wants access, the server that issues access tokens, and the server that holds the protected data.
    Token
    A string an app presents to show what it is allowed to do, instead of presenting a password.
    Bearer token
    A token that any party in possession of it can use, in any way another holder could. Whoever holds it can use it. It travels in a header such as Authorization: Bearer ….
    JWT
    JSON Web Token: a compact, URL-safe way to carry claims between two parties, as a JSON object that can be signed or encrypted. Its three parts are joined with dots: header.payload.signature.
    PKCE
    Proof Key for Code Exchange: a technique that protects the authorization code flow against an intercepted code.
    RBAC
    Role-based access control: permissions are granted to roles, and people are given roles.
    Single sign-on
    One sign-in that lets you use several applications.
    TLS
    Transport Layer Security: the protocol that lets two programs talk over the Internet in a way designed to prevent eavesdropping, tampering and message forgery.
    HTTPS
    HTTP carried over a TLS connection that has been secured for it. Its addresses start with https://.
    Certificate
    A signed document that ties a public key to a name. Internet certificates follow the X.509 format.
    Certificate authority
    An organisation that others trust to create and sign certificates.
    01

    Who are you, and what may you do?

    Easy

    Goal: tell authentication from authorization every time, and know when a server should answer 401, 403 or 404.

    Why this step

    Every other lesson builds on two questions a system asks about every request: who is this? and may they do that? People mix the two up, and most real security bugs live in the gap between them. Get these two words straight first.

    What is it? Authentication

    What it is
    Proving who or what is making a request. NIST describes it as the process of determining the validity of the authenticators used to claim a digital identity.
    The problem it solves
    A server cannot see who is on the other end of a connection. Anyone can type any name. Authentication is how a name is backed by proof.
    Everyday comparison
    Showing your passport at a border. The officer does not ask what you may do yet. They only check that you are who you say you are.
    What it is not
    It does not say what you are allowed to do. A valid passport does not let you into every room.
    Where you meet it
    The login page of the Todo app, a password, a passkey, a token an API checks, a certificate a server shows.

    What is it? Authorization

    What it is
    Deciding what an already identified caller may do: which resources, and which actions on them.
    The problem it solves
    Knowing who someone is is not enough. Alice is Alice, but she may read her own todos and not Bob's.
    Everyday comparison
    The key card that opens your office but not the server room. The card reader knows the card is real (authentication) and then checks which doors it opens (authorization).
    What it is not
    It does not prove identity. It assumes authentication already happened, and it is only as good as that.
    Where you meet it
    Roles such as admin, "only the owner may delete", a 403 page, Kubernetes RBAC, a cloud permission policy.

    The vocabulary

    Identity
    Who or what someone claims to be: a user, an app, a service.
    Credential
    The thing used to back that claim: a password, a key, a token, a certificate.
    Factor
    A category of proof. NIST uses the familiar labels: a password is something you know, a code from a look-up list or a device is something you have, and a biometric match can serve as something you are. Using two different categories is multi-factor.
    Caller, client
    Whoever sends the request: a browser, a mobile app, another service.
    Resource
    What the request wants: a todo, a page, an API endpoint.

    Two gates, in this order

    A request goes through two checks, and the order matters. Gate 1 asks who you are. Only if it can answer does gate 2 ask whether you may do this. Watch what each gate answers:

    401, 403 and 404

    HTTP has words for each outcome. Their exact meanings come from RFC 9110, and they are often used wrongly:

    CodeMeansUse it when
    401 UnauthorizedThe request lacks valid authentication credentials for the resource. The server must send a WWW-Authenticate header with at least one challenge.There is no token, or it is expired, malformed or not signed by someone you trust.
    403 ForbiddenThe server understood the request and refuses to fulfil it. If credentials were given, they are not enough, and sending the same ones again will not help.The caller is known and is not permitted.
    404 Not FoundNo representation was found, or the server is not willing to disclose that one exists.Someone asks for another user's todo. Answering 404 instead of 403 does not reveal that it exists.

    The name Unauthorized for 401 is misleading: it is about authentication. Remember it as "I do not know who you are". The 403 is "I know who you are, and no".

    Line by line: a 401 on the wire
    GET /api/todos HTTP/1.1
    The request has no Authorization header, so there is nothing to authenticate.
    HTTP/1.1 401 Unauthorized
    The status line. The server stops here.
    WWW-Authenticate: Bearer realm="todo"
    Required by RFC 9110 on a 401: it names the way to authenticate. Bearer means "send a token in the Authorization header".

    Practice

    What you just learned

    • Authentication proves who you are. Authorization decides what you may do. The first must come before the second.
    • 401 means no valid credentials. 403 means known, and not allowed. 404 can also be used to hide that something exists.
    • A password is "something you know". Two different kinds of proof make a multi-factor sign-in.
    02

    The cryptography you need

    Easy

    Goal: choose between a hash, a MAC, encryption and a signature, and know that base64 is not secrecy.

    Why this step

    Tokens, certificates, cookies and TLS are all built from four small tools. You do not need the mathematics. You need to know what each tool promises, and what it does not promise, because most mistakes are using the right-sounding tool for the wrong job.

    This lesson builds on step 01. It asks nothing else of you.

    What is it? A hash

    What it is
    A function that turns any input into a fixed-size fingerprint. The same input always gives the same fingerprint, and a tiny change gives a completely different one.
    The problem it solves
    Checking that something is unchanged, without comparing the whole thing.
    Everyday comparison
    A tamper seal on a jar. It does not hide what is inside. It shows that someone opened it.
    What it is not
    Not encryption: you cannot get the input back. Not proof of who made it: anyone can compute a hash.
    Where you meet it
    File checksums, Git commit ids, password storage (with a slow, salted hash, step 03), the SHA-256 inside signatures.

    What is it? A MAC (HMAC)

    What it is
    A hash that also mixes in a shared secret key. HMAC, defined in RFC 2104, builds one from an ordinary hash.
    The problem it solves
    Proving that a message came from someone who knows the secret, and that it was not changed on the way.
    Everyday comparison
    A tamper seal that only you and your friend know how to make.
    What it is not
    Not a signature: both sides hold the same secret, so either could have made it, and you cannot prove to a third party which did.
    Where you meet it
    Webhook signatures, the signature of an HS256 token, cookies signed by a framework.

    What is it? Encryption

    What it is
    Scrambling data so that only someone with the right key can read it, and unscrambling it again with that key.
    The problem it solves
    Keeping data secret while it is stored or travels.
    Everyday comparison
    A locked box. Whoever has the key can open it.
    What it is not
    Not a guarantee that nobody changed it, unless the scheme also authenticates (modern ones do). Not the same as a hash: encryption can be reversed.
    Where you meet it
    HTTPS (step 04), encrypted disks and backups, encrypted tokens.

    What is it? A digital signature

    What it is
    A value made from a message and a private key, which anyone can check with the matching public key.
    The problem it solves
    Letting many parties verify who made something and that it is unchanged, without sharing any secret with them.
    Everyday comparison
    A wax seal pressed with a ring only one person owns, whose pattern everyone knows.
    What it is not
    Not encryption: the message is still readable. The signature only shows who made it and that it is intact.
    Where you meet it
    Certificates (step 05), JWTs signed with RS256 or ES256 (step 09), signed container images, Git commit signatures.

    How a signature works

    Encodings are not secrets

    Base64 turns bytes into text made only of letters, digits and a few symbols, so they can travel in places that only allow text. Base64url is the same idea with - and _ in place of + and /, so it is safe in a web address (RFC 4648, section 5). Anyone can reverse it with no key. A JWT is base64url text, and that is why you can read what is inside one.

    Line by line: base64url
    Text → bytes
    The text hi? is the three bytes 0x68 0x69 0x3F.
    Bytes → 6-bit groups
    Three bytes are 24 bits, which split into four groups of 6 bits. Each 6-bit value (0 to 63) is one character from a 64-character alphabet.
    The alphabet
    A-Z a-z 0-9 and then - and _ for base64url. Plain base64 uses + and /, which have special meanings in addresses.
    Padding
    Plain base64 pads with =. In JWTs the padding is left off.

    What you must never do

    • Do not invent your own algorithm. Use the standard ones in well-reviewed libraries.
    • Do not use MD5 or SHA-1 where security matters. RFC 6151 updates the security considerations for MD5, and researchers produced the first collision for full SHA-1 in 2017. Use SHA-256 or better.
    • Do not treat encoding as protection. Base64 hides nothing.
    • Do not store passwords with a plain hash. Step 03 shows what to use.

    Practice

    What you just learned

    • A hash is a fingerprint. A MAC is a fingerprint with a shared secret. Encryption hides data. A signature proves who made something, checked with a public key.
    • You sign with the private key and verify with the public key. Never the other way round.
    • Base64url is an encoding, not protection: anyone can read it.
    03

    Passwords, sessions and cookies

    Intermediate

    Goal: explain a classic login from end to end, store passwords correctly, set a session cookie's flags, and say what CSRF is and what stops it.

    Why this step

    Most websites still sign you in with a password and then remember you with a cookie. Even when you later move to tokens and OpenID Connect, a cookie is what keeps the browser signed in to your own app. The mistakes here (a weak password hash, a cookie any script can read, a forgeable request) are some of the most common in the world.

    This lesson builds on steps 01 and 02: the two gates, and what a hash is.

    What is it? A session

    What it is
    A record the server keeps, saying "this browser is signed in as Alice, since 10:02". A random session id names the record.
    The problem it solves
    HTTP forgets everything between requests. Without a session you would have to send your password with every click.
    Everyday comparison
    A cloakroom ticket. The ticket number means nothing alone. The attendant's list says whose coat it is.
    What it is not
    Not the login itself. The login happens once. The session is what is left afterwards, and whoever holds the id is that user until it ends.
    Where you meet it
    Almost every website with a login, including the sign-in the Todo app will get in level 6.

    What is it? A cookie

    What it is
    A small named value a server asks the browser to store and send back on later requests to the same place. The server sets it with a Set-Cookie header (RFC 6265).
    The problem it solves
    It is how the browser carries the session id without the page having to do anything.
    Everyday comparison
    A sticker the shop puts on your jacket, which staff read each time you come back.
    What it is not
    Not a place for secrets in readable form, and not private: the browser attaches it automatically, even on requests another site triggers. That is exactly what CSRF abuses.
    Where you meet it
    Login sessions, language choices, shopping carts, "remember me".

    A classic login, end to end

    Storing passwords

    The server must be able to check a password but should never be able to read it back. So it stores a hash, made with a slow, salted password hashing function:

    • Salted: a random value is mixed in for each password, so two users with the same password get different hashes and precomputed tables are useless.
    • Slow on purpose: an ordinary hash such as SHA-256 is built to be fast, which helps an attacker try billions of guesses. A password hash has a cost setting that makes each guess expensive.

    OWASP's Password Storage Cheat Sheet ranks the choices. Argon2id is the first choice (at least 19 MiB of memory, 2 iterations, 1 degree of parallelism). scrypt is next (N=217, r=8, p=1). bcrypt is for legacy systems (work factor 10 or more, and a 72-byte input limit). PBKDF2 is for when FIPS-140 compliance is required (600,000 iterations with HMAC-SHA-256, 220,000 with HMAC-SHA-512).

    In ASP.NET Core Identity, the default password hasher uses PBKDF2 with HMAC-SHA-512, a 128-bit salt, a 256-bit subkey and 100,000 iterations. That is below OWASP's number for HMAC-SHA-512, and it can be raised with PasswordHasherOptions.IterationCount. The hash is stored with its own settings in front, so old hashes still verify and can be upgraded when the user next signs in.

    Line by line: what an ASP.NET Core Identity password hash contains
    Byte 0: 0x01
    The format marker, "version 3".
    Next 4 bytes
    Which pseudo-random function was used (HMAC-SHA-512 by default).
    Next 4 bytes
    The iteration count (100,000 by default).
    Next 4 bytes
    The salt length in bytes (16 by default, which is 128 bits).
    Then
    The random salt, and then the 32-byte derived key. All of it is stored base64-encoded in one column.

    What the rules for passwords are today

    NIST's Digital Identity Guidelines (SP 800-63B, revision 4) changed some old habits. Where the password is the only factor it must be at least 15 characters long. Where it is only one part of multi-factor authentication, 8 is the minimum. Systems should accept at least 64 characters. They must not impose composition rules (such as "one capital, one symbol") and must not force periodic changes. They must check new passwords against a blocklist of known-compromised and common passwords, and limit failed attempts.

    Cookie attributes

    The attributes of a cookie decide who can read it and which requests carry it. Change them below and see what the browser does in eight situations:

    AttributeWhat it does
    SecureThe cookie is sent only on https requests (browsers make an exception for localhost).
    HttpOnlyJavaScript cannot read it through document.cookie. The browser still sends it with requests the script makes.
    SameSite=StrictSent only on requests that start on the same site.
    SameSite=LaxAs Strict, plus cross-site top-level navigations that use a safe method such as GET (following a link).
    SameSite=NoneSent on cross-site requests too. Must be used with Secure.
    DomainIf set, the cookie also goes to every subdomain. If left off, it goes only to the host that set it, which is safer.
    PathThe cookie is sent only for addresses under this path.
    Max-Age, ExpiresHow long the browser keeps it. Without either, it is a session cookie and goes when the browser closes.
    __Host- prefixThe browser accepts the cookie only if it also has Secure, no Domain and Path=/. It cannot be overwritten from a subdomain.

    Site is not origin. An origin is scheme, host and port. A site is wider: app.example.com and api.example.com are different origins but the same site. SameSite is about sites. That is why a takeover of a sibling subdomain can still attack a cookie that is SameSite=Strict, and why the __Host- prefix matters.

    Session ids, fixation and logout

    • Random and long. OWASP's session management cheat sheet asks for at least 64 bits of entropy and, for ids you make yourself, at least 128 bits from a cryptographically secure random number generator. Use your framework's, never your own.
    • New id at login. If the id stays the same across login, an attacker who planted a known id before login owns the session after it. This is session fixation. Issue a new id after any change of privilege, and destroy the old one.
    • Expire it. Use an idle timeout (the cheat sheet gives 2 to 5 minutes for high-value applications and 15 to 30 minutes for low-risk ones) and an absolute timeout (for example 4 to 8 hours for an office worker's session).
    • Logout means the server forgets. Deleting the cookie in the browser does not invalidate a copy someone already stole. The server must end the session.

    CSRF: a request the user never meant to make

    What is it? CSRF

    What it is
    Cross-site request forgery: a page on another site makes the user's browser send a request to your site, and the browser attaches the user's cookie automatically.
    The problem it creates
    Your site cannot tell a forged request from one the user chose to make. It sees a valid cookie.
    Everyday comparison
    Someone slips a pre-filled bank form into your hand while you are logged in at the counter, and the clerk accepts it because you are standing there.
    What it is not
    Not cross-site scripting (XSS): the attacker does not run code in your page and cannot read the response. They only cause a request.
    What stops it
    Never change state on GET. Use SameSite cookies as one layer, and a real defence on top: anti-forgery tokens, or a custom request header that a plain cross-site form cannot send, or checking Origin and Sec-Fetch-Site. OWASP calls SameSite a defence in depth that does not replace a proper CSRF defence in most deployments.

    Practice

    What you just learned

    • A login happens once. A session and its cookie carry it afterwards, so protect the cookie as you would the password.
    • Store passwords with a slow, salted function (Argon2id first). Never a fast hash, never encryption.
    • Set Secure, HttpOnly and SameSite, prefer __Host-, issue a new id at login, and end sessions on the server.
    • CSRF abuses the browser attaching cookies by itself. Use SameSite plus a real CSRF defence.

    HTTPS and TLS: the private pipe

    Intermediate

    Goal: describe the TLS 1.3 handshake step by step, read the TLS lines of curl -v and openssl s_client, and say what TLS does not protect.

    Why this step

    Everything else in this module rides on a connection that someone could be watching or changing. TLS is what makes that connection safe enough to carry passwords, cookies and tokens. You will meet it as a padlock, as https://, and as the first cause of "it works on my machine".

    This lesson builds on step 02 (hashes, key pairs, signatures) and step 01 (who are you?). The certificate itself is step 05.

    What is it? TLS

    What it is
    Transport Layer Security: a protocol that lets two programs talk over the Internet in a way designed to prevent eavesdropping, tampering and message forgery (RFC 9846). The current version is TLS 1.3.
    The problem it solves
    A request crosses many machines owned by strangers. Without TLS any of them can read it, change it, or pretend to be the server.
    Everyday comparison
    A sealed armoured van with a guard who checks the receiving office's identity papers before the doors open. Contents, seals and addressee are all protected.
    What it is not
    Not protection once the data arrives: the server sees everything in clear. Not proof that the site is honest, only that you are talking to whoever holds the certificate's key. Not the same as a login.
    Where you meet it
    Every https:// address, database connections, service-to-service calls, email servers.

    What is it? HTTPS

    What it is
    Ordinary HTTP sent through a TLS connection. The https scheme names a server that can set up a TLS connection secured for HTTP (RFC 9110).
    The problem it solves
    The same as TLS, for the web: the page, the cookies and the form data are private and unchanged.
    Everyday comparison
    The letter is the same letter. Only the envelope changed.
    What it is not
    Not a different version of HTTP, and not a guarantee that the page is safe to use.
    Where you meet it
    The address bar, curl https://…, the Secure cookie attribute from step 03.

    What TLS promises, and the versions

    • Confidentiality: nobody on the path can read the data.
    • Integrity: nobody on the path can change it without detection.
    • Authentication of the server (and, optionally, of the client): you know who is at the other end, by their certificate.

    TLS 1.0 and 1.1 are formally deprecated (RFC 8996) and must not be used. TLS 1.2 is still met everywhere. TLS 1.3 is specified in RFC 9846 (July 2026), which replaced RFC 8446 and also obsoletes the TLS 1.2 specification, while keeping a few optional changes that TLS 1.2 implementations can adopt (its section 1.4).

    What changed in 1.3, in the RFC's own list (section 1.3): only modern encryption (AEAD) remains; every key exchange now provides forward secrecy, because static RSA and Diffie-Hellman suites were removed; all handshake messages after the ServerHello are encrypted; the key derivation was redesigned around HKDF; and the handshake got shorter.

    The handshake

    Before any HTTP is sent, the two sides agree on keys. Follow the messages of RFC 9846's full handshake, in order:

    In a plain sentence: both sides do a key exchange in the open (using key shares, so nobody who watches can compute the secret), the server proves it owns the certificate by signing the conversation, and everything after that is encrypted and checked.

    Line by line: what you see in openssl s_client
    Protocol: TLSv1.3
    The version that was negotiated.
    Cipher is TLS_AES_256_GCM_SHA384
    A TLS 1.3 cipher suite names only the record encryption (AES-256 in GCM mode) and the hash used for key derivation (SHA-384). RFC 9846 requires TLS_AES_128_GCM_SHA256 and recommends TLS_AES_256_GCM_SHA384 and TLS_CHACHA20_POLY1305_SHA256.
    Negotiated TLS1.3 group: X25519MLKEM768
    The key exchange used a hybrid: X25519 (classical) combined with ML-KEM-768 (post-quantum), so a future quantum computer cannot read recorded traffic. RFC 10024 (August 2026) defines this group. Your curl and OpenSSL print it if both sides support it.
    Peer signature type: ecdsa_secp256r1_sha256
    How the server signed CertificateVerify: ECDSA on curve P-256 with SHA-256.
    Verify return code: 0 (ok)
    The certificate chain was checked against the trust store and passed. Other codes name the failure (step 05).

    Details that matter

    • Forward secrecy. The keys come from a fresh key exchange per connection, so stealing the server's long-term private key later does not unlock recorded traffic.
    • Session resumption and 0-RTT. A client can resume a past session and even send data in the first flight ("early data"). That data can be replayed by an attacker, so it is only safe for requests that change nothing. RFC 9846 has a whole section on this (section 8).
    • The server name is visible. server_name (SNI) travels in clear in the ClientHello, so anyone on the path learns which site you visit, even though the content is encrypted. Encrypted Client Hello (RFC 9849, March 2026) encrypts the ClientHello under a key the server publishes.
    • HSTS. A server can tell browsers "only ever use HTTPS for this site" with Strict-Transport-Security: max-age=… (RFC 6797), so a first plain-HTTP request cannot be downgraded.
    • Where TLS ends. In the Todo platform the gateway terminates TLS and talks plain HTTP to the pods behind it unless you add more. TLS protects the part of the path it covers, and no more.

    Practice

    What you just learned

    • TLS gives confidentiality, integrity and server authentication. HTTPS is HTTP over TLS.
    • The handshake exchanges key shares, then the server proves itself with a certificate and a signature. After the ServerHello everything is encrypted.
    • TLS 1.3 gives forward secrecy on every connection. The server name is still visible unless Encrypted Client Hello is used.

    Certificates: tying a key to a name

    Intermediate

    Goal: read any certificate, explain the chain of trust, and diagnose the usual certificate errors.

    Why this step

    TLS proves that the server holds a private key. That would be worthless if you did not know whose key it is. A certificate is the answer: a signed statement that a public key belongs to a name. Most TLS problems in real life are certificate problems: expired, wrong name, missing intermediate, untrusted root.

    This lesson builds on step 02 (signatures) and step 04 (where the certificate appears in the handshake).

    What is it? A certificate

    What it is
    A signed document that binds a public key to a name (and some rules). Internet certificates use the X.509 format, profiled in RFC 5280.
    The problem it solves
    A public key is just numbers. Without a certificate you cannot tell whether a key belongs to your bank or to someone in the middle.
    Everyday comparison
    A passport: a document with your name and photo, stamped by an authority that others trust, with an expiry date.
    What it is not
    Not secret: a certificate is public by design. It is not the private key. And it does not vouch that the site is honest, only that the key belongs to that name.
    Where you meet it
    Every HTTPS site, API gateways, mutual TLS between services, code signing, container registries.

    What is it? A certificate authority

    What it is
    An organisation that others trust to create and sign certificates after checking that the requester controls the name.
    The problem it solves
    Nobody can check every site themselves. A few trusted authorities do it, and everybody relies on their signature.
    Everyday comparison
    The passport office.
    What it is not
    Not one company: your operating system and browser each ship a list of trusted roots, and you can add your own (step 06).
    Where you meet it
    Let's Encrypt, a company's internal CA, the "trusted root certificates" store on your PC.

    What is inside

    FieldWhat it says
    SubjectWho the certificate is for. For a website this used to be the common name (CN). Today the name that counts is in the SAN.
    Subject alternative names (SAN)The DNS names or IP addresses the certificate is valid for, such as todo.example.com or *.example.com. This is what a client matches the host name against. RFC 9525 says the common name must not be used to identify a service.
    IssuerWho signed it.
    ValidityNot before and not after. Outside these dates the certificate is invalid.
    Public keyThe key being vouched for (RSA, ECDSA P-256, Ed25519 …).
    Basic constraintsCA:TRUE if this certificate may sign other certificates, and an optional path length limit.
    Key usage, extended key usageWhat the key may be used for: digitalSignature, keyCertSign, and purposes such as serverAuth or clientAuth.
    SignatureThe issuer's signature over all of the above.

    The chain of trust

    Servers do not send certificates signed directly by a root. They send a chain: the leaf (for the site), signed by an intermediate CA, signed by a root CA. The client already has the root in its trust store, so it only has to check each link. Watch the checks, and then four ways they fail:

    Read a certificate yourself

    Paste any certificate, or a whole chain, into the tool. It shows every field, checks each signature and tells you what is wrong. It runs in your browser and sends nothing anywhere. Never paste a private key into a web page: the tool refuses them.

    Line by line: the first bytes of a certificate
    30 82 …
    A DER SEQUENCE (tag 0x30) with a two-byte length (0x82). A certificate is a SEQUENCE of three things.
    First element: tbsCertificate
    "To be signed": the version, serial number, signature algorithm, issuer, validity, subject, public key and extensions. This is exactly what the issuer signs.
    Second element
    The signature algorithm, repeated outside the signed part so a verifier knows what to do before reading the rest.
    Third element
    The signature, a BIT STRING.
    PEM
    The same bytes, base64-encoded and wrapped between -----BEGIN CERTIFICATE----- and -----END CERTIFICATE----- (RFC 7468).

    Kinds of certificate

    The CA/Browser Forum's Baseline Requirements define policy identifiers for what a CA checked: domain validated (DV, 2.23.140.1.2.1: the requester controls the domain), organization validated (OV, 2.23.140.1.2.2: the organisation's identity was checked too) and individual validated (2.23.140.1.2.3). A wildcard such as *.example.com covers exactly one label, so shop.example.com but not a.shop.example.com and not example.com itself.

    07

    Certificates in production

    Advanced

    Goal: explain how a public certificate is issued and renewed with no human, and write the cert-manager objects that give the Todo gateway HTTPS.

    Why this step

    Your own CA is fine for a laptop. A public site needs a certificate that every browser trusts, and the rules say it must be renewed far more often than it used to. The only workable answer is automation, so this lesson is about the protocol that does it (ACME) and the Kubernetes tool that speaks it (cert-manager).

    This lesson builds on steps 05 and 06.

    What is it? ACME

    What it is
    Automatic Certificate Management Environment (RFC 8555): a protocol where a client asks a CA for a certificate, proves it controls the name, and downloads the result, with no person in the loop.
    The problem it solves
    Manual issuance means emails, forms and a calendar reminder that someone forgets. With short lifetimes that is an outage waiting to happen.
    Everyday comparison
    A standing order at the bank instead of remembering to pay each month.
    What it is not
    Not a CA: it is the conversation with one. Let's Encrypt is a CA that speaks ACME.
    Where you meet it
    Let's Encrypt, other public CAs, cert-manager, Caddy, certbot.

    What is it? Certificate Transparency

    What it is
    Public, append-only logs where CAs record the certificates they issue (RFC 9162 describes version 2.0).
    The problem it solves
    A CA could issue a certificate for your domain to someone else and you would never know. A public log lets domain owners watch for certificates they did not ask for.
    Everyday comparison
    A public register of every passport issued, which anyone can search.
    What it is not
    Not prevention: it makes mis-issuance visible.
    Where you meet it
    Search sites for a domain's certificates, browser and platform policies that ask for proof of logging (Android publishes its policy), monitoring alerts.

    How a certificate is proven and issued

    • HTTP-01 (RFC 8555): serve a file over plain HTTP on port 80. Simple, but cannot issue a wildcard.
    • DNS-01 (RFC 8555): publish a TXT record. Works for hosts not reachable from the Internet and is required for wildcards (Let's Encrypt: "Wildcard issuance must use the DNS-01 challenge").
    • TLS-ALPN-01 (RFC 8737): prove control through a special TLS handshake on port 443.

    Lifetimes are shrinking

    The CA/Browser Forum's Baseline Requirements (version 2.3.1) set the maximum validity of publicly trusted TLS certificates:

    Issued on or afterLongest allowed
    before 2026-03-15398 days
    2026-03-15200 days
    2027-03-15100 days
    2029-03-1547 days

    Domain validation data may be reused for less time too (200 days now, 100 days from 2027-03-15). Let's Encrypt is moving earlier than the minimum: its tlsserver profile gives 45-day certificates from 13 May 2026, the default profile moves to 64 days on 10 February 2027 and to 45 days on 16 February 2028, and it also offers opt-in certificates valid for six days. The practical meaning: a certificate you install by hand will not last the year.

    Revocation, and why it matters less now

    A CA can revoke a certificate before it expires (for example after a key leak). Checking that live (OCSP) never worked well: Let's Encrypt stopped including OCSP URLs in certificates on 7 May 2025 and turned its OCSP responders off on 6 August 2025. Short lifetimes and automated renewal do most of the work revocation used to be asked to do. You can still limit who may issue for your domain with a CAA DNS record (RFC 8659), and ask the CA when it would like you to renew with ARI (RFC 9773).

    Mutual TLS: the client shows a certificate too

    Advanced

    Goal: explain when mutual TLS fits, issue a client certificate, and require one in Kestrel.

    Why this step

    With ordinary TLS only the server is proven. For a service that must know which other service is calling (and where there is no user to log in), the client can be proven the same way: with a certificate. It is the strongest everyday answer to "who is this machine?".

    This lesson builds on steps 05 and 06: you reuse your root and the commands for signing.

    What is it? Mutual TLS (mTLS)

    What it is
    TLS where the server also asks the client for a certificate and checks it. The handshake gains a CertificateRequest from the server, and a Certificate and CertificateVerify from the client (RFC 9846).
    The problem it solves
    It authenticates the calling program with a key it never sends, instead of a shared secret that can be copied from a config file.
    Everyday comparison
    Both people at a meeting show ID, not just the visitor.
    What it is not
    Not for the public: you cannot hand certificates to every visitor. Not user login: it identifies the machine or app, which is usually what you want between services.
    Where you meet it
    Service meshes, partner and bank APIs, Kubernetes components, zero-trust networks.

    Use the root from step 06. The only differences from a server certificate: the key usage is clientAuth, and the name says which service it is. Create client.ext:

    h.ClientCertificateValidation = …
    Kestrel checks the client certificate during the TLS handshake, before any ASP.NET Core code runs.     What you just learned

    • Mutual TLS adds a client certificate and a proof of its private key to the handshake, so the server knows which machine is calling.
    • A client certificate has clientAuth usage and chains to a CA the server trusts for clients.
    • Kestrel's RequireCertificate plus AddCertificate() enforces it. Behind a TLS-ending proxy it must be arranged differently.

    Tokens and JWT, byte by byte

    Intermediate

    Goal: decode any JWT by hand, name each claim, and explain how an API checks a signature without calling the issuer.

    Why this step

    After sign-in, programs do not send passwords. They send tokens. Most of them are JWTs, and a JWT is nothing mysterious: three pieces of base64url text you already know how to read. Once you can take one apart, access tokens, ID tokens and the next four levels stop being magic.

    This lesson builds on step 02 (base64url, signatures) and step 01 (who and what).

    What is it? A token

    What it is
    A string that stands in for a login. A client presents it with each request, and the API decides from it who is calling and what they may do.
    The problem it solves
    An API has no browser session, no cookie jar and no login page. It needs a small piece of proof a program can attach to a request and that works across many servers.
    Everyday comparison
    A festival wristband. Staff glance at it, and do not phone the box office each time.
    What it is not
    Not a password: it is limited in time and in what it allows. And a token usually proves nothing about who is holding it (see bearer, below).
    Where you meet it
    The Authorization: Bearer … header on every API call in the rest of this module.

    What is it? A bearer token

    What it is
    A token that any party in possession of it can use, in any way another holder could (RFC 6750). "Bearer" means "whoever bears it".
    The problem it solves
    Simplicity: no extra proof is needed with each call.
    Everyday comparison
    Cash. It does not matter whose pocket it is in.
    What it is not
    Not tied to a person or a device. If it leaks in a log or a URL, whoever finds it can use it until it expires. That is why they are short-lived, and why step 26 shows how to bind them to a key.
    Where you meet it
    Nearly every OAuth access token.

    What is it? A JWT

    What it is
    A JSON Web Token (RFC 7519, pronounced "jot"): a compact, URL-safe way to carry claims between two parties, as a JSON object that is signed (and, rarely, encrypted).
    The problem it solves
    A self-contained token: an API can check it and read it with no database lookup, only the issuer's public key.
    Everyday comparison
    A signed letter that says who it is about and what they may do, on which anyone can check the seal.
    What it is not
    Not encrypted. A normal JWT is signed, which proves it was not changed. Anyone holding it can read it. Never put a secret in one.
    Where you meet it
    OAuth access tokens (RFC 9068 profiles them), OpenID Connect ID tokens, and the OIDC tokens GitHub Actions issues (the Actions Lab).

    What is it? A JWK and a JWKS

    What it is
    A JSON Web Key (JWK, RFC 7517) is a key written as JSON. A JWK Set (JWKS) is a list of them. Identity providers publish their public signing keys as a JWKS at a well-known address.
    The problem it solves
    How does an API get the issuer's public key, and keep up when it changes? It fetches the set, picks the key by kid, and caches it.
    Everyday comparison
    A published list of the official signature specimens for each year.
    What it is not
    Not secret: a JWKS has only public keys. Private keys never appear.
    Where you meet it
    The jwks_uri in an OpenID Connect discovery document (step 14).

    Self-contained or by reference

    Two shapes of access token exist. An opaque token is a random string that means nothing alone: the API asks the authorization server what it stands for (token introspection, RFC 7662). A self-contained token such as a JWT carries its meaning, so the API can decide on its own. The price: it cannot be withdrawn before it expires, so keep lifetimes short (step 10).

    Three parts

    A JWT in its compact form is header.payload.signature: three base64url pieces separated by dots. Paste the token below into the workbench (or use the example): it splits, decodes, explains every claim, and checks the signature the way an API would. Try changing a letter in the signature or the payload.

    The header

    It says how the token was signed. alg is the signature algorithm, typ the kind of token, and kid (key id) says which of the issuer's keys signed it. JWT access tokens following RFC 9068 use typ: at+jwt.

    The claims

    ClaimNameMeans
    issIssuerWho made and signed the token.
    subSubjectWho it is about. For a user, the stable id of the user. Never an email address you treat as a key.
    audAudienceWho it is for. An API must check that it is on the list.
    expExpiration timeThe moment from which it must not be accepted (seconds since 1970).
    nbfNot beforeThe moment before which it must not be accepted.
    iatIssued atWhen it was made.
    jtiJWT IDA unique name for this token.

    Other claims carry the application's own facts: scope, role, client_id. RFC 9068 requires iss, exp, aud, sub, client_id, iat and jti in a JWT access token.

    Line by line: build a JWT by hand
    1. Write the header
    {"alg":"HS256","typ":"JWT"}. Its base64url is eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9. Every JWT that starts eyJhbGci is a JSON header starting {"alg".
    2. Write the payload
    {"sub":"alice","aud":"todo-api"}, and base64url it.
    3. Join them
    base64url(header) + "." + base64url(payload). This text, exactly, is the signing input.
    4. Sign it
    HS256: HMAC-SHA-256(secret, signing input). RS256: an RSA signature over the SHA-256 of it, with the private key. ES256: ECDSA on P-256, written as the two 32-byte numbers r and s joined (not the DER form certificates use).
    5. Append
    signing input + "." + base64url(signature). That is the token. To verify, recompute from the first two parts and compare.

    Choosing a signature algorithm

    AlgorithmKindFits when
    HS256HMAC, one shared secretOne program both makes and checks the token. Anyone who can check can also forge.
    RS256, PS256RSA signatureAn issuer makes tokens and many others check them with a public key. RS256 is the one RFC 9068 requires every server to support.
    ES256ECDSA P-256The same, with much smaller keys and signatures.
    Ed25519EdDSAThe same, modern and fast. RFC 9864 (2025) made Ed25519 the name to use and deprecated the older EdDSA value.

    RFC 9068 recommends asymmetric signing for access tokens: it is what lets any number of APIs verify tokens without being able to make them.

    What you just learned

    • A JWT is header.payload.signature, each part base64url. It is signed, not encrypted: anyone can read it.

    • Asymmetric algorithms let many APIs verify a token and none of them forge it. The API fetches and caches the issuer's public keys and picks one by kid.

    Validating a JWT, and the ways it goes wrong

    Advanced

    Goal: list the checks a token must pass, carry out the classic attacks on a weak validator, and configure a validator that resists them.

    Why this step

    A token is only as good as the code that checks it. Almost every JWT vulnerability is a validation mistake, not a break of the cryptography. The fastest way to learn them is to commit each one yourself against a deliberately weak API, then see the one-line fix.

    This lesson builds on step 09. Nothing here attacks a real system: the API is a simulation inside this page.

    What a validator must check

    RFC 7519 (section 7.2) and RFC 8725 (JSON Web Token Best Current Practices) say, in short: if any step fails, reject the token. In the order a careful API does them:

    1. Well formed. Three parts, valid base64url, valid JSON. Only parameters it understands.
    2. Algorithm on the allow-list. The verifier chooses the algorithms (RFC 8725, 3.1 and 3.2). Never none. Each key is used with exactly one algorithm.
    3. Signature valid for the issuer's key, selected by kid from a key set you trust (3.3).
    4. Issuer is the one you expect, and the key belongs to it (3.8).
    5. Audience includes this API (3.9).
    6. Expiry and not-before, with a small clock allowance. Require exp to be present.
    7. Type is right (typ: at+jwt for access tokens, 3.11), so an ID token cannot be used as an access token.
    8. Then read the claims and authorize. Never before.

    Configure a library; do not write this yourself. In ASP.NET Core you set the authority and the audience on AddJwtBearer (step 20) and the library does all of the above. The mistakes below are what happens when someone bypasses it, or configures it loosely.

    Other ways it goes wrong

    • kid and jku as injection. The kid header is used to look up a key. If it goes straight into a database or file path query, it is an injection. Blindly following a jku or x5u URL in the header could enable server-side request forgery. Only fetch keys from addresses you configured (RFC 8725, 3.10).
    • ID token as access token. An ID token is for the app that signed the user in, not for APIs. Use typ and audience checks so one kind cannot stand in for the other (3.11 and 3.12).
    • Secrets in the payload. It is readable by anyone who holds it.
    • Tokens in URLs, logs and browser storage. Anywhere a token is written, it can be read. Keep them in memory or, for a browser, behind the BFF of step 22.
    • Long or no expiry. A JWT cannot be recalled. Keep access tokens to minutes, and use refresh tokens (step 13) to renew.

    Practice

    About these labs. The API here is a simulation written for this lesson that behaves the way RFC 8725 describes each flaw. It is not a real library, and whether a given library is exposed to a flaw like these depends on its version and how it is configured. What carries over is the habit: pass an allow-list, verify before you read, check every claim you rely on.

    What you just learned

    • A validator checks, in order: format, algorithm allow-list, signature, issuer, audience, expiry, type. Any failure rejects.
    • The token must never choose the algorithm. none and key confusion are what happens when it does.
    • Decode is not verify. A secret that can be guessed is not a secret. A token for another audience is not for you.

    OAuth 2.0: access without handing over a password

    Intermediate

    Goal: say what OAuth is for, name its four roles in any system, and tell the front channel from the back channel.

    Why this step

    "Sign in with Google", "connect your calendar", "this app wants to access your GitHub": all of it is OAuth. It is the most misunderstood protocol on this page, because it is not about signing in. It is about letting one program act for you at another, without giving it your password.

    This lesson builds on step 09 (tokens) and step 01 (who and what).

    What is it? OAuth 2.0

    What it is
    An authorization framework (RFC 6749) that lets a third-party application obtain limited access to an HTTP service, either on behalf of a resource owner or on its own behalf.
    The problem it solves
    Before it, an app that wanted your data asked for your password. The RFC lists what that caused: apps storing passwords in the clear, servers forced to support passwords, apps getting overly broad access with no limit on time or scope, no way to revoke one app without changing the password for all, and a breach of any app exposing the password.
    Everyday comparison
    A hotel key card. The hotel does not give a visitor the master key. It issues a card that opens one room, for a few days, and can be cancelled on its own.
    What it is not
    Not a login protocol. OAuth says what an app may do, not who you are. A token proves permission, and nothing in OAuth says how to read an identity from it. That is what OpenID Connect adds (step 14).
    Where you meet it
    Every "Allow this app to access…" screen, and the access token behind every API call in level 6.

    What is it? A scope

    What it is
    A named permission the client asks for, such as todos.read or openid. The server may grant less than was asked.
    The problem it solves
    "Access" is too coarse. A scope limits a token to part of what the user could do.
    Everyday comparison
    The tick boxes on a consent form.
    What it is not
    Not a role. A scope says what this token may do; a role says what a user may do. A call needs both to allow it (step 16).
    Where you meet it
    The consent screen, and the scope claim of an access token.

    What is it? Consent

    What it is
    The resource owner's approval of what a client asks for, given at the authorization server.
    The problem it solves
    The user, not the app, decides what the app may do.
    Everyday comparison
    Signing a permission slip.
    What it is not
    Not repeated on every use: the authorization server can remember it.
    Where you meet it
    The screen that lists the permissions an app wants.

    The four roles

    OAuth's word (RFC 6749)It is…In the Todo app
    Resource ownerAn entity able to grant access to a protected resource. When it is a person, an end-user.Alice.
    ClientAn application making protected-resource requests on behalf of the resource owner and with its authorization. The word says nothing about where it runs.The Angular app (through its backend, step 22).
    Authorization serverThe server issuing access tokens to the client after authenticating the resource owner and obtaining authorization.Keycloak, or Google.
    Resource serverThe server hosting the protected resources, accepting access tokens.The Todo API.

    The authorization server and the resource server can be the same machine or different ones, and one authorization server can issue tokens for many resource servers.

    Two kinds of client

    OAuth (RFC 6749, section 2.1) sorts clients by whether they can keep a secret. A confidential client can: a program on your server. A public client cannot: an app that runs on the user's device, such as a single-page app in a browser or an installed phone app. Anything shipped to the user can be read by the user, so it cannot hold a secret. This one distinction decides which protections you need in step 12.

    Front channel and back channel

    Two different routes carry OAuth messages:

    • The front channel is the user's browser: redirects, the address bar, history. Anything here can be seen by the user, extensions, logs and malicious pages. Only short-lived, low-value things go here.
    • The back channel is a direct HTTPS call from the client's server to the authorization server. Nobody in between can see or change it. Tokens travel only here.

    The whole design of the authorization code flow is: use the front channel for the part that needs the user, and get the valuable thing (the token) over the back channel.

    The documents

    OAuth 2.0 is a family. RFC 6749 (2012) is the core. RFC 9700 (January 2025) is the current best practice that tightens it: it makes PKCE the norm, forbids the password grant and exact-matches redirect URIs. OAuth 2.1 is an Internet-Draft (revision 16, 3 September 2026), not yet an RFC: it collects those changes into one document. This module teaches what RFC 9700 asks for, which is what the draft also requires.

    Practice

    What you just learned

    • OAuth lets a client act for a resource owner without their password, with limited scope and lifetime.
    • Four roles: resource owner, client, authorization server, resource server. Clients are confidential or public.
    • The front channel (browser) can be seen; the back channel is private. Tokens use the back channel.
    • OAuth is about permission, not identity.

    The authorization code flow with PKCE, message by message

    Advanced

    Goal: write every request of the flow yourself, and explain what each parameter protects against.

    Why this step

    This is the flow behind nearly every modern sign-in, and every parameter in it is there because of a real attack. Learn the messages, and then learn the attack each one answers.

    This lesson builds on step 11 (roles, channels) and step 02 (hashes).

    What is it? The authorization code

    What it is
    A short-lived, single-use value the authorization server returns through the browser, which the client then trades for tokens over the back channel.
    The problem it solves
    Tokens must not travel through the browser. A code can, because on its own it opens nothing, and the server will only honour it for the right client.
    Everyday comparison
    A collection slip. You hand it to the right counter and receive the parcel, which was never in your hands on the way.
    What it is not
    Not a token, and not a secret by itself: it can leak from the address bar, so something must tie it to the client that asked.
    Where you meet it
    The ?code=… in the address after you approve an app.

    What is it? PKCE

    What it is
    Proof Key for Code Exchange, pronounced "pixy" (RFC 7636): the client makes a random code_verifier, sends only its SHA-256 hash (code_challenge) at the start, and sends the verifier when exchanging the code.
    The problem it solves
    A stolen code is useless to anyone who lacks the verifier. It was designed against the authorization code interception attack.
    Everyday comparison
    Writing a number in the hotel register in a sealed envelope when you book, and showing the number itself when you collect the room: the clerk checks that it matches the sealed one.
    What it is not
    Not client authentication. It does not prove which app this is, only that this is the same one that started the flow. RFC 9700: public clients MUST use PKCE, confidential clients are RECOMMENDED to, and it applies to web apps as well.
    Where you meet it
    code_challenge and code_verifier in the requests below.

    The whole flow, with real values

    Switch a protection off to see which attack it was stopping. The values are generated for you each time.

    The two requests you must be able to write

    A GET to the authorization endpoint with these parameters (RFC 6749 4.1.1, RFC 7636 4.3, OpenID Connect):

    scopeopenid todos.readWhat the client asks for.
    staterandom, per attemptTies the callback to this browser (against CSRF).

    2. The token request (a back channel POST)

    The client sends the code and the verifier, form-encoded, to the token endpoint (RFC 6749 4.1.3, RFC 7636 4.5): grant_type=authorization_code, code, redirect_uri (the same as in the first request), client_id and code_verifier.

    The token endpoint answers a failed request with JSON and an error from RFC 6749 5.2: invalid_request (a parameter is missing or malformed), invalid_client (client authentication failed), invalid_grant (the code is invalid, expired, already used, does not match the redirect_uri, or fails PKCE), unauthorized_client, unsupported_grant_type and invalid_scope. By far the most common in practice is invalid_grant: use the code only once, and quickly.

    A first look at pushed authorization requests

    Instead of putting every parameter in the browser's address, a client can POST them to the authorization server first (PAR, RFC 9126) and redirect the user with only a reference. The parameters then travel on the back channel and cannot be altered in the browser. From .NET 9 the OpenID Connect handler uses PAR by default if the server supports it, which makes the flow three steps instead of two.

    What you just learned

    • The code goes through the browser; the tokens come back over a direct call. PKCE ties the code to the client that asked for it.
    • state, exact redirect_uri matching and iss each stop a different attack.
    • Public clients must use PKCE, and everyone should. Use S256.

    Other grants, and the two to stop using

    Intermediate

    Goal: choose the right grant for any caller, and say why two of the original four are out.

    Why this step

    The authorization code flow needs a person and a browser. Services, command-line tools and televisions have neither, and OAuth has a grant for each. You also need to know which old ones to refuse in code review.

    This lesson builds on steps 11 and 12.

    What is it? A grant

    What it is
    A way of getting a token: a recipe for what the client sends to the token endpoint, and what it received before.
    The problem it solves
    Different callers (a person in a browser, a nightly job, a TV) can prove authorization in different ways.
    Everyday comparison
    Ways of getting into a building: a keycard, a visitor pass, a code texted to you.
    What it is not
    Not the token itself, and not a role.
    Where you meet it
    The grant_type parameter.

    What is it? A refresh token

    What it is
    A long-lived credential the client uses to obtain new access tokens without bothering the user again (RFC 6749 section 6).
    The problem it solves
    Access tokens should live for minutes. A refresh token lets the app keep working all day without asking you to sign in again.
    Everyday comparison
    A season ticket you swap for a day pass each morning.
    What it is not
    Not sent to APIs. It goes only to the authorization server, and it is more valuable than an access token, so it needs more care.
    Where you meet it
    The refresh_token in the token response, and offline_access or access_type=offline.

    Which grant?

    GrantUse it forStatus
    Authorization code with PKCEA person signing in through a browser, in any kind of client.The default.
    Client credentialsA program acting for itself, with no user (RFC 6749 4.4).Current.
    Device authorizationA device with no browser or keyboard, where the user finishes on another device (RFC 8628).Current.
    Refresh tokenGetting a new access token without the user (RFC 6749 6).Current, with rotation for public clients.
    Token exchangeSwapping one token for another with a different audience or subject, for example a service calling another service on behalf of the user (RFC 8693).Current.
    Implicit (response_type=token)Used to return the access token directly in the redirect.Do not use. RFC 9700 2.1.2: vulnerable to leakage and replay. Omitted from the OAuth 2.1 draft.
    Resource owner passwordThe client collects the username and password and sends them to the token endpoint.Must not be used (RFC 9700 2.4): it exposes the user's credentials to the client, and cannot work with MFA or passkeys.

    The service authenticates itself to the token endpoint (RFC 9700 2.5 recommends asymmetric methods such as a signed JWT or mutual TLS over a shared secret) and receives an access token whose subject is the service.

    Refresh tokens, and detecting theft

    A refresh token is more dangerous than an access token because it lasts longer. For public clients RFC 9700 requires that refresh tokens are either sender-constrained or rotated: every use returns a new one and spends the old one. If an old one is presented again, two parties hold it, and the server can revoke the whole family.

    Practice

    What you just learned

    • Code with PKCE for people. Client credentials for programs. Device flow for devices without a browser.
    • The implicit and password grants are out. The password grant must not be used, because it hands your password to the client.
    • Refresh tokens must be rotated or sender-constrained for public clients, so a copy is detected.

    OpenID Connect: OAuth plus proof of who signed in

    Advanced

    Goal: explain what OpenID Connect adds to OAuth, validate an ID token, read a discovery document and say which token goes where.

    Why this step

    OAuth gives an app a token for an API. An app that wants to know who signed in needs something else, and using the access token for that is a classic mistake. OpenID Connect (OIDC) is the standard way, and it is what "Log in with Google" really is.

    This lesson builds on steps 09 to 13.

    What is it? OpenID Connect

    What it is
    A simple identity layer on top of OAuth 2.0 (OpenID Connect Core 1.0). It lets a client verify the identity of the end-user, based on the authentication performed by an authorization server, and get basic profile information.
    The problem it solves
    OAuth never defined how an app learns who the user is, so every provider invented its own way. OIDC standardised it, with one token (the ID token) and one way to validate it.
    Everyday comparison
    OAuth is the hotel key card. OIDC is the registration slip that says whose card it is.
    What it is not
    Not a separate protocol: it is the code flow of step 12 with openid in the scope, plus an id_token. Not SAML, which solves a similar problem in XML.
    Where you meet it
    Log in with Google, Microsoft, Okta, Keycloak. The "OpenID Provider" and "relying party" are its names for the server and the app.

    What is it? An ID token

    What it is
    A JWT issued by the provider, saying that an end-user authenticated: who (sub), when, how, and for which client (aud).
    The problem it solves
    A signed statement of the sign-in event, which the app can check itself.
    Everyday comparison
    A receipt for the check-in, stamped by the hotel and addressed to you.
    What it is not
    Not for APIs. Its audience is the client app. Sending it to an API as if it were an access token is a mistake that audience and type checks (step 10) are there to catch.
    Where you meet it
    The id_token field of the token response.

    What is it? Single sign-on

    What it is
    One sign-in at the identity provider that lets you into several applications.
    The problem it solves
    One place to enforce MFA, offboard people and see sign-ins, and no password per app.
    Everyday comparison
    A wristband that opens every stage at the festival.
    What it is not
    Not the same session in each app: each app still makes its own local session after validating its own ID token.
    Where you meet it
    Company portals, and "Sign in with Google" on many sites at once.

    The three tokens, and who each is for

    TokenForSent toRead by
    ID tokenThe client app: who signed inNobody. The app keeps it.The client.
    Access tokenThe API: what the client may doThe resource server, in Authorization: Bearer.The API. The client treats it as opaque.
    Refresh tokenThe authorization server: get a new access tokenThe token endpoint only.The authorization server.

    The claims of an ID token

    ClaimMeaning
    issThe issuer: an https URL with no query or fragment.
    subThe subject: a locally unique, never reassigned identifier for the user at this issuer, no longer than 255 ASCII characters. Use it as the user's key, together with iss.
    audMust contain the client's client_id.
    exp, iatWhen it expires and when it was issued. The token's expiry is unrelated to the length of the user's session at the provider.
    nonceThe value the client sent in the request. It must be present and equal.
    auth_time, acr, amrWhen the user authenticated and how strongly and by which methods.
    azpThe authorized party: the client the token was issued to.
    at_hashThe left half of the hash of the access token, binding the two together.

    Validating an ID token

    OpenID Connect Core section 3.1.3.7 lists what the client MUST do in the code flow:

    1. The iss must exactly match the issuer identifier the provider published (from discovery).
    2. The aud must contain the client's own client_id. Reject the token if it lists audiences the client does not trust.
    3. If azp is present, it should be this client's id.
    4. Validate the signature with the keys the issuer provides, using an algorithm the client expects (RS256 by default). When the token arrives directly from the token endpoint over TLS, the TLS server validation may be used in place of checking the signature.
    5. The current time must be before exp.
    6. If a nonce was sent, a nonce claim must be present and equal.

    Then use iss + sub as the user's identity. Google puts it plainly: do not use the email claim as a unique identifier, because it may change; always use sub.

    Discovery: how a client finds everything

    A provider publishes a JSON document at {issuer}/.well-known/openid-configuration (OpenID Connect Discovery 1.0). Libraries read it, which is why you configure only the issuer (the "authority"). The fields you will meet: issuer, authorization_endpoint, token_endpoint, userinfo_endpoint, jwks_uri (where the signing keys are), end_session_endpoint, scopes_supported, response_types_supported, id_token_signing_alg_values_supported and code_challenge_methods_supported.

    UserInfo, and signing out

    The UserInfo endpoint returns claims about the user for an access token with the right scope (profile, email). Signing out has two halves: the app ends its own session, and it can send the browser to the provider's end_session_endpoint (RP-Initiated Logout 1.0) with an id_token_hint and a pre-registered post_logout_redirect_uri, so the provider ends its session too. Without that second half the user is still signed in at the provider, and the next click on "sign in" completes silently.

    Practice

    What you just learned

    • OpenID Connect is OAuth's code flow with openid in the scope, plus an ID token that tells the client who signed in.
    • Validate the issuer, audience, signature, expiry and nonce. Key the user by iss and sub, never email.
    • ID token for the app, access token for the API, refresh token for the authorization server.
    • Discovery gives a client every endpoint and the keys from one address.

    "Log in with Google", by hand

    Advanced

    Goal: register an app with Google, run Google's sign-in flow yourself, and check a real Google ID token.

    Why this step

    You now know every message. Here you send them, for real, to a real provider, and read the answer. After this, "Log in with Google" is no longer a button but a flow you can debug.

    This lesson needs a Google account, a free Google Cloud project, and a terminal with curl. If you have none of these, read it and tick the step yourself: the next levels do not depend on it.

    What could and could not be tested. The tool and the commands on this page were tested. The steps in Google's console and the live sign-in need your Google account, so they were checked against Google's documentation and its live discovery document, not run. Google changes its console labels: the goal of each step is given as well as the label.

    What Google is, in OIDC's words

    Google is an OpenID Provider and you are the relying party. Its discovery document is at https://accounts.google.com/.well-known/openid-configuration. Today it says: issuer https://accounts.google.com, authorization endpoint https://accounts.google.com/o/oauth2/v2/auth, token endpoint https://oauth2.googleapis.com/token, keys at https://www.googleapis.com/oauth2/v3/certs, ID tokens signed with RS256, and PKCE methods plain and S256.

    Google offers two ways to add the button. The standard redirect flow you build here works in any language. The Sign in with Google button (Google Identity Services) shows a button or One Tap prompt and returns an ID token to your page for your server to verify. It uses the browser's FedCM API, and Google says to enable FedCM for new integrations. Note Google's own distinction: the sign-in API returns only ID tokens, and access to Google APIs is a separate authorization step.

    Part 1: create the client

    1. In the Google Cloud console, open Google Auth Platform and its Clients page, in a free project of your own.
    2. Branding and audience: give the app a name and a support email. Choose External as the audience, and leave the publishing status at Testing. In Testing, only the test users you list (up to 100) can authorise the app, and authorisations expire after seven days. Add your own Google account as a test user. (An app that asks only for the basic profile, email and openid scopes is exempt from the listing and the expiry.)
    3. Create a client of type Web application. Under Authorized redirect URIs add exactly the address shown by the tool below. Google requires https for redirect URIs but exempts localhost, and it matches them exactly, including scheme, case and trailing slash.
    4. Copy the client ID into the tool. Keep the client secret for your terminal: it never goes into this page.

    Part 2: send the request

    The tool creates state, nonce and a PKCE challenge, shows the request parameter by parameter, and sends you to Google. When you come back it checks state and gives you the exchange command with your own values.

    Part 3: exchange the code, in your terminal

    Run the command the tool printed. Google answers with JSON: access_token, expires_in, scope, token_type and id_token. Copy the id_token.

    Part 4: check the ID token

    Fetch Google's keys with curl https://www.googleapis.com/oauth2/v3/certs and paste the whole key set into the key box of the workbench below, with the id_token. The workbench picks the key by kid. Set the issuer to https://accounts.google.com, the audience to your client ID, and the algorithms to RS256.

    Then check by eye, as OpenID Connect requires: iss is https://accounts.google.com (Google documents both that and accounts.google.com), aud is your client ID, exp is in the future, and nonce is the one the tool showed you. For a Google Workspace account, hd is the domain you accept.

    What to store about the user

    Google's guidance is blunt: do not use the email claim as the user's unique identifier. Always use sub, which is unique to a Google Account even if the user changes their email. Store the pair (iss, sub). The hd request parameter is only a hint for the login screen. Google says not to rely on that optimisation to control access, because client-side requests can be modified. Check the hd claim in the ID token on your server.

    Clean up

    When you are done, delete the client in the console, or at least remove the test user, and revoke the app at myaccount.google.com/permissions. In step 23 you will add Google to Keycloak, so your app never talks to Google itself.

    • Logging in with Google is the OIDC code flow against Google's published endpoints. You can run every message by hand.
    • The client secret stays in your terminal and your server. State and nonce are checked.
    • Key a Google user by iss and sub. Never trust email as an identifier, and never use the hd parameter as access control.

    Access models: ACL, RBAC, ABAC, ReBAC

    Intermediate

    Goal: explain each model in one sentence, design roles for an app, and say when roles alone are not enough.

    Why this step

    Authentication tells you who. Then every system needs rules for what that person may do, and the shape of those rules decides how easy the system is to run, to audit and to get wrong. Four models cover nearly everything. Real systems mix them.

    This lesson builds on step 01 (authorization) and step 11 (scopes).

    What is it? An access control model

    What it is
    A way of writing down who may do what to which thing. Every rule has the same parts: a subject (who), an action (what), a resource (to which) and sometimes a context (when, from where).
    The problem it solves
    Without a model, access rules are scattered if statements that nobody can list, review or change safely.
    Everyday comparison
    The rules of a building: a guest list on the door, badges by job, "managers on the 4th floor after 6", "anyone on the team that rents this office".
    What it is not
    Not authentication, and not the code that enforces it. A model is the rules; they still have to be checked on every request.
    Where you meet it
    Roles in Keycloak, Kubernetes RBAC (step 18), cloud permission policies, a sharing dialog.

    What is it? RBAC

    What it is
    Role-based access control: permissions are granted to roles, and people are given roles. Alice is an editor, and editor may create todos.
    The problem it solves
    You manage a few roles instead of thousands of person-by-permission grants. Joining a team is one assignment, and leaving is one removal.
    Everyday comparison
    Job titles: the title says what the badge opens.
    What it is not
    Not able to say "only your own": a role covers every object of a kind. And not a scope: a scope limits a token, a role describes a user (step 11).
    Where you meet it
    [Authorize(Roles = "admin")], Keycloak realm roles, Kubernetes Roles.

    What is it? ABAC and ReBAC

    What it is
    ABAC (attribute-based) decides by evaluating attributes of the subject, the object, the requested operation and sometimes the environment against policy (NIST SP 800-162). ReBAC (relationship-based) decides by a relationship between the user and the object: member of the team that owns the folder. Google's Zanzibar system, described at USENIX ATC 2019, stores and evaluates such lists globally for its services.
    The problem it solves
    Roles cannot express "only your own", "only under 500", "only from the office network", or "anyone on the owning team".
    Everyday comparison
    ABAC: "managers may approve expenses under 500 in their own department". ReBAC: "you can edit a file if you are in the team that owns its folder".
    What they are not
    Not replacements for roles. Most systems use roles for features and an ownership or attribute rule for individual objects.
    Where you meet them
    Cloud policy conditions, document-sharing systems, resource.Owner == user.Id in your own code.

    Four models, one example each

    ModelRule looks likeStrengthWeakness
    ACL (access control list)This document: alice read, bob read and write.Simple, per object.Hard to see "what can Alice access?" and to change at scale.
    RBACeditor may todos:create. Alice is an editor.Few things to manage and audit.Role explosion when every special case becomes a role. Cannot say "own".

    Principles that apply to all of them

    • Deny by default. Anything not allowed is refused. OWASP lists the opposite as the first common weakness.
    • Least privilege. Give each role, token and service only what it needs.
    • Separation of duty. The person who creates a payment is not the one who approves it. Roles alone cannot say "not the same person"; it needs a rule about the object.
    • Enforce on the server, on every request. The decision can live in a library or a policy engine, but the check must be where the data is.
    • Mind how fresh a role is. A role carried in a token is as old as the token. Changing a user's role does not change tokens already issued.

    Policy as code

    As rules grow, they move out of scattered if statements into one place that can be read, tested and reviewed. Open Policy Agent (the language is Rego) and Cedar (a policy language created at AWS) are two open-source examples for applications, and Kyverno (Part 4) does it for Kubernetes admission. Whichever one you use, the split is the same: a decision (allow or deny, from a request and some data) and an enforcement point that asks and obeys.

    Play with RBAC

    Tick which role grants which permission, and give each person a role. A permission ending in :own applies only to todos the caller owns. Watch which decisions change, and read the reason given for each.

    Practice

    What you just learned

    • Every rule is subject, action, resource and sometimes context. ACL lists on the object, RBAC by role, ABAC by attributes, ReBAC by relationship.
    • RBAC manages few things but cannot say "own". Real systems pair roles with an ownership or attribute rule.
    • Deny by default, least privilege, separation of duty, and enforce on the server.
    • A role describes a user, a scope limits a token; a call needs both.

    Broken access control, and how to close it

    Advanced

    Goal: recognise the common access-control flaws in code and fix each one in ASP.NET Core.

    Why this step

    Broken access control is first in the OWASP Top 10 for 2025. The 2025 edition reports that 100% of the applications tested had some form of it. The flaws are not clever: they are checks that someone forgot. The way to learn to see them is to read real-looking code and be asked "what happens if".

    This lesson builds on steps 01, 16 and 10. The code is C# for the Todo API you secure in level 6.

    What is it? Broken access control

    What it is
    Failures that let users act outside their intended permissions. OWASP lists, among others: access that should be denied by default but is open, changing a URL or request to reach someone else's data, missing checks on POST, PUT and DELETE, acting as another user, and tampering with a token or cookie.
    The problem it causes
    Information disclosure, modification or destruction of data, or business functions used beyond a user's limits.
    Everyday comparison
    A hotel that checks you have a key card but not which room the card is for.
    What it is not
    Not an authentication failure: the user usually is signed in. The system simply never asks whether this user may do this.
    Where you meet it
    Everywhere. API1, API3 and API5 of the OWASP API Security Top 10 (2023) are its three object, property and function forms.

    The three forms in the API list

    OWASP API (2023)In plain wordsExample
    API1: Broken Object Level AuthorizationThe caller can reach another user's object by changing an id.GET /todos/2 returns Bob's todo.
    API3: Broken Object Property Level AuthorizationThe caller can read or write a field they should not.Setting isAdmin in a profile update.
    API5: Broken Function Level AuthorizationThe caller can use a function reserved for others.A normal user calls the admin endpoint.

    Eight to find

    Each snippet is the endpoint with the flaw. Work out what happens before you answer. A correct answer shows the fixed code. Every snippet here, broken and fixed, is built and called over HTTP by the tests, so what they claim is what the code does.

    The patterns that close them

    • Deny by default. A fallback policy requires an authenticated user for every endpoint that has no policy of its own, so a forgotten endpoint is closed, not open. Public endpoints opt out with [AllowAnonymous].
    • Named policies for functions. RequireAuthorization("Admin"), defined once with AddAuthorizationBuilder().AddPolicy(...).
    • Identity only from the validated token. Never from the body, a header or a query string.
    • Ownership in the query. Every query that returns or changes an object is filtered by the owner from the token, so a forgotten check cannot widen the result.
    • Resource-based authorization when the rule needs the loaded object. An attribute runs before the data is loaded, so the check has to be called from the handler:
    Line by line: the resource handler
    AuthorizationHandler<OperationAuthorizationRequirement, Todo>
    A handler for requirements about one kind of resource, here a Todo. OperationAuthorizationRequirement is the framework's helper for "an operation named X", so one handler serves Read, Update and Delete.
    context.Succeed(requirement)
    Says this requirement is met. If no handler succeeds, the answer is no: deny by default.
    authz.AuthorizeAsync(user, todo, requirement)
    Asks the framework: may this user do this operation to this object? It is called after the object is loaded.
    return Results.NotFound()
    For an object, the same answer for "no such todo" and "not yours", so the response reveals nothing.

    Test it, always

    OWASP: developers and QA should include functional access control in unit and integration tests. A small table is enough: for each endpoint, who may and who may not, and the status code each gets. Step 21 gives you the table for the Todo API.

    Practice

    What you just learned

    • Most access control bugs are a missing check: for the object, the field, or the function.
    • Identity comes from the validated token. Ownership belongs in the query. Roles belong on the endpoint.
    • Deny by default with a fallback policy, so a forgotten endpoint is closed.
    • For objects, "not yours" and "not there" give the same answer.

    Access control around the platform

    Advanced

    Goal: write a Kubernetes Role, test it with kubectl auth can-i, and explain how a pod gets cloud credentials with no stored secret.

    Why this step

    The same ideas that protect your API protect the platform under it: who may read Secrets in a namespace, which pod may touch which cloud resource. In Part 4 you restricted what pods can do. Here you decide what identities may do.

    This lesson builds on steps 09 and 16, and on Part 1's cluster and Part 4's service accounts.

    What is it? A service account

    What it is
    An identity for processes that run in a pod. A process inside a pod can use it to authenticate to the cluster's API server.
    The problem it solves
    Programs need an identity too, and a human's login is the wrong one.
    Everyday comparison
    A staff badge for a robot, which opens only the doors the robot needs.
    What it is not
    Not a user: it exists inside the cluster, in a namespace, and its token is short-lived and bound to a pod.
    Where you meet it
    The serviceAccountName of a pod, and the subject of a RoleBinding.

    What is it? Workload identity

    What it is
    Letting a workload prove who it is to a cloud, with a token its platform issues, instead of a stored key. In Kubernetes the cluster is an OpenID Connect identity provider and the cloud is a relying party.
    The problem it solves
    Long-lived cloud keys in config files and environment variables leak. A short-lived, signed, audience-bound token does not need to be stored.
    Everyday comparison
    A visitor pass that the building's reception issues, which another building accepts because it trusts that reception.
    What it is not
    Not a boundary between containers: Amazon's own documentation says containers are not a security boundary, and that this does not change it.
    Where you meet it
    IAM roles for service accounts (IRSA) on EKS; the GitHub Actions OIDC trust in the Actions Lab is the same idea.

    Kubernetes RBAC

    Kubernetes authenticates a request, then authorizes it with RBAC (among other authorizers). Its rules, from the documentation:

    • A Role sets permissions within one namespace. A ClusterRole is not namespaced.
    • A RoleBinding grants a Role or ClusterRole to subjects within a namespace. A ClusterRoleBinding grants it cluster-wide. A RoleBinding that points at a ClusterRole still grants only inside its own namespace.
    • Permissions are purely additive: there are no "deny" rules. To take access away, remove the grant.
    • A rule names apiGroups (the core group is ""), resources, verbs, and optionally resourceNames to limit it to specific objects.
    • Escalation is prevented: you may create or update a Role only if you already hold every permission in it at that scope, or you have the escalate verb. Binding follows a similar rule.
    Line by line: the Role and its binding
    rules[0]
    May get and list pods in the namespace todo (and nothing else about pods: no delete, no create).
    rules[1] with resourceNames
    May get only the ConfigMap called todo-settings. Without resourceNames, a rule covers every object of the kind.
    subjects
    Who receives the Role: here the service account todo-reporter in todo.
    roleRef
    Which Role. It cannot be changed after creation: to point somewhere else you replace the binding.

    Test what an identity can do without becoming it. kubectl auth can-i asks the API server's authorization layer; add --as to ask for someone else, and --list to list everything.

    Dangerous permissions

    get or list on secrets reads every secret in the namespace. create on pods or deployments lets someone run code under any service account in the namespace. escalate and bind let a person grant what they do not hold. Give them to very few identities, and review bindings the way you would review a firewall rule.

    Service account tokens

    Since Kubernetes 1.22 a pod gets a short-lived, automatically rotating token by the TokenRequest API, mounted as a projected volume. The token is a JWT, bound to the pod, and by default its audience is the Kubernetes API server. A token requested for another audience is useless to the API server, and the reverse. Opt out of mounting credentials with automountServiceAccountToken: false for pods that never call the API.

    Workload identity

    Kubernetes can act as an OpenID Connect provider: with token projection on and an https issuer, the API server serves a discovery document at /.well-known/openid-configuration and its keys at /openid/v1/jwks, so an outside system can verify service account tokens. Amazon EKS hosts such an endpoint for each cluster. In IAM roles for service accounts (IRSA) you register the cluster as an OIDC provider once, associate an IAM role with a service account, and the pod's token is exchanged with the AWS Security Token Service (AssumeRoleWithWebIdentity) for temporary credentials.

    The cloud's trust policy is where the least privilege is written: which issuer, and which service account in which namespace, may assume which role. It is the access control of step 16 applied to a machine, with the token checks of step 10.

    Practice

    What you just learned

    • Kubernetes RBAC: Roles and bindings, namespaced or cluster-wide, purely additive, with resourceNames to narrow a rule and escalation prevented.
    • kubectl auth can-i --as … --list tests an identity without being it.
    • Service account tokens are short-lived, bound JWTs. A cloud can trust the cluster's issuer and swap a token for temporary credentials, with no stored key.
