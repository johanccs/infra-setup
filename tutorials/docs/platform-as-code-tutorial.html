    What you'll build

    Right now your cluster depends on commands you typed: three helm upgrade --install lines and a kubectl apply. Nobody can review them, and if the cluster disappears you have to remember them in the right order. By the end of this part, Git describes everything and Argo CD builds it:

    That pattern is called app of apps: an Application whose job is to create other Applications. Adding a new platform component becomes "add one file to infra/platform/apps/ and merge".

    What problem each piece solves

    The problemThe pieceWhat it does about it
    The platform was installed by hand, so nobody can review or repeat it.App of apps (steps 4–6)Each component is a file in Git. Argo CD installs and keeps them all.
    "Latest" today is a different version tomorrow, so two rebuilds aren't the same.Pinned chart versions (step 2)Every chart version is written down. Upgrades are commits.
    Things install in the wrong order: the todo chart needs object types the monitoring chart creates.Retries and sync options (step 5)Argo CD waits and tries again until the order sorts itself out.
    Any app can deploy anything anywhere, including cluster-wide permissions.AppProjects (step 5)A team's apps may only deploy from its repo, into its namespace.
    A typo in a values file only shows up after it's merged.A check in CI (step 10)Every pull request renders every chart before anyone merges.

    Words you'll meet

    Application
    An Argo CD object (kind: Application) that says "keep this folder or chart deployed to that namespace".
    App of apps
    An Application whose folder holds other Applications. One root app then builds everything.
    AppProject
    A fence around a team's Applications: which repos, which namespaces, which kinds of resource.
    Sync
    Argo CD making the cluster match Git. Synced means they match; OutOfSync means they don't.
    Self-heal and prune
    Self-heal undoes changes made by hand in the cluster. Prune deletes things that were removed from Git.
    Finalizer
    A marker that makes Kubernetes run cleanup before deleting an object. Here it deletes everything an Application created.
    Pinned version
    An exact version number written down, instead of "the newest".

    02

    Write down exact versions

    Goal: you know the exact version of every component the rebuild will install.

    Why this step

    A rebuild that isn't identical isn't a rebuild. If a command says "the newest", running it next month gives a different platform. Pin everything, and make each upgrade a deliberate commit you can revert.

    It's the same idea as a package-lock.json or exact NuGet versions, applied to infrastructure.

    You already pinned most of these in parts 1 and 2. These are the numbers the files below use:

    ComponentVersionWhere it was pinned
    kube-prometheus-stack (Helm chart)92.3.0part 2, step 2
    loki (Helm chart)7.3.0part 2, step 8
    alloy (Helm chart)1.13.1part 2, step 8
    NGINX Gateway Fabric (Helm chart and Gateway API types)2.7.2part 1, step 5
    Argo CDv3.5.4new: part 1 used the stable link

    If your cluster from part 2 is still running, check that it matches. The CHART column shows names like kube-prometheus-stack-92.3.0; the number after the last dash is the chart version:

    Newer releases will exist by the time you read this. Stay on these for the tutorial. Upgrading is step 11.

    Chart version and app version are different numbers. helm search repo shows both. The chart version is the package's version; the app version is the software inside it. You always pin the chart version, which in turn fixes the app version.

    03

    Lay out the repo

    Goal: the repo has infra/platform/apps/, infra/platform/loadgen/ and infra/bootstrap/.

    Why this step

    Argo CD watches folders. Give each kind of thing its own folder so one Application can own exactly one job: infra/platform/apps/ holds Applications and nothing else, infra/platform/loadgen/ holds plain manifests, and infra/bootstrap/ holds the one file you apply by hand.

    The result:

    git mv moves a file and tells Git it's the same file, so its history follows it. The deploy/ folder from part 1 is now empty, and Git doesn't keep empty folders.

    04

    Describe the platform as Applications

    Goal: four new files in infra/platform/apps/, one per platform component.

    Why this step

    Each helm upgrade --install from part 2 becomes an Argo CD Application. There's a twist: the chart lives in someone else's Helm repository, but your values file lives in your Git repo. A multi-source Application reads from both. One source is the chart; the other is your repo, given a name (ref: values) so the chart can refer to files in it as $values/….

    In each file, put your GitHub user name in repoURL. The versions are the ones from step 2.

    Line by line: the monitoring Application
    finalizers
    When this Application is deleted, first delete everything it created. Without it, deleting the Application leaves the monitoring stack running with nothing managing it. You'll use this in step 9.
    sources (plural)
    Two places to read from. Part 1's app used source (singular) because chart and values were in the same repo.
    chart + targetRevision
    For a Helm repository, the chart's name and its exact version. For a Git repo, targetRevision is a branch, tag or commit.
    releaseName: mon
    The same release name as part 2, so resources keep the same names (mon-grafana) and your port-forward commands still work.
    $values/…
    "The file at this path in the source called values", which is the second source, your repo.
    ref: values
    Names that source. It's only used for values files; Argo CD doesn't deploy anything from it.
    ignoreDifferences
    Some controllers write into their own resources after install, here a certificate in the webhook settings. Argo CD would see that as drift and undo it, forever. This tells it to ignore those fields.
    ServerSideApply=true
    The stack's object type definitions are too large for the normal apply mode. The same reason part 1's Argo CD install needed --server-side.
    RespectIgnoreDifferences=true
    Also skip those fields when syncing, not only when comparing.

    The load generator is plain YAML in your repo, so it needs only one source:

    Pausing the load generator now means a commit. kubectl scale … --replicas=0 from part 2 gets undone within seconds, because selfHeal puts the cluster back the way Git says. To pause, set replicas: 0 in infra/platform/loadgen/loadgen.yaml and push. You'll see this happen on purpose in step 8.

    What you just learned

    • An Application can combine a chart from a Helm repository with values from Git.
    • Platform components are deployed exactly like apps. The platform team uses its own paved road.
    05

    Fence in the todo team

    Goal: the todo app belongs to its own AppProject, and is set up to cope with being installed before the monitoring stack.

    Why this step

    So far every Application uses the default project, which allows any repo, any namespace and any resource, including cluster-wide permissions. On a shared cluster, that means one team's mistake can break everyone.

    An AppProject is a fence around a team's Applications: which repos they may deploy from, which namespaces they may deploy into, and which kinds of resource they may create. Platform components stay in default for now; the todo app gets its own project.

    Line by line: the AppProject
    sync-wave: "-1"
    The root app applies its files in waves, lowest number first. The project goes in wave -1 so it exists before the todo Application (wave 0, the default) refers to it.
    sourceRepos
    Where this team's Applications may read from. Their own repo only.
    destinations
    Where they may deploy: this cluster, namespace todo, nothing else.
    clusterResourceWhitelist
    Cluster-wide resource types the team may create. Anything not on this list is refused, including ClusterRoles, which could grant power over the whole cluster. Namespace is allowed so CreateNamespace=true still works.
    orphanedResources.warn
    Flags resources in the todo namespace that don't come from Git. Someone ran kubectl create by hand. You'll see it in step 8.

    Now update the todo Application you moved in step 3. Replace the whole file:

    Line by line: what changed
    project: team-todo
    Inside the fence.
    SkipDryRunOnMissingResource=true
    The todo chart contains a ServiceMonitor and a PrometheusRule. Those types only exist once the monitoring stack is installed. On a fresh cluster both install at once, and without this option Argo CD's dry run fails on the unknown types before it even tries.
    retry
    If a sync fails, try again: after 15 s, then 30 s, then 60 s, up to 3 minutes apart, 10 times. By then the monitoring stack has created the types and the sync succeeds. Ordering problems in GitOps are usually solved with retries, not with scripts.

    What you just learned

    • An AppProject is where a platform team sets limits for app teams: sources, destinations, resource types.
    • On a fresh cluster things arrive in whatever order they arrive. Design for that with retries instead of fixed ordering.
    06

    Write the root app and the bootstrap script

    Goal: deleting the cluster and running ./infra/bootstrap.sh brings everything back.

    Why this step

    Something has to start the chain. The root Application watches infra/platform/apps/, so every file there becomes a child Application. The bootstrap script does the three things Git can't: create the cluster, install Argo CD, and apply the root app.

    The script does the three things Git can't do for itself: create the cluster, install the NGINX gateway controller and install Argo CD, then apply the root app. It's the same commands you ran in parts 1 and 2, gathered in one file with the versions pinned at the top:

    Line by line: the script
    set -euo pipefail
    Stop at the first failing command, treat unset variables as errors, and notice failures inside pipes. Every bash script that changes infrastructure should start with this.
    cd "$(dirname "$0")/.."
    Moves to the folder above the script, which is the repo root. The paths below then work wherever you run the script from.
    ARGOCD_VERSION, NGF_VERSION
    Argo CD and the gateway are pinned too, instead of the stable link used in part 1.
    --config infra/kind-config.yaml
    The file from part 1 that opens port 8080 on your PC. Without it the cluster has no way in and localhost:8080 shows nothing.
    --timeout=5m
    Don't wait forever.

    Why is the gateway installed by the script and not by Argo CD? The todo app can't work without it, and it needs two kinds of source (a kustomize folder and an OCI chart), which would distract from the pattern in this part. At work it would be another Application. That's the first idea in "Where to go next".

    Check the commit on GitHub contains infra/platform/apps/ with six files (five Applications and the project). Argo CD reads from GitHub, not from your PC, so anything not pushed doesn't exist as far as the rebuild is concerned.

    07

    Watch it converge

    Goal: all six Applications (root and its five children) are Synced and Healthy, and the Todo API dashboard shows live data.

    Over the next five or so minutes you'll see something like this. Expect some red on the way:

    1. root syncs and creates the project and five child Applications.
    2. monitoring, loki, alloy and loadgen start syncing at once.
    3. todo may show SyncFailed or Retrying for a minute, because the ServiceMonitor type doesn't exist yet. Then it succeeds on a retry.
    4. Everything ends Synced and Healthy. root is the last to say Healthy.

    Open the Argo CD page (kubectl -n argocd port-forward svc/argocd-server 8443:443, sign in with the password the script printed) and click root. You'll see the tree: root → Applications → each Application's resources.

    Then open Grafana (kubectl -n monitoring port-forward svc/mon-grafana 3000:80). The Todo API dashboard is there and filling, with no command from you beyond the script.

    And open http://localhost:8080: the todo app is back, served through the NGINX gateway. The database is new, so the list is empty.

    How long did it take? Write the number down. Most of it is image downloads. You've turned "half a day and a good memory" into one script and a few minutes, and anyone with the repo can do the same.

    What you just learned

    • Losing the cluster is now cheap. That changes how you work: you can experiment freely, because the way back is one command.
    • GitOps systems converge. Errors along the way are normal; only the end state matters.

    Drills for a GitOps platform

    The next four steps are drills, run the same way as in part 2: predict, break, diagnose, fix through Git, write three lines in drills.md. These ones test the platform's behaviour rather than the app's.

    08

    Drill: change things behind Git's back

    Goal: you know which hand changes Argo CD undoes, and which it can only warn you about.

    Predict, then try each one

    For each command, predict what happens in the next 30 seconds, run it, and watch kubectl get and the Argo CD page.

    Check your answers

    1 to 3 are undone within seconds. selfHeal means Argo CD compares the cluster with Git all the time, not just after a commit. Hand-made emergency fixes don't survive, which is the point: the fix has to go through Git, or it gets lost.

    4 stays. Argo CD only manages what's in Git; it has no reason to delete something it never created. Because of orphanedResources.warn in the team's project, the todo app shows a warning about one orphaned resource. Click it in Argo CD. Without that setting, nothing at all would tell you.

    Delete it with kubectl -n todo delete configmap quick-fix. Then write your three lines.

    When you really need a hand change during an incident, disable auto-sync on that one Application from the Argo CD page, make the change, then put the fix in Git and re-enable it. Write down that you did it. At work, that's what a change log is for.

    09

    Drill: test the fence

    Goal: the AppProject refuses a cluster-wide permission, and removing a component from Git removes it from the cluster.

    Break it: a team asks for too much

    Add this file to the todo chart, as if a developer wanted their app to read every Secret in the cluster. Commit and push.

    Diagnose

    • What does the todo app show in Argo CD? What's the exact message?
    • Did the rest of the app's resources still sync?
    • Who would normally decide whether a team gets this permission, and how would they grant it?
    Check your answers

    The sync fails with a message that ClusterRole isn't permitted in project team-todo. Nothing in the sync is applied, so the app stays on its last good state. The fence holds even though the developer controls their own chart.

    A request like this goes to the platform team, who add it to the platform's own Applications after a review, not through the app's chart.

    Remove a component

    The root app prunes the loadgen Application, because its file left the folder root watches. The finalizer on that Application then deletes everything it created: the Deployment, the pod and the loadgen namespace. One commit retires a whole component, and the history shows when and who.

    10

    Drill: a typo in the platform

    Goal: you see what a broken values file does, then add a check that catches it before merge.

    Break it, loudly

    Make two mistakes in one commit. In infra/platform/monitoring-values.yaml, remove two spaces in front of sidecar: so it no longer sits under grafana:. In infra/platform/apps/loki.yaml, change targetRevision to 99.0.0. Commit both and push.

    Diagnose

    • What does each Application show in Argo CD, and where is the message?
    • Is Grafana or Loki down? What would happen if one of their pods restarted now?
    Check your answers

    loki shows a ComparisonError: Argo CD can't find chart version 99.0.0. monitoring shows the same kind of error, because the values file is no longer valid YAML (the dedented sidecar: leaves the lines under it with the wrong indentation). The message is on the Application's page under its conditions.

    Nothing is down yet. Argo CD can't work out the new desired state, so it leaves the old one running. But the platform is stuck: no other change to those components can go out until this is fixed.

    Fix it

    Revert the commit and push.

    Break it, quietly

    This time make a typo that is still valid. In infra/platform/monitoring-values.yaml, delete the s from serviceMonitorSelectorNilUsesHelmValues so it reads serviceMonitorSelectorNilUseHelmValues. Commit and push. Predict what Argo CD shows first.

    Diagnose

    • What do the Applications show in Argo CD? Would a render check in CI have caught this?
    • What happens in Prometheus' Target health page, and which alert from part 2 fires? How long does it take?
    • Why did that setting matter? (Look at part 2, step 2.)
    Check your answers

    Everything stays Synced and Healthy. A misspelled key is still valid YAML, and Helm ignores values it doesn't know. A render check would pass too.

    The setting you misspelled made Prometheus watch every ServiceMonitor. Back at its default, it only watches ones labelled release: mon, and the todo chart's ServiceMonitor doesn't carry that label. The todo-api target disappears from Target health, the dashboard's graphs go to No data, and TodoApiDown fires after a few minutes. It's the same signature as drill 4 in part 2, with a different cause.

    A pipeline that is green proves your files parse and your versions exist. It doesn't prove a setting is spelled right. The alerts you wrote in part 2 are what caught this.

    Fix it

    Revert the commit and push. Prometheus picks the ServiceMonitor up again within a minute, and the alert resolves a little later. Write your three lines for both.

    Render everything on every pull request

    This workflow renders each chart with its values, at its pinned version, whenever a pull request touches platform/ or charts/. If a version doesn't exist or a file doesn't parse, the check fails and the pull request shows a red cross.

    Line by line: the check
    on: pull_request
    Runs on pull requests only. This is a gate before merge, not a build.
    yq
    A command-line YAML reader, preinstalled on GitHub's Ubuntu runners. It reads the pinned version out of each Application, so the version lives in one place.
    helm template … > /dev/null
    Renders the chart and throws the output away. Only success or failure matters.
    helm lint --strict
    Treats warnings in your own chart as errors.

    This catches versions that don't exist and files that don't parse. It doesn't catch the quiet typo from the drill above, which is valid YAML the chart just ignores. Some teams add helm template diffs as a pull request comment so reviewers can see what actually changes; that's in "Where to go next".

    To make it a real gate, on GitHub open Settings → Branches, add a rule for main, require pull requests and require the render check to pass.

    Requiring pull requests on main blocks the pipeline's tag commit from part 1, unless you allow GitHub Actions to bypass the rule. Use a ruleset with GitHub Actions in the bypass list, or skip the requirement for this lab and just use pull requests by habit.

    11

    Upgrade a component the safe way

    Goal: Alloy runs a newer chart version, through a pull request, and you know how you'd roll it back.

    Why this step

    Platform components need upgrades for security fixes and new features. With everything pinned, an upgrade is a one-line pull request: reviewable, checked by CI, and revertable.

    1. Alloy chart 1.13.1 was the newest when this was written, so there may be nothing newer. To practise anyway, first pin an older one: set targetRevision: 1.12.1 in infra/platform/apps/alloy.yaml, push, and wait for it to sync. Then upgrade as below. See what exists with helm repo update and helm search repo grafana/alloy --versions.
    2. Read the release notes for every version you're skipping over. Look for "breaking" and for changed values. Grafana's charts link to them from github.com/grafana/alloy/releases.
    3. Make a branch, change targetRevision in infra/platform/apps/alloy.yaml, push, and open a pull request. Wait for the render check.
    4. Merge. Watch the alloy Application sync and its pod restart.
    5. Check the effect, not just the sync: in Grafana's Explore, do new log lines from {namespace="todo"} still arrive?

    To roll back, revert the merge commit and push. That's safe here because Alloy keeps no state. For components that change stored data or object types during an upgrade (databases, operators with new CRD versions), going back might not work. The release notes say so, and it's why you read them first.

    What you just learned

    • "Synced" means Argo CD applied what Git says. It doesn't mean the component works. Always check the effect.
    • Pinned versions make upgrades boring, which is what you want from a platform.

    When something breaks

    What you seeLikely causeWhat to do
    root is Synced but shows no childrenThe files aren't pushed, or path is wrongCheck infra/platform/apps/ on GitHub, not on your PC
    An app says $values/… file not foundThe ref: values source is missing, or the path doesn't matchPaths after $values/ start at the repo root
    monitoring fails with "metadata.annotations: Too long"ServerSideApply=true is missingAdd it to syncOptions
    monitoring stays OutOfSync on webhook configurationsThe ignoreDifferences block is missing or mis-indentedCompare with step 4; it sits under spec, beside destination
    todo keeps failing on ServiceMonitor after several minutesThe monitoring stack itself failedFix monitoring first; todo recovers on its next retry
    todo says the project team-todo doesn't existThe project file wasn't pushed, or the sync-wave annotation is missingCheck infra/platform/apps/team-todo-project.yaml on GitHub
    todo says the destination or repo isn't permittedThe URL in the project differs from the app's, often by a trailing .git or capital lettersMake sourceRepos match repoURL exactly
    An Application won't delete and stays "Deleting"The finalizer is waiting for resources that can't be deletedLook at which resource is stuck in the Argo CD page; as a last resort remove the finalizer with kubectl -n argocd edit application <name>

    Where to go next

    • Part 4, Secure the Road, adds scanning, signing and admission policies, using the pattern from this part for each new component.
    • Move the gateway under Argo CD. Add an Application for the Gateway API types (a kustomize source, config/crd/gateway-api/standard at tag v2.7.2) and one for the controller chart, so infra/bootstrap.sh shrinks to the cluster, Argo CD and the root app.
    • Let Argo CD manage itself. Install Argo CD from its Helm chart through an Application in infra/platform/apps/, so upgrading Argo CD is a pull request too.
    • Generate Applications. An ApplicationSet creates one Application per folder or per cluster from a template, instead of a file per component.
    • Show the diff on pull requests. Render the chart before and after the change and post the difference as a comment, so reviewers see what will actually change in the cluster.
    • A platform project. Move the platform components out of default into a platform AppProject, and restrict default so it allows nothing.
